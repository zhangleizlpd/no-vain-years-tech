## Clarifications

### Session 2026-10-16

- Q: 以后再遇到改名，修正怎么做？ → A: **一条命令完成全部修正**（维护者原话：「后续出现类似情况，可以通过一条命令完成全部的修正动作」）。命令覆盖 PSKY 那次手工走过的五步（登记 / 锚 / 待审提交 / 采集范围 / 验证），默认预览、确认后写入、幂等可续跑、带对称的撤销命令 → US5、FR-011 ~ FR-016。
- Q: 登记的来源？ → A: **自动发现候选 + 维护者确认**。纯人工录入发现太慢（PSKY 用了 10 天）；自动发现后直接生效会把退市误当改名、悄悄拼错历史，与 US2 冲突。确认候选即以其参数进入修正命令，发现与修正共用一条路径 → US4、FR-018、FR-019。
- Q: 估值锚是否随改名迁移？ → A: **自动迁移 + 进入复核逾期**。迁移保住估值痕迹的连续性；改名常伴随并购（PSKY 的 V 是并购前的 9.65），复核逾期让旧估值不会悄悄当作有效。复用锚列表现有的「复核逾期」状态，不新增界面 → US3、FR-017。
- Q: v1 必须接续哪些消费方？ → A: **日线 + 标的隐含波动率 / IV 分位**。覆盖期权台最核心的两个读数；期权链 / 期权日快照要处理 OCC 调整合约，复杂度明显更高，与财报事件一起留到后续 → FR-004。
  - _amend 2026-10-16（plan 期）_：上屏的 IV 分位是行情源直接给的值，只读最近一期，本仓自算的 IV 分位只用于交叉核对、不上屏。所以 IV 这一半的接续只影响自算的交叉核对，屏幕上的数字不受影响。日线这一半的价值不变。

## 背景

2026-10-06 Paramount Skydance 收购 Warner Bros. Discovery 后更名 Skydance Corporation，代码 **PSKY → SKYD**，并由 Nasdaq 转板 NYSE（[SEC 8-K](https://www.sec.gov/Archives/edgar/data/0002041610/000110465926113913/tm2626659d7_8k.htm)、[MIAX 公司行动公告](https://www.miaxglobal.com/alert/2026/10/06/update-miax-exchange-group-options-markets-corporate-action-alert-paramount-2)）。本仓因此出现三个后果（2026-10-16 直查 prod）：

1. **标的被当成两只**：标的表以「市场 + 代码」唯一，代码实质上就是标的身份。PSKY 名下有 2019-12-05..2026-10-05 共 1716 根日线与 1178 条期权合约，SKYD 名下 0 根日线 —— 两者互不相关，改名后日线、隐含波动率、期权链等连续序列在 10-06 断开。
2. **事件没被任何人记下**：公司行动数据对这次改名零条记录。
3. **锚只能删了重建**：估值锚按代码唯一，旧码锚只能删掉、在新码上重建，估值历史随之断开。

另有**代码回收**的反向风险：PARA 当初改名 PSKY 后，PARA 这个代码被回收给了一家无关公司（Banzai International）。按裸代码拼接会把两家公司的历史缝在一起，而且不会报任何错。

**分层取舍**（2026-10-16 与维护者定）：

| 层  | 内容                                        | 本 feature                   |
| --- | ------------------------------------------- | ---------------------------- |
| ①   | 两行标的都不删，旧码当已停用、新码另起      | 已在 prod 生效，无需实现     |
| ②   | 代码变更登记 + 消费方按登记接续             | **本 feature**               |
| ③   | 标的改用永久内部 ID、代码降为带生效期的属性 | **不做**（涉及 29 张外键表） |

业内参照：永久 ID + 带生效起止日期的外部标识映射；改名 / 并购存续**延续**同一身份，分拆 / 退市后不再上市**不延续**（[Databento security master](https://databento.com/docs/venues-and-datasets/security-master)、CRSP PERMNO、FactSet symbology history）。本 feature 取其中「带生效日的映射」这一半，不做永久 ID。

## User Scenarios & Testing _(mandatory)_

### User Story 1 — 登记一次改名，新码名下看到完整历史 (Priority: P1)

维护者得知某标的改了代码（如 PSKY → SKYD，生效 2026-10-06），登记一条变更。此后凡是需要连续序列的地方（K 线、隐含波动率分位、期权台雷达），查询新码时都能看到改名前的旧码段历史，拼接处没有缺口、没有重复。

**Why this priority**: 这是本 feature 存在的理由。没有它，任何改名都意味着历史清零：IV 分位要重新攒一年样本，K 线从改名日起只剩几根。

**Independent Test**: 在只有 PSKY 历史、没有 SKYD 历史的数据集上登记 PSKY → SKYD @ 2026-10-06，查询 SKYD 的日线序列，应当从 2019-12-05 连续到最新一个交易日。

**Acceptance Scenarios**:

1. **Given** 旧码有生效日前的日线、新码只有生效日起的日线，**When** 登记旧码 → 新码并查询新码日线，**Then** 返回旧码段 + 新码段，按日期连续，生效日前后各属一段。
2. **Given** 尚未登记任何变更，**When** 查询新码，**Then** 结果与本 feature 上线前逐条一致。
3. **Given** 已登记，**When** 撤销这条登记，**Then** 查询新码回到只有新码自身数据的状态。

---

### User Story 2 — 代码回收不被误拼 (Priority: P1)

某个旧码在改名之后被交易所分配给一家无关公司（如 PARA）。查询这个被回收的代码时，只能看到回收之后那家新公司的数据；查询改名后的新码时，也不会混进回收后那家公司的数据。

**Why this priority**: 误拼不报错，只会让数字悄悄变错。估值和期权决策直接读这些序列，后果比「历史缺一段」更严重，所以和 US1 同为 P1。

**Independent Test**: 构造「A 改名 B（生效 D），D 之后 A 被回收给另一家公司并产生新数据」的数据集，分别查询 A 和 B，两个序列在 D 前后的归属都正确。

**Acceptance Scenarios**:

1. **Given** A → B @ D 已登记，且 A 在 D 之后有一家新公司的数据，**When** 查询 B 的连续序列，**Then** 只包含 A 在 D 之前的段 + B 的段。
2. **Given** 同上，**When** 查询 A，**Then** 只返回 A 在 D 之后（回收后）的数据。

---

### User Story 3 — 估值锚随改名延续 (Priority: P2)

旧码上有估值锚时，登记改名之后，锚连同估值、置信度、复核计划和变更痕迹**自动迁到新码**，同时被标记为「需复核」：改名常伴随并购，旧估值可能已经失效（PSKY 的 V 是并购前的 9.65），迁过去的估值在维护者复核前不能悄悄当作有效估值使用。

**Why this priority**: 锚数量少（百余只），改名罕见，手动删了重建能兜底；但估值痕迹断开会让「这只票历史上怎么估的」查不到。

**Independent Test**: 旧码有锚、新码无锚，登记改名后按澄清结论检查新码锚的状态和痕迹连续性。

**Acceptance Scenarios**:

1. **Given** 旧码有锚、新码无锚，**When** 登记改名，**Then** 锚出现在新码名下并带「需复核」标记，变更痕迹连续可查，旧码名下不再有锚（不再以旧码身份参与取价）。
2. **Given** 迁移过来的锚带「需复核」标记，**When** 维护者完成复核（确认原估值或改写估值），**Then** 标记清除。在此之前，该锚以现有的「复核逾期」状态呈现（锚列表已有此状态，见 `list-anchors.usecase.ts:141` 的 `overdue`），不新增界面。
3. **Given** 新码上已经存在锚，**When** 登记改名，**Then** 不覆盖新码锚，并向维护者报告冲突。

---

### User Story 4 — 改名被及时发现 (Priority: P3)

改名发生后，系统自动发现「疑似改名」并生成候选（信号：行情源报某锚的代码不存在；新码建议：同一市场内名称相近的标的），通知维护者。候选**不会自动生效**：维护者确认后，系统用候选里的参数执行 US5 的修正命令（仍然先预览、再确认）；维护者也可以否决候选。发现与修正共用同一条路径。

**Why this priority**: 这次从改名到被发现用了 10 天，是因为没有任何东西在看。PR #495 让「某市场锚全部停摆」会告警、「行情源不认识某代码」会在日志里点名，已经补上了最痛的一段；本条是在那之上把「发现」变成「登记候选」。

**Independent Test**: 模拟行情源对某代码报「不存在」，并且标的清单中出现同名新码，检查候选的产生和后续处置。

**Acceptance Scenarios**:

1. **Given** 行情源开始报某旧码不存在，且同一市场有名称相近的标的，**When** 下一个采集周期结束，**Then** 生成一条疑似改名候选（含旧码、新码建议、线索与首次观测时间）并通知维护者。
2. **Given** 一条候选，**When** 维护者确认，**Then** 以候选参数进入 US5 修正命令的预览；**When** 维护者否决，**Then** 候选关闭，同一线索不再重复生成。
3. **Given** 旧码报不存在，但找不到任何新码线索（如退市），**When** 生成候选，**Then** 候选只标明「代码失效、未找到新码」，不预填新码，不能直接确认为改名。

### User Story 5 — 一条命令完成改名后的全部修正 (Priority: P1)

下次再遇到改名，维护者只需执行**一条命令**（给出市场、旧码、新码、生效日、证据），系统就完成全部修正动作，并给出一份逐项结果报告。不再需要像 PSKY 那次一样，手工依次查日志、删锚、驳回待审提交、核对采集范围、等下一拍验证。

本次手工走过的修正动作，即这条命令要覆盖的清单：

1. 登记代码变更（US1）；
2. 把旧码上的估值锚迁到新码，并标记「需复核」（US3）；
3. 处置旧码上仍待审的估值提交，防止它日后被批准、让旧码重新进入取价批次；
4. 采集范围纠正：旧码移出采集，新码纳入采集（新码在标的清单里不存在时先补齐）；
5. 验证：确认旧码不再出现在取价批次中、新码取到价格、连续序列可读，并把结果写进报告。

**Why this priority**: 这是维护者原话里的诉求（2026-10-16）。PSKY 那次的修正分散在三个系统、需要 prod 写权限，前后花了一个多小时，中间还被凭据权限拦住一次。改名每年都会发生，每次重来一遍既慢又容易漏步。

**Independent Test**: 在含「旧码锚 + 旧码待审提交 + 旧码历史日线」的数据集上执行命令，检查五项动作的结果与报告是否逐项吻合；同样的参数再执行一次，结果不变。

**Acceptance Scenarios**:

1. **Given** 旧码有锚、有待审提交、有历史数据，**When** 先以预览模式执行命令，**Then** 列出将要执行的全部动作及其影响面，不做任何写入。
2. **Given** 预览结果已经过维护者确认，**When** 正式执行，**Then** 五项动作全部完成，报告逐项给出结果（成功 / 跳过及原因 / 失败及原因）。
3. **Given** 执行到中途某一步失败，**When** 修好问题后用同样的参数重新执行，**Then** 已完成的步骤被识别并跳过，从失败处继续，最终状态与一次跑通相同。
4. **Given** 一次修正已经完成，**When** 执行对应的撤销命令，**Then** 登记被撤销，锚和采集范围回到修正前的状态，报告逐项给出结果。

### Edge Cases

- **链式改名** A → B → C：查询 C 能回溯到 A 段；中间码 B 的生效区间是 [B 生效日, C 生效日)。
- **改回原码** A → B → A：按生效日区间各自归属，不形成环。
- **生效日不是交易日**（周末宣布、下一个交易日生效）：以登记的生效日为界；它前一个交易日属于旧码段，它当天或之后的第一个交易日属于新码段。
- **新码在生效日前已有数据**（如新码曾是另一只票、或行情源提前铺了新码）：生效日前一律以旧码段为准，新码生效日前的数据不计入连续序列。
- **分拆 / 退市 / 并购中被吞并的一方**：不是延续性事件，不允许登记为改名。
- **跨市场**（转板只是交易所变化、市场不变，如 Nasdaq → NYSE 仍属美股）：只登记同一市场内的代码变化；跨市场（美股 → 港股）不在范围内。
- **期权合约**：改名后，旧码期权在 OCC / 交易所侧通常转为新码下的调整合约（MIAX 公告称以新合约类别交易）。合约层面是否接续由 plan 阶段按实际数据决定；本 feature 至少保证标的层面的接续。
- **登记错误**：可以撤销；撤销后不残留任何拼接结果。
- **旧码锚仍在**：旧码不再被行情源识别，留着旧码锚会让取价整批失败（PR #495 之前的事故形态；之后只会少一只锚、不再拖垮整批）。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 能登记一条代码变更：市场、旧码、新码、生效日、事件类型（目前只有「改名 / 存续延续」一种）、来源与证据（如公告链接或观测记录）、登记人与登记时间。
- **FR-002**: 系统 MUST 拒绝不合法的登记：旧码等于新码、跨市场、生效日晚于今天、同一（市场, 旧码, 生效日）重复，并说明拒绝原因。
- **FR-003**: 系统 MUST 支持撤销登记，并保留撤销痕迹（谁、何时、为什么）；撤销后消费方的读结果与从未登记过一致。
- **FR-004**: 需要连续序列的消费方，在查询新码时 MUST 能取得「旧码在生效日之前的段 + 新码自生效日起的段」，按日期连续、不重复、不缺口。v1 必须接续的消费方：**日线**（雷达 K 线 / 估值曲线）与**标的隐含波动率及 IV 分位**。期权链 / 期权日快照、财报事件不在 v1 范围；估值锚不走读时拼接，而是按 US3 迁移。
- **FR-005**: 接续 MUST 按生效日区间判定归属。一个代码在任一日期至多归属一个连续身份，回收后的数据 MUST NOT 进入改名前那条序列。
- **FR-006**: 接续 MUST 是**读时拼接**：不搬动、不改写、不删除旧码名下已落库的数据。这样撤销登记零副作用，误登记也不会造成不可逆的数据损失。
- **FR-007**: 未登记任何变更的标的，所有消费方的读结果 MUST 与本 feature 上线前逐条一致（零回归）。
- **FR-008**: 系统 MUST 支持链式改名的回溯（A → B → C），且对环和区间重叠的登记予以拒绝。
- **FR-009**: 维护者 MUST 能查看全部登记（含已撤销的），以及每条的证据与来源。
- **FR-010**: 旧码不再被行情源识别之后，系统 MUST NOT 再因这个旧码让同批其它标的取价失败（已由 PR #495 在取价层保证；本 feature 不得回退这一点）。
- **FR-011**: 系统 MUST 提供一条修正命令：输入市场、旧码、新码、生效日、证据，一次完成 US5 列出的五项动作（登记、锚处置、待审提交处置、采集范围纠正、验证），并输出逐项结果报告。
- **FR-012**: 修正命令 MUST 默认只预览，不写入。正式写入前须复述将要执行的动作，并得到维护者显式确认。
- **FR-013**: 修正命令 MUST 幂等且可续跑：用同样的参数重复执行不产生重复效果；中途失败后重跑时，从未完成的步骤继续。
- **FR-014**: 修正命令的每一项写入 MUST 经由系统的正常业务路径完成，并留下与人工操作同等的痕迹（例如删锚落变更痕迹、驳回提交带理由），不得以直接改库替代。
- **FR-015**: 系统 MUST 提供与修正命令对称的撤销命令，同样默认预览、需要确认、输出逐项报告。
- **FR-016**: 修正命令所需的权限 MUST 在命令内部自行解决，维护者执行时无需另外准备或手工传入任何凭据。
- **FR-017**: 修正命令 MUST 把旧码锚连同其估值、置信度、复核计划迁到新码，变更痕迹前后连续；迁移后的锚 MUST 处于「复核逾期」状态，直到维护者复核。撤销命令把锚迁回旧码，复核状态一并复原。
- **FR-018**: 系统 MUST 在行情源报某锚的代码不存在时，自动产生疑似改名候选并通知维护者。候选附带新码建议：同一市场内名称相近的标的（如 PSKY「Paramount Skydance」→ SKYD「Skydance」）。
  - _amend 2026-10-16（plan 期）_：原文另有一条线索「标的清单里旧码消失」。经核对，标的清单同步从不标记消失的代码（只更新名称 / 状态等字段），这条线索今天观测不到，因此改为「名称相近」作为新码建议的来源。
- **FR-019**: 候选 MUST NOT 自动生效。确认即以候选参数进入修正命令（仍先预览再确认）；否决后同一线索不再重复生成。找不到新码线索的候选只能标为「代码失效」，不能确认为改名。

### Key Entities

- **代码变更登记**：表示「某市场内，某代码自某日起改称另一代码，且是同一家公司的延续」。属性：市场、旧码、新码、生效日、事件类型、来源（人工 / 自动发现）、证据、登记人与时间、撤销状态与撤销痕迹。
- **连续身份**（派生概念，不落为新实体）：沿登记链串起来的一组（代码, 生效区间）。消费方按日期查到某一天对应哪个代码。
- **标的**（既有）：仍以「市场 + 代码」唯一，本 feature 不改它的身份定义。
- **估值锚**（既有）：仍以代码唯一，改名时随修正命令迁到新码并进入复核逾期（US3）。
- **疑似改名候选**：系统根据行情源线索生成的待确认事项。属性：市场、旧码、疑似新码（可空）、线索类型、首次观测时间、处置状态（待处置 / 已确认 / 已否决）与处置痕迹。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 登记 PSKY → SKYD @ 2026-10-06 之后，在 SKYD 名下查询日线，能连续取到 2019-12-05 至最新交易日的序列，缺口 0、重复 0。
- **SC-002**: 回收场景（PARA 类）下，误拼条数为 0：被回收代码与改名后新码各自的序列里，不出现另一方的任何一天。
- **SC-003**: 未登记任何变更的标的，消费方读结果与上线前逐条比对，差异 0。
- **SC-004**: 一条登记从提交到在所有 v1 消费方上可见，不超过 1 个采集周期；撤销同样在 1 个采集周期内完全复原。
- **SC-005**: 维护者完成一次改名登记（含填写证据）不超过 5 分钟，且不需要直接操作数据库。
- **SC-006**: 下次改名时，从维护者执行修正命令到报告给出「全部完成」，人工操作只有「执行命令 + 确认预览」两步；除等待下一个取价周期外，耗时不超过 10 分钟（PSKY 那次的手工修正用了一个多小时）。
- **SC-007**: 同一组参数连续执行修正命令两次，第二次的报告全部为「已完成，跳过」，系统状态无任何变化。

## Assumptions

- 改名是低频事件（本仓锚池百余只，一年内预计个位数次）。性能目标按「读时多一次区间判定」设定，不为海量登记做优化。
- 生效日以交易所 / 公司公告为准，登记时由维护者确认。行情源上新码出现的日期仅作佐证，不作为生效日的权威来源。
- 读时拼接的价格**不做**复权或比例调整：改名不改股本。拆股 / 合股等需要调整的事件不在本 feature 范围内（由既有的复权口径处理）。
- 不改标的的唯一身份定义，也不迁移 29 张外键表（第③层，明确不做）。
- PR #495（shim 剔除未知代码 + 按市场判锚停摆）是本 feature 的前置：它解决「一只坏码拖垮整批」和「停摆没人知道」，本 feature 解决「改名后历史断开」。两者相互独立，本 feature 不依赖 #495 的实现细节。
