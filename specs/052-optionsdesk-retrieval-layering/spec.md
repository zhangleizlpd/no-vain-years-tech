# Feature Specification: 选约检索分层落地 + 三视角逐层判据重梳

**Feature Branch**: `052-optionsdesk-retrieval-layering`
**Created**: 2026-08-12
**Status**: Draft
**里程碑**: sell-put 可视化决策系统 —— optionsdesk 选约引擎重构的 **P3 片**（主 plan：`docs/private/plans/2026-08/08-11-optionsdesk-leg-engine-master.md`，本机私有）
**架构 canonical**: [ADR-0064](../../docs/adr/0064-optionsdesk-retrieval-layering.md)（五层职责 + 五条跨层不变量 + 不设重排层 + 检索 port + 特征计算位置）

## 背景：一个已 ship 的缺陷，和它暴露的结构问题

### 缺陷本身

`051` ship 后，收租视角按折算年化降序的**前 14 行全部是深度实值**。实测（2026-08-12，`us:KBR`，spot `37.56`）：`K = 105`（相对 spot **+179.6%**）排在第 3 位、年化 `384%`。

成因是公式在实值区退化 —— 深度实值 put 的 `bid ≈ K − spot`，故准备金 `K − bid ≈ spot` **恒定**而分子随 `K` 增长。那 13 行的准备金**同为 `39.60`**，经济上是**同一笔交易**：花 39.60 买入现价 37.56 的股票。

🚨 **再完美的精排也修不了它** —— 按公式它们确实是年化最高的一批。问题在于它们**根本不该成为候选**。

**根因**：`050` 退役了收租的锚轴判据 `K ≤ W`，而没有给收租配一道等价的**成色**条件。主 plan §2.2 当时把由此产生的候选集扩大写成「腿变多是预期不是 bug」—— 这句话把一个真缺陷**掩盖了两片**。

📌 **建仓视角没坏**：它有有效成本硬门槛 `K − bid < spot`，`K = 105` 时 `39.60 > 37.56` 当场出局。⇒ `050` 的门槛形状是对的，只是**没给收租配一道**。

### 结构问题

缺陷之所以能藏两片，是因为**层与层的边界只活在代码里，没有被显式定义**。ADR-0064 补上了定义，本片是它的实施载体。

### 为什么必须先于 `053`

`053` 要做「按排序截 top-N」。**在坏排序上截断，砍掉的正是好的那些** —— 判据不修就做截断，等于把缺陷放大并固化。

## Clarifications

### Session 2026-08-12

- Q: 系统硬门槛与用户筛选要不要合并成一个机制？ → A: **合并**。筛选控件的**默认值就是系统条件**：服务端解出默认值下发、填进控件，用户不动即系统推荐口径，用户改了按页面值召回。<br>定案依据：它把不可见的门槛变成**可见且可谈判**的值——ADR-0064 不变量 ④ 要的「门槛可发现」被以更强的形式满足。<br>📌 连带定名：**「检索条件」= 有控件、可覆盖**；**「硬门槛」= 无控件、不可调**。全仓**只有一个 filter 概念**（筛选 = 用户对检索条件的覆盖），不存在第二种筛选。
- Q: 检索条件的生效时机？ → A: **点「搜」显式提交**，不做实时防抖。<br>定案依据：改条件 = 改召回 = 改排名基准，不该由输入停顿触发。<br>📌 连带：右端槽位另给「**复位**」回到系统默认值——否则用户调宽后无路可退（只能退出页面重进）。
- Q: 用户覆盖的值要不要持久化？ → A: **不持久化**。每次进入视图回到系统默认值。
- Q: 仓位水位变化要不要联动检索条件？ → A: **不联动**。已代码实证：水位 → `intent` / `rentDepth` → **只影响推荐标与排序**，召回成员集不变（`RecallContext` 只有 `spot`）。
- Q: 排名基准是「固定门槛下的召回集」还是「当前检索条件下的召回集」？ → A: **当前检索条件下的召回集**。用户放宽条件 ⇒ 候选集变大 ⇒ 活跃标与排名重算，**这是定义如此**。<br>📌 这条**反转了 `053` 起草时写的 `FR-009`**（「筛选 MUST NOT 进入排名基准」）——那条假设筛选在排名之后，而合并机制下筛选是召回参数。`053` 已同步改写。
- Q: 死腿条件取什么？ → A: **`OI ≥ 1 或当日有成交`**，三视角一律。<br>实测依据：过了权利金门槛的 2572 条里 **OI=0 的有 1014 条（39.4%）**——权利金门槛只看 `bid`，结构上抓不到它们；其中 **34 条当日有成交**（新挂档），所以必须带「或有成交」的免死条款。起手取最保守档，更严的档（`OI≥10` / `OI≥50`）需要实盘反馈才能标定。
- Q: 精排主键取什么？ → A: **建仓 / 收租走分层排序**（先流动性档、档内折算费率降序、年化打平时长期优先）；**全腿保持费率降序 + 成色排序特征令深度实值沉底**。<br>🚫 **加权评分否决**：权重现在是拍脑袋的且没有可校准数据（ADR-0064 候选表已列）。分层与帕累托前沿都不需要权重，选分层是因为它更贴「先过流动性、再看收益」的心智。
- Q: 活跃标的分组维度？ → A: **同到期日内 top N，且绝对量过线才发标**。<br>实测依据：现行「候选集内 top 3」在 `us:LULU` 收租视角把 3 个标**全部**给了 `DTE=38`，而 `DTE=157` 的 OI 合计 `28113` 是全场最高、最大单腿 OI `2763` 也几乎持平 `3050`——它拿不到标是因为**当日成交量结构性集中在近月**（38d 成交 747 vs 157d 仅 38），排名和把长期腿按死。<br>📌 绝对线是必需的：同到期日口径下 `DTE=45` 的 top-1 只有 `OI=4`（该到期日 OI 合计仅 23）——**相对判据在死到期日里会误报**。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 收租视角不再被公式退化产物占满 (Priority: P1)

用户切到收租视角，看到的是行权价在 spot 附近或以下的腿，而不是行权价远高于 spot 的深度实值合约。

**Why this priority**: 这是**缺陷修复**。当前收租视角的可见部分基本不可用——前 14 行是同一笔经济交易的 13 种写法。

**Independent Test**: 可独立验：对 `us:KBR` 取当日快照，断言收租候选集内不存在行权价高于成色上界的腿，且候选集内年化落在合理区间。

**Acceptance Scenarios**:

1. **Given** 某标的当日快照，**When** 用户打开收租视角，**Then** 候选集内每条腿的行权价 ≤ 成色上界
2. **Given** 行权价恰等于成色上界的腿，**When** 召回，**Then** 该腿**在**候选集内（边界取闭区间）
3. **Given** 行权价网格稀疏、spot 之上最近一档远离 spot，**When** 召回，**Then** 由绝对比例兜底条件二次收窄，两条取严
4. **Given** 用户切到建仓视角，**When** 查看候选集，**Then** 行为与本片之前一致（有效成本硬门槛已挡住深度实值，零判据改动）
5. **Given** 用户切到全腿视角，**When** 查看，**Then** 深度实值腿**仍在**（不砍腿），只是排在末段

---

### User Story 2 - 排在前面的腿是真能挂出去的 (Priority: P1)

用户看到的前几条腿，不再是「年化很高但几乎没人交易」的纸面数字，而是持仓厚、价差窄、单笔权利金有分量的腿。

**Why this priority**: 与 US1 同级。排序的作用是「把值得看的放前面」；把挂不出去的单放前面 = 排序反向工作。

**Independent Test**: 可独立验：对同一候选集分别按旧主键与新主键排序，断言新排序的前 N 条在流动性指标上严格不劣。

**Acceptance Scenarios**:

1. **Given** 某视角候选集内既有高年化薄腿也有中年化厚腿，**When** 精排，**Then** 厚腿排在薄腿之前
2. **Given** 同一流动性档内的多条腿，**When** 精排，**Then** 按折算费率降序
3. **Given** 同档内两条腿的年化落在「打平」带内，**When** 精排，**Then** 期限长的排在前面
4. **Given** 候选数少于降级阈值，**When** 精排，**Then** 不分档，直接按折算费率降序
5. **Given** 全腿视角，**When** 精排，**Then** 深度实值腿因成色特征排在末段，但**未被移出**候选集

---

### User Story 3 - 系统给的默认条件看得见、可以谈判 (Priority: P1)

用户进入某视角时，检索条件控件里已经填好系统推荐的值；用户看得见这些值，不同意就当场改，改完点「搜」拿新结果，点「复位」回到系统值。

**Why this priority**: 这是本片把「不可见的硬门槛」变成「可见且可覆盖的默认值」的整个价值。没有它，用户面对的仍是一个不解释自己为何这样筛的黑箱。

**Independent Test**: 可独立验：进入视图断言控件已填系统值；改值不点搜断言结果不变；点搜断言结果按新值；点复位断言回到系统值。

**Acceptance Scenarios**:

1. **Given** 用户进入某视角，**When** 首屏渲染，**Then** 检索条件控件已填入服务端下发的系统默认值
2. **Given** 用户改了某个条件的值，**When** 未点「搜」，**Then** 呈现结果不变
3. **Given** 用户改值后点「搜」，**When** 结果返回，**Then** 按用户值召回，且该维度显示计数
4. **Given** 用户点「复位」，**When** 结果返回，**Then** 全部条件回到系统默认值，计数全部消失
5. **Given** 用户离开视图再进入，**When** 首屏渲染，**Then** 条件回到系统默认值（覆盖值不持久化）
6. **Given** 用户放宽某条件使候选集变大，**When** 结果返回，**Then** 活跃标与排序按新候选集重算 —— 同一条腿的标可能变化，**这是定义如此**

---

### User Story 4 - 长期限的腿也能拿到活跃标 (Priority: P2)

用户在长期限的腿上也能看到活跃标，而不是所有标都挤在最近一个到期日。

**Why this priority**: 纯信号质量。它不影响成员集合，但影响用户能否在自己偏好的期限段里找到「有人在交易」的那几张。

**Independent Test**: 可独立验：断言活跃标分布覆盖多个到期日，且不出现在整体无人交易的到期日上。

**Acceptance Scenarios**:

1. **Given** 候选集横跨多个到期日，**When** 打标，**Then** 活跃标按到期日分组评比，不再集中于单一到期日
2. **Given** 某到期日整体持仓与成交都极低，**When** 打标，**Then** 该到期日内即使有相对第一的腿也**不发标**（绝对量未过线）
3. **Given** 某到期日无候选腿，**When** 打标，**Then** 不产生空分组、不报错

---

### Edge Cases

- **成色上界解不出**（链上不存在行权价 ≥ spot 的合约）→ 退化为仅用绝对比例兜底条件
- **spot 缺失** → 依赖 spot 的条件全部不可解 ⇒ 沿用既有的「链未就绪」状态，不猜一个默认值
- **用户把某条件放宽到超出数据范围**（如行权价上界高于链上最大行权价）→ 该条件不再产生排除，计数为 0 且不显示
- **用户把某条件收紧到候选为空** → 空态 MUST 区别于「该视角本来就没有合格腿」，并给「复位」入口
- **候选数恰等于降级阈值** → 不降级（边界取「严格小于才降级」）
- **同一到期日内所有腿的 OI 与成交完全相同** → 打标按稳定的次级判据决胜，MUST NOT 随机
- **候选数超过召回层候选上限 K** → 截到 K 且该情形可被观测（MUST NOT 静默）
- **greeks 缺失的腿** → 照常进候选（继承 `050`），只是不参与依赖 greeks 的特征

## Requirements _(mandatory)_

### 分层与命名（ADR-0064 落地）

- **FR-001**: 五层（召回 / 粗排 / 特征加工 / 精排 / 表达）MUST 在代码上可分辨：每层有独立入口，且每层的判据可被单独测试。
- **FR-002**: 召回层的条件 MUST 分成两类且用不同的词：**检索条件**（有控件、系统给默认值、用户可覆盖）与**硬门槛**（无控件、不可调、表达不成范围区间）。
- **FR-003**: 全仓 MUST 只有一个 filter 概念 —— 筛选 = 用户对检索条件的覆盖。MUST NOT 存在第二种「呈现层再筛一次」的语义。
- **FR-004**: 粗排层 MUST 落位置与接口但**当前为 no-op**（单路召回，无合并去重可做）。MUST NOT 在其中引入与精排不同口径的打分。

### 召回层 · 三视角判据

- **FR-005**: 收租视角 MUST 有**成色条件**：行权价上界取「spot 之上最近一档行权价」与「`spot × (1+X)`」**两者取严**。边界取闭区间（恰等于上界的腿在候选内）。
- **FR-006**: 🚨 全腿视角 MUST NOT 设成色条件 —— 它是参照视角，且 `051` 已 ship 的「切到全腿视角看被排除的腿」入口依赖它保留全部腿。
- **FR-007**: 建仓视角 MUST NOT 新增行权价上界 —— 其有效成本硬门槛 `K − bid < spot` 已等价挡住深度实值（实测 `K=105` 时 `39.60 > 37.56` 出局）。
- **FR-008**: 三视角 MUST 一律设**持仓量条件**：`OI ≥ 下限` **或** 当日有成交。「或有成交」是**新挂档的免死条款**，MUST NOT 省略。
- **FR-009**: 权利金条件 MUST 沿用 `050` T017 的标定值，本片**不改**。
- **FR-010**: 相对价差条件 MUST 只作用于两个意图视角，全腿视角不设（继承 `050`）。
- **FR-011**: 每个视角的每条检索条件 MUST 有一个**系统默认值**，且该默认值 MUST 由服务端计算并下发。<br>🚫 客户端 MUST NOT 自行计算任何默认值 —— 它们依赖 spot（每天变），客户端自算即「同一判据两处各算一份」（ADR-0064 不变量 ③）。

### 召回层 · 用户覆盖

- **FR-012**: 用户 MUST 能覆盖任一检索条件的值。覆盖 MUST 经**显式提交**（「搜」）才生效，MUST NOT 由输入停顿自动触发。
- **FR-013**: MUST 提供「**复位**」使全部条件回到系统默认值。
- **FR-014**: 用户的覆盖值 MUST NOT 持久化 —— 离开视图再进入回到系统默认值。
- **FR-015**: 每个视角 MUST 各自持有自己的检索条件状态，切视角 MUST NOT 带走上一个视角的值。
- **FR-016**: 仓位水位变化 MUST NOT 联动改变检索条件（已代码实证水位不进召回，只影响打标与排序）。

### 精排层

- **FR-017**: 意图视角（建仓 / 收租）的精排 MUST 为**分层**形态：先按流动性档分组，档内按折算费率降序。
- **FR-018**: 同档内两条腿的折算费率落在「打平」带内时，**期限长的 MUST 排在前面**。
- **FR-019**: 候选数少于降级阈值时 MUST NOT 分档，直接按折算费率降序（薄链上分档会退化成按流动性排）。
- **FR-020**: 全腿视角的精排 MUST 保持折算费率降序，并 MUST 引入**成色排序特征**使深度实值腿自然排在末段。🚫 MUST NOT 通过移出候选实现（那会破坏 `FR-006`）。
- **FR-021**: 🚫 MUST NOT 引入加权评分 —— 权重无可校准数据（ADR-0064 已列为否决候选）。
- **FR-022**: 精排层 MUST 只读特征集，MUST NOT 直接读原始腿（ADR-0064 不变量 ②）。

### 特征加工层与打标

- **FR-023**: 活跃标的分组维度 MUST 从「整个候选集」改为「**每个到期日**」。
- **FR-024**: 活跃标 MUST 同时满足两条才发：同到期日内排名进前 N（相对）**且**绝对量过线（绝对）。🚫 只用相对判据会在整体无人交易的到期日里误报。
- **FR-025**: 每个特征 MUST 恰好有一个计算地点（ADR-0064 不变量 ③）。

### 排名基准

- **FR-026**: 排名与打标的基准 MUST 为**当前检索条件下的召回集**。用户放宽条件使候选集变大时，活跃标与排序 MUST 随之重算 —— 这是定义如此，MUST 在界面上不做特殊解释。

### 两级截断

- **FR-027**: 召回层 MUST 有**候选上限 K**，且 K MUST 与表达层的用户可见条数 N 是两个不同的数、`K ≫ N`（ADR-0064 不变量 ①）。本片只落 K，N 归 `053`。
- **FR-028**: 候选数触及 K 时 MUST 可被观测（不依赖读日志）。

### 计数

- **FR-029**: 每条检索条件被用户**收窄**时 MUST 显示其排除计数。系统默认值下 MUST NOT 显示 —— 默认值本身就摆在控件里，第二次告知是噪音。
- **FR-030**: 计数的措辞 MUST 表达「当前条件之外还有 N 条」，MUST NOT 沿用暗示「被系统滤掉」的旧措辞。

### 检索 port

- **FR-031**: 召回 MUST 经一个只暴露**业务语义**的接口：入参 = 视角 + 检索条件 + 候选上限，出参 = 候选集。<br>🚫 接口 MUST NOT 出现存储侧概念（查询片段 / 游标 / 分页 token）—— 漏进去的话换实现时接口照样要重写。
- **FR-032**: 召回判据 MUST 可脱离真实数据库单独测试（该接口存在的直接收益）。

### 零改动面

- **FR-033**: `045` 的锚派生规则与意图矩阵 MUST 零改动。
- **FR-034**: 表达层的档位口径与截断阈值 MUST 不在本片改动（归 `053`）。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 在**任一真实链**上，收租视角的候选集内**零条**腿的行权价高于成色上界。
- **SC-002**: 在起草期作为缺陷证据的那条链上（`us:KBR`），收租视角候选集的年化落在合理区间，**不再出现三位数年化的深度实值腿**。
- **SC-003**: 对同一候选集，新精排的前 N 条在流动性指标上**严格不劣于**旧精排的前 N 条。
- **SC-004**: 活跃标的分布**覆盖多个到期日**，且**零条**出现在整体无人交易的到期日上。
- **SC-005**: 建仓视角的候选集在本片前后**逐条相同**（零判据改动的可验证形态）。
- **SC-006**: 🚨 被意图视角的任一条件排除的腿，**100% 可在全腿视角内被找到** —— `051` 那个入口的回归防线。
- **SC-007**: 每条检索条件都有服务端下发的系统默认值；客户端代码内**零处**自行计算默认值。
- **SC-008**: 用户改值未提交时结果不变；提交后按新值；复位后回到系统值 —— 三条各有断言。
- **SC-009**: 召回判据的单元测试**不依赖真实数据库**（检索 port 存在的可验证收益）。
- **SC-010**: 五层各自有独立入口与独立测试；「先筛再排名」这类顺序错误**有断言可捕获**。
- **SC-011**: 所有待标定量均由**实测标定**产出，spec 与代码内**零处**拍出来的数值。

## Assumptions

- **本片是缺陷修复 + 架构落地，不是新功能** —— 用户可见的变化是「收租视角终于可用」与「排在前面的腿挂得出去」，而非多了什么。
- **权利金门槛没有误伤，实测否定了一次怀疑** —— 起草期怀疑它砍掉了活跃腿（未过门槛但 `OI≥100` 的有 247 条），逐段核后发现那批平均 `bid` 仅 `0.031–0.060`、平均年化 `0.6%–3.3%`：**是真垃圾，不是便宜好货**。⇒ 沿用 `050` 标定值不动。
- **业界流动性标准在本标的池上不适用** —— 按业界口径（价差/bid ≤ 3% 可接受、`OI ≥ 1000` 可接受）重算，过了权利金与持仓两条后的 1592 条里只有 **40 条（2.5%）** 达到价差标准、**153 条（9.6%）** 达到 OI 标准。因为业界数值是拿高流动性大盘股校准的，而本池是中小盘。⇒ 流动性 MUST 作为**分档信号**而非硬门槛，且档界 MUST 用本池标定。
- **「挂许愿单」策略改变了流动性的度量方式** —— 宽价差伤害的是**立即成交**；挂单等对手方来则价差不构成成本，只影响成交概率。⇒ 流动性的有效信号偏向**持仓与成交**（有没有人在这张合约上活动），而非价差窄不窄。
- **用户偏好长期限的直觉，其实是「长期腿流动性更好」的间接表现** —— `us:LULU` 实测：分层后 A 档 7 条里 **6 条 DTE ≥ 129**，而这**不是**人为给长期加权的结果，是流动性分档自然筛出来的。⇒ 本片 MUST NOT 引入任何期限先验（继承 `050` 不变量「DTE 不作排序主键」）。
- **年化对短期的偏袒只在 ATM 附近成立** —— 全池实测按价外程度 × 期限分组：ATM 段 `29.6% → 16.9%`（短期胜），而 `−15 ~ −30%` 段 `6.6% → 7.4%`、深度价外段 `2.3% → 3.8%`（**长期反超**）。且**离散度很大**，分组均值不能当规则。⇒ 佐证「不设期限先验」。
- **本片带一处 mobile 改动** ⇒ 按 Constitution §V 走**单 PR**（server + `export-openapi` + regen + mobile 消费 + 验证同 PR）。
- **口径声明** —— 本 spec 引用的所有实测数字取自 2026-08-12 dev 库最新交易日快照，判据在 SQL 里**复现** `050` 实装阈值（`DTE` 用 `expiry_date − session_date`、有效成本的 `P` 用 `bid` 近似）。**量级可信，逐条数字不可当实装输出引用。**
