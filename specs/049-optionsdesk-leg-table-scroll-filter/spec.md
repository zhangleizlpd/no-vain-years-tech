# Feature Specification: 选约表横滑范式换代 + 意图 Tab 重设计

**Feature Branch**: `049-optionsdesk-leg-table-scroll-filter`
**Created**: 2026-08-10
**Status**: Draft
**里程碑**: sell-put 可视化决策系统 —— optionsdesk 选约引擎重构的 **P0 片**（主 plan：`docs/private/plans/2026-08/08-11-optionsdesk-leg-engine-master.md`，本机私有）

> ⚠️ **本片范围于 2026-08-11 收窄**：原 spec 含「行权价区间筛选」一整块（US2 + `FR-008`–`FR-018` + `FR-023`）。经 08-11 讨论定案，筛选要走**服务端召回 + 截断**而非客户端过滤，且它与「腿族硬分类改软打标」的整体重构绑在一起 ⇒ 整块**移交后续片**（P3）。本片只保留**不依赖契约变化、且是 048 硬前置**的两块：横滑范式换代 + Tab 重设计。
> 📌 已完成的筛选行 mockup 帧（`design/049-leg-table-states.dc.html` 的 5 帧中 4 帧）随之移交 P3，形态已定稿不必重画。

## 背景：为什么切在这里

047 已 ship 的选约表有一个**正确性缺陷**和一笔**视觉欠账**，两者都落在同一张表上。

### 一、横滑失步是缺陷，不是规模问题（已由 ADR-0063 定案）

047 的实现让**表头与每一个数据行各挂一个横向滚动容器**、共享一个位移值、靠「谁滚了就把其余容器推到同一位移」来同步。真机上反复出现**列左右震荡 / 表头自己在滚 / 行间失步**，2026-07 起至少三次，行数从 10240 到 200 都复现。

[ADR-0063](../../docs/adr/0063-mobile-frozen-column-table-scroll-sync.md)（Accepted, 2026-08-10）定案：根因是**跟随者容器把系统钳制后的位移写回共享值**，形成不收敛的自激环 —— **与行数无关**，只要任一容器的钳制边界与其余不同，环就不收敛。采纳方案 E（零滚动容器：单一横向拖拽手势 → 单一共享位移 → 各行各自位移），并逐条否决了其余六个候选。

⇒ 本片是该 ADR 的**实施载体**。ADR 只落了决策，被判为缺陷载体的那段实现一行未动。

**这条决定了本片排在最前**：048 的跨标的聚合表要复用同一套横滑范式，在缺陷载体上再叠一层聚合，等于把同一个环复制到第二个屏；而后续 P1–P3 的重构都在这张表上做，先把地基上的缺陷修掉，后面每一片都少一个变量。

### 二、意图 Tab 视觉过弱

三个 Tab 夹在意图条与 12 列表头之间，字号与行高都是全屏最小的一档，**看不出它是这张表的主控件**。

📌 **本片只改 Tab 的「壳」**（视觉形态），不碰它的语义。Tab 从「腿族成员集合」改成「视角」是 P1/P2 的事 —— 那次改的是壳里的内容（显示哪个费率、打什么标、档位按哪个口径着色），与本片的视觉改动不重叠。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 横向看隐藏列，表不散架 (Priority: P1)

用户在标的详情页的选约表上左右滑动查看被隐藏的列（费率、成本、Δ、σ 距、OI、成交额、标注、动作）。行权价那一列始终钉在左侧不动，表头与所有数据行**作为一个整体**横向移动。用户随手来回滑动多次、松手，表停在该停的位置。

**Why this priority**: 这是**缺陷修复**，不是新功能。当前实现会让表在真机上散架 —— 列震荡、表头自漂、行与行之间错位到读错数（行权价对上了别人的报价）。一张读错数的期权表比没有表更危险。且它是 048 与后续三片的共同前置。

**Independent Test**: 只做这一块就能独立交付：真机上对同一张 730 行的表反复手滑，配数值探针观察位移写入与方向反转计数，与修复前的对照数据比较。

**Acceptance Scenarios**:

1. **Given** 选约表已渲染且列宽合计超出可视宽，**When** 用户横向滑动，**Then** 表头与全部可见行的同一列左缘逐像素对齐，行权价列一像素不动
2. **Given** 用户随手来回快速滑动十余次，**When** 松手并静置三秒，**Then** 位移停止增长并收敛；🚨 **判定必须靠数值探针** —— 「净位移为零但写入仍在涨」是自激环的签名，此时静态截图看起来是对齐的
3. **Given** 用户在表格区域纵向滑动，**When** 纵向位移超过方向仲裁阈值，**Then** 列表纵向滚动且横向位移不变（横向手势让位）
4. **Given** 用户横滑到最右端，**When** 继续向左拖，**Then** 最后一列完整露出且不越界，松手不回弹到越界位置
5. **Given** 用户旋转屏幕或进入分屏，**When** 可视宽度改变，**Then** 横向位移被拉回新的合法区间，且仍能滑到最右列

---

### User Story 2 - 一眼看出自己在哪个意图下 (Priority: P2)

用户扫一眼就能分辨当前停在「全腿 / 建仓腿 / 收租腿」的哪一个，且点击热区足够大不误触。

**Why this priority**: 纯视觉可用性。功能今天是通的（三个 Tab 都能进、切换都生效），只是不显眼。放在 US1 之后，因为它不影响正确性、也不阻塞后续片。

**Independent Test**: 独立可测：选中态与未选态在样式上可区分、三个 Tab 均可进入、切换后表内容确实更换。

**Acceptance Scenarios**:

1. **Given** 用户停在某个 Tab，**When** 扫视 Tab 行，**Then** 选中项与未选项在视觉上明确可分（不依赖读屏语义）
2. **Given** 某个 Tab 下零适格腿，**When** 用户点它，**Then** 仍可进入并显示空态 —— MUST NOT 置灰或隐藏（继承 047 FR-020）
3. **Given** Tab 行加高、表头栈新增指示条，**When** 用户进入详情页并滚到腿区，**Then** 表格数据区仍有可用高度（栈不把表压成一条缝）

---

### Edge Cases

- 表格列宽合计**不超过**可视宽（宽屏 / 未来减列）→ 无可滑动余量，横向指示条整条不渲染，拖拽不产生位移
- 用户在锚卡 / 温度计 / 区间时序区域横滑 → 位移照常发生（那时表在屏外，视觉无感），MUST NOT 为此加坐标判定这类脆逻辑
- 未选仓位水位时同屏渲两条就地注明 → 表头栈达到最高值，数据区仍须可见 ≥3 行（`SC-006`）

## Requirements _(mandatory)_

### Functional Requirements

#### 横向滑动（US1）

- **FR-001**: 选约表的横向位移 MUST 由**单一来源**驱动，表头与全部数据行读同一个位移值；MUST NOT 存在任何「跟随者把自己的实际位移写回共享值」的路径（该路径是 ADR-0063 判定的自激环成因）
- **FR-002**: 首列（行权价 / 到期）MUST 保持钉住不动，其钉住方式沿用 047 的布局判据（首列渲在横向位移区之外），本片不改
- **FR-003**: 横向与纵向手势 MUST 各自归属明确：横向位移超过仲裁阈值才接管横滑；纵向位移超过阈值则让位给列表纵向滚动。MUST NOT 出现纵滑被横向手势吃掉、或横滑期间列表纵向抖动
- **FR-004**: 横向位移 MUST 被约束在合法区间内（左端为零、右端为「内容宽减可视宽」），松手后的惯性衰减同样受该约束；**可视宽变化时（旋转 / 分屏）位移 MUST 被拉回新区间**
- **FR-005**: 由于新范式不再有系统原生的横向滚动条，系统 MUST 自绘一条横向位置指示条，其长度比例反映「可视宽 / 内容宽」、位置反映当前位移。**有可滑动余量时 MUST 常显** —— MUST NOT 做成「滑动时才出现、停手后淡出」：隐藏列占了表总宽的一半以上，静态首屏是用户唯一能得知「这张表还能横滑」的时机。无可滑动余量时整条不渲染。指示条为只读，本片不做可拖拽
- **FR-006**: 指示条的位置 MUST 由驱动表格的**同一个**位移值派生，MUST NOT 另立第二个来源（否则引入表与指示条不同步这一新的失步面）
- **FR-007**: 047 已定的列集、列宽、首列宽度与「横向滑动查看隐藏列」这一能力 MUST 保持不变 —— 本片只换实现机制，不改 047 `FR-003` 的任何判据

#### 意图 Tab（US2）

- **FR-008**: 三个意图 Tab 的视觉 MUST 重新设计，使选中态一眼可辨、点击热区足够。**形态已于 mockup 阶段定稿为稿 A**：等分三格 + 选中格 `surface-sunken` 底 + 底部 3px 短横条，行高约 40px
- **FR-009**: Tab 改版 MUST NOT 改变其行为契约：三个 Tab 恒可进入、恒不置灰、恒不按条件隐藏（继承 047 `FR-017` / `FR-020`）；就地注明仍渲在 Tab 行下方；切 Tab 仍只更换表格数据而不重建列表
- **FR-010**: Tab 的无障碍语义（角色、选中状态、标签）MUST 保留；且选中与未选 MUST 在**视觉样式**上可区分，不得仅靠无障碍语义编码
- **FR-011**: 表头区（警示条 + 计数条 + 意图与水位条 + Tab 行 + 就地注明 + 列头 + 指示条）的总高 MUST 留给表格数据区可用高度。**mockup 已给出证据**：sticky 栈净高 142px、含 chrome 后占 844 视口 **27.8%**、数据区约 12 行；最坏档（未选水位时同屏两条就地注明）为 **32.6%**，仍在 35% 目标内

### Key Entities

> 本片不引入新的业务实体（横滑位移与 Tab 选中态都是呈现层状态）。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 真机上对 730 行的选约表连续手动横滑十余次并松手静置，位移写入停止增长、方向反转计数不再增加；与修复前同条件对照，反转计数下降**两个数量级以上**（修复前实测 558 次 / 修复后个位数）
- **SC-002**: 横滑过程中任意时刻截停，表头与全部可见行的同列左缘偏差 **≤ 1 像素**（修复前实测首行与全表错开约 35 像素）
- **SC-003**: 纯纵向滑动时横向位移变化为 **0**；纯横向滑动时列表纵向位置不变
- **SC-004**: 横滑到最右端时最后一列**完整可见且无越界空白**；旋转屏幕后仍满足该条
- **SC-005**: 选中的意图 Tab 与未选的在视觉样式上可区分（可由自动化断言以样式自比较验证，不依赖无障碍语义）
- **SC-006**: 新 Tab 形态 + 指示条落地后，表格数据区在标准手机视口下仍可见 **≥ 3 行**腿数据，含「未选水位时同屏两条就地注明」的最坏档

## Assumptions

- **本片零服务端改动、零契约改动**：不新增字段、不改端点、不重新生成 `api-client`。凡涉及契约的改动（筛选参数、截断、新标、费率下沉）全部属于 P1–P3
- **表格列数维持 12 列不变**，因此本片不需要横向虚拟化（ADR-0063 假设横向不虚拟化，前提是列数受控）
- **纵向虚拟化沿用 047 的现状**（全页单一纵向滚动容器），本片只改横向，两个方向正交
- **真机是唯一的验收环境**（针对 US1）：合成手势是单指、单向、无交错的干净手势，ADR-0063 已实证缺陷实现在它下面**完全测不出问题**；网页端视口宽松同样必然假绿
- **Tab 的语义在本片不变** —— 它仍是 047 定义的「腿族成员集合」。改成「视角」是 P1/P2 的事，本片只改视觉，两次改动不重叠
- **048 的 V-C 验证判据需随本片改写**（ADR-0063 已记：规模不再是那道 gate 的风险源），但 048 已于 2026-08-11 冻结，改写动作等四片落完后连同 048 spec 一并重写
