# Feature Specification: 检索条件抽屉版式重构 —— 输入位可辨识 + 右边界对齐 + OR 显式化

## 背景：这一片在改什么

`optionsdesk` 详情屏的**检索条件抽屉**由 `052` T012 交付（六维条件 + 三态边际计数 + 显式提交），`053` T015 刚把输入范式从「`TextInput` + 系统键盘」改成「只读值 + 自绘键盘」（起因是真机验收读出两条 FAIL：输入法把整个抽屉顶出屏外、六个值淡到读不出）。

功能面到此已经对了，**版式面没有**。`053` 真机验收当场由 owner 提出四条，均属版面而非判据：

| #   | 问题                         | 现状证据                                                                                                                                  |
| --- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **「复位」独占一行、很突兀** | 右对齐单独占整行，左侧全空                                                                                                                |
| ②   | **框不像输入位**             | 圆角 pill + 居中文字读起来像标签 / 胶囊；只靠蓝边表示选中、**没有光标**，用户不知道该点哪、点了能不能改（owner 原话：「会增加解释成本」） |
| ③   | **右侧大片留白、右边界不齐** | `权利金` / `OI` / `价差` 三行的框挤在左侧约 40% 宽，右侧 60% 全空；而 `行权价` / `期限天` 是「框 – 框」占得多 ⇒ 各行右边界不齐，视觉碎    |
| ④   | **OR 关系只靠一个「或」字**  | `OI ≥ [1] 或 Vol ≥ [1]` 的「或」夹在两个框之间，结构与其余行不同，读起来会顿                                                              |

**本片只改版式**：六维判据、默认值解算、三态边际计数、提交语义全部零改动。

### ④ 的调研结论（已联网核过，clarify 期别重查）

🚨 **这个 OR 在业内是反常的**：主流期权筛选器（Barchart · 富途 moomoo · Interactive Brokers · MarketChameleon）都把 OI 与成交量当作**两条彼此独立、AND 组合**的筛选项（IB 默认 `volume ≥ 100` **且** `OI ≥ 500`），**没有一家做成「任一满足」**。

⇒ 本仓的「或」是 `052` 刻意选的（流动性判据：两者任一能证明这条腿挂得出去），**但它违反用户从别处带来的预期** ⇒ 不能靠一个小「或」字传达。

通用共识两条：① GitLab Design System · Filtering —— 多条件组合时 AND/OR 匹配规则应是**可见的规则选择器**（match any / match all），不是埋在字段间的连接词；② NN/g · Group Form Elements Using White Space —— 逻辑分组必须靠**间距 / 区块标题 / 分组标签**兑现，靠邻近性暗示不够。

📌 调研**没有**裁定「两个数字阈值的 OR 该怎么写」的唯一答案 —— 这正是 § Clarifications 第 1 问的由来。

### 已定方案：A′ 组合（owner 2026-08-14 裁定，mockup 四帧已走完）

**基线 = A**（齐右边界的下划线行 + 2px 光标 + 品牌浅底），四处调整：

| #   | 采用                            | 说明                                                                                                                                                                                                                        |
| --- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **C 的安置**                    | 「复位」并入键盘右整列。🚨 **顺序 = 复位在上、搜在下** —— owner 先选「搜在上」，被指出「主操作离拇指最远、破坏性操作占右下角」后**改回常规序**。视觉双通道保留：搜 = brand 实心主按钮 / 复位 = 次级描边，实测体量 214 vs 58 |
| ②   | **A 原样**                      | 下划线 + 光标 + 品牌浅底，不动                                                                                                                                                                                              |
| ③   | **`权利金` 与 `价差` 并成一行** | 候选 1「等分两半」。已实测**并得下**：不折行、不截字、不挤单位；最紧处值区内宽 76px，装 6 位小数需 52px，**余 24px**。收租视角 5 行 → 4 行，sheet 572px = 屏高 68%                                                          |
| ④   | **B 的样式**                    | 带框分组块 + 品牌浅底标签，文案**暂只做「满足任一」**；槽位实测 130px ≥ 未来 segmented 所需 124px ⇒ **升级只换槽内内容**，块高 / 字段区版式 / 行数不变                                                                      |

⚠️ **候选 1 的已知代价（owner 知情后仍选）**：右边界**从一条变两条**（权利金齐 171px 中缝、价差齐 356px 外缘）—— 全屏只有这一行带两条对齐线；`%` 离数字 93px（候选 2 是 65px、候选 3 是 39px，但各有别的代价；A 原状是 235px）。

### 🚨 起草期核出的一条：行形态不是两种，是**任意子集**

brief 的硬约束写的是「版式 MUST 对建仓 4 行 6 框 / 收租 5 行 8 框两种行数都成立」。核过实装后**这个枚举不完整**，且 A′ 的 ③ 在其中一种形态下**没有定义**：

| 视角     | 行集（`ROWS_BY_TAB`）                            | 行数 / 框数 | A′ ③ 合并后 | 备注                                                 |
| -------- | ------------------------------------------------ | ----------- | ----------- | ---------------------------------------------------- |
| **全腿** | `行权价` · `期限天` · `权利金` · `活性`          | 4 行 7 框   | **仍 4 行** | 🚨 **无价差行** ⇒ 权利金**没有配对者**，合并行不成立 |
| **建仓** | `期限天` · `权利金` · `活性` · `价差`            | 4 行 6 框   | 3 行        | 无行权价行（有效成本硬门槛已等价挡住深度实值）       |
| **收租** | `行权价` · `期限天` · `权利金` · `活性` · `价差` | 5 行 8 框   | 4 行        | brief 的 572px / 68% 那组读数量的就是它              |

更强的一条：`criteriaRowsFor` 的第二个分支是**「有值必可见」** —— 服务端若为某视角下发了本不属于该视角的维度默认值，那一行**照样出现**。⇒ 行集在结构上是**五行的任意子集**，不是三种固定形态。

⇒ 本片把约束提到「任意子集都成立」（`FR-012`），并把「权利金独自一行时怎么排」显式挂到 § Clarifications 第 2 问上 —— 它与「单位贴不贴数字」是同一个取向问题。

### 🚨 `~/ui` 的键盘是**两个 feature 共用**的

A′ ① 要往键盘右整列加一个次级键，而这块键盘不是本屏私有：

```text
apps/mobile/src/ui/numeric-keypad.tsx
  ├── apps/mobile/src/alert/value-input-sheet.tsx   ← 026 告警阈值屏（原产地）
  └── apps/mobile/src/optionsdesk/leg-criteria-sheet.tsx  ← 本屏（053 T015 上提时的第二个 consumer）
```

⇒ 扩展 MUST 是**加法**（可选入参），`alert` 侧的渲染与行为零变化（`FR-023` / `SC-006`）。这条不写下来的失败形态是：右列被改成「恒两键」，`alert` 屏多出一个它没有语义的按钮，而 typecheck 全绿。

## User Scenarios & Testing

### User Story 1 — 一眼看出哪里能改、改的是哪一格 (Priority: P1)

用户打开检索条件抽屉，不需要试点就知道六个值是**可以改的输入位**，并且看得出光标现在落在哪一格。

**Why this priority**: 这是 owner 提的四条里**唯一带「解释成本」这个词**的一条 —— 它不是好不好看的问题，是用户不知道能不能改。其余三条（版面碎、复位突兀、OR 读着顿）都不阻断使用，这条阻断。

**Acceptance Scenarios**:

1. **Given** 抽屉刚打开，**When** 用户扫视六个值，**Then** 它们读起来是输入位（下划线 + 光标 + 品牌浅底）而不是标签 / 胶囊
2. **Given** 键盘落点在某一格，**When** 用户看该格，**Then** 光标可见，且选中态同时有边框与底色两个通道（不只靠颜色）
3. **Given** 某格没有值，**When** 用户看它，**Then** 呈「不限」占位符，MUST NOT 呈 `0`（「下限设为 0」与「不设下限」在契约里是两件事）
4. **Given** 用户点任意一格，**When** 落点挪过去，**Then** **系统键盘不弹起** —— 光标只是视觉暗示，值仍是只读显示
5. **Given** 某格有值且未被选中，**When** 用户看它，**Then** 值与行标签同深、可读（`053` T013 FAIL ② 的回归防线）

---

### User Story 2 — 一屏读完，不被留白和参差打断 (Priority: P2)

用户纵向扫这几行时，右边界是齐的，不会出现「左侧 40% 挤满、右侧 60% 空着」的碎感；抽屉的高度也不至于把键盘挤出屏。

**Why this priority**: 纯观感与扫读效率，不阻断功能。放 P2 是因为它是四条里**改动面最大**的一条（合并行 + 全行重排），而收益是可读性。

**Acceptance Scenarios**:

1. **Given** 用户打开任一视角的抽屉，**When** 纵向扫视各行，**Then** 值区右边界对齐（权利金 / 价差合并行的两条对齐线是已知且知情的例外）
2. **Given** 视角同时有权利金行与价差行，**When** 抽屉渲染，**Then** 两者并成一行、等分两半，字段区少一行
3. **Given** 视角没有价差行（全腿），**When** 抽屉渲染，**Then** 权利金独自成行且版式仍成立，MUST NOT 出现半空的合并行骨架
4. **Given** 行最多的视角（收租），**When** 抽屉渲染，**Then** sheet 未超限高，键盘末行 `0` / `.` / `⌫` 三键完整在屏内且可点
5. **Given** 任一格里是最长的合法值（含小数），**When** 渲染，**Then** 不折行、不截字、不把单位挤走

---

### User Story 3 — 主操作落在拇指够得到的地方 (Priority: P2)

用户改完条件要提交时，「搜」在右下角拇指自然落点上；「复位」这个破坏性动作不在那里，也不再独占一整行。

**Why this priority**: 与 US2 同属版面，但它带一个**正确性侧的小闸** —— 破坏性操作占右下角是误触风险，不只是难看。

**Acceptance Scenarios**:

1. **Given** 抽屉打开，**When** 用户看操作区，**Then** 复位与搜同在键盘右整列、**复位在上、搜在下**，字段区不再有独占一行的复位
2. **Given** 两键同列，**When** 用户区分它们，**Then** 视觉双通道成立：搜是 brand 实心主按钮、复位是次级描边，且体量明显不同
3. **Given** 抽屉打开，**When** 用户扫全屏，**Then** MUST NOT 出现两个「搜」或两个「复位」
4. **Given** `alert` 的参数输入屏复用同一块键盘，**When** 该屏渲染，**Then** 右整列仍是单一确定键，渲染与行为零变化

---

### User Story 4 — 读得出「这两个条件是任一满足」 (Priority: P2)

用户看 OI 与 Vol 这一行时，能读出它是「任一满足即可」，而不是把「或」当成排版噪声略过、按业内习惯默认成「都要满足」。

**Why this priority**: 它防的是**读错判据**——用户按 AND 的预期设阈值，实际生效的是 OR，筛出来的腿比预期多，而**屏幕上没有任何地方会红**。放 P2 是因为当前判据本身没错，错的是表达。

**Acceptance Scenarios**:

1. **Given** 视角含活性行，**When** 用户看该行，**Then** 两个阈值在一个**带框分组块**内、块上有分组标签写明匹配规则，MUST NOT 只靠字段间的「或」字
2. **Given** 分组块渲染，**When** 用户改其中任一个阈值，**Then** 整行只出现**一个**「已改」蓝点（两框是一个维度，不是两维）
3. **Given** 分组块的规则位，**When** 本片交付，**Then** 该槽位的宽度已足以容下未来的规则选择器 —— 升级只换槽内内容，块高与字段区行数不变

---

### Edge Cases

- **全腿视角没有价差行** → 权利金独自成行，合并行 MUST NOT 出现半空骨架 (covers FR-012)
- **服务端为某视角下发了本不属于该视角的维度默认值** → 那一行照样出现（「有值必可见」优先于行集），版式仍须成立 (covers FR-012)
- **默认值契约未到手** → 六格全空、全呈「不限」，版式仍须成立 (covers FR-004, FR-012)
- **最长合法值**（权利金四位小数 / 行权价三位整数 / 天数三位）→ 不折行、不截字、不挤单位 (covers FR-011, FR-013)
- **收租视角**（行最多）→ sheet 未超限高且键盘末行可点 (covers FR-014)
- **`alert` 屏复用键盘** → 右列仍单键 (covers FR-023)
- **用户连点复位**（右上角，破坏性）→ 幂等，且它不在拇指自然落点上 (covers FR-021)

## Requirements

### 输入位可辨识（US1）

- **FR-001**: 值控件 MUST 读起来是**可编辑的输入位**（下划线 + 光标 + 品牌浅底），MUST NOT 是圆角 pill + 居中文字这种读成标签 / 胶囊的形态。
- **FR-002**: 🚨 值 MUST 仍是**只读显示 + 自绘键盘**，系统键盘 MUST NOT 弹起。⇒ 光标**只能是视觉暗示**，MUST NOT 为了拿到原生光标而改回文本输入控件。<br>📌 存在理由：`053` T015 正是为此把范式改掉的（该机数字键盘占约 60% 屏高，弹起后整个抽屉被顶出屏外，连正在编辑的框都看不见）。**回退即复发，且 web e2e 不会红**（web 没有输入法）。
- **FR-003**: 选中态 MUST 保持**双通道**（边框与底色同时变），MUST NOT 只靠颜色。
- **FR-004**: 空值 MUST 仍呈「不限」占位符，MUST NOT 预填 `0` 或 `∞` —— 两者都是**值**，不是「没有边界」。
- **FR-005**: 值 MUST 与行标签同深可读，MUST NOT 淡于标签（`053` T013 FAIL ② 的回归防线）。

### 版面与对齐（US2）

- **FR-010**: 各行值区 MUST 齐右边界，MUST NOT 留出「左侧约 40% 挤满、右侧 60% 全空」的现状。
- **FR-011**: 当某视角**同时**含权利金行与价差行时，两者 MUST 并成一行、等分两半。已实测并得下：最紧处值区内宽 76px，装 6 位小数需 52px，余 24px ⇒ 不折行、不截字、不挤单位。<br>⚠️ **已知代价（owner 知情后仍选）**：该行右边界从一条变两条（权利金齐 171px 中缝、价差齐 356px 外缘），全屏只有这一行带两条对齐线。
- **FR-012**: 🚨 版式 MUST 对**五行的任意子集**成立，不只是三种已知形态。<br>📌 存在理由：行集由 `criteriaRowsFor` 决定，它除了 per-视角的固定行集，还有第二个分支「**有值必可见**」—— 服务端为某视角下发了本不属于该视角的维度默认值时，那一行照样出现。已知三形态为 全腿 4 行 7 框 / 建仓 4 行 6 框 / 收租 5 行 8 框。<br>🚫 权利金在没有配对者时 MUST NOT 渲染成半空的合并行骨架。
- **FR-013**: 单值行的单位（如 `%`）与数字的距离 MUST 有一条明确取向并逐行一致。[NEEDS CLARIFICATION: 「右边界齐」与「单位贴数字」二者取哪个？候选 1 已选但张力在其余单值行仍在（`%` 离数字 93px；候选 2 为 65px、候选 3 为 39px，A 原状 235px）。同一问的第二半：全腿视角权利金独自成行时按哪种排法？]
- **FR-014**: sheet MUST 不超过既有限高，且键盘末行三键 MUST 完整在屏内且可点。🚨 键高 MUST 固定、MUST NOT 用 `flex-1` —— bottom-sheet 里父容器无确定高度，`flexBasis:0` 会塌缩把末行挤出屏，而 **web 视口够高照样全绿**。
- **FR-015**: 行数最多的视角（收租，合并后 4 行）的 sheet 占屏比 MUST 有真机读数并写回本 spec。mockup 期实测 572px = 屏高 68%。

### 操作区（US3）

- **FR-020**: 「复位」MUST NOT 独占字段区的一整行；它 MUST 并入键盘右整列。
- **FR-021**: 右整列的顺序 MUST 为**复位在上、搜在下**。<br>📌 存在理由：owner 初选「搜在上」，被指出「主操作离拇指最远、破坏性操作占右下角」后**改回常规序**。这条是误触风险，不只是观感。
- **FR-022**: 两键 MUST 视觉双通道可分：搜 = brand 实心主按钮 / 复位 = 次级描边，且体量明显不同（实测 214 vs 58）。
- **FR-023**: 🚨 对 `~/ui` 那块共用键盘的扩展 MUST 是**加法**（可选入参）；`alert` 参数输入屏的渲染与行为 MUST 零变化。<br>📌 存在理由：该键盘有**两个** consumer（`alert/value-input-sheet.tsx` 原产地 + 本屏）。把右列改成「恒两键」会让 `alert` 屏多出一个它没有语义的按钮，而 **typecheck 全绿**。
- **FR-024**: 同屏 MUST NOT 出现两个「搜」或两个「复位」（继承 `052` 的约定：右列的确定键随键盘常驻在屏内，字段区不再复制一个）。

### OR 关系显式化（US4）

- **FR-030**: OI 与 Vol 的「任一满足」MUST 由**带框分组块 + 分组标签**表达，MUST NOT 只靠夹在两框之间的「或」字。<br>📌 存在理由见 § 背景：主流期权筛选器一律把这两项做成独立 AND 项，用户带来的预期与本仓判据**相反**；而 GitLab DS / NN-g 的共识是匹配规则要么是可见的规则选择器、要么靠间距与分组标签兑现，邻近性暗示不够。
- **FR-031**: 分组块内的规则位 MUST 预留到足以容下未来的规则选择器（实测槽位 130px ≥ 所需 124px）⇒ 将来升级**只换槽内内容**，块高、字段区版式与行数不变。
- **FR-032**: 本片的规则文案 MUST 只做「满足任一」。[NEEDS CLARIFICATION: 「两者都要」（AND）要不要在本片真做？做 = 新增 FR 且要改 `livenessMin` 的契约语义；不做 = 规则位退化成一行只读的规则说明。这一问决定本片是「纯版式」还是「版式 + 一处契约语义」。]
- **FR-033**: 该行 MUST 仍是**一个维度** —— 整行只出一个「已改」蓝点、只出一份边际计数。🚫 MUST NOT 因为分了组就把两框拆成两维（拆开会让同一条腿同时计进两行边际计数）。

### 判据与既有约束零改动（继承）

- **FR-040**: 🚨 六维判据、默认值解算、三态边际计数 MUST **零改动** —— `apps/mobile/src/optionsdesk/leg-criteria.rules.ts` **零行 diff**。本片只改版面与接线。
- **FR-041**: 🚨 **0 新增 design token / 0 新配色** —— `apps/mobile/src/theme/` 零 diff，已冻结调色板内取色。
- **FR-042**: 键盘的 4×3 数字网格与固定键高 MUST 不动（见 `FR-014` 的塌缩坑）。
- **FR-043**: 「不限」语义（空值 = 不限）MUST 保留。
- **FR-044**: 提交语义 MUST 零改动 —— 显式点「搜」才生效（明禁输入停顿自动生效）；成对维度半空归零仍改回表单本身。
- **FR-045**: 抽屉走 RN `Modal` 渲到 root 层的结构 MUST 不动（它是「真盖住底部 Tab 栏」的成立前提，`053` T013 已 PASS）。

### 真机验收

- **FR-050**: 本片 MUST 走真机验收，判据至少含：① 三种行形态各一屏，值不折行不截字 ② 收租视角 sheet 占屏比与键盘末行可点性 ③ 任一格上系统键盘不弹起 ④ 值的可读性。<br>📌 存在理由：这四类 **web 结构性验不到**（见 frontmatter `web_compat_notes`），而 `052` / `053` 已因此连撞两次。

## Success Criteria

- **SC-001**: 三种已知行形态（全腿 4 行 7 框 / 建仓 4 行 6 框 / 收租 5 行 8 框）在真机上各有一屏读数，**零折行、零截字、单位未被挤走**。
- **SC-002**: 除权利金 / 价差合并行的两条已知对齐线外，其余各行值区右边界**逐行一致**（真机像素实测，不靠目测）。
- **SC-003**: 收租视角 sheet 占屏比有真机读数并写回本 spec；键盘末行三键完整在屏内**且实测可点**。
- **SC-004**: 六个格上系统键盘 **100% 不弹起**（真机验；`053` T015 的回归防线）。
- **SC-005**: 值与行标签的深浅在真机上可分辨为「同深」，非「值明显更淡」（`053` T013 FAIL ② 的回归防线，读数写回）。
- **SC-006**: `alert` 参数输入屏的既有 e2e **零改动全绿**，且该屏键盘右列仍是单一确定键（`FR-023` 的可验证形态）。
- **SC-007**: `leg-criteria.rules.ts` 的 git diff 为**零行**（`FR-040` 的机器判据）。
- **SC-008**: `apps/mobile/src/theme/` 的 git diff 为**零行**，新增 design token 数为 **0**（`FR-041` 的机器判据）。
- **SC-009**: 全屏不出现两个同名按钮（「搜」/「复位」各恰一个）。
- **SC-010**: 分组块内规则位的实测宽度 ≥ 未来规则选择器所需宽度，且该判据有断言或读数留痕（`FR-031` 的可验证形态）。
- **SC-011**: 「五行任意子集」有覆盖 —— 除三种固定形态外，MUST 至少构造一次「服务端下发了本不属于该视角的维度默认值」的形态并断言版式成立（`FR-012` 的可验证形态；真实数据下该分支可能恒不触发）。
- **SC-012**: OI / Vol 行改任一框，「已改」计数仍按**一维**计（`FR-033` 的可验证形态，防分组把维度拆成两份）。
