# Feature Specification: 检索条件抽屉版式重构 —— 输入位可辨识 + 右边界对齐 + OR 显式化

## 背景：这一片在改什么

`optionsdesk` 详情屏的**检索条件抽屉**由 `052` T012 交付（六维条件 + 三态边际计数 + 显式提交），`053` T015 刚把输入范式从「`TextInput` + 系统键盘」改成「只读值 + 自绘键盘」（起因是真机验收读出两条 FAIL：输入法把整个抽屉顶出屏外、六个值淡到读不出）。

功能面到此已经对了，**版式面没有**。`053` 真机验收当场由 owner 提出四条，均属版面而非判据：

| #   | 问题                         | 现状证据                                                                                                                                  |
| --- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **「复位」独占一行、很突兀** | 右对齐单独占整行，左侧全空                                                                                                                |
| ②   | **框不像输入位**             | 圆角 pill + 居中文字读起来像标签 / 胶囊；只靠蓝边表示选中、**没有光标**，用户不知道该点哪、点了能不能改（owner 原话：「会增加解释成本」） |
| ③   | **右侧大片留白、右边界不齐** | `权利金` / `OI` / `价差` 三行的框挤在左侧约 40% 宽，右侧 60% 全空；而 `行权价` / `期限天` 是「框 – 框」占得多 ⇒ 各行右边界不齐，视觉碎    |
| ④   | **OR 关系只靠一个「或」字**  | `OI ≥ [1] 或 Vol ≥ [1]` 的「或」夹在两个框之间，结构与其余行不同，读起来会顿                                                              |

**本片只改版式**：六维判据、默认值解算、三态边际计数、提交语义全部零改动。

### ④ 的调研结论（已联网核过，clarify 期别重查）

🚨 **这个 OR 在业内是反常的**：主流期权筛选器（Barchart · 富途 moomoo · Interactive Brokers · MarketChameleon）都把 OI 与成交量当作**两条彼此独立、AND 组合**的筛选项（IB 默认 `volume ≥ 100` **且** `OI ≥ 500`），**没有一家做成「任一满足」**。

⇒ 本仓的「或」是 `052` 刻意选的（流动性判据：两者任一能证明这条腿挂得出去），**但它违反用户从别处带来的预期** ⇒ 不能靠一个小「或」字传达。

通用共识两条：① GitLab Design System · Filtering —— 多条件组合时 AND/OR 匹配规则应是**可见的规则选择器**（match any / match all），不是埋在字段间的连接词；② NN/g · Group Form Elements Using White Space —— 逻辑分组必须靠**间距 / 区块标题 / 分组标签**兑现，靠邻近性暗示不够。

📌 调研**没有**裁定「两个数字阈值的 OR 该怎么写」的唯一答案 —— 本片对此的处置是 `FR-030`（带框分组块 + 分组标签）+ `FR-032`（规则位只做只读说明，不实装 AND），定案见 § Clarifications。

### 已定方案：A′ 组合（owner 2026-08-14 裁定，mockup 四帧已走完）

**基线 = A**（齐右边界的下划线行 + 2px 光标 + 品牌浅底），四处调整：

| #   | 采用                            | 说明                                                                                                                                                                                                                        |
| --- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **C 的安置**                    | 「复位」并入键盘右整列。🚨 **顺序 = 复位在上、搜在下** —— owner 先选「搜在上」，被指出「主操作离拇指最远、破坏性操作占右下角」后**改回常规序**。视觉双通道保留：搜 = brand 实心主按钮 / 复位 = 次级描边，实测体量 214 vs 58 |
| ②   | **A 原样**                      | 下划线 + 光标 + 品牌浅底，不动                                                                                                                                                                                              |
| ③   | **`权利金` 与 `价差` 并成一行** | 候选 1「等分两半」。已实测**并得下**：不折行、不截字、不挤单位；最紧处值区内宽 76px，装 6 位小数需 52px，**余 24px**。收租视角 5 行 → 4 行，sheet 572px = 屏高 68%                                                          |
| ④   | **B 的样式**                    | 带框分组块 + 品牌浅底标签，文案**暂只做「满足任一」**；槽位实测 130px ≥ 未来 segmented 所需 124px ⇒ **升级只换槽内内容**，块高 / 字段区版式 / 行数不变                                                                      |

⚠️ **候选 1 的已知代价（owner 知情后仍选）**：右边界**从一条变两条**（权利金齐 171px 中缝、价差齐 356px 外缘）—— 全屏只有这一行带两条对齐线；`%` 离数字 93px（候选 2 是 65px、候选 3 是 39px，但各有别的代价；A 原状是 235px）。

### 🚨 行集统一到 5 行（clarify 2026-08-14 裁定，推翻 `052` 两条）

brief 的硬约束写的是「版式 MUST 对建仓 4 行 6 框 / 收租 5 行 8 框两种行数都成立」。核过实装后**这个枚举不完整**，且 A′ 的 ③ 在其中一种形态下**没有定义**。以下是 `052` 的交付态（= 改版前）：

| 视角     | `052` 的行集（`ROWS_BY_TAB`）                      | 行数 / 框数 | 藏起来的行 → 其默认值                            |
| -------- | -------------------------------------------------- | ----------- | ------------------------------------------------ |
| **全腿** | `行权价` · `期限天` · `权利金` · `活跃度`          | 4 行 7 框   | `价差` → `relativeSpreadMax: null`               |
| **建仓** | `期限天` · `权利金` · `活跃度` · `价差`            | 4 行 6 框   | `行权价` → `strikeMin: null` / `strikeMax: null` |
| **收租** | `行权价` · `期限天` · `权利金` · `活跃度` · `价差` | 5 行 8 框   | 无（五行全在）                                   |

**裁定：三视角一律显示全部 5 行**（`FR-012`）。这消掉了「任意子集」这个版式复杂度，也让 A′ ③ 在三个视角都成立（权利金恒有配对者）。

#### 为什么这么改是安全的 —— 逐条实证，不是推论

| 判据                             | 实证                                                                                                                                                                              |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 当前被藏起来的两行，判据生不生效 | **一律不生效** —— `defaultCriteria()` 里全腿的 `relativeSpreadMax` 与建仓的 `strikeMin` / `strikeMax` **都是 `null`**                                                             |
| 这是巧合还是结构保证             | **结构保证** —— `criteriaRowsFor` 的第二分支是「**有值必可见**」：服务端下发非 `null` 默认值的维度一律出现，哪怕行集里没它 ⇒ `ROWS_BY_TAB` 在结构上**只可能藏住判据不生效的维度** |
| `null` 在服务端是不是真的无判据  | 是 —— `matchesCriterion` 每一支都是 `criteria.X !== null && …` 守卫                                                                                                               |
| 服务端要不要跟着改               | **不要** —— `applyOverride` 遍历全部六维、**无 per-视角白名单** ⇒ 任何视角本来就能收任何一维的覆盖。本片是**纯客户端**改动，零契约、零 server diff                                |
| 有没有先例                       | 有 —— 全腿**现在就在**显示两个默认 `null` 的空行（行权价 / 期限天）。源码注释原话：「不限」≠「没有这个控件」                                                                      |

⇒ **默认候选集逐视角零变化**。改的只是「哪些旋钮露出来」。

#### 代价（知情后仍选）

**① 推翻 `052` 两条带 FR 编号的裁定**，MUST 在本 spec 与 PR body 显式登记 supersede：

| `052` 条文 | 原论证                                                                                                      | 本片处置                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `FR-007`   | 建仓无行权价行 —— 有效成本硬门槛 `K − bid < spot` 已等价挡住深度实值，硬门槛不可调 ⇒ 整行不出现而非画禁用态 | 推翻。见下方②与 `FR-016`                            |
| `FR-010`   | 全腿无价差行 —— 参照视角不受流动性门槛约束                                                                  | 推翻。默认仍 `null`（参照性不变），只是把旋钮露出来 |

🚨 该改动落在 `leg-criteria.rules.ts` 的 `ROWS_BY_TAB` 上 ⇒ **`FR-040` 的「该文件零行 diff」必须同步松绑**（见 `FR-040`）。

**② 建仓视角上「可见旋钮」与「隐形硬门槛」落在同一个量上** —— `K − bid < spot` 无控件、不可调、且**不进边际计数**（`soleFailure === null` 那一支明写「硬门槛不过 ⇒ 不进任何一维的计数」）。用户设了行权价却看到腿更少时，少掉的那部分可能是硬门槛切的，而屏上不解释。⇒ 由 `FR-016` 的口径提示显式化。

**③ 全腿的逃生口风险已被现有机制兜住**（本来是最大顾虑，核完发现比预期小）：`051` ship 了「点流动性排除数 → 切全腿看被排除的腿」。默认 `null` ⇒ 逃生口默认完好（`053` `SC-012` 不变）；用户真手动设了 ⇒ `052` 的边际计数**会报**（`marginalHits` 那一支**没有** `tab !== 'all'` 守卫）⇒ 屏上出现「价差上界之外还有 N 条 · 去改」。那个 `tab !== 'all'` 守卫只管 `051` 的「分视角流动性排除数」，说的是系统默认闸，全腿本来就没有 ⇒ 不受影响。**腿消失是自解释的，不是静默的。**

#### 一条 `052` 当时没考虑到的（支持本裁定的最强论据）

硬门槛答的是「**不要深度实值**」，它**没有**答「我只想接这个价位以下的货」。建仓视角此前**无法表达**「只看行权价 ≤ 100 的腿」—— 这是**功能缺口**，不只是版面问题。

### 🚨 `~/ui` 的键盘是**两个 feature 共用**的

A′ ① 要往键盘右整列加一个次级键，而这块键盘不是本屏私有：

```text
apps/mobile/src/ui/numeric-keypad.tsx
  ├── apps/mobile/src/alert/value-input-sheet.tsx   ← 026 告警阈值屏（原产地）
  └── apps/mobile/src/optionsdesk/leg-criteria-sheet.tsx  ← 本屏（053 T015 上提时的第二个 consumer）
```

⇒ 扩展 MUST 是**加法**（可选入参），`alert` 侧的渲染与行为零变化（`FR-023` / `SC-006`）。这条不写下来的失败形态是：右列被改成「恒两键」，`alert` 屏多出一个它没有语义的按钮，而 typecheck 全绿。

## Clarifications

### Session 2026-08-14

- Q: OI / Vol 的「两者都要」（AND）要不要在本片真做？ → A: **不做**，分组块内的规则位只做一行**只读**的「满足任一」说明。<br>定案依据：做 AND 要动 `livenessMin` 的契约语义 + 服务端召回层，直接推翻本片「判据零改动」的核心边界；而升级槽位已实测留够（130px ≥ 未来 segmented 所需 124px）⇒ 将来只换槽内内容，**版式零返工**。🚫 **禁用态的 segmented 一并否掉** —— `052` 源码已立判据「禁用态是『暂时不能改』，这里是『压根没有这个旋钮』」，画一个点不动的选择器等于承诺一个不存在的能力。

- Q: 单值行的「右边界齐」与「单位贴数字」取哪个？ → A: **一律齐右边界**，单位跟在值区右端（`%` 离数字最远 93px，知情接受）。<br>定案依据：右边界不齐是 owner 提的四条起因之一（③），取「单位贴数字」只解一半；而 93px 的代价只落在带单位的那一行（六维里只有价差带 `%`）。

- Q: 三视角的检索条件行集怎么定？ → A: 🚨 **三视角一律显示全部 5 行**，且建仓的行权价行**带硬门槛口径提示**。<br>定案依据、逐条实证与三项代价见 § 背景「行集统一到 5 行」。要点三条：① 当前被藏的两行默认值**都是 `null`** 且这是**结构保证**（「有值必可见」使 `ROWS_BY_TAB` 只可能藏住不生效的维度）⇒ 改动**行为惰性**、默认候选集零变化 ② `applyOverride` 无 per-视角白名单 ⇒ **服务端零改动、纯客户端** ③ 它答了一个 `052` 没答的功能缺口 —— 建仓此前无法表达「只看行权价 ≤ 100 的腿」（硬门槛答的是「不要深度实值」，不是用户的价位偏好）。<br>🚨 **代价**：推翻 `052` `FR-007` + `FR-010` 两条（MUST 在 PR body 登记 supersede），且 `FR-040` 的「`leg-criteria.rules.ts` 零行 diff」随之松绑。

- Q: 真机验收里「sheet 占屏比」的门槛怎么定？ → A: **相对判据** —— 同视角 sheet 高度 MUST NOT 劣于改版前，硬上限沿用代码里已有的 `max-h-[92%]`，另加结构判据「键盘末行实测可点」。<br>定案依据：🚫 **不用绝对百分比** —— `053` T013 已实证**百分比的分母不明**（`051` 的「138.5dp / 27.9%」反推屏高 496dp，而本机实测 831dp；取全屏 / app 区 / 内容区能算出三个不同的数）。拿一个分母不明的百分比当门槛会重蹈那个坑。相对判据 + 结构判据都是能验的。

- Q: OI / Vol 分组块的标签叫什么？ → A: **「活跃度」**，沿用已有用户可见文案，**零新词**。<br>定案依据：这一维在计数行里**已经有名字** —— `countLabels.livenessMin = '活跃度下限'`，用户在「活跃度下限之外还有 N 条」里见过它。🚫 brief 原提的「活性」会成为同一个东西的**第三个**叫法（代码 `livenessMin` / 文案「活跃度」/ 新词「活性」）。🚫 「流动性」同样否掉 —— 它会与计数行的「活跃度」在屏上并存，除非顺手改掉 `countLabels`，而那超出本片版式边界。<br>⚠️ **绊线**：选约表另有一列叫「活跃」（标注枚举，同源不同物）。两者 MUST NOT 在同一屏上被读成一件事，impl 期需复核。

- Q: 区间行（行权价 / 期限天）要不要拆成显式的 ≥ / ≤？ → A: **不拆**，保持「标签 + [框] – [框]」。<br>定案依据：拆开要多一份标签宽度，直接吃掉本片花力气争取的值区宽度（右边界对齐是四条起因之一）；且 `–`（区间取交）与活跃度那行的「或」（择一）**已经是两种可区分的中缝语义**。⚠️ 代价登记：这让两个区间行仍然是「方向感靠输入框位置暗示」那条既有原则的例外（`权利金 ≥` / `价差 ≤` 把方向写进了标签）。

## User Scenarios & Testing

### User Story 1 — 一眼看出哪里能改、改的是哪一格 (Priority: P1)

用户打开检索条件抽屉，不需要试点就知道六个值是**可以改的输入位**，并且看得出光标现在落在哪一格。

**Why this priority**: 这是 owner 提的四条里**唯一带「解释成本」这个词**的一条 —— 它不是好不好看的问题，是用户不知道能不能改。其余三条（版面碎、复位突兀、OR 读着顿）都不阻断使用，这条阻断。

**Acceptance Scenarios**:

1. **Given** 抽屉刚打开，**When** 用户扫视六个值，**Then** 它们读起来是输入位（下划线 + 光标 + 品牌浅底）而不是标签 / 胶囊
2. **Given** 键盘落点在某一格，**When** 用户看该格，**Then** 光标可见，且选中态同时有边框与底色两个通道（不只靠颜色）
3. **Given** 某格没有值，**When** 用户看它，**Then** 呈「不限」占位符，MUST NOT 呈 `0`（「下限设为 0」与「不设下限」在契约里是两件事）
4. **Given** 用户点任意一格，**When** 落点挪过去，**Then** **系统键盘不弹起** —— 光标只是视觉暗示，值仍是只读显示
5. **Given** 某格有值且未被选中，**When** 用户看它，**Then** 值与行标签同深、可读（`053` T013 FAIL ② 的回归防线）

---

### User Story 2 — 一屏读完，不被留白和参差打断 (Priority: P2)

用户纵向扫这几行时，右边界是齐的，不会出现「左侧 40% 挤满、右侧 60% 空着」的碎感；抽屉的高度也不至于把键盘挤出屏。

**Why this priority**: 纯观感与扫读效率，不阻断功能。放 P2 是因为它是四条里**改动面最大**的一条（合并行 + 全行重排），而收益是可读性。

**Acceptance Scenarios**:

1. **Given** 用户打开任一视角的抽屉，**When** 纵向扫视各行，**Then** 值区右边界对齐（权利金 / 价差合并行的两条对齐线是已知且知情的例外）
2. **Given** 任一视角，**When** 抽屉渲染，**Then** 权利金与价差并成一行、等分两半，字段区恒为 4 行
3. **Given** 用户在三个视角之间切换，**When** 抽屉重渲，**Then** 行数与各行位置**不跳** —— 行集不随视角变
4. **Given** 任一视角，**When** 抽屉渲染，**Then** sheet 未超限高，键盘末行 `0` / `.` / `⌫` 三键完整在屏内且可点
5. **Given** 任一格里是最长的合法值（含小数），**When** 渲染，**Then** 不折行、不截字、不把单位挤走

---

### User Story 3 — 主操作落在拇指够得到的地方 (Priority: P2)

用户改完条件要提交时，「搜」在右下角拇指自然落点上；「复位」这个破坏性动作不在那里，也不再独占一整行。

**Why this priority**: 与 US2 同属版面，但它带一个**正确性侧的小闸** —— 破坏性操作占右下角是误触风险，不只是难看。

**Acceptance Scenarios**:

1. **Given** 抽屉打开，**When** 用户看操作区，**Then** 复位与搜同在键盘右整列、**复位在上、搜在下**，字段区不再有独占一行的复位
2. **Given** 两键同列，**When** 用户区分它们，**Then** 视觉双通道成立：搜是 brand 实心主按钮、复位是次级描边，且体量明显不同
3. **Given** 抽屉打开，**When** 用户扫全屏，**Then** MUST NOT 出现两个「搜」或两个「复位」
4. **Given** `alert` 的参数输入屏复用同一块键盘，**When** 该屏渲染，**Then** 右整列仍是单一确定键，渲染与行为零变化

---

### User Story 4 — 读得出「这两个条件是任一满足」 (Priority: P2)

用户看 OI 与 Vol 这一行时，能读出它是「任一满足即可」，而不是把「或」当成排版噪声略过、按业内习惯默认成「都要满足」。

**Why this priority**: 它防的是**读错判据**——用户按 AND 的预期设阈值，实际生效的是 OR，筛出来的腿比预期多，而**屏幕上没有任何地方会红**。放 P2 是因为当前判据本身没错，错的是表达。

**Acceptance Scenarios**:

1. **Given** 任一视角，**When** 用户看活跃度那一行，**Then** 两个阈值在一个**带框分组块**内、块上有「活跃度」分组标签并写明匹配规则，MUST NOT 只靠字段间的「或」字
2. **Given** 分组块渲染，**When** 用户改其中任一个阈值，**Then** 整行只出现**一个**「已改」蓝点（两框是一个维度，不是两维）
3. **Given** 分组块的规则位，**When** 本片交付，**Then** 该槽位的宽度已足以容下未来的规则选择器 —— 升级只换槽内内容，块高与字段区行数不变

---

### User Story 5 — 每个视角都能表达自己那套价位与流动性偏好 (Priority: P2)

用户在建仓视角想说「我只接行权价 100 以下的货」，或在全腿视角想临时收一下价差，都能在抽屉里直接表达 —— 不必因为「这个视角没有那个旋钮」而放弃。

**Why this priority**: 它带一条 `052` 没答的**功能缺口**（建仓此前无法表达价位偏好：硬门槛答的是「不要深度实值」，不是用户的价位偏好），同时是「行数不随视角跳」的成立前提。放 P2 是因为默认行为零变化——不设值时它完全不生效。

**Acceptance Scenarios**:

1. **Given** 用户在建仓视角，**When** 打开抽屉，**Then** 行权价行可见且默认呈「不限」；设一个上界后候选按该上界收窄
2. **Given** 建仓视角的行权价行，**When** 用户看它，**Then** 有口径提示写明**另有一道有效成本硬门槛在生效、且它不在这里调**
3. **Given** 用户在全腿视角，**When** 打开抽屉，**Then** 价差行可见且默认呈「不限」——`051` 那个「点流动性排除数切过来看被排除的腿」的入口**默认不受影响**
4. **Given** 用户在全腿视角**手动**设了价差上界导致腿减少，**When** 结果更新，**Then** 边际计数报出「价差上界之外还有 N 条 · 去改」，MUST NOT 让腿静默消失
5. **Given** 三个视角任一，**When** 用户不动任何一格，**Then** 该视角的候选集与改版前**逐条一致**（本片改的是旋钮露不露出来，不是判据）

---

### Edge Cases

- **某视角的某一维默认值为空**（全腿的价差 / 建仓的行权价 / 全腿的期限段）→ 该行**照常出现**并呈「不限」，MUST NOT 因为空就把行藏起来 (covers FR-012)
- **默认值契约未到手** → 八格全空、全呈「不限」，版式仍须成立 (covers FR-004, FR-012)
- **用户在全腿视角手动设了价差上界** → 腿减少必须由边际计数报出，MUST NOT 静默；且 `051` 的排除数入口语义不受影响 (covers FR-017)
- **建仓视角用户设了行权价、结果比预期更少** → 口径提示已说明另有硬门槛在切，MUST NOT 让用户把硬门槛的效果记在自己头上 (covers FR-016)
- **最长合法值**（权利金四位小数 / 行权价三位整数 / 天数三位）→ 不折行、不截字、不挤单位 (covers FR-011, FR-013)
- **收租视角**（行最多）→ sheet 未超限高且键盘末行可点 (covers FR-014)
- **`alert` 屏复用键盘** → 右列仍单键 (covers FR-023)
- **用户连点复位**（右上角，破坏性）→ 幂等，且它不在拇指自然落点上 (covers FR-021)

## Requirements

### 输入位可辨识（US1）

- **FR-001**: 值控件 MUST 读起来是**可编辑的输入位**（下划线 + 光标 + 品牌浅底），MUST NOT 是圆角 pill + 居中文字这种读成标签 / 胶囊的形态。
- **FR-002**: 🚨 值 MUST 仍是**只读显示 + 自绘键盘**，系统键盘 MUST NOT 弹起。⇒ 光标**只能是视觉暗示**，MUST NOT 为了拿到原生光标而改回文本输入控件。<br>📌 存在理由：`053` T015 正是为此把范式改掉的（该机数字键盘占约 60% 屏高，弹起后整个抽屉被顶出屏外，连正在编辑的框都看不见）。**回退即复发，且 web e2e 不会红**（web 没有输入法）。
- **FR-003**: 选中态 MUST 保持**双通道**（边框与底色同时变），MUST NOT 只靠颜色。
- **FR-004**: 空值 MUST 仍呈「不限」占位符，MUST NOT 预填 `0` 或 `∞` —— 两者都是**值**，不是「没有边界」。
- **FR-005**: 值 MUST 与行标签同深可读，MUST NOT 淡于标签（`053` T013 FAIL ② 的回归防线）。

### 版面与对齐（US2）

- **FR-010**: 各行值区 MUST 齐右边界，MUST NOT 留出「左侧约 40% 挤满、右侧 60% 全空」的现状。
- **FR-011**: 权利金与价差 MUST 并成一行、等分两半。**容量判据 = 最紧处值区内宽 ≥ 52px**（装 6 位小数所需）⇒ 不折行、不截字、不挤单位。<br>📌 **2026-08-14 实装读数订正**：本条原记「内宽 76px，余 24px」，那是 **mockup 槽位**的读数；T005 实装后在 390×844 窄视口（该 e2e 文件头 `test.use`，≈ 真机宽度）实测为 **71px，余 19px** —— 功能判据仍满足，短的是余量。订正理由与 analyze A1 对 `SC-010`／130px 的判定**同源**：mockup 里那个槽位不是实装组件，其读数不能当实装判据。⇒ 本条的**可验证形态是 ≥ 52 那个下界**（T005 e2e 已常驻断言），不是任何一个具体的余量数字。<br>⚠️ **已知代价（owner 知情后仍选）**：该行右边界从一条变两条（权利金齐中缝、价差齐外缘），全屏只有这一行带两条对齐线。<br>⚠️ 上句两个 px 位置读数同为 mockup 来源，**未经实装复测**，勿当实装判据引用。
- **FR-012**: 🚨 **三视角的行集 MUST 一致 —— 一律显示全部 5 行**（合并后字段区恒 4 行）。切换视角 MUST NOT 改变行数或各行位置。<br>📌 定案依据与三项代价见 § 背景「行集统一到 5 行」。<br>🚫 某一维默认值为空 MUST NOT 成为藏起该行的理由 —— 空 = 「不限」，那是一个**用户可用的旋钮**，不是「没有这个旋钮」。<br>⚠️ **连带的实现面登记**：行集统一后 `criteriaRowsFor` 的第二分支（「有值必可见」）在结构上**不再可达**（固定行集已含全部 5 行）。它是留作防御并加注释、还是简化掉，归 plan 裁定；本 spec 只登记这个 orphan 的产生，MUST NOT 让它无声留着。
- **FR-013**: 单值行 MUST **一律齐右边界**，单位（如 `%`）跟在值区右端并逐行一致。<br>⚠️ **知情代价**：`%` 离数字最远 93px（候选 2 为 65px、候选 3 为 39px，A 原状 235px）。取「齐右边界」是因为右边界不齐是 owner 提的四条起因之一（③），取「单位贴数字」只解一半；而六维里只有价差带单位 ⇒ 代价只落在那一格。
- **FR-014**: sheet MUST 不超过既有限高，且键盘末行三键 MUST 完整在屏内且可点。🚨 键高 MUST 固定、MUST NOT 用 `flex-1` —— bottom-sheet 里父容器无确定高度，`flexBasis:0` 会塌缩把末行挤出屏，而 **web 视口够高照样全绿**。
- **FR-015**: sheet 高度的验收 MUST 走**相对判据 + 结构判据**：① 同视角 sheet 高度 MUST NOT 劣于改版前 ② 硬上限沿用代码里已有的 `max-h-[92%]` ③ 键盘末行**实测可点**。读数 MUST 写回本 spec（mockup 期实测 572px ≈ 屏高 68%）。<br>🚫 **MUST NOT 用一个绝对百分比当门槛** —— `053` T013 已实证百分比的**分母不明**（`051` 的「138.5dp / 27.9%」反推屏高 496dp，而该机实测 831dp；取全屏 / app 区 / 内容区能算出三个不同的数）。

### 行集统一（US5）

- **FR-016**: 建仓视角的行权价行 MUST 带**口径提示**，写明另有一道有效成本硬门槛在生效、且它不在这里调。<br>📌 存在理由：`K − bid < spot` 无控件、不可调、**且不进边际计数**（`soleFailure === null` 那一支明写「硬门槛不过 ⇒ 不进任何一维的计数」）⇒ 用户设了行权价却看到腿更少时，少掉的那部分可能是硬门槛切的，而屏上不解释。形态沿用权利金那个 ⓘ（tap 触发的 popup tip，热区 44×44），🚫 MUST NOT 新造一种提示形态。
- **FR-016a**: 🚨 该 ⓘ MUST 落在**行标签内**（定宽标签之内），MUST NOT 落在值区右侧、也 MUST NOT 落在值区内部。<br>📌 **mockup 2026-08-14 实测定案**（三候选同帧对照，读数见 `design/handoff-info-placement.md`）：行标签是定宽 `flex: none` ⇒ 值区的起点与宽度**一个像素都不被碰**，`FR-010` 的右边界对齐**由结构保证**而非「量出来正好齐」。另外两个候选各破一条 —— 落值区右侧使该行值区右缘短 **32px**（直接违反 `FR-010`）；落值区内部虽保住右缘，但两个框各被挤掉 **15px**（125 → 110）。<br>📌 容量已验：mockup 的 76px 标签内 `scrollWidth == clientWidth`（零溢出），而实装标签是 `w-20` = 80px **更宽 4px** ⇒ 本帧过了实装必过。
- **FR-017**: 全腿视角的价差行默认 MUST 为「不限」—— `051` 那个「点流动性排除数切到全腿看被排除的腿」的入口 MUST NOT 因本片而失效。<br>📌 用户**手动**设了它导致腿减少时，`052` 的边际计数会报「价差上界之外还有 N 条 · 去改」（该路径已实证无 `tab !== 'all'` 守卫）⇒ 腿消失是自解释的。本条要守的是**默认态**，不是禁止用户设。
- **FR-018**: 本片对 `052` `FR-007`（建仓无行权价行）与 `FR-010`（全腿无价差行）构成 **supersede**，MUST 在本 spec 与 PR body 显式登记，MUST NOT 当作无感知调整。
- **FR-019**: 行集统一 MUST NOT 改变任一视角的**默认候选集** —— 不动任何一格时，三视角的候选与改版前逐条一致。<br>📌 可行性前提已实证：被藏两行的默认值都是 `null`，服务端各维守卫一律 `!== null`，且 `applyOverride` 无 per-视角白名单 ⇒ **服务端零改动**。

### 操作区（US3）

- **FR-020**: 「复位」MUST NOT 独占字段区的一整行；它 MUST 并入键盘右整列。
- **FR-021**: 右整列的顺序 MUST 为**复位在上、搜在下**。<br>📌 存在理由：owner 初选「搜在上」，被指出「主操作离拇指最远、破坏性操作占右下角」后**改回常规序**。这条是误触风险，不只是观感。
- **FR-022**: 两键 MUST 视觉双通道可分：搜 = brand 实心主按钮 / 复位 = 次级描边，且体量明显不同（实测 214 vs 58）。
- **FR-023**: 🚨 对 `~/ui` 那块共用键盘的扩展 MUST 是**加法**（可选入参）；`alert` 参数输入屏的渲染与行为 MUST 零变化。<br>📌 存在理由：该键盘有**两个** consumer（`alert/value-input-sheet.tsx` 原产地 + 本屏）。把右列改成「恒两键」会让 `alert` 屏多出一个它没有语义的按钮，而 **typecheck 全绿**。
- **FR-024**: 同屏 MUST NOT 出现两个「搜」或两个「复位」（继承 `052` 的约定：右列的确定键随键盘常驻在屏内，字段区不再复制一个）。

### OR 关系显式化（US4）

- **FR-030**: OI 与 Vol 的「任一满足」MUST 由**带框分组块 + 分组标签**表达，MUST NOT 只靠夹在两框之间的「或」字。<br>📌 存在理由见 § 背景：主流期权筛选器一律把这两项做成独立 AND 项，用户带来的预期与本仓判据**相反**；而 GitLab DS / NN-g 的共识是匹配规则要么是可见的规则选择器、要么靠间距与分组标签兑现，邻近性暗示不够。
