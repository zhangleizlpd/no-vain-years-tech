# Feature Specification: 研报库 guest 投递入口

**Feature Branch**: `057-research-report-guest-ingest`
**Created**: 2026-08-15
**Status**: Tasks-ready
**Input**: 见 `docs/private/plans/streamed-soaring-stallman.md`（本机私有，未公开）

> 本片是 [PRD §3.8 研报库](../../docs/prd/portfolio/portfolio-master-prd.md) 的第一个 use case。研报库在 PRD 里与 §3.5 预警管理、§3.6 笔记管理同级，而 §3.5 已落成独立 bounded context `alert` —— 本片据此立第 11 个 context `research`。
>
> 研报按 **`market:code` 逻辑键**归档（PRD §3.8 原文「按标的（market+code）归档」），**不建到标的注册表的外键** —— 与 [014](../014-stock-detail/spec.md) 已确立的「与 015 运行时零跨 ctx，仅共享 `market:code` 逻辑键」同构。

## Clarifications

### Session 2026-08-15

- Q: 内容指纹（文件字节哈希）的唯一性作用域是什么？ → A: **每投递方唯一，归档对象复用** —— 唯一键 = (投递方, 指纹)；同一字节被两个投递方各投一次产生两行元数据，但指向同一份归档对象（对象位置由指纹导出）。理由：两个投递方各自存档同一份研报是有信息量的事件（US5 归属完整性），而对象复用使容量零浪费。
- Q: 同一投递方重投相同字节、而库中已有该指纹的未完成记录时怎么处理？ → A: **就地续做** —— 命中未完成记录则重传对象，成功后原地翻已完成，不新增行、不报冲突。理由：隧道上传超时后 agent 重试是常态，「拒绝并等人工」会把常态变成频繁人工活；而同字节写同一位置是幂等重写，即便对象上次其实已传成也无害。未完成记录是「这次没传成」的证据，不是「已归档」的证据，不应成为障碍物。
- Q: 投递方配额按什么口径计量？ → A: **按各自投递的字节累加** —— 共享对象双方各计一次（高估实际占用，天然保守）；未完成记录计入（就地续做语义使重试不会重复膨胀）；被拒的投递不计。理由：配额的目的是防单个投递方失控而非精确会计；8GB × 2 远低于 40G 总容量，为精度维护一套去重视图不划算。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 投递一份研报并确认它进了库 (Priority: P1)

隧道内的外部投递方（下称「投递方」）手上有一份关于某个标的的深度研报 PDF。他通过随身的 agent 把文件连同三项说明（这是哪只标的、研报日期、标题）一次性交给系统；系统当场告诉他收下了，并给回一个可以指认这份研报的标识。

**Why this priority**: 这是整个特性存在的理由。没有它，后面所有校验、幂等、配额都无处附着。

**Independent Test**: 用一份真实的研报 PDF（约 2MB）走完整投递路径，断言：对象落进了归档存储、元数据库多了一行、返回的标识能反查到那一行。单这一条就构成可用的 MVP —— 归档库开始有内容。

**Acceptance Scenarios**:

1. **Given** 一份合规 PDF 与齐全的三项说明，**When** 投递，**Then** 系统确认收下，并返回可反查的归档标识
2. **Given** 投递已成功，**When** 查归档存储与元数据，**Then** 两侧各有且仅有一份，且元数据记录了原始文件名、字节数、内容指纹、投递方与投递时刻
3. **Given** 标的写法是后缀式（如 `1698.HK`），**When** 投递，**Then** 落库的是归一后的形式，且后续按归一形式可检索到

---

### User Story 2 - 重复投递不产生重复归档 (Priority: P1)

投递方的 agent 在隧道上传时超时了，它按常规重试。用户不希望库里因此出现两份一模一样的研报，也不希望配额被白吃一份。

**Why this priority**: 隧道上传超时后 agent 重试是**常态而非异常**。没有幂等，归档库会在正常使用中就被污染，且 40G 配额被无谓消耗。与 US1 同级。

**Independent Test**: 同一份字节投递两次，断言第二次返回与第一次相同的归档标识，且归档存储中对象数与元数据行数都仍是 1。

**Acceptance Scenarios**:

1. **Given** 某份研报已归档，**When** 用完全相同的字节再次投递，**Then** 返回首次那条记录，归档存储不新增对象
2. **Given** 某份研报已归档，**When** 用**不同**字节但相同标的与相同研报日期投递，**Then** 两份各自独立归档（它们是同一标的的不同版本，不是重复）

---

### User Story 3 - 不合规投递被明确拒绝且原因可辨 (Priority: P2)

投递方的 agent 传错了东西：可能是张图片改了扩展名、可能文件太大、可能漏填了标的、也可能标的是不支持的市场。用户希望系统当场拒绝，并且拒绝理由足够具体，让 agent 能自己纠正而不是盲目重试。

**Why this priority**: 投递方是大模型驱动的 agent，**含糊的拒绝会让它反复重试**，既烧限频也污染日志。拒绝理由的可辨识度直接决定这条通道好不好用。

**Independent Test**: 逐一构造五类不合规输入（非 PDF / 超大 / 缺必填项 / 非法市场 / 配额耗尽），断言各自被拒且拒绝理由互不相同、可被 agent 区分。

**Acceptance Scenarios**:

1. **Given** 一个改成 `.pdf` 扩展名的非 PDF 文件，**When** 投递，**Then** 被拒，且判据基于文件内容而非文件名
2. **Given** 一份超出单份上限的文件，**When** 投递，**Then** 被拒，且理由与「非 PDF」可区分
3. **Given** 缺少标的 / 研报日期 / 标题中任一项，**When** 投递，**Then** 被拒，且指出缺的是哪一项
4. **Given** 标的市场不在支持范围，**When** 投递，**Then** 在到达业务处理之前就被拒
5. **Given** 该投递方累计用量已达配额，**When** 投递一份本身完全合规的文件，**Then** 仍被拒

---

### User Story 4 - 归档内容对投递方单向不可见 (Priority: P2)

投递方能往库里放东西，但**看不到库里有什么** —— 包括他自己之前放进去的。用户本人通过归档存储的管理面与元数据库直接查看。

**Why this priority**: 研报含用户的持仓与主观判断，是单向收集箱不是共享资料库。这条决定了整条通道的安全形状。

**Independent Test**: 用投递方的凭证尝试读取、列举、修改、删除，断言全部被拒；并断言拒绝发生在**通道与服务两层**，而不只靠「服务端没实现」。

**Acceptance Scenarios**:

1. **Given** 投递方持有效凭证，**When** 尝试读取或列举已归档研报，**Then** 被拒
2. **Given** 服务端未实现任何读取动作，**When** 检查通道层配置，**Then** 通道层**也**显式只放行投递动作（两层各拒一次，不依赖对方）

---

### User Story 5 - 每一份归档都能追溯到投递方 (Priority: P3)

库里将来会有多个来源的研报。用户希望任意一份都能回答「这是谁放进来的、什么时候放的」。

**Why this priority**: 归档库的可信度依赖来源可追溯；但它不阻塞前四条，故 P3。

**Independent Test**: 两个不同投递方各投一份，断言两条记录的投递方归属不同且与实际一致。

**Acceptance Scenarios**:

1. **Given** 两个不同投递方，**When** 各投递一份，**Then** 两条记录的投递方归属互不相同且正确
2. **Given** 一条归档记录，**When** 查看它，**Then** 能读出投递方身份与投递时刻

---

### Edge Cases

- **对象已写入但元数据落库失败** → 必须留下可被扫出的未完成记录。系统对归档存储**没有删除权限**，孤儿对象清不掉，所以「查得到」是唯一的补救前提
- **归档存储可达性不确定**（既非明确成功也非明确失败，例如存储服务欠费停用）→ 不得断言投递失败。对已经成功上传的投递方说「失败了」会导致他重复投递
- **归档能力未配置**（尚未接通存储）→ 报「该能力未启用」，不得表现为服务故障
- **凭证缺失 vs 凭证不符** → 对外不可区分，避免被用来探测凭证是否存在
- **同标的同日期的两份不同研报** → 各自独立归档；本片不实装版本号推进规则（属 PRD §3.8 后续），但数据结构须留位
- **标的写法多样**（前缀式 / 后缀式 / 带交易所后缀 / 大小写混杂）→ 一律归一后落库，库里不得出现同一标的的两种写法
- **投递方在标的位置做百分号编码** → 会被市场白名单拒绝。方向是拒绝而非放行（安全），但拒绝理由须明确写出「不要编码」，否则 agent 会反复试错

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 接受投递方提交的单份 PDF 文件，并同时接收三项必填说明：标的、研报日期、标题
- **FR-002**: 系统 MUST 接受可选的「来源」说明；未提供时 MUST 落为「自研」
- **FR-003**: 系统 MUST 基于**文件内容**判定是否为 PDF，MUST NOT 依据文件名或调用方声明的类型
- **FR-004**: 系统 MUST 拒绝超出单份大小上限的投递，且该拒绝 MUST 与「非 PDF」在语义上可区分
- **FR-005**: 系统 MUST 把标的归一为 `market:code` 形式后落库；市场取值 MUST 限于 `cn` / `hk` / `us`
- **FR-006**: 系统 MUST 以 **(投递方, 文件内容指纹)** 作为归档唯一性判据。同一投递方重复投递相同内容 MUST 返回其既有记录且 MUST NOT 重复写入归档存储；不同投递方投递相同内容 MUST 各留一行元数据，但 MUST 复用同一份归档对象（对象位置由指纹导出，与投递方无关）
- **FR-007**: 系统 MUST 保证「归档存储中存在对象」与「元数据中存在已完成记录」不出现后者有而前者无的组合；两者不一致时 MUST 留下可扫出的未完成记录
- **FR-007a**: 投递命中同一投递方名下该指纹的**未完成**记录时，系统 MUST 就地续做（重传对象，成功后原地翻为已完成），MUST NOT 报冲突、MUST NOT 新增记录。因对象位置由指纹导出，续做时的重传即便对象上次已写成也属幂等重写
- **FR-008**: 系统 MUST 区分自身写入动作的三种结局：确认写入成功 / 确认被拒 / 无法确定（超时、连接中断、网关错误）；MUST NOT 把「无法确定」当作「被拒」。该判定 MUST 基于写入动作自身的响应，MUST NOT 依赖事后回查对象是否存在 —— 后者需要读取权限，与 FR-018 冲突
- **FR-009**: 系统 MUST 对投递方施加身份校验，校验失败一律以同一种方式拒绝，MUST NOT 泄露失败原因的差异
- **FR-010**: 系统 MUST 对每个投递方独立计量累计归档用量，超出配额 MUST 拒绝后续投递。计量口径 = **该投递方名下全部记录的字节之和**（含未完成记录；与其他投递方共享同一对象的记录**照常全额计入**；被拒绝的投递不计入）—— 该口径高估实际占用，方向保守
- **FR-011**: 系统 MUST 记录每份归档的投递方身份与投递时刻
- **FR-012**: 系统 MUST NOT 向投递方提供任何读取、列举、修改或删除已归档研报的能力
- **FR-013**: 投递通道 MUST 在服务端之外**独立地**只放行投递动作；该限制 MUST NOT 依赖「服务端恰好没实现读取」
- **FR-014**: 投递通道 MUST 按投递方独立限频，MUST NOT 与既有行情通道共用配额
- **FR-015**: 投递方使用的凭证 MUST NOT 与系统内部访问归档存储所用的凭证相同，且投递方 MUST NOT 能获知后者
- **FR-016**: 单个投递方凭证 MUST 可独立吊销与轮换，且 MUST NOT 牵连其他投递方或既有行情通道
- **FR-017**: 归档存储 MUST 为私有访问，MUST NOT 允许匿名读取
- **FR-018**: 系统访问归档存储所用的凭证 MUST 只具备写入能力，MUST NOT 具备读取、列举或删除能力
- **FR-019**: 数据结构 MUST 为「同标的多版本」与「非投递方来源的归档（如系统接口拉取、账号内用户导入）」预留位置，使后续接入不需要变更既有结构
- **FR-020**: 投递方的操作说明 MUST 让 agent 能自行判断限频、体积上限与标的写法要求，MUST NOT 需要试错才能发现

### Key Entities

- **研报归档记录（Research Report）**：一份已投递研报的全部可检索事实。承载：归属标的（`market:code` 逻辑键，非外键）、研报日期、标题、来源、版本位、内容指纹、字节数、原始文件名、归档存储中的位置、归档状态（未完成 / 已完成）、投递方归属（可为「隧道投递方」或「账号用户」两类之一）、投递时刻。**唯一性 = (投递方, 内容指纹)**；归档位置由内容指纹单独导出，因此同一字节在多个投递方名下只占一份存储。
- **投递方（Depositor）**：一个可独立鉴权、独立限频、独立吊销、独立计量配额的投递身份。本片只实装「隧道投递方」一类；「账号用户」一类由 PRD §3.8 后续 feature 接入。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 投递方用一条命令即可完成一份研报的投递，无需先申请凭证、再上传、再确认的多步往返
- **SC-002**: 一份 2MB 研报从发起投递到收到确认，在隧道链路上 30 秒内完成
- **SC-003**: 同一份研报被重复投递任意次，归档库中始终只有一份，配额只被计一次
- **SC-004**: 五类不合规投递（非 PDF / 超大 / 缺必填 / 非法市场 / 配额耗尽）各自返回可区分的拒绝理由，agent 无需试错即可纠正
- **SC-005**: 投递方在拿到有效凭证的前提下，除投递外无法完成任何其他动作 —— 包括读取自己刚投的那份
- **SC-006**: 投递方凭证泄漏的最坏后果被限定为「向归档区写入垃圾」，泄漏者无法读走任何已归档研报
- **SC-007**: 吊销任一投递方的凭证，其余投递方与既有行情能力零影响，且无需重新部署服务
- **SC-008**: 归档库中任意一份研报都能回答「哪只标的 / 什么日期 / 谁投的 / 何时投的」
- **SC-009**: 既有 6 条行情能力在本片上线前后行为零变化，其原有通道断言全部仍然成立

## Assumptions

- **单份上限 16MB**：两份真实样例分别为 2,020,387 与 2,148,529 字节，16MB 留出约 8 倍余量。上限是配置值，可后续调整而无需改结构。
- **单投递方配额 8GB**：按样例约 2MB/份估算约 4000 份/投递方，两个投递方合计仍远低于 40G 总容量。此值未经用户明确确认，作为可配置默认值落地。
- **版本号本片不推进**：数据结构留版本位，但「同一标的多版本 Version+1」的业务规则属 PRD §3.8 后续 feature，本片所有记录版本位取固定初值。
- **来源默认「自研」**：当前两份样例均为用户自有工具链产出。字段保留自由文本，将来混入券商研报时无需改结构。
- **不解析 PDF 正文**：本片只归档与元数据检索。正文抽取、检索、阅读器均属 PRD §3.8 后续范围。
- **研报日期取投递方声明值**：系统不从 PDF 内容中反推，也不与投递时刻做一致性校验（自研研报的「分析日期」与投递日可能相差数日）。
- **标的不校验存在性**：归一后的 `market:code` 不与标的注册表比对 —— 比对会拒绝合法的新标的，且会引入本片刻意避免的跨 context 依赖。
- **本人读取路径为归档存储管理面与数据库直连**：本片不建任何读取接口，含用户自己的。

## Out of Scope

- 账号用户（app 侧）投递入口与其上传界面 —— 数据结构已留位，接入时不需要变更既有结构
- PDF 阅读器（双指缩放 / 翻页）、同标的多版本推进规则、正文解析与检索 —— 均属 PRD §3.8 后续 feature
- 投递方侧任何读取面（列表 / 下载 / 预览）
- [014](../014-stock-detail/spec.md) 详情页「分析 Tab」由空态占位改为真实列表
- 既有头像 / 背景图归档位置的迁移
