# Feature Specification: mock 行情写入留痕 —— 假数据不得与真行情同形落进真表

**Feature Branch**: `054-marketdata-mock-write-provenance`
**Created**: 2026-08-13
**Status**: Draft
**Input**: 问题陈述 `docs/private/plans/2026-08/08-13-mock-writer-gap-problem-statement.md`（本机私有，2026-08-13 由 052 T016 标定期实撞得出）

## 背景（一句话）

`MARKETDATA_PROVIDER=mock` 的语义是「没有 vendor 也能**读**」，但仓内存在**定时写手**会把 mock 产出**持久化进真表**、且盖与真行情相同的来源标识 —— 任何人本地跑 dev server 都在无声积累伪造行情，事后不可分辨。

📌 缺口的准确形状：**不是「mock 不该存在」，是「mock 的产物没有留痕」。** 同一个 `option-snapshot-remediation.ts` 已经为 ② 级兜底路径论证过正确做法 ——「降级留痕的形态是**行状态**，不是 log，因为那条独立于 app 进程的探针看不见 log」—— 并落了 `source = premarket_backfill`。mock 路径缺的正是同一样东西。

## Clarifications

### Session 2026-08-13

- Q: 「dev 库同步失败无人感知 ⇒ 脏数据长期留存」并入本 feature 还是另开？ → A: **不并入**。FR-001~009 一落地，这条的危害等级就从「不可分辨」降到「可分辨但没清」，优先级自然下降；并入会让 feature 横跨 server 代码 + host 定时任务 + 通知链三套工具链、三个不正交的验证面。
- Q: 「新增 vendor 写入路径」的防再入守门做不做、怎么做？ → A: **做，且优先靠结构性阻断**（新增路径自动继承约束），而不是维护一份必然会漏的清单。仅当结构覆盖不到时才补机器可判的检查。⇒ FR-010。
- Q: dev（无 vendor 凭据）环境是否必须仍能端到端验证「定时写手写库」路径本身？ → A: **不必须**。该路径的端到端验证归集成测试（起真实数据库容器）—— 那才是正确层级；dev 手工跑 cron 本来也不是既有做法。⇒ FR-011，且它把 FR-004 的「拒绝写入」这一支放开为可选。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 拿库里数据下结论的人，能先判定这批数据是不是真的 (Priority: P1)

任何人（或 agent）在用行情数据做标定、回测、参数选择、报告之前，能用一次**只读查询**判定：这批数据里有没有伪造行、是哪些行。判定不依赖当时哪个进程在跑、不依赖翻应用日志、不依赖本人记得曾经跑过 mock。

**Why this priority**: 这是事故的**唯一**止损点。052 T016 的七个策略参数在伪造行情上全部算得出数、与真标定同形；不看这一眼，错误的参数会带着「实测」标签写进 spec，此后没有任何一处会红。没有这条，其余都是锦上添花。

**Independent Test**: 在一个已知混入伪造行的库上跑那条判定查询，能准确列出伪造行；在一个干净库上跑，返回空。全程不启动应用。

**Acceptance Scenarios**:

1. **Given** 某交易日的数据由 mock 写入，**When** 执行来源判定查询，**Then** 这些行被明确标为非真实来源，且可数出行数
2. **Given** 某交易日的数据由真实 vendor 写入，**When** 执行同一查询，**Then** 返回零条伪造行
3. **Given** 同一交易日先由 mock 写入、后由真实 vendor 补齐，**When** 执行同一查询，**Then** 两类行各自可辨，不互相覆盖成一种颜色
4. **Given** 数据写于本 feature 之前（无痕历史行），**When** 执行同一查询，**Then** 结果是「来源不可考」而**不是**「真实」

---

### User Story 2 - 伪造行情不被当作真行情消费 (Priority: P2)

已有的覆盖率探针、完整性探针、以及面向用户的读路径，不会把伪造行当成「这天有数据了」。

**Why this priority**: 留了痕但没人看，等于没留。事故当天正是「行数对得上、日志全绿」骗过了所有既有判据 —— 覆盖率探针数到 3617 行就认为当天达标，从而**关掉**了本可以补救的重试。

**Independent Test**: 在混入伪造行的库上跑既有覆盖率 / 完整性判定，结果与「这天没有数据」等价或显式标注降级，而不是「达标」。

**Acceptance Scenarios**:

1. **Given** 某交易日只有伪造行，**When** 覆盖率探针评估该日，**Then** 判定为不达标（等价于缺数），而非达标
2. **Given** 某合约当日只有伪造行，**When** 面向用户 / 面向标定的读路径取该合约，**Then** 要么取不到，要么带明确的非真实标识返回 —— 不得以与真行情无差别的形态返回

---

### User Story 3 - 同一类错误不会静默重演 (Priority: P3)

将来新增一条走 vendor 抽象的写入路径时，「它在无 vendor 配置下会不会无声写库」这件事是被检查的，而不是靠作者记得。

**Why this priority**: 污染面比事故暴露的更宽 —— mock 被绑在**约 30 个 vendor port** 上，server 内有 **8 个 `@Cron`**，其中至少 3 条走 vendor 且写库（期权快照补救 08:00/18:00、分钟级同步驱动、交易日历同步 21:00）。今天只修撞到的那一条，剩下两条是同一个坑的两次未爆。

**Independent Test**: 人为新增一条不留痕的 vendor 写入路径，检查报红；把它接上留痕，检查转绿。

**Acceptance Scenarios**:

1. **Given** 一条新增的定时写入路径未接来源留痕，**When** 跑仓内既有的机器检查，**Then** 明确指出该路径
2. **Given** provider 配置缺失或拼错，**When** 应用启动，**Then** 不得静默落到 mock 分支后继续写库

### Edge Cases

- **既有污染怎么办**：本 feature 之前写下的行无法追认来源。它们只能被判为「不可考」；是否需要一次性清理、以及清理范围（只 dev 库？）需明确。
- **幂等键冲突**：期权快照的幂等键是 `(合约, 交易日, 来源)`。若来源标识发生变化，同一合约同一交易日可能同时存在真行与伪造行 —— 读取侧的取数规则必须有确定答案，不能靠 `LIMIT 1` 的偶然顺序。
- **mock 写入被禁的代价**：若结论是「mock 下不许写」，dev 从此**验不了补救路径本身**（`retrySameDay` / `backfillPremarket` 的端到端行为）。这条路径的验证手段必须有替代，否则是拆东墙补西墙。
- **dev 库的唯一清理机制**（📌 **明确排除在本 feature 之外**，见 Clarifications Q1）：dev 库靠每日 `truncate + reload` 同步保持干净。它一失败，脏数据就长期留存 —— 而事故当天同步失败的消息发出去 7 小时无人看见。本 feature 落地后这条仍在，但危害从「不可分辨」降为「可分辨但没清」。
- **prod 被误配成 mock**：当前没有任何东西阻止这件事，且一旦发生，症状与本事故完全相同但影响面是生产。
- **部分写**：一批采集中途失败，已落的那部分行仍须带正确的来源标识，不能因为整批未完成就跳过留痕。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 由非真实 vendor 产出的行情数据，若被持久化，其持久化**结果自身** MUST 携带可分辨的来源标识 —— 判定不依赖应用日志、不依赖写入时的进程配置、不依赖写入者仍在运行
- **FR-002**: 该判定 MUST 能由一个**独立于应用进程**的只读查询完成
- **FR-003**: 系统 MUST NOT 让伪造行情以与真实 vendor 数据**相同**的来源标识落库
- **FR-004**: 任何写入路径 MUST 二择一 —— 要么留下 FR-001 的痕，要么在该配置下**拒绝写入**；MUST NOT 存在「既写了又没留痕」的第三种情况
- **FR-005**: 既有的覆盖率 / 完整性判定 MUST NOT 把只有伪造行的交易日判为「达标」
- **FR-006**: 面向用户呈现或面向标定分析的读路径 MUST 能排除伪造行，或以显式标识返回 —— MUST NOT 与真实行情无差别
- **FR-007**: 写于本 feature 之前的无痕历史行 MUST 被判定为「来源不可考」，MUST NOT 被判定为真实
- **FR-008**: `provider` 配置缺失或取值非法时，系统 MUST NOT 静默落到 mock 分支 —— 必须启动即失败或显式告警
- **FR-009**: `provider = mock` 下的**只读**能力 MUST 保持不变（这是 mock 存在的理由；本 feature 不得以「顺手关掉 mock」的方式解决）
- **FR-010**: 「新增一条走 vendor 抽象的写入路径而未接留痕」这件事 MUST **在结构上走不通** —— 由机制本身阻断（新增路径自动继承约束），而非靠维护一份「哪些写手要留痕」的清单。仅当结构确实覆盖不到时，才补机器可判的检查（Q2 决策：优先结构性）
- **FR-011**: 「定时写手写库」路径本身的端到端验证 MUST 由集成测试承担（起真实数据库容器）；MUST NOT 依赖「在 dev 环境用 mock 数据真跑一遍」这种验证方式（Q3 决策：dev 端到端验证非必须）

### Key Entities

- **行情快照行**：一条「某合约 / 某标的在某交易日的行情」记录。关键属性：所属合约、交易日、**来源标识**、写入时刻。来源标识是本 feature 的核心 —— 它是**行状态**，不是日志。
- **来源标识（`source`）**：现有值域在期权快照上是 `eod`（正常采集）与 `premarket_backfill`（② 级兜底）。它同时是幂等键的第三段，因此改动它的值域会连带影响幂等语义与所有消费端判据。
- **行情提供方配置（`provider`）**：决定整个 vendor 抽象层绑到真实实现还是 mock 实现的单一开关。当前它只被理解为「读」的开关，事故正源于此。
- **定时写手**：应用内按时刻触发、会持久化 vendor 数据的路径。当前已知走 vendor 且写库的有三条（期权快照补救、分钟级同步驱动、交易日历同步）。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 给定任意一批行情数据，判定「其中有没有伪造行、是哪些」耗时 **< 1 分钟**，且只需一次只读查询、无需启动应用、无需查阅日志
- **SC-002**: 复现 052 T016 那次事故的完整条件（本地 dev server 跑 mock + 直连 dev 库 + 触发定时写手），伪造数据**要么根本不落库、要么落库即可辨** —— 两种结果都能让「拿它去标定」这个动作在下结论**之前**被拦下
- **SC-003**: 在混入伪造行的库上，既有覆盖率判定给出的答案与「这天缺数」等价 —— 而不是像事故当天那样判为达标并因此关闭重试
- **SC-004**: 已知的每一条走 vendor 且写库的定时路径（当前 3 条）都被本 feature 覆盖，**没有**「只修了撞到的那一条」的遗留
- **SC-005**: `provider = mock` 下所有既有只读能力零回归

## Assumptions

- **prod 侧清白，本 feature 是预防不是补救**：事故当天已验证 prod 数据完整（补跑同步后恢复为正常行数 / 正常 spot 数），同步脚本逐列照搬无误，故障是一次瞬时断网。本 feature 修的是「这件事本来就不该可能发生」。
- **`modules: [marketdata]`**：缺口在 marketdata 的写入与配置绑定层。若最终方案改动 `source` 值域，会连带 `optionsdesk` 的读取侧透出（`leg-retrieval.port` / DTO 已把 `source` 暴露给前端）—— 那属于方案落地时的连带面，届时补进 `modules`。
- **无 UI 改动**：本 feature 不产出 mockup（`web_compat: na`）。若 FR-006 的结论是「带标识返回给用户」，那才引入呈现层需求，需回头补。
- **不预设解法**：问题陈述列了四个候选方向（专属来源标识 / mock 下写手直接 return / cron 总闸 env / mock 对写路径抛），本 spec **刻意不选** —— 选型属 `/speckit-plan`。Clarifications Q3 答「dev 端到端验证非必须」后**四个候选全部保留**，且 FR-010 的「优先结构性」会让其中「自动继承约束」的那类占优。
- **明确不在范围**（Clarifications Q1）：dev 库每日同步失败的**感知与告警**链路。它是污染留存的放大器，不是根因；且它落在 host 定时任务 + 通知链上，与本 feature 的 server 代码面不正交。另开。
- **已落地的缓解不重做**：`ops/runbook/scheduled-tasks.md` 已补「同步成功但灌进来是 mock 数据」的数据形状自检 SQL；`specs/052` 已记该期数据被污染、标定改用另一期。本 feature 不重复这两件。
