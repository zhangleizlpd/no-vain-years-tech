# Feature Specification: 锚的模型导入通道

**Feature Branch**: `059-anchor-model-import`
**Created**: 2026-08-16
**Status**: Planned
**Input**: 把 045 设计好但零生产调用方的「模型 import」路径做成可用的 API 通道：本地估值流程跑完后，调 API 把估值 V 等字段写进估值锚，赶在每日锚驱动采集之前就位。

## Clarifications

### Session 2026-08-16

- Q: 待审收件箱的条目要不要状态流转？ → A: **三态（待处理 / 已采纳 / 已否决）** —— 成本只是一个状态字段。理由：没有「已否决」的话，被否决的提交会永远停在待处理里，每次查都看到同一批，收件箱很快失去信号价值（「有没有新东西」这个判断变成每次都要重新过一遍全部历史）。
- Q: 通道限频取多少？ → A: **直写入口每分钟 6 次、提交入口每分钟 2 次，两个独立计量** —— 提交口与研报投递同档。理由：一轮估值涉及个位数标的，直写 6 次/分钟够用且能拦住脚本失控循环；提交口面向他人、护的是本方存储，与研报同档即可。两口独立计量，避免一方把另一方挤掉。
- Q: 要不要给「单次或单日新建锚数」设上限？ → A: **不设上限，但响应 MUST 标明本次是新建还是更新** —— 理由：日均个位数，设上限反而让「今天真的要加 10 只」变成需要绕过的障碍；而「新建锚拖长当轮采集」是可观测的（既有的每日同步报告会报逐维度耗时），只要新建这件事在响应里可见，事后归因就成立。**上限属于运维策略而非产品规则，真需要时在通道层加比在业务层加更合适。**
- Q: 要不要加「新估值相对现值偏离过大即拒绝」的护栏？ → A: **不设** —— 理由：本片收到的数由本人的估值流程算出，不是从文本里读出来的，误读风险不存在；而估值大幅变动（暴跌后重估）恰恰是最需要被记录的信号，设阈值会在最重要的时刻挡住写入。**变更痕迹已完整记录旧值 → 新值**，事后可查，无需事前拦。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 估值流程跑完即可把 V 写进锚 (Priority: P1)

本人在本地跑完一轮估值（产出标的、估值 V、口径日期、估值方法、置信度），不再需要打开 App 一个个手填，而是让流程直接把结果送进系统。若该标的还没有锚，系统为它建一条；若已有锚，则按「模型说了算」的语义刷新。

**Why this priority**: 这是本 feature 存在的唯一理由。045 早就把「V 由估值模型产出、首期走批量导入」写进决策记录，但导入路径只有零件没有装配，导致 V 至今只能人工一个个填。没有这条，其余都无从谈起。

**Independent Test**: 单独实现这一条即可交付价值——本地跑一条命令送入一只标的的估值，随后在 App 锚管理里能看到该锚及其派生的 W、四区间、L 层。

**Acceptance Scenarios**:

1. **Given** 标的尚无锚, **When** 本人送入该标的的估值, **Then** 系统建出锚，且该锚的置信度被标记为模型来源
2. **Given** 标的已有锚且估值有变, **When** 本人再次送入, **Then** 锚上的估值、口径日期、估值方法、置信度一并刷新，且不报冲突
3. **Given** 某只标的昨天刚导入过, **When** 今天再导入一次, **Then** 同样成功——首日写入的「模型来源」身份不得反过来阻断后续导入
4. **Given** 导入成功, **When** 查看该锚的变更痕迹, **Then** 该次变更被记为「来自模型」而非「来自人工」
5. **Given** 一只全新标的在当日锚驱动采集开始前完成导入, **When** 当日采集运行, **Then** 该标的已进入采集工作集

---

### User Story 2 - 重复导入不白白冲掉我的人工调整 (Priority: P2)

本人对某只锚的 L 层做过人工调整（那是模型置信度只读时唯一的干预手段）。导入按既有语义会让人工调整回落。本人需要两件事：一是估值没变时**根本不该触发**回落；二是真的发生回落时，被冲掉了什么必须当场看得见。

**Why this priority**: 没有这一条，通道能用但难用——重复调用、同一轮模型跑两遍、估值其实没变，每次都会白白抹掉一次人工判断，且悄无声息。这会让使用者很快弃用这条通道。

**Independent Test**: 对同一只锚用完全相同的入参连调两次，第二次应零变化零痕迹；再对一只带人工调整的锚导入一次有变化的估值，返回结果里应逐条列出被冲掉的项。

**Acceptance Scenarios**:

1. **Given** 某锚的估值/口径日期/估值方法/置信度与本次送入的值完全相同, **When** 再次导入, **Then** 系统不做任何写入、不产生变更痕迹
2. **Given** 某锚存在人工调整且本次送入的估值确有变化, **When** 导入, **Then** 人工调整按既有回落语义失效，且返回结果逐条列出「哪一项被冲掉、原值是什么、回落成什么」
3. **Given** 某锚不存在任何人工调整, **When** 导入, **Then** 返回的差异清单为空，系统不得编造条目
4. **Given** 某锚已逾期待复审, **When** 导入, **Then** 复审日期不被重置、逾期标记不被解除

---

### User Story 3 - 他人的估值只能进收件箱，碰不到锚 (Priority: P3)

同一条访客通道上还有其他调用方。他们可以把自己算出的估值送进来供本人参考，但**不能**直接改锚——锚按标的全局唯一，一次误提交既会覆盖本人的估值判断、冲掉人工调整，还会因为建锚即开采集闸而烧掉一整轮上游配额。

**Why this priority**: 通道一旦开放就必须先把这条边界定死，但它不阻塞 P1/P2 的交付价值——即使暂时只有本人能用，通道也是完整可用的。

**Independent Test**: 用非本人的凭证调直写入口应被拒；调提交入口应成功落入收件箱，且锚表行数与内容完全不变。

**Acceptance Scenarios**:

1. **Given** 调用方不是本人, **When** 调用直写入口, **Then** 被拒绝
2. **Given** 调用方不是本人, **When** 调用提交入口, **Then** 提交被记录到收件箱，锚表零变化
3. **Given** 收件箱里有一条待审提交, **When** 本人认可并采纳, **Then** 它经由与本人导入完全相同的路径落锚（系统不得存在第二条写锚路径）
4. **Given** 任何调用方, **When** 尝试读取或列举锚, **Then** 被拒绝——本通道不提供任何读取面

---

### Edge Cases

- **标的写法不规范**（缺市场前缀如 `AOS`、后缀式如 `PEP.US`、大小写不一）→ 必须拒绝。这不是洁癖：写法不规范的锚会**建立成功**然后永远取不到行情，在界面上表现为一行「行情不可用」，与「该标的还没被采集到」无法区分，等于一个查不出来的僵尸。
- **置信度超出量表范围**（如送入 999）→ 必须以「输入不合法」拒绝，不得表现为服务故障。
- **估值为零或负** → 必须拒绝（既有边界条件，本片不得回归）。
- **市场不在白名单**（本期只收美股与港股）→ 拒绝且不落库。
- **同一标的当日被导入多次** → 第二次起若值未变则零副作用；若值有变则正常更新并回报差异。
- **导入与更新之间锚被并发删除** → 以「不存在」收敛，不得写出指向已删锚的孤儿痕迹。
- **凭证缺失 vs 凭证不符** → 两者对外不可区分（不得成为探测通道是否存在的信号）。
- **一次导入大量全新标的** → 每只新标的都会让当日采集多做一整轮历史回填与全链发现，可能显著拉长该轮耗时。系统**蓄意不拦**（见 Clarifications），但每次响应必须标明是新建还是更新（FR-016），使「某日采集变慢」事后可归因。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 提供一条按**标的**寻址的估值导入入口，接受「标的 / 估值 / 口径日期 / 估值方法 / 置信度」五个字段；标的尚无锚时 MUST 建锚，已有锚时 MUST 更新。调用方 MUST NOT 需要知道任何系统内部标识。
- **FR-002**: 经本入口写入的置信度 MUST 同时把该锚的置信度来源标记为「模型」，与既有约定一致（045 FR-001）。**既有的「模型来源锚的置信度对人工只读」这条门控 MUST 原样保留**，本片 MUST NOT 放宽它——人工对置信度不满意时的干预位在 L 层。
- **FR-003**: 本入口 MUST 校验标的写法为规范形式（市场 + 代码），不合规即拒绝。⚠️ 该校验目前**只存在于客户端**，服务端缺失；本片开的是程序化写入面，MUST 在服务端补齐。
- **FR-004**: 本入口 MUST 校验置信度落在量表范围内，越界 MUST 以「输入不合法」拒绝，MUST NOT 让越界值穿透到存储层变成服务故障。
- **FR-005**: 本入口 MUST 只接受白名单内的市场（本期：美股、港股），其余拒绝且不落库。
- **FR-006**: 当本次导入的值与锚上现值**完全相同**时，系统 MUST 不做任何写入、MUST NOT 产生变更痕迹。
- **FR-007**: 当导入导致既有人工调整回落时，系统 MUST 把被冲掉的每一项**逐条回报给调用方**（哪一项、原值、回落值）。**禁静默回落**（继承 045 FR-035 ①）。人工调整不存在时回报清单 MUST 为空，MUST NOT 编造条目。
  - 该回报的**持久面由既有变更痕迹承担** —— 痕迹本就记录被清空的人工调整位及其原值。系统 MUST NOT 为差异报告另建第二份存储（两份必漂移，且痕迹是 PIT 还原的唯一真相源）。
- **FR-008**: 经本入口产生的变更痕迹 MUST 标记来源为「模型」。该来源标记 MUST NOT 由调用方在请求里指定——它是系统对写入路径的判断，不是调用方的声明（否则「来自模型」这个信号可被伪造，失去意义）。
- **FR-009**: 导入 MUST NOT 重置复审日期、MUST NOT 解除逾期标记（继承 045 FR-035）——复审语义是「人确认估值仍成立」，模型产出新值不构成确认。
- **FR-010**: **只有本人可以直接写锚**。判据 MUST 在通道层完成（通道能分辨调用方身份），MUST NOT 依赖服务端对某个可被覆写的请求头做授权判断。
- **FR-011**: 其他调用方送入的估值 MUST 只落入待审收件箱，锚表 MUST 零变化。收件箱条目 MUST 记录提交方，该记录仅作归属、不作授权依据。
- **FR-012**: 待审条目被采纳时 MUST 经由与本人导入**完全相同**的路径落锚。系统 MUST NOT 存在第二条写锚路径。
- **FR-013**: 本通道 MUST NOT 暴露任何读取、列举、修改或删除锚的能力；非投递类动作 MUST 在通道与服务两层各拒一次（两层各自独立，不依赖对方）。
- **FR-014**: 导入必须能在每日锚驱动采集开始之前完成，使当日新增的锚在**当轮**采集中即被纳入工作集。
- **FR-015**: 凭证缺失与凭证不符 MUST 对外不可区分。
- **FR-016**: 每次导入的响应 MUST 标明本次是**新建**还是**更新**（或因值未变而未写入）。理由：新建锚会让当日采集额外承担一整轮历史回填与全链发现，该事实必须对调用方可见，否则「某日采集突然变慢」事后无从归因。系统 MUST NOT 对新建锚数设置上限——上限属运维策略，真需要时在通道层施加。
- **FR-017**: 两个入口 MUST 各自独立限频（直写入口比提交入口宽松），一方触顶 MUST NOT 影响另一方。

### Key Entities

- **估值锚**（既有）：按标的全局唯一的估值判断载体，携带估值 V、口径日期、估值方法、置信度及其来源、人工调整位、复审状态。本片不改变其结构，只新增一条写入路径。
- **锚变更痕迹**（既有）：一次变更一行，记录改前值、变更字段集与来源（模型 / 人工）。本片新增的写入路径必须留痕。
- **锚提交（收件箱）**（新增）：其他调用方送入但尚未被采纳的估值。携带与导入相同的五个字段 + 提交方 + 可选留言 + 处理状态。处理状态为三态：**待处理 / 已采纳 / 已否决**——「已否决」不可省，否则被否决的条目会永远停在待处理里，收件箱失去「有没有新东西」这个信号。它与估值锚之间**没有强制关联**——一条提交可能永远不被采纳。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 本人跑完一轮估值后，**一次调用**即可把一只标的的估值送进系统，无需打开界面、无需知道任何内部标识。
- **SC-002**: 当日在采集开始前导入的**全部**新标的，在当轮采集中即被纳入工作集（不出现「要等次日」的情况）。
- **SC-003**: 用完全相同的入参连续导入同一只标的，第二次起产生**零**数据变化与**零**变更痕迹。
- **SC-004**: 凡因导入而失效的人工调整，**100%** 在该次调用的返回结果里被逐条列出，无一遗漏、无一编造。
- **SC-005**: 本人以外的调用方，**无法**通过本通道使锚表产生任何变化。
- **SC-006**: 不合规输入（标的写法、置信度越界、非法估值、市场越界）**100%** 被拒绝，且各类拒绝原因彼此可区分——不出现「建立成功但永远没有行情」这类静默失败。
- **SC-007**: 既有锚管理能力（App 内建锚 / 改锚 / 复审 / 删锚 / 雷达）行为**零变化**。

## Assumptions

- **估值字段由上游流程直接产出**：本片假定调用方在跑估值时已经得到「估值 / 口径日期 / 估值方法 / 置信度」四个值，系统**不从任何文档中反推**它们。从已归档研报反推估值属另一条链路，不在本片范围。
- **调用方是隧道内的脚本，不是浏览器**：故本片零前端面。
- **本人身份由通道凭证代表**：通道已具备按凭证分辨调用方的能力，本片复用该机制而非另建身份体系。
- **收件箱的审阅方式是数据库直连**：与既有研报库的读取方式一致（本人走管理面 + 数据库直连）。故本片**不做**审阅界面、不做采纳按钮、不做重跑命令——采纳动作就是本人用自己的凭证把同样的值重放一次。真到了每天十几条要审时再按真实用量决定形状。
- **收件箱规模极小**：日均个位数，故不预先为它建任何检索优化。
- **导入是逐只进行的**：本片不做批量事务语义（一次调用一只标的）。调用方需要送多只时循环调用，逐只独立成败。
- **市场范围本期为美股 + 港股**：港股锚不触发期权链采集（那条闸只对美股生效），其价值在于估值台账与雷达呈现；A 股本期不收。
- **蓄意不设「估值偏离过大即拒绝」的护栏**：本片收到的数由本人估值流程算出，不存在「从文本里读错」的失效模式；而大幅重估恰恰是最需要被记录的信号。事前拦截会在最重要的时刻挡住写入，而事后可查（变更痕迹完整记录旧值 → 新值）。若将来出现「数由非本人流程产出」的调用方，此假设需重审。
