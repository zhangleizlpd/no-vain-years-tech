# Feature Specification: 选约表显示口径跟进 —— 让用户看懂换代后的选约引擎

**Feature Branch**: `051-optionsdesk-leg-display-semantics`
**Created**: 2026-08-11
**Status**: Draft
**里程碑**: sell-put 可视化决策系统 —— optionsdesk 选约引擎重构的 **P2 片**（主 plan：`docs/private/plans/2026-08/08-11-optionsdesk-leg-engine-master.md`，本机私有；范畴权威在其 §2.3）

> 📌 **跨端片**（2026-08-12 定，原为纯 mobile）。主体是 mobile 呈现层，**外加一处服务端契约增量** —— P1 下发的「被流动性门槛排除」计数是**全表标量、不分视角**，而 `FR-009` 要求空态按视角分支，在原契约下不可诚实实现。契约**只加不删**，per Constitution §V 单 PR 原子 merge。
> ⚠️ 本片**不改变任何一条腿是否出现**，只改变「出现的腿怎么被读懂」。集合层的行为变化已在 P1 发生。

## 背景：契约变了，说话的口径没变

P1（`050`）把选约引擎的召回 / 打标 / 精排三层整块换代，并新增六个契约字段。但呈现层一行没动 —— 实测基线（2026-08-11）：这六个字段在 mobile 非测试代码里**零消费**。于是用户现在面对的是一张「数据是新的、说明是旧的」的表。

四处具体的错位：

### 一、顺序不是精排顺序

P1 把精排收回服务端，每个 Tab 各下发一份**有序的合约代码列表**。呈现层却仍在按腿本体那一份的顺序渲染 —— 那是 legacy 载体顺序（档位 → 到期日 → 行权价 → 代码），P1 之后它已不承载任何 Tab 的排序语义。

🚨 **这条不是体验问题，是 P3 的前置条件**。P3 要做服务端截断，而截断必须发生在排序之后；排序若留在客户端，服务端截断会砍掉本该排前面的腿 —— 而返回条数与每个数字都正常，**不会红**。

### 二、标全都没有

推荐标（哪几条更贴合当前意图）与月度链标（哪些到期日流动性最好）在 P1 都已算好下发，呈现层一个都没接。用户拿到的是一张没有任何优先级提示的宽表。

### 三、档位口径与 Tab 脱节

档位判定在 P1 起**跟 Tab 走**（建仓用周化档界、收租与全腿用年化），同一条腿在两个 Tab 判出不同档是定义如此。呈现层读的仍是那个 legacy 的单值档位 —— 于是切 Tab 时颜色不变，而它本应该变。

同类问题还有费率列的口径副标：Tab → 口径的映射目前**硬编码在客户端**，而 P1 已把这份映射下发。两份映射必然漂移，且漂移时两边都渲染得出结果。

### 四、有腿消失了，没人交代

P1 的权利金门槛作用于三个 Tab —— 被它挡下的腿在界面上**确实消失**。这是有意识的取舍，也**部分推翻了 047 的一条承诺**（「任何腿至少在一个 Tab 里可见」）。P1 为此下发了两个门槛计数作为**唯一的补偿**，呈现层没接 ⇒ 这笔代价目前是白付的。

与之绑在一起的是空态：P1 实测低价标的的建仓候选会被流动性门槛砍到个位数甚至零条。空态若只说「没有符合条件的腿」，用户无法区分「这只票本来就没有」和「有二十条但被挡了」——而这两种情况该采取的行动完全不同。

## Clarifications

### Session 2026-08-11

- Q: 两个门槛计数与新增就地说明放在哪个槽位？ → A: **统一落 `renderSectionFooter`（既有的 `LegBlockNotice`）**，新增的「推荐标口径」说明一并移到这里。定案依据是取证得到的三条：① 该槽位**已经是空态与状态的载体**，而本片把「计数」与「空态解释」绑成同一件事（US2）② 它**非 sticky**，sticky 栈零增长 —— 既有就地说明挂在 Tab 行下方、在 sticky 栈内，新增说明留在那里会吃掉归 P3 的余量 ③ 它紧跟最后一行，**可见性与紧迫性同向**：列表越短越显眼，而 730 行时用户有的是腿看、计数本就不急。P3 的第二对计数往同一容器追加即可。
- Q: 推荐标与月度链标落在哪里？ → A: **两个标都进钉住首列** —— 推荐标贴行权价（上行）、月度链标贴到期日（下行）。三条依据：① **月度链标语义上是到期日的属性**，贴着到期日渲染能防止它被读成腿的属性 ② 推荐标是本片最该被一眼看到的信号，而横滑范式下右侧列在任意时刻只露一部分，**钉住列是唯一恒可见的位置** ③ **表宽不变** ⇒ 不触碰 049 的横滑几何（内容宽、指示条长度比），本片不必重做那一轮真机验收。已知代价：钉住列 88px 内已有行权价与口径徽标，排布需要挤。
- Q: 两个计数是只读数字，还是可操作入口？ → A: **权利金计数纯文字；流动性计数可点击 → 切到全腿视角**。依据是一条结构性的不对称：权利金门槛挡下的腿**根本不在响应里**（服务端已移出），客户端没有数据可去；流动性门槛排除的腿**就在全腿视角内**。⇒ 交互的不对称如实映射数据的不对称，比两个长得一样更诚实，也正是 US2-AS2「必须让我知道去哪儿还能看到它们」最强的实现形式。零新屏、零服务端改动。
- Q: 「带推荐标但不在任何意图 Tab」的腿怎么显示？（服务端的推荐标判定**完全不看 Tab 成员**，故这类腿真实存在：050 实测 1878 条期限段合格腿里 351 条被流动性门槛排除，其中带内 Δ 的不在少数） → A: **照实显示，不做视觉区分**。推荐标的语义是「这条腿的 Δ 贴合你当前的意图」，与「它能不能进候选」是**两件正交的事**，两者都为真时照实显示才诚实。真正要修的是**标的措辞** —— 它必须读作「贴合当前意图」而不是「建议买入」；加第三种视觉状态是用视觉复杂度掩盖措辞问题。这也是唯一不需要放宽 FR-011 的选项。
- Q: 「收租腿明显变多」（050 退役了锚轴判据的结果）要不要在界面上给用户解释？ → A: **界面上不解释，归入 PR body / release note**。它是一次**一次性的换代感知**而非常驻状态，用常驻文案解释只在升级当天存在的差异，代价是永久的注意力成本。⇒ 本片**不新增**任何关于「腿数变化」的界面文案。

### Session 2026-08-12

- Q: 推荐标的措辞放不进钉住列（实测两字标 81px / 可用 72px），单字能解决吗？ → A: **不走单字，走「两字标 + 撤掉全腿视角的口径徽标」**（实测 64px）。四种载体全部在真实渲染里量过：两字+徽标 `81px` ❌ · 单字+徽标 `73px`（超 1px，微调可放下）· **两字+撤徽标 `64px` ✅** · 纯符号 `56px` ✅。
  否决单字的理由**不是空间**：① **8px 的单个汉字在功能上是符号不是文字**，用户仍得查图例 ⇒ 消歧机制退化成「符号 + 图例」，绕一圈回到已否决的方案 ② 若取「荐」字，它读作「推荐你买」—— 正是 FR-011a 点名禁止的那层意思，等于用 1px 的代价把 clarify Q4 赖以成立的前提拆掉。
  📌 **撤徽标有独立于空间的理由**（读实现后得出）：`get-legs.usecase.ts` 里该 legacy 标量的判据已是 `tabs.includes('build') ? 'weekly' : 'annualized'` —— 它说的是**「这条腿也在建仓视角里」**（Tab 成员关系），却顶着一个口径形状的标签（`周`/`年`）；而全腿视角的档位在 050 下**恒年化**。标签与含义已经对不上，它本就该随「腿族」概念一起退役，不是为腾地方而做的让步。
- Q: 月度链标画成空心小方块可以吗？ → A: **不行，改文字标「月」**。判据是 mockup 评审时的实证——spec 作者本人看到方块仍需发问「这是什么」，说明它在「认得出来」这一关就没过。两个标统一为同载体（描边短文字标）、以视觉权重区分（推荐标 tag 色描边 / 月度链标中性描边）。实测第 2 行占 60.4px / 可用 72px；「月度」二字 68.4px 在三位数 DTE 下越线，故取单字（FR-014b）。
- Q: 费率列头「费率 / 周化 · 折年」两行太挤？ → A: **去掉「费率」，列头直接就是口径**（建仓「周化」+「折年参照」；收租与全腿「年化」单行）。省字宽只是次要收益，主要收益是**列头即 `basisByTab` 的值** ⇒ FR-017 在视觉上自明。实测原结构在 56px 列宽下撑破，改后 12 列表头无一撑破（FR-017a）。
- Q: `excludedFromIntentTabs` 是全表标量（`get-legs.usecase.ts:650`，判据为 build 或 rent 任一期限段合格即计入），`FR-009`「空态按计数分支」因此不可诚实实现 —— 怎么办？ → A: **改服务端，按视角拆计数**（本片因此转跨端片）。
  否掉的两条：① **客户端措辞退让到全表口径** —— 它不是「弱化版 FR-009」，是**不做 FR-009**：用户仍然分不清「建仓视角空」是本来就没有还是被挡了。而 `US2` 的立论是「P1 用腿会消失换候选集干净，计数是这笔交易的**唯一对价**」，退让等于只付代价不取对价。② **客户端自算** —— 客户端拿不到期限段判据（在服务端的召回纯函数里），且 `FR-003` 明令 MUST NOT 重算成员判据，自算等于造第二份实现。
  📌 服务端代价小：意图视角成员在召回时**已经算出**，拆计数是同一次遍历内的事。真正的代价是本片从纯 mobile 变跨端（单 PR + regen + 两层验证），owner 已确认「视情况而定，不强求纯 mobile」。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 顺序与成员都以服务端为准（Priority: P1）

我切到建仓视角，希望第一屏看到的就是这个视角下最值得看的几条腿。我不需要知道系统按什么排，但我需要相信**我看到的第一条就是系统认为的第一条**。

**Why this priority**：这是本片唯一带**正确性**含义的一块，其余都是可读性。它同时是 P3 服务端截断的前置——排序留在客户端，P3 的截断就会砍错行且不会报错。

**Independent Test**：对同一只票，取服务端下发的某个 Tab 的有序列表，与界面上该 Tab 的实际渲染顺序逐行比对，要求完全一致；并确认代码里不存在任何客户端排序动作。不依赖标、档位、计数三块中的任何一块。

**Acceptance Scenarios**：

1. **Given** 服务端为某 Tab 下发了一份有序的腿列表，**When** 我打开该 Tab，**Then** 界面渲染顺序与该列表**逐行相同**。
2. **Given** 某腿不在某 Tab 的有序列表内，**When** 我打开该 Tab，**Then** 该腿不出现在该 Tab 内（成员判据 **MUST NOT** 在客户端重算）。
3. **Given** 我在三个 Tab 之间来回切换，**When** 每次切回，**Then** 每个 Tab 的顺序都与首次进入时相同（顺序不因切换而变化）。
4. **Given** 某 Tab 的有序列表为空，**When** 我打开该 Tab，**Then** 该 Tab **仍可进入**并显示空态，不被隐藏或置灰。

### User Story 2 - 消失的腿必须有交代，空表必须能被解释（Priority: P1）

我打开建仓视角发现只有三条腿，甚至一条都没有。我需要立刻知道这是「这只票本来就没有合适的腿」还是「有一批腿被系统挡掉了」——因为前者我该换一只票看，后者我该去看看被挡掉的是什么。

**Why this priority**：与 US1 同级。P1 用「腿会消失」换来了候选集的干净，两个计数是这笔交易的**唯一对价**；不呈现等于只付代价不取对价。而空态是这个问题最尖锐的形态。

**Independent Test**：构造两种数据——① 某票有腿被权利金门槛挡下、② 某票的建仓候选被流动性门槛清空——验证两种情况下界面给出的解释**互不相同**且都指向正确的后续动作。不依赖顺序、标、档位。

**Acceptance Scenarios**：

1. **Given** 某票有 N 条腿被权利金门槛挡下（三个 Tab 都看不到），**When** 我查看该票选约表，**Then** 界面呈现该条数，且措辞明确表达**这些腿在三个 Tab 里都不存在**。
2. **Given** 某票有 M 条腿被流动性门槛排除出意图 Tab（仍在全腿 Tab 可见），**When** 我查看该票选约表，**Then** 界面呈现该条数，措辞**MUST NOT 暗示这些腿消失了**，且该条数**可点击直接切到全腿 Tab**。
3. **Given** 权利金门槛的那个计数，**When** 我尝试与它交互，**Then** 它**不提供任何入口** —— 那些腿不在响应里，给入口等于给一个空承诺。两个计数在交互上的差别本身就是它们语义差别的一部分。
4. **Given** 两个计数**都是 0**，**When** 我查看该票选约表，**Then** 计数区不占据视觉重量（隐藏或弱化），**MUST NOT** 让两个 0 与真实的告警长得一样刺眼。
5. **Given** 建仓 Tab 为空**且**流动性门槛排除数 > 0，**When** 我打开建仓 Tab，**Then** 空态文案指向「被门槛挡下」而**不是**「没有符合条件的腿」。
6. **Given** 建仓 Tab 为空**且**两个门槛计数都是 0，**When** 我打开建仓 Tab，**Then** 空态文案指向「这只票在该期限段内确实没有合格腿」。

### User Story 3 - 标：哪几条更贴合我当前的意图（Priority: P2）

在已经进来的这些腿里面，我想一眼看出哪几条更贴合我当前的意图，以及哪些到期日是月度链——那是流动性最好的那批。

**Why this priority**：US1/US2 落地后表已经是可信且可解释的，US3 让它好用。标不改变任何集合。

**Independent Test**：固定同一份数据，切换标的级意图与水位档，验证推荐标的开关行为；对含已知月度到期日的数据，验证月度链标的命中位置。集合与顺序不因打标发生任何变化。

**Acceptance Scenarios**：

1. **Given** 服务端判定某腿带推荐标，**When** 我在**任意** Tab 里看到这条腿，**Then** 它的推荐标取值**处处相同** —— 标随标的级意图，**不随 Tab 变**。
2. **Given** 标的级意图是收租，**When** 我打开**建仓** Tab，**Then** 该 Tab 内的推荐标仍按**当前收租档带**判，且 **MUST** 配就地说明。说明的口径是「这些推荐按你当前的收租意图打」，**不是**「这个 Tab 没有推荐」。
3. **Given** 标的级意图是待定 / 不开新仓，**When** 我查看该票选约表，**Then** 全表**零推荐标**，腿数据照常全量呈现。
4. **Given** 某腿 greeks 缺失，**When** 我查看该腿，**Then** 它**恒不带**推荐标，但**照常出现在它所属的每个 Tab 内**（缺一个打标量不等于这条腿不合格）。
5. **Given** 某到期日是月度到期日，**When** 我查看该到期日下的腿，**Then** 它们**全部**带月度链标 —— 判据取自服务端下发的标，**MUST NOT** 由客户端按「是不是周五」自行推断。

---

### User Story 4 - 档位与费率口径跟着 Tab 走（Priority: P2）

我在建仓视角看到一条腿被判为「好」，切到收租视角同一条腿变成「可接受」。我需要这是**正常的**——因为两个视角问的是两笔不同的账，而不是系统算错了。

**Why this priority**：与 US3 同级。它决定用户对颜色的信任：颜色若在切 Tab 时纹丝不动，用户会以为档位与视角无关，从而按错误的口径读数。

**Independent Test**：取一条同时属于两个意图 Tab 且两处档位不同的腿，切换 Tab，验证其档位显示随之改变；并验证费率列的口径副标同样随 Tab 改变、且其取值来自服务端而非客户端硬编码。

**Acceptance Scenarios**：

1. **Given** 某腿同时属于建仓与收租 Tab 且两处档位不同，**When** 我在两个 Tab 分别查看这条腿，**Then** 各显示**各自口径**的档位，**MUST NOT** 用其中一个覆盖另一个。
2. **Given** 某腿在某 Tab 内但该 Tab 下不判档，**When** 我在该 Tab 查看这条腿，**Then** 该格显缺省态，**MUST NOT** 回落到别的 Tab 的档位顶上。
3. **Given** 我切换 Tab，**When** 费率列渲染，**Then** 其口径副标取自**服务端下发的映射**，**MUST NOT** 由客户端硬编码一份。
4. **Given** 服务端下发的映射里出现客户端未知的口径取值，**When** 渲染发生，**Then** 显缺省态而非崩溃或猜测。

---

### User Story 5 - 旧口径的说明必须跟着换代一起改（Priority: P3）

我读到界面上的一句说明，它讲的是系统的判定逻辑。我需要这句话**现在**是对的，而不是上一版是对的。

**Why this priority**：范围小且已扫清（两处），但它是唯一一类**测试永远抓不到**的缺陷——文案断言是自指的，改成什么都绿。放在 P3 是因为它不阻塞其余四块，但它必须在本片内完成。

**Independent Test**：把界面上所有讲判定逻辑的说明文案逐条对照当前的服务端判据，确认每一句仍成立。

**Acceptance Scenarios**：

1. **Given** 水位未选，**When** 我打开收租 Tab，**Then** 就地说明如实描述当前行为：**成员集合与已选水位时完全相同，差别只在于没有推荐标** —— 它 **MUST NOT** 让我以为选了水位之后展示的腿会变少。
2. **Given** 我打开全腿 Tab，**When** 我看每一行的钉住列，**Then** 那个口径徽标**已不存在**——它标的「腿族」在 P1 已被拆掉，而它现在的取值其实是 Tab 成员关系、却顶着口径形状的标签（FR-019a）。

---

### Edge Cases

- **某腿带推荐标、却不属于任何意图 Tab**（被门槛排除但 Δ 落在当前意图带内）—— 照实显示推荐标，**不做视觉区分**；靠标的措辞消歧（FR-011a）。这不是罕见组合：051 开工时的实测里，期限段合格腿中约五分之一被流动性门槛排除。
- **某腿在有序列表里但不在腿本体集合里**（或反之）——两份数据的一致性由服务端保证，但客户端撞上时不能崩：以腿本体为准渲染，无法定位的代码跳过。
- **两个门槛计数一个为 0 一个不为 0** —— 只呈现非零那个的说明，不为了对称硬凑一句。
- **标的级意图在我看表的过程中变化**（另一处改了水位）—— 标随之全变而集合与顺序**一行不动**，这是正确行为。
- **全部三个 Tab 同时为空** —— 面板照常在，三个 Tab 都可进入，各自显各自的空态。
- **月度到期日恰好是非交易日被前移** —— 客户端只消费服务端下发的标，该情形对客户端**不构成分支**（这正是禁止客户端按「是不是周五」推断的理由）。
- **某票腿数极多（730 行量级）** —— 新增的标与档位是逐行渲染成本，MUST NOT 让该票的滚动出现可感知的卡顿。

## Requirements _(mandatory)_

### Functional Requirements

#### 顺序与成员（US1）

- **FR-001**: System MUST 按**服务端下发的每 Tab 有序列表**渲染各 Tab 的行顺序。
- **FR-002**: System MUST NOT 在客户端对腿做任何排序。机械判据：呈现层代码中针对腿集合的排序调用**零命中**。
- **FR-003**: System MUST NOT 在客户端重算 Tab 成员判据；成员关系一律取自服务端下发的数据。
- **FR-004**: 腿本体那一份集合的既有顺序 MUST NOT 被用作任何 Tab 的呈现顺序；它只作为按代码定位腿的数据源。
- **FR-005**: 某 Tab 为空时该 Tab MUST 仍可进入并显空态，MUST NOT 隐藏或置灰（沿用既有约定）。

#### 门槛计数与空态（US2）

- **FR-006**: System MUST 呈现**两个门槛计数**，且两者 MUST 各自可辨识。
- **FR-006a**: System MUST 额外下发**按意图视角拆分**的「被流动性门槛排除」计数（建仓 / 收租各一个数）。
  🚨 **它与既有标量 MUST 并存而非替换**（契约只加不删），且 **MUST NOT 断言「标量 == 建仓数 + 收租数」** —— 两个期限段在 `[30,49]` 刻意重叠，一条落在重叠区且被门槛挡下的腿在标量里记一次、在两个分视角数里各记一次。⇒ 恒有 `标量 ≤ 建仓数 + 收租数`。
  📌 **权利金门槛的计数不拆视角**：该门槛对三个视角一律作用、被它挡下的腿已整条移出响应，本就无视角之分。两个计数在这一点上的不对称，与它们语义上的不对称是同一件事。
  📌 **不拆出「全腿」那一档**：全腿视角不受流动性门槛约束（`FR-006` 既有约定），它恒不会因该门槛变空。
- **FR-007**: 两个计数的措辞 MUST 分别表达其**不对称语义**：一个是「这些腿在三个 Tab 里都不存在」，另一个是「这些腿只是不进意图 Tab，在全腿 Tab 仍可见」。
  🚫 MUST NOT 使用同一个暗示「滤掉 / 过滤」的词把两者混为一谈。
- **FR-007a**: 流动性门槛的计数 MUST 可点击并切到全腿 Tab；权利金门槛的计数 MUST NOT 提供任何入口（那些腿不在响应里，入口只能是空承诺）。两个计数在**交互上的差别**是其语义差别的组成部分，MUST NOT 为了对称把两者做成一样。
- **FR-008**: 两个计数均为 0 时，计数区 MUST NOT 占据与非零时相同的视觉重量。
- **FR-009**: 意图 Tab 空态的文案 MUST 依据**该视角自己的**排除计数（`FR-006a`）分支：该视角排除数 > 0 → 指向门槛并给入口；该视角排除数为 0 → 指向「该期限段内确实没有合格腿」。
  🚫 MUST NOT 用全表标量做这个判断 —— 建仓视角空而标量为 20 时，那 20 条可能全是被排除出收租的，据此说「有 20 条被挡了」对建仓视角是错的，**且不会红**（数字真实、文案通顺，只是指向了别的视角的腿）。
- **FR-010**: 计数呈现 MUST 为后续片的**第二对计数**预留位置，使其加入时不需要重新设计该区域。
- **FR-010a**: 两个门槛计数、空态解释、以及本片新增的就地说明 MUST 落在**腿列表之后的非常驻区**（紧跟最后一行、随内容滚动），三者同区。
  🚫 MUST NOT 落在切 Tab / 表头所在的**常驻区** —— 那里的高度余量归后续片（见 Assumptions 与 SC-009）。既有的就地说明目前正在常驻区内，本片 MUST 将其一并移出。

#### 标（US3）

- **FR-011**: System MUST 呈现推荐标，取值一律取自服务端；同一条腿在不同 Tab 的推荐标取值 MUST 相同。
- **FR-011a**: 推荐标的**措辞** MUST 表达「这条腿的 Δ 贴合当前意图」，MUST NOT 表达「建议买入 / 该选它」。
  🚨 判定不看 Tab 成员 ⇒ 存在「带推荐标却进不了任何意图 Tab」的腿（被门槛排除但 Δ 在带内），这类腿**照实显示、不做视觉区分**。措辞是这个组合唯一的消歧手段：「贴合意图」与「够得着」本就是两件正交的事，措辞写成后者才会自相矛盾。
- **FR-012**: 标的级意图为收租而用户处于建仓 Tab 时，System MUST 配**就地说明**，口径为「这些推荐按当前的收租意图打」。
- **FR-013**: greeks 缺失的腿 MUST 不带推荐标，且 MUST 照常出现在其所属的每个 Tab 内。
- **FR-014**: System MUST 呈现月度链标，取值一律取自服务端。
  🚫 MUST NOT 由客户端按「到期日是不是周五」推断。
- **FR-014a**: 两个标 MUST 落在**钉住列**（横滑之外那一列）—— 推荐标随行权价、月度链标随到期日。
  🚨 月度链标 MUST 与**到期日**相邻而非与腿的其他属性相邻：它是到期日的属性，位置错了会被读成腿的属性。
  🚫 本片 MUST NOT 改变表格总宽与列集 —— 那会改变横滑的内容宽与位置指示条的长度比，触发一轮本可避免的几何回归。
- **FR-014b**: 两个标 MUST 采用**同一种载体**（自述其义的短文字标），差别只体现在**视觉权重**上，MUST NOT 让其中一个退化成纯几何符号。
  📌 判据来自 mockup 阶段的实证：月度链标初版画成空心小方块，**本 spec 的作者本人**在评审时仍需发问「这是什么」。⇒ 「更弱」该体现在视觉权重上，不该体现在**认不认得出**上；纯几何符号连「这是什么」都要查图例，与 FR-011a 否决符号方案的理由是同一条。

#### 档位与费率口径（US4）

- **FR-015**: System MUST 按**当前 Tab 的口径**显示每腿档位；同一条腿在不同 Tab 显示不同档位是预期行为。
- **FR-016**: 某 Tab 下不判档的腿 MUST 显缺省态，MUST NOT 回落到其他 Tab 的档位。
- **FR-017**: 费率列的口径副标 MUST 取自**服务端下发的 Tab→口径映射**，MUST NOT 在客户端硬编码该映射。
- **FR-017a**: 费率列的列头 MUST **直接呈现该视角的口径本身**（如「周化」/「年化」），MUST NOT 在其上再套一层「费率」之类的通用标题。
  📌 两个好处：① 列头即 `basisByTab` 下发的那个值 ⇒ FR-017「口径取自服务端」在视觉上自明，而不是藏在一个通用标题下面 ② 省掉的字宽让列头不再撑破列（mockup 阶段实测：原两行结构在 56px 列宽下撑破，改后 12 列表头逐列量过无一撑破）。
- **FR-018**: 服务端下发的口径取值超出客户端已知值域时，System MUST 降级为缺省态，MUST NOT 崩溃或猜测。

#### 文案复核（US5）

- **FR-019**: 界面上所有描述**判定逻辑**的说明文案 MUST 与当前服务端判据一致。需处置的四处：① 未选水位时收租视角的就地说明（订正措辞）；② 全腿视角每行的口径徽标（**整条撤除**，见 FR-019a）；③ 页脚财报图例（订正措辞，见 FR-019b）；④ 三个视角的 Tab 标签（订正措辞，见 FR-019c）。
  📌 ③④ 是 **2026-08-12 impl 期逐条复核时新发现**的（spec 阶段只扫清了 ①②，Assumptions 已预留该分支）。复核基数：`optionsdesk-copy.ts` 全文 604 行中做出判定逻辑 / 口径主张的条目 **62 条**，其余为纯标签（屏名 / 列名 / 按钮字 / 占位符）不在复核面内。
- **FR-019a**: 全腿 Tab 每行的**口径徽标 MUST 撤除**，不是改措辞。
  📌 判据：该 legacy 标量在服务端已退化为「这条腿是否也在建仓召回集内」（Tab 成员关系），却顶着一个**口径形状**的标签；而全腿 Tab 的档位判定口径恒为年化。标签与含义不符，随「腿族」概念一并退役。
  ⇒ 撤除后钉住列腾出的宽度正好容纳推荐标的两字措辞（FR-011a），二者是同一处改动的两面。
  🚫 MUST NOT 保留徽标而把推荐标压成单字或符号 —— 那会让 FR-011a 的消歧退化到图例上。
- **FR-019b**: 页脚的财报图例 MUST 把「整表无财报标」这条规则挂在**标的级意图**上，MUST NOT 说成某一类腿的属性。
  📌 判据：服务端 `earningsLegFamilyFor(intent, dte)` 只在 `intent === 'build_position'` 时返建仓域 ⇒ 无标 ⟺ **标的级意图为建仓**，三个视角一起无。原文案「建仓腿按设计无财报标」既沿用已退役的腿族措辞，又在「收租意图 × 建仓视角」下**当场为假**——那些行确实带财报标，而该图例渲在四态三视角恒在的页脚里、无条件分支。
- **FR-019c**: 三个视角的 Tab 标签 MUST 读作**视角**，且 MUST NOT 在标签里携带费率口径。
  📌 两个判据各自独立：① 「建仓腿 / 收租腿」沿用 P1 已退役的腿族措辞（Key Entities 已定 Tab = 视角），与 FR-019a 撤徽标同因；② 标签里的「·周化 / ·年化」是客户端的**第二份** `basisByTab` 映射，正是 FR-017 所禁——口径的唯一落字处是费率列头本身（FR-017a）。
  ⇒ 措辞与本片其余文案统一为「全腿视角 / 建仓视角 / 收租视角」（`emptyIntentTitle` / `gateLiquidityNoteAll` 已在用同一组词）。
- **FR-020**: 未选水位时收租视角的就地说明 MUST 如实描述：**成员集合与已选时相同，差别只在于零推荐标**。

#### 边界与不改动

- **FR-021**: 本片 MUST NOT 改变任何一条腿是否出现、出现在哪个 Tab —— 集合层归 P1，本片只改呈现。
- **FR-022**: 链未就绪 / 读取失败两个既有显式状态的行为 MUST NOT 改变。
- **FR-023**: 服务端与契约的改动 MUST **仅限** `FR-006a` 那一处计数增量。除此之外零改动 —— 召回 / 打标 / 精排判据、锚派生、意图矩阵、schema 一律不动。
  📌 `FR-006a` 动的是**计数的粒度**，不是任何判据：拆出的两个数复用召回层已算出的视角成员，判据一个字不改。

### Key Entities

- **腿（Leg）**：选约表的一行。本片新消费其三个属性——每 Tab 各自的档位、是否推荐、是否月度链。
- **Tab（视角）**：全腿 / 建仓 / 收租三者之一。P1 起它是**看同一批数据的三种眼光**，不再是腿的分类。每个 Tab 各有自己的有序腿列表与费率口径。
- **门槛计数（Gate Counts）**：一对语义**不对称**的数——被权利金门槛移出响应的条数（真消失）、被流动性门槛排除出意图 Tab 的条数（未消失）。
- **就地说明（Notice）**：Tab 面板内解释当前口径的短文案。本片新增一条（推荐标口径），订正一条（未选水位）。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 三个 Tab 的渲染顺序与服务端下发的对应列表**逐行相同**，零误差（全量核对，含 730 行量级的票）。
- **SC-002**: 呈现层代码中针对腿集合的**客户端排序调用零命中**（机械扫描）。
- **SC-003**: 两个门槛计数的显示值与服务端下发值**逐次相等**，零误差。
- **SC-004**: 在「有腿被门槛挡下」与「计数为 0」两种空表情形下，用户看到的空态文案**互不相同**，且各自指向正确的后续动作（两种情形各有一条 UI 断言）。
- **SC-005**: 同一条腿在其所属的**每个** Tab 内推荐标取值一致（全量核对，零例外）。
- **SC-006**: 存在至少 1 条腿在两个意图 Tab 内显示**不同档位**，且两处各自与服务端下发值相等 —— 证明档位确实跟 Tab 走。
- **SC-007**: greeks 缺失的腿在其所属的每个 Tab 内**均可见**且**均不带**推荐标（全量核对）。
- **SC-008**: 界面上描述判定逻辑的说明文案**逐条复核过**，与当前服务端判据零冲突（人工核对留痕；已知两处已订正）。
- **SC-009**: 常驻区（切 Tab / 表头等）的高度**严格不高于**本片开工前的实测基线 —— 本片新增的计数与说明全部落在腿列表之后的非常驻区，且既有的就地说明也已移出常驻区 ⇒ 该高度**只可能持平或下降**，MUST NOT 上升。

- **SC-012**: 按视角拆分的排除计数与该视角**实际被挡下的条数逐次相等**（零误差），且在含 `[30,49]` 重叠区腿的数据上满足 `全表标量 ≤ 建仓数 + 收租数`（🚨 判据取**不等式**，取等号会在重叠区红错方向）。

## Assumptions

- **本片消费 P1 已下发的六个字段，另新增一处计数增量**（`FR-006a`）—— 除该增量外服务端零改动。契约只加不删 ⇒ 旧客户端不受影响。
- **顺序的唯一真相源是服务端下发的每 Tab 有序列表**；腿本体集合的既有顺序仅作为按代码定位的数据源，其排序含义在 P1 之后已作废（保留是为了不惊动尚未升级的客户端）。
- **计数区不进常驻区** —— 049 真机实测常驻栈已占屏 30.6%（阈值 35%），而后续片要把筛选行加回来（+40dp ⇒ 约 35.4%，已越线）。这 4.4% 的余量归后续片，本片不能吃。⇒ 落位已在 Clarifications 定案：计数 / 空态解释 / 就地说明三者同落腿列表之后的非常驻区。
- **既有就地说明目前在常驻区内**，本片将其一并移出 ⇒ 常驻区高度只会持平或下降（SC-009 因此取「严格不高于」而非「不劣于」）。
- **第二对计数（符合条件数 / 显示条数）归后续片**，但其位置在本片一次设计到位 —— 与本片这对同区追加，同一块界面做两遍是浪费。
- **文案复核范围 spec 阶段扫清为两处**（2026-08-11 全文件扫过），其中一处已在 P1 的代码注释里登记并显式推迟到本片。
