# Feature Specification: 交易日历数据源韧性改造

**Feature Branch**: `044-marketdata-calendar-resilience`
**Created**: 2026-07-16
**Status**: Implemented（clarify 3 问 + analyze 6 项均已收敛；PoC 已 prod 实证；17 task 全部实装）
**Input**: 2026-07-15 生产事故根因定位产物（东财 `kline/get` 端点被定向下线 → 日历停更 → 22 维同步静默停摆 2 天）

## 背景：本次事故（动手前先内化）

交易日历（`marketdata.trading_day`）是**全部 22 个 marketdata 同步维度的总闸口**：tick 每分钟 claim 维度后先过「交易日 gate」——日历里没有当日 → 全维度剔除、`fired=[]`、零 `sync_run`。

**故障链**（每环均已实证）：

1. 2026-07-15 起东方财富**定向下线** `/api/qt/stock/kline/get` 路由。prod + 本地双侧路径分化实测：同主机 `trends2/get` → **200**、`kline/get` → **000/RST**、`/` → **404**（服务器活着）。→ **排除** IP 封禁（IP 级不可能只封一条 path）、**排除**限流（我方 3 次/天，比社区反推触发线低 2–3 个数量级；零调用历史的机器首包即被拒）。定级 = **vendor breaking change**。
2. 日历填充服务 per-market `catch` → **仅 WARN 静默降级**，`inserted:0`，不抛不报警。
3. `trading_day` 停在 07-14 → 交易日 gate 关。
4. tick 仍活着且正常 claim（`updated_at` = 07-15 14:00 实证）、推进 `nextFireAt`，但 gate 剔除全部维度 → **零 `sync_run`**。且设计上「非交易日不补」+ misfire≠backfill → 漏窗永久丢失，缺口归 backfill CLI。
5. 看守 `ops/marketdata-sync-report/report.sh` 的零行判定**去问那张已经坏掉的表**「昨日是否交易日」→ 日历缺 07-15 → 答「否」→ 判「无同步属预期」→ `exit 0` ✅ 绿 → **无人知晓，静默 2 天**。

**两条附加事实**：

- **静默毒饵已实证**：候选替代 host `push2delay.eastmoney.com` 返回 `HTTP 200 + rc:0 + 正确中文名 + klines:[]`（空数组）。若无脑接入，会把**每一天**判成非交易日，且**不触发任何告警**——比连不上更危险（连不上会炸，这个不会）。
- **授权面**：`push2his.eastmoney.com/robots.txt` = `User-agent: * / Disallow: /`（对比 `www` 是 `Allow: /`）；东财法律声明禁止未经交易所书面同意复制/传播行情。**该依赖本就无授权**——真正的根因不是「用太多」，而是把「交易日历」这个确定性、可离线的事实，绑在一个无文档、无 SLA、无授权、明确禁爬的第三方内部接口上。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 主源失效时同步不中断（Priority: P1）

作为平台运维，当交易日历的主数据源失效（端点消失 / 网络不可达 / 返回损坏数据）时，系统应自动改用下一个数据源完成日历填充，使 22 个同步维度照常运行——而不是整站同步静默停摆。

**Why this priority**: 这是本次事故的直接止血面。日历是所有同步的总闸口，单点失效 = 全站数据停更。没有这条，任何其他改进都无意义。

**Independent Test**: 让主源失败（抛异常）→ 验证日历仍被次源填充完整 → 交易日 gate 正常开启 → 维度照常触发。可完全独立于告警能力验证。

**Acceptance Scenarios**:

1. **Given** 主源不可用（抛异常），**When** 日历填充运行，**Then** 系统自动改用次源，日历完成填充，结果与主源成功时同构，下游 gate 正常开启。
2. **Given** 主源可用且返回合理数据，**When** 日历填充运行，**Then** 采用主源结果，**且不调用**链上后续节点（不产生无谓 vendor 调用）。
3. **Given** 某一市场的源失败、其余市场正常，**When** 日历填充运行，**Then** 失败市场独立降级，其余市场不受影响（一市场坏不拖垮全局）。
4. **Given** 日历已含某区间数据，**When** 重复填充同区间，**Then** 不产生重复行、行数不翻倍。

---

### User Story 2 - 「成功但数据不合理」也触发降级（Priority: P2）

作为平台运维，当某个数据源返回「传输层成功、业务层却给出不合理数据」（如 30 天窗口内交易日数为零或异常少）时，系统必须判定该源失败并降级，而不是把这份坏数据当成「这段时间不开市」写进日历。

**Why this priority**: 这是本次事故最深刻的教训，也是**换任何源都必须先具备的前置安全网**。已实证的 `push2delay` 毒饵会返回 200 + 业务成功码 + 空数组；现有降级范式**只在抛异常时**降级，接不住这种「成功但空」的失败。没有这条，接入新源等于把一次响亮的故障换成一次无声的错误。

**Independent Test**: 让源返回 200 + 空数组 → 验证系统**不**接受该结果、继续降级；若全链如此 → 显式失败且告警可达，而非静默写空。可独立于具体源验证。

**Acceptance Scenarios**:

1. **Given** 某源返回 HTTP 成功 + 业务成功码 + **零交易日**，**When** 日历填充运行，**Then** 该源被判失败并降级到下一节点（**不**将空结果写入日历）。
2. **Given** 某源返回的窗口内交易日数**低于合理下界**，**When** 日历填充运行，**Then** 该源被判失败并降级。
3. **Given** 链上所有节点均失败（含「成功但不合理」），**When** 日历填充运行，**Then** 系统**显式失败**且该失败可观测/可告警；**禁止**静默降级为「本区间无交易日」。

---

### User Story 3 - 日历不健康第一时间告警，且看守不被坏数据欺骗（Priority: P3）

作为平台运维，当交易日历填充失败或数据陈旧时，我应在阈值内**主动收到通知**，而不是两天后自己发现；并且负责发现停摆的看守**不能仅凭那张可能已损坏的日历表**得出「无需同步属预期」的结论。

**Why this priority**: 决定「故障暴露时长」。本次 US1/US2 若已就位，事故不会发生；但残余失败（全链皆失效）仍需被听见。本次事故潜伏 2 天的真凶正是看守的循环信任——它问的正是坏掉的那张表。

**Independent Test**: 制造日历不健康 → 验证告警在阈值内送达既有通知通路；杀掉 app 进程 → 验证告警仍能发出；构造「零 sync_run + 日历不健康」→ 验证看守告警而非放行。

**Acceptance Scenarios**:

1. **Given** 日历填充失败 / 日历不健康，**When** 达到告警阈值，**Then** 运维经既有运维通知通路收到告警。
2. **Given** app 进程不可用，**When** 日历不健康，**Then** 告警仍能送达（告警链路不与被监控进程同生共死）。
3. **Given** 窗口内零同步记录 **且** 日历不健康，**When** 看守运行，**Then** **告警**（禁止据陈旧日历判「昨日非交易日、无同步属预期」）。
4. **Given** 窗口内零同步记录 **且** 日历健康 **且** 昨日确为非交易日（周末 / 长假），**When** 看守运行，**Then** 不告警（既有防误报能力不回归）。
5. **Given** 窗口内零同步记录 **且** 日历健康 **且** 昨日为交易日，**When** 看守运行，**Then** 告警夜间同步疑似停摆（既有能力不回归）。
6. **Given** 长假期间日历填充成功但无新增交易日，**When** 看守/探针运行，**Then** 不告警（不因长假误报）。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 交易日历填充必须支持**按序多节点降级**：任一节点失败时自动尝试下一节点，直至成功或全链耗尽。
- **FR-002**: 节点「失败」的判据必须**同时覆盖**两类：① 抛出异常（连接 / HTTP / 解析）；② **返回成功但数据不合理**（零交易日 / 窗口内交易日数低于合理下界）。
- **FR-003**: 全链失败时系统必须**显式失败且可观测**；**禁止**静默产出「该区间无交易日」的成功语义。
- **FR-004**: 降级必须 **per-market 独立**：单一市场的全链失败不得影响其余市场的填充结果。
- **FR-005**: 主源成功时**不得**调用链上后续节点。
- **FR-006**: 填充对同一 (market, date) 必须幂等，重复运行不产生重复行。
- **FR-007**: 系统必须移除对「已下线且明确禁止自动访问」的第三方内部接口的依赖。
- **FR-008**: 日历填充的成败必须**可观测**——不得仅以静默 WARN 后继续的方式吞掉失败。
- **FR-009**: 日历不健康（填充失败 / 陈旧）必须在阈值内**主动告警**到既有运维通知通路。
- **FR-010**: 告警探针必须**独立于 app 进程**运行——app 不可用时仍能告警。
- **FR-011**: 告警判定必须能区分「真不健康」与「长假/周末期间正常无新增交易日」，不得因后者误报。
- **FR-012**: 看守（夜间同步报告）在窗口内零同步记录时，**不得仅依据可能已陈旧的日历表**得出「无同步属预期」的放行结论；日历不健康时必须告警。
- **FR-013**: 看守既有的两项能力不得回归：「日历健康 + 昨日为交易日 + 零同步 → 告警」与「日历健康 + 昨日非交易日 + 零同步 → 放行」。
- **FR-014**: **降级运行必须可观测**：填充由非主源（降级层）服务时，须记录该事实并在阈值内告警。**降级 ≠ 健康** —— 系统虽仍工作，但已失去冗余且降级层能力有限，属需人工介入的状态，**不得静默长期运行**。主源恢复后信号须自动解除。
- **FR-015**: 源的成功判定**不得仅依赖状态码/成功码**。若源以「成功码 + 错误消息 + 空数据」形态返回错误，必须能识别并判该节点失败。
- **FR-016**: 向源请求的区间宽度超出其单次可服务上限时，必须**分片请求后合并**，且合并结果须与「单次可服务范围内的等价请求」逐日一致（零丢失、零重复）；**禁止**以「截断上限」方式规避——那会把响亮的错误换成无声的残缺。

### Key Entities

- **交易日历（trading_day）**：`(market, date)` 二元组集合，表示某市场某日开市。是全部同步维度的准入闸口。本 feature 不改其形态，只改**谁来填**与**填不上时怎么办**。
- **日历数据源节点**：可按序排列的多个来源，各自能就「某市场某区间的交易日列表」作答；可失败、可被降级跳过。
- **日历健康信号**：用于判定「填充链路是否还活着」的可观测事实；须能被独立于 app 的探针读取。

## Success Criteria _(mandatory)_

- **SC-001**: 主源不可用时，交易日历仍能在当日同步窗口开始前完成更新，22 个同步维度**零中断**。
- **SC-002**: 任一数据源返回不合理数据（零/异常少交易日）时，系统 **100%** 不将其写入日历。
- **SC-003**: 日历不健康后，运维在 **24 小时内**收到告警（对照本次事故：2 天无人知晓）。
- **SC-004**: 本次事故场景（主源端点消失）可被自动化测试复现，且系统在无人干预下自动改用其他源完成填充。
- **SC-005**: 长假（连续 ≥7 个自然日无新增交易日）期间**零误报告警**。
- **SC-006**: 全链失败时，故障在 **24 小时内**被听见（不再存在「静默成功」路径）。
- **SC-007**: **降级运行在 24 小时内被感知** —— 主源失效但降级层接住时，运维仍能知悉，不因「系统还在工作」而静默（防「降级静默数月、直到降级层能力耗尽才全盘爆炸」）。
- **SC-008**: 超出源单次上限的宽区间请求，分片合并结果与等价单次请求**逐日 100% 一致**（零丢失、零重复）。

## Assumptions

- 「合理下界」以**保守**取值：自然月窗口内交易日数显著低于常识下界即视为不合理（真实值 ~20–22 个/30 天；下界取值在 plan 阶段锁定，需容忍长假月份）。
- 本 feature 仅改日历的**写入源**与**运维告警**；`trading_day` 表结构、消费侧读表判定、tick/gate 逻辑、backfill CLI **均不改**。
- 既有运维通知通路（飞书）已在 prod 就位并被多个定时任务复用，本 feature **复用**之，不新建通知基建。
- 「非交易日不补 / misfire≠backfill」是既有设计决策，本 feature **不推翻**——历史缺口仍归 backfill CLI。
- **健康心跳**（clarify Q2）落在可被 app 外部进程读取之处，使探针无需经 app 即可判定（沿用既有「探针直读数据层」的运维范式）。
- **静态日历**（clarify Q1 的 L2）以「离线生成 + 入仓」形态存在，其覆盖区间有限且**已知**——超出覆盖即判该节点失败（见 state_branches），不静默返空。

## Out of Scope

- **本次事故的历史数据回补**（07-15 / 07-16 缺口）——本 feature 上线后的独立 ops 动作，走 backfill CLI。
- 040–043 那 11 个新维度的**首夜全量回填**——那是 master INV-3 规划内的多夜 ops，与本事故缺口无关。
- `trading_day` 表结构变更 / 消费侧读表逻辑 / tick claim 与 gate 机制 / backfill CLI 行为。

### Session 2026-07-16

- **Q: fallback 链的深度与构成？** → **A: 两层 —— L1 活源 + L2 静态离线日历。**
  - L1 = 活数据源（覆盖三市场，形态与现状同构：指数有 bar = 开市）。
  - L2 = **静态内嵌日历**：由官方权威日历**离线生成 + 入仓**，年更（与官方发布同频，人工跑一次脚本）。**不做运行时文档解析**——运行时解析版式一变即失效，且其数据与静态表同源，多一层运行时脆弱性并不真正拓宽尾部风险覆盖。
  - **否决三层方案**（再插一层运行时官方文档解析）：调研实证官方仅发布 PDF + HTML、无 API/CSV/ICS；且该层与 L2 数据同源。
  - **依据**：官方自 2024-09-23 起实施恶劣天气交易安排（台风/黑雨不再休市）→ 港股「不可预测休市」风险源已被官方消除 → 静态日历的历史反对理由失效。

- **Q: 「日历不健康」用什么信号判定？** → **A: 填充成功心跳（liveness），非数据新鲜度（freshness）。**
  - 填充链路每次成功即更新一个**可被外部读取的健康事实**；探针查该心跳是否陈旧。
  - **否决「max(date) 陈旧」**：长假连休 ≥7 天时日历本就无新增交易日 → 阈值须放宽到 >10 天才躲得过春节 → **与 SC-003「24h 内告警」直接冲突**；且需人工年年维护长假白名单；本质上答不了「是没数据，还是链路死了」。
  - 心跳天然免疫周末/长假（长假期间填充照样「成功但无新增」→ 心跳新 → 不告警），且 app 挂掉时心跳自然陈旧 → 照样告警（满足 FR-010）。与既有 `nvy-watchdog` 的 no-show 心跳范式同构。

- **Q: L2 静态层是否需覆盖 us？** → **A: 否，us 仅 L1 覆盖。**
  - 实证（prod 只读查 `sync_dimension.market_scope`）：22 维中 `{hk}`=16 / `{cn,hk}`=5 / `{cn,hk,us}`=**1（仅 `universe`）**；**无任何 `{us}`-only 维度**。
  - 交易日 gate 为 **OR 语义**（「全 marketScope 休市才剔除该维度」）→ `universe` 只要 cn 或 hk 开市即放行。
  - ⇒ **us 日历不是任何维度的准入判据**；L1 对 us 失效时 us 日历陈旧，但**不阻塞任何同步**。故 L2 无需覆盖 us，也无需引入美股官方假期表（scope 缩减）。

- **Q: 腾讯 limit 硬上限（PoC 实测 = 2000）怎么处理？** → **A: 分片请求 + 合并（补 FR-016 / SC-008）。**
  - user 判断：拒绝超大 limit 是 vendor **合理的服务端自保**，不是缺陷；解法与本仓既有 OOM 根治同族 —— **chunk-oriented 批处理**（`BACKFILL_ROW_CHUNK=500` 先例）。
