# Feature Specification: 雷达跨标的聚合三视图（M2c）

**Feature Branch**: `048-optionsdesk-radar-aggregate-views`
**Created**: 2026-08-09
**Status**: Draft
**Input**: 见 § 上游依据

## 背景：为什么切在这里

045（M1）交付 P1 雷达时，`FR-020` 明写「顶部四视图 seg **只交付标的视图**，其余三项依赖期权链数据，本片 **MUST NOT 渲染 seg 控件**（避免出现三个永远空的 Tab）」。那三个视图此后**在 p1 §8 里程碑表四片中一格都没收** —— 与 08-02 拍板 P7 温度计归属时「四片里它一直无主」是同一个形状，08-04 对账四份 plan 时补上，单开为 M2c。

**为什么不并进 M2b（047）**：切口是**风险类别**，不是数据粒度。

| 判据       | M2b（047，已 ship）                                           | M2c（本片）                                          |
| ---------- | ------------------------------------------------------------- | ---------------------------------------------------- |
| 主要风险   | **数据管道** —— 期权 EOD 漏采即永久缺口，完整性告警是唯一防线 | **口径与排序** —— 档位统一主排序键、禁跨腿族折年直比 |
| 新增数据面 | 3 个维度 + shim 两端点                                        | **零**（复用 047 落的快照）                          |
| 延期后果   | 每延一天少一天**不可回补**的快照                              | 只是少一个聚合视图，P2 逐票选约照常可用              |

把「不可逆的数据风险」与「可反复调的呈现口径」压进同一片，会让前者被后者拖住 —— 这是不并片的实质理由（另一条是体量：M1 = 28 task、M2a = 29 task，合片估 45+）。

**本片补的是哪一维**：045 的标的视图是**逐票看**（一行一只票），047 的选约表是**单票下钻**（一票内看全部腿），本片补的是**横向聚合** —— 跨标的把腿摆在一起比。

### 本片必须自建（不是白捡）

1. **顶部 seg 控件本身** —— 045 明确没渲染它，本片是它的首次出现，且**会改动 045 已 ship 的雷达页版式**（标的视图从「整页」变成「seg 下的默认页」）。
2. **跨标的聚合读路径** —— 047 的读路径是「给定一只票取其链」，本片是「跨全部锚定标的取适格腿并统一排序」，是新的查询形态（零新增维度，但不是零新增代码）。
3. **跨族统一排序** —— 047 的排序在单票单族内，本片要在**混族集合**上排，而两族口径不可直比。这是本片的核心难点，不是既有能力的复用。

### 本片必须先验证（不是假设，是待验事实）

- **V-B · 聚合规模的实际分布**：先验档位（见 frontmatter `perf_budgets` 注释）建立在「两个意图视图的行数由带天然收窄，不是全链规模 × 标的数」这个**推断**上。它依赖各票适格腿的真实分布 —— 047 实测的是单票全链 730 行，**没有量过「带内还剩多少」**。
  - **验法**：对当前锚定标的全集，**逐票组装 `LegTabContext`（`zone` + `w` + `rentDepth`）后调 047 的 `legTabs()` 实际计数**，拿到跨标的总行数与响应体量级。<br>🚨 **MUST NOT 手写「DTE ∈ 带内」这类简化 SQL 条件** —— 收租腿的真实判据是 `DTE 带 ∧（锚轴 K ≤ W ∨ 市场轴 |Δ| ∈ rentAbsDeltaBand(rentDepth)）`，只按 DTE 数会**显著高估**，而这个数字是 PoC 规模、虚拟化决策与 `perf_budgets` 重估的唯一输入。
  - **不通过的后果**：先验档位与虚拟化策略都要重估；若机会视图行数与全链同量级，`FR-024` 的虚拟化要求从「建议」升为「硬前置」。
  - ✅ **2026-08-09 实测完成（T000，只读计数；一次性脚本不入仓）** —— 结论：**几百行量级，`FR-024` 不升硬前置**。
    - **口径**：当前锚全集 12 个锚，其中 `excluded = true` 的 3 个按 `FR-006a` 在基础 `WHERE` 排除，进聚合 9 个；行情基准 = 上一个已收盘 session（`2026-08-07` 收盘），计数基准日 `2026-08-09`。成员判定**一律走 047 已 ship 的 `leg-tab.rules.ts` 本体** —— 逐票 `classifyZone` → `computeW` → `classifyIntent` → 组装 `LegTabContext{zone, w, rentDepth}` → 调 `isBuildLeg` / `isRentLeg`，**零手写简化条件**。
    - **为什么是混合口径（先说清，否则数字会被当成逐腿实测抄走）**：计数所用环境的期权 EOD 快照表当前**零行** ⇒ 逐腿 `|Δ|` 取不到，`GetLegsUseCase` 对 9 票一律回 `chain_not_ready`。故按「判据读不读 Δ」把计数劈成两半：**不读 Δ 的那半精确算** —— 收租腿·锚轴判据 = `DTE ∈ [150,365] ∧ K ≤ W`，9 票里 7 票落在锚轴（区间 ∈ 薄带 / 偏贵 / 不动区），故收租族约 88% 的行是**精确值不是估计**；**读 Δ 的那半用同批同票的真实 Δ 分布标定留存率** —— 建仓带 `|Δ| ∈ [0.40, 0.55]` 实测留存 `3.2%`（`10 / 311`），收租市场轴并集带以同批数据里最长可用 DTE 段的 `32.8%`（`40 / 122`）作代理。
    - **行数（各聚合视图的逻辑全量）**：机会视图 **≈ 210 行**（收租族 ≈ 191 + 建仓族 ≈ 18，两族 DTE 带不相交故并集 = 相加）· 收租腿视图 ≈ 191 行（其中 **168 行为精确值**）· 建仓腿视图 ≈ 18 行。**硬上界 810 行** = 把两个 Δ 相关判据全放开、只留 DTE 带与锚轴（收租 238 + 建仓 572）。**绝对天花板 3159 行** = 9 票的适格认沽合约全集，任何视图都不可能超过它。
    - **响应体**：单行序列化实测 `877 B`（047 `LegView` + 本片票级列，用 1074 行真实数据标定；047 侧单行 `685 B`，与其 ship 时记录的 `489 KB / 730 行` 同量级）⇒ 机会视图 ≈ **180 KB**，硬上界 ≈ **694 KB**。
    - **判决 → `FR-024` 维持「建议」不升「硬前置」**：机会视图 ≈ 210 行、硬上界 810 行，与 047 **已 ship 且真机验证可用**的单票选约表（730 行）同量级甚至更小 ⇒ V-C 的范式**原样复用**即可，不需要换架构。⚠️ 这不等于虚拟化可省：Guardrail 6（`SectionList` MUST 是页面唯一纵向滚动容器）照旧有效 —— 降的是「这条要不要另起架构」的等级，不是「列表要不要虚拟化」。
    - **给 V-C / T001 的输入**：PoC 合成数据集规模按「实测值 ≥2 倍」取 **≥ 1620 行**（= 硬上界 810 的 2 倍，**不是**估计值 210 的 2 倍 —— 要扛住的是上界）。
    - **三个让数字打折的因素（写下来，免得后人当精确值抄）**：① 建仓族与收租族·市场轴这两块是**留存率标定**不是逐腿实测，快照落数后 T026 必须复测；② 当前 9 票**全部未选仓位水位** ⇒ 意图恒 `pending`、市场轴取三档**并集带**（三档里最宽的那个）⇒ 该段现估计**偏高**，选了水位只会更少；③ 标定数据的采集窗 DTE 只到 103 天，收租带（150–365）在其中**结构性为 0**，故该段留存率是**代理值** —— 但它只作用于 2 只市场轴票的 70 张合约，改不了量级结论。

- **V-C · 047 的双向滚动范式能否搬到跨标的规模（PoC gate，2026-08-09 user 拍板）**：<br>📌 **2026-08-09 plan 期订正 —— 本条起草时写的「三者叠加没有现成范式」是错的，据实装证据作废**：047 已把「纵向虚拟化 × 横滑隐藏列 × 首列钉住」三者跑通**并 ship**，且抽成了与 symbol 无关的通用组件：`LegColumnScroller({ offset, children })` / `LegStickyCell` / `LegRow({ leg, offset })` / `LegTableHeader({ offset })` / `legColumnWidth(key)`（均在 `apps/mobile/src/optionsdesk/`）。其解法是**首列渲在横向滚动之外**（天然钉住，不依赖 `position: sticky`）+ 每行一个共享 `offset` 的横向容器 + `SectionList` 作唯一纵向容器 —— **方向正交故不争手势**，成本 `O(视口行数)` 不随总行数增长（047 plan D-UI-1）。
  - ⇒ **本条要验的不是「能不能共存」，而是「这套已 ship 的范式在跨标的规模与结构下是否仍成立」**。风险等级由此下调，但 gate 保留。
  - **两处与 047 的真实差异**（PoC 的靶心）：① **规模**：047 是单票 730 行，本片是跨标的（V-B 待测），每行多挂一个横向容器，`O(视口行数)` 的常数不变但总行数上限不同 ② **结构**：047 的表在详情页内、由 `SectionList` 的 `ListHeaderComponent` 承载 046 三块；本片的表在雷达页内、上方是 seg 控件 + 时间条 + 图例，且 seg 切换要**换整份 `section.data`**。
  - **验法**：impl 期**第一个 task** 起最小 PoC（**真机跑，非 web e2e** —— 嵌套滚动手势争用属 `.claude/rules/mobile-impl-playbook.md` § RN 布局陷阱那一族，Playwright 视口宽松必然假绿），喂合成大数据集（按 V-B 实测规模，取不下于其 2 倍），验四条：① 横滑与纵滚手势各自归属正确、无粘滞 ② 横滑时 ticker 列真的钉住 ③ 虚拟化真的生效（滚动中视图回收，非全量渲染）④ seg 切换换 `section.data` 后横向 `offset` 与滚动位置的行为符合预期（047 无此场景，是本片新增面）。
  - 🚨 **gate 语义 —— PoC 未过 MUST NOT 开工任何聚合表 UI task**，且 **MUST NOT 由 impl 自行降级绕过**（如偷偷改成分页、砍掉 sticky、砍掉横滑列）。那些都是**产品逻辑的取舍，不是实现细节**：`FR-023` 的全量可见、`FR-007a` 的分层列集、sticky 首列各自都有独立理由，砍哪个是 user 的权衡。
  - **不通过的处置**：**停下来回 user 拍板**（user 明示「因为技术问题，我可以权衡不同产品逻辑」）。带着 PoC 的实测证据给出可选降级路径与各自代价，由 user 选，选完回改 spec 对应 FR —— 不是在 impl 里静默妥协。

### 🚨 合规红线（不是偏好，是禁令）

## User Scenarios & Testing _(mandatory)_

### User Story 1 — 一屏看全局：今天全市场哪条腿最肥（Priority: P1）

盘前决策时，用户此前只能逐票进 P2 才知道某票有没有值得挂的腿 —— 7 只票就是 7 次下钻，且**看完第 7 只时已经忘了第 1 只的档位**。机会视图把全部适格腿摆进一个按档位排序的列表，一屏读出「今天值得动手的腿在哪几只票上」。

**Why this priority**: 这是本片存在的理由，也是 M2c 独立价值的全部（「跨标的选腿一屏看全局」）。另两个视图是它的分族切片，没有它两者只是换了个入口的重复。

**Independent Test**: 在有多只锚定标的、且至少两只有当日快照的状态下打开雷达页切到机会视图，能看到跨标的混族列表按档位降序排列，每行标明所属票、腿族口径与意图；只实现这一个 story 即可交付「一屏看全局」的完整价值。

**Acceptance Scenarios**:

1. **Given** 多只锚定标的均有当日期权链快照，**When** 用户进入雷达页并切到机会视图，**Then** 系统呈现跨标的的适格腿列表，按档位为主排序键降序排列，每行显式标注 ticker、所属腿族口径（周化 / 年化）与意图。
2. **Given** 机会视图已呈现混族列表，**When** 用户查看任一行的费率数字，**Then** 该数字为**该行自身腿族口径**的值（建仓腿显周化、收租腿显年化），折年若呈现则为小字副标并标「参照 · 不排序」。
3. **Given** 机会视图中同时存在周化 `2.5%` 的建仓腿与年化 `18%` 的收租腿，**When** 系统排序，**Then** 两者按**各自族内算出的档位**参与统一排序，系统 MUST NOT 将二者的折年数直接比较。
4. **Given** 用户在机会视图中找到一条想细看的腿，**When** 点击该行，**Then** 跳转至该标的的 P2 详情页并定位到对应腿。

### User Story 2 — 分族切片：只看建仓腿 / 只看收租腿（Priority: P2）

用户当天的意图往往是单一的（今天是「找建仓机会」还是「找收租机会」）。分族视图去掉混族噪声，在单一口径下横比全部标的。

**Why this priority**: 价值真实但可由机会视图 + 心智过滤替代，故次于 P1。它也是「统一排序」这一难点的**退化情形**（单族内无跨族可比性问题），实现上应先于混族排序被验证。

**Independent Test**: 切到建仓腿视图，列表只含建仓腿族的腿、按周化口径排序；切到收租腿视图同理按年化 —— 两者各自可独立验证排序正确性，不依赖混族逻辑。

**Acceptance Scenarios**:

1. **Given** 多只标的均有当日快照，**When** 用户切到建仓腿视图，**Then** 列表仅含建仓腿族的腿（跨标的），按周化口径的档位排序，MUST NOT 混入收租腿。
2. **Given** 同上，**When** 用户切到收租腿视图，**Then** 列表仅含收租腿族的腿，按年化口径的档位排序。
3. **Given** 某个分族视图当日无任何成员，**When** 用户切到该视图，**Then** 视图可正常进入并显示空态文案，MUST NOT 置灰该 seg 项、MUST NOT 隐藏面板。

### User Story 3 — 看得见的缺口：谁没数据、谁不判档（Priority: P2）

跨标的聚合最危险的失败模式是**静默缺席** —— 一只票因为没快照而整体不出现在列表里，屏幕上看起来只是「它今天没有好腿」。两种状态在视觉上不可区分，而它们的应对完全相反（一个是等，一个是查管道）。

**Why this priority**: 与 047 把「greeks 缺失的腿留在表内并标注」列为硬要求同源 —— 聚合放大了这个风险（单票页面上「没数据」很显眼，聚合列表里它就是一行不存在）。定为 P2 因为它是 P1 正确性的守卫，而非独立价值。

**Independent Test**: 构造一只有锚但无任何快照的标的，进入聚合视图，该票以「链数据未就绪」形态显式可见；再构造一只 greeks 缺失的腿，其在列表内可见、标「数据不全」、不参与档位排序。

**Acceptance Scenarios**:

1. **Given** 某锚定标的从无任何期权链快照，**When** 用户进入任一聚合视图，**Then** 该票以「链数据未就绪」形态显式可见并说明何时会有，MUST NOT 静默缺席。
2. **Given** 某条腿 greeks 缺失，**When** 它出现在聚合列表中，**Then** 该行标「数据不全」、费率列显缺失占位而非数值、动作列标「无法判档」，且 MUST NOT 参与档位着色与主排序。
3. **Given** 聚合数据的 `asOf` 非当日，**When** 视图呈现，**Then** 显式呈现「数据截至 X · 收盘」，MUST NOT 静默当作当日实时值。
4. **Given** 全部标的当日均无适格腿，**When** 用户进入机会视图，**Then** 呈现空态文案「今日无解，空仓是常态」，MUST NOT 呈现空白页或错误页。

### Edge Cases

- 某标的**已选水位** vs **未选水位**：未选时意图无从判定，但其腿照常进聚合、照常判档排序，仅意图列标「意图未定」（`FR-027`）。
- 某标的处于**不动区**：腿数据照常全量展示（承 047 `FR-021`），警示走**首列行内标记**而非置顶（`FR-028`）—— 聚合面一屏混多票，「置顶」既不知道指谁、又会打破档位主排序。
- 一条腿**两族皆不属**（DTE 落在 2 周与 150 天之间的大片区域）：三个聚合视图**一个都不进**（机会视图 = 两族并集，非全腿超集，见 `FR-005`）。⚠️ 该腿在 P2 的「全腿」Tab 里**仍然可见** —— 这是设计而非缺口：P1 回答「今天该盯谁」，P2 回答「这只票有什么」。
- 聚合结果**行数远超预期**（V-B 未通过）：全量可见原则与可用性的张力 —— MUST NOT 用改变逻辑集合的分页解决（承 047 `FR-005`）。
- 用户从机会视图点一条腿跳到 P2，但该腿在 P2 的**默认 Tab 下不可见**（如它是建仓腿而 P2 默认停在收租腿 Tab）：需要明确的定位行为，不能静默落到列表顶部。
- 锚**复审逾期**或**复核锚红标亮**的标的：其腿照常参与聚合（提醒非拦截）；提醒走**首列行内标记**（同 `FR-028` 不动区），**MUST NOT 渲染票级徽标** —— 徽标只属「标的」视图（`FR-020` 适用范围）。

- **FR-011**: 三个视图的**主排序键 MUST 恒为档位**，且档位 MUST 在**族内各自口径**下计算（建仓腿走周化、收租腿走年化，分母 = 准备金 `K−P`）。

- **FR-013a**: **薄档行**的费率列 MUST 同屏显出该行的 `ask` 口径值（形如 `7.2% (ask 11.4%)`），承 047 `FR-010`。<br>📌 **理由 = 动作列在薄档这一格上是有意的信息损失，必须由费率列补回**：策略 SoT 的「尴尬区」实为按 `ask` 二分且随意图分叉的两态，而动作标签被定死为四态、且为建议语义，承载不了它 ⇒ 把二分所需的那个数摆到屏幕上，让人自行套用 SoT。<br>🚫 **这不是「`ask` 参与判档」的口子** —— 分档口径**恒为 `bid`**，`ask` 只作同屏参照，MUST NOT 进入任何档位判定或排序输入。<br>📌 **本条 2026-08-09 由 analyze 第二轮补写**：mockup 已按 047 范式画了 `ask` 同屏，但 spec 未继承该条 ⇒ 属 mockup 超出 spec，补写以消除 drift。

- **FR-015**: 一切档位边界、腿族判据与意图矩阵规则 MUST 追溯到 047 已落的具名常量，MUST NOT 在本片代码中自造参数或复制字面量（承 047 `FR-022`）。

### Functional Requirements — 降级与未定态

- **FR-027**: 某标的**尚未选择仓位水位档**时，其腿 MUST 照常进聚合并照常判档、照常参与排序；意图列 MUST 显式标「意图未定 · 选水位以判定」。<br>⚠️ **「照常」有一处不对称，MUST 如实告知实现者**：收租腿在市场轴上的成员带随 `rentDepth` 取值，而水位未选时 047 判据取**三档并集**（`rentAbsDeltaBand(null)`）⇒ 该票拿到的是比选定水位后**更宽的超集**，不是字面意义的「照常」。这是 047 既定行为，本片沿用不改。MUST NOT 静默按最保守档假设、MUST NOT 因意图无从判定而从聚合中消失、MUST NOT 单独分组置底。<br>📌 **理由 = 档位不依赖水位**（2026-08-09 user 拍板）：档位只由费率与腿族口径决定，水位只喂意图判定矩阵。⇒ 把这些腿踢出列表或压到底部**没有排序上的依据**，只会让一条「好」档的腿因为一个无关的未填项而看不见。<br>📌 **本条是 047 `FR-017` 在聚合面留下的真空洞**，不是重复：047 给的兜底是「Tab 默认停**全腿**」—— 而 P1 的三个聚合视图里**没有「全腿」这个位置**（机会视图 = 建仓 ∪ 收租，见 `FR-005`），那个兜底在这里无处落地。补水位的入口仍在 P2（点该行进详情页即可选），本片不重复提供。

- **FR-028**: 标的处于**不动区**时，其腿 MUST 照常进聚合、照常判档与排序；警示 MUST 实现为**首列（sticky 常显列）内 ticker 旁的行内标记**，MUST NOT 单独置顶、MUST NOT 聚合成顶部横幅（2026-08-09 定）。<br>📌 **判据 = 「置顶」在聚合面失去意义**：047 的「警示注置顶」针对单票详情页（一页一票）；聚合视图一屏混多票，置顶既不知道指谁、也会打破档位主排序。<br>📌 **形态与陈旧标（`FR-010a`）同族** —— 都是「这只票整体有情况」的票级提示，都落首列，视觉上可并列。<br>🚫 顶部横幅已承载「链数据未就绪」（`FR-008`）与「意图未定」（`FR-027`）两类，再叠一类会糊成一堆且看不出具体哪行受影响。

### Key Entities

- **适格腿（聚合行）**：一条期权合约在某交易日的快照，附带其所属腿族口径、档位、意图、动作标签、财报标与所属 ticker。它不是新实体 —— 是 047 已落快照的**跨标的投影**，本片不新增持久化。
- **腿族**：建仓腿（`DTE ≤ 14` ∧ `|Δ| ∈ [0.40,0.55]`，周化口径）与收租腿（`DTE ∈ [150,365]` ∧（**锚轴** `K ≤ W`〔`thin` / `expensive` / `overvalued`〕**或市场轴** `|Δ| ∈ rentAbsDeltaBand(rentDepth)`〔其余 zone〕），年化口径）。两族 DTE 值域不相交 ⇒ 一条腿恒属至多一族。<br>🚨 **收租腿不是 DTE 单条件** —— 轴二分与 `rentDepth` 依赖是判据的组成部分，判据单点在 047 `leg-tab.rules.ts`，本片 MUST 复用不重述。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 用户从进入雷达页到读出「今天值得动手的腿在哪几只票上」，**无需进入任何详情页**；此前该判断需要逐票下钻，次数 = 锚定标的数。
- **SC-002**: 机会视图中任意两行的相对顺序，**可由二者各自的族内档位单独解释** —— 抽查任意跨族相邻行对，其顺序 MUST NOT 只能用折年数直比来解释。这是 `FR-012` 的可验证形式。
- **SC-003**: 屏幕上每一行的费率主数字，**等于该行档位的判定值**（抽查任意行，其主数字口径与其腿族口径一致）。
- **SC-004**: 「没有数据」与「有数据但今天没有好腿」两种状态在三个视图中**始终可区分**，无需查日志或数据库。
- **SC-005**: 045 已 ship 的标的视图在本片后**行为零回归**（版式、排序、徽标、点行跳转四项逐一比对）。
- **SC-006**: 聚合视图在当前锚定标的全集下可一路滚动至列表末尾，全程满足两条**可观测**判据：① 滚动条长度自始至终反映**全量行数**而非已加载行数 ② 滚动过程中不出现**持续可见的空白占位区**（虚拟化回收跟得上滚动速度）。这是 `FR-023` 与 `FR-024` 的验收形式 —— 判据刻意不取帧率，因为 perf 口径已明确排除客户端渲染。

## Assumptions

- **锚定标的全集即聚合范围**：聚合的标的来源 = 045 已实装的锚工作集。<br>⚠️ 其中 `excluded` 的处置**已于 2026-08-09 从本段升格为 `FR-006a`** —— 它是可验证的行为要求，不是背景假设。留在 Assumptions 里的那半年它没有 FR、没有 `state_branch`、没有 task，任何扫描都够不到。
- **腿族互斥**：建仓腿与收租腿的 DTE 值域不相交，故无需处理一条腿同属两族的情形；两族皆不属的腿不进两个意图视图。<br>⚠️ 互斥只由 **DTE 值域**保证；成员资格本身还含轴二分与 `|Δ|` 带（见 Key Entities），MUST NOT 据本条把腿族简化成 DTE 判定。
- **档位阈值不在本片重定**：四档阈值沿用 047 已落常量（建仓腿周化 `≥2%` / `1–2%` / `0.6–1%` / `<0.6%`；收租腿年化 `≥15%` / `10–15%` / `5–10%` / `<5%`），分档口径恒为 `bid`。
