# Feature Specification: 选约表查询下沉 —— 每视角独立请求 + 服务端筛选与截断

**Feature Branch**: `053-optionsdesk-leg-query-pushdown`
**Created**: 2026-08-12
**Status**: Clarified（2026-08-12，4 问 4 答）
**里程碑**: sell-put 可视化决策系统 —— optionsdesk 选约引擎重构的 **P3 片（末片）**（主 plan：`docs/private/plans/2026-08/08-11-optionsdesk-leg-engine-master.md`，本机私有）

## 背景：这一片在收尾什么

四片重构的前三片各自解决了一层：`049` 修掉横滑自激环并重设计 Tab 壳；`050` 把判定层重做成召回 + 打标 + 精排；`051` 让 mobile 按新契约呈现。到这里为止，**读取路径仍是 047 的形态**：一次请求、下发全量适格腿、三个视角共用同一份响应体。

本片把这条路径改掉，做四件互相咬合的事：

1. **每个视角各自一次请求** —— 为「不同视角不同过滤器」解耦。这是筛选参数能上服务端的前提。
2. **行权价筛选参数进请求** —— 这块原本是 `049` 的 US2（`FR-008`–`FR-018` + `FR-023`），08-11 定案「筛选要走服务端召回而非客户端过滤」后整块移交本片。**mockup 5 帧中 4 帧已定稿，形态不必重画。**
3. **服务端截断 top-N** —— 顺序恒为 **排名 → 筛选 → 截断**，截断作用在已排好序的尾巴上。阈值按视角分档（`FR-017`）。
4. **截断计数「已显示前 M 条 · 其余 N−M 条未显示」** —— 截断的补偿。`051` 已把它的落位一次设计到位并留好槽位；措辞由本片 mockup 面板 A 两变体对照后定案（见 § Clarifications）。

三件连带项：**费率下沉 SQL**（`050` 显式否决并移交本片，理由是截断要求 `ORDER BY … LIMIT` 落在数据层）、**预热**（`FR-024`，错峰）、以及 **三次请求的一致性处置**（主 plan 未决 #1，已于本片 clarify 定案 —— `FR-003` / `FR-004a`）。

### 为什么截断值得做（这一问被正面质疑过，答案带真实数据）

2026-08-12 起草期用 dev 库最新交易日快照量过一遍**每视角的真实腿数**，结论是：**截断在当前规模下不构成需求，但仍按计划做**（owner 定案）。数据如实登记在此，因为它**改变的是验证策略**，不是范围。

| 视角 | 12 条链的最大值 | 若三视角一律取 200，触发截断的链数                       |
| ---- | --------------- | -------------------------------------------------------- |
| 建仓 | **108**         | **0 / 12** —— 阈值是最大值的 1.85 倍，**结构性永不触发** |
| 收租 | 324             | 2 / 12                                                   |
| 全腿 | **639**         | 3 / 12                                                   |

📌 上表是**定案前的分析口径**（三视角一律 200）。它直接导出了最终的分档阈值 —— 全腿视角改取 800（`FR-017`），因为一律 200 会打破 `051` 已交付的一个入口，详见 § Clarifications。按最终阈值重算：**12 条链里只有收租视角的 2 条会触发截断**。

承载能力那一侧三个数都还有余量：server `p50 45.5ms / p95 54.1ms` @730 行（`050` T017 实测）；渲染 822 行虚拟化只挂 16 个节点、零白屏（`049` 真机）；payload 最大链 639 腿、库侧 15 个核心字段实测 **182 kB / 292 B 每腿**。

🚨 **由此得到本片最重要的一条验证约束**：**截断相关的 UI 分支在真实数据上拿不到覆盖**（建仓视角零覆盖，收租 / 全腿各只有 2–3 条链够得着）。这与 `051` 那条「`SC-010` 的 730 行量级已不可达」是同一类坑 —— 必须在 spec 阶段就定好用什么验，MUST NOT 留到 impl 期临场发挥（见 `SC-006` 与 `FR-017a`）。

📌 **规模的驱动量是「单只票的价位」，不是「池子有多少只票」**：链大小 = 到期日数 × 行权价档数，其中到期日数几乎恒定（16–17），差异全在行权价档数（49 → 116）。⇒ 标的池从 12 只扩到 500 只**不会**让单链变大；进一只高价大票才会。

> **口径声明**：上表是 2026-08-12 dev 库最新交易日快照，按 `050` 实装阈值在 SQL 里**复现**判据（权利金 `max(0.20, spot×0.0018)`、流动性相对价差 ≤ `0.35`、建仓另加 `DTE ∈ [1,49]` 且 `K − bid < spot`、收租 `DTE ∈ [30,365]`）。⚠️ **这是复现不是实装口径实测** —— `DTE` 用的是 `expiry_date − session_date`（实装以「当日」为基准）、`P` 用 `bid` 近似。量级可信，逐条数字不可当作实装输出引用。

## Clarifications

### Session 2026-08-12

- Q: 行权价筛选什么时候生效（上服务端后每次生效 = 一次往返）？ → A: **实时 + 防抖** —— 输入停顿后自动生效，无显式提交动作。<br>定案依据：`049` 的 mockup 帧②已定稿，筛选行右端只有「清除」/「完成」两个互斥槽位、**没有应用键**，形态本身就在表达实时生效；改成「确认才生效」要回头重画。<br>🚫 同场排除「客户端本地预筛给即时反馈、服务端结果回来再校正」—— 客户端手上只有**截断后的那一段**，用户筛的区间可能大部分落在截断线之后，本地预筛会给出一个**看起来完全正常的错误子集**，且不会红。

- Q: 预热怎么做（主 plan 只写了「预热」两字，无定义）？ → A: **错峰** —— 进详情页先只取当前视角，它落地后再后台并发取其余两个。<br>定案依据：首屏只付一份 payload（三视角并发约 670 kB，弱网下会明显拖慢首屏），切换仍零等待，且预取在秒级内完成 ⇒ 一致性窗口仍远小于「不预取」。<br>📌 连带定案：**每个视角各自保留自己的筛选状态**（主 plan §1 目标原文「每个 Tab 独立请求，为『不同 Tab 不同过滤器』留出解耦」）—— 切视角不带走上一个视角的区间，筛选变更只重取当前视角。

- Q: 三次请求跨交易日切换点落在不同业务日，怎么处置（主 plan 未决 #1）？ → A: **检测 + 重取** —— 复用契约里**已有的** `asOf`（区块级，每个响应都带），发现三个视角的业务日不一致即重取全部（最多一次），仍不一致则显式提示。<br>定案依据：① 跨交易日窗口里用户想看的是**最新**数据，钉住首个请求的业务日等于故意让后两个视角用旧数据，方向反了 ② **零新增契约字段** —— 主 plan 候选①「全量版本戳」想要的能力，`asOf` + `asOfFreshnessTier` 已经在了 ③ 「钉业务日」会引入新问题（客户端钉住旧业务日后看不到当天新数据，还得再配一套「服务端已有更新业务日 → 提示刷新」）。<br>📌 同场收窄：三个可变源里只有**时钟**是真开放的。**快照期**与业务日强相关（每天一次盘后采集窗），钉住业务日基本等于钉住它；**仓位水位**不是竞态而是用户自己的动作，有确定答案 —— 见下条。
- Q: 仓位水位在请求之间被改，只重取收租视角够不够？ → A: **不够，MUST 让三个视角全部失效重取**。<br>定案依据：主 plan 把这条写成「改水位 → 只影响 `rent` Tab」，**这个描述不成立**。水位 → `intent` → **推荐标**，而推荐标是**标的级、不随 Tab 变**（跨片不变量 #3，`051` `state_branches` 已钉死「标的级意图为收租、用户打开建仓 Tab → 推荐标按当前收租档带判」）⇒ 只重取收租视角会让另外两个视角继续用旧口径打标，**数字与标都在、只是口径不对，且不会红**。

- Q: 截断的作用域 —— 全腿视角是否也截？ → A: **按视角分档：意图视角 200 / 全腿视角 800**。<br>定案依据：① 🚨 **一律 200 会当场打破 `051` 已交付的功能** —— `051` ship 了「流动性门槛计数点击 → 切到全腿视角看那些被排除的腿」这个入口（其 `state_branches` 逐字），而最大链 639 → 200 意味着砍掉 439 行，任一被排除的腿存活率约 31% ⇒ 用户点进去看到的是一张不含目标的表，**条数正常、数值正常、不会红** ② 全腿视角取 800 则今天恒不触发（实测最大 639），入口保住，同时为未来的大链留一道保险丝 —— 比「全腿完全不截」更贴合「为未来铺路」这个选择截断的初衷。<br>🚨 **800 是起手档，不是实测标定值**：它按「覆盖当前最大真实链 + 约 25% 余量」取（639 × 1.25 ≈ 800）。本仓纪律要求阈值有判据而非拍数（047 `FR-052a`）⇒ 该值 MUST 随实测复核，且链规模逼近它时 MUST 可被观测（见 `FR-017c`）。

- Q: 截断计数的措辞取哪个（mockup 面板 A 两变体对照后）？ → A: **只带新信息** ——「已显示前 200 条 · 其余 24 条未显示」，**不复述「符合条件 N 条」**。<br>定案依据：照 `FR-018` 原字面写，「符合条件 224」与 sticky 区块头的「筛后 224」是**同一个数**，一屏内出现两次；未筛选时同样重复（等于区块头的「共 324」）。两个数在一屏里长得不一样却相等，会被读成两个不同的量。<br>📌 代价与其消解：「符合条件的条数」改由区块头单独承担 ⇒ 两处必须同屏可见。**该前提由结构保证**（区块头在 sticky 栈内，滚到底部仍在屏上），已写入 `FR-018` 并附「若区块头移出 sticky 栈则本条重审」的绊线。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 按行权价段位收窄，只看自己够得着的那几档 (Priority: P1)

用户在标的详情页的选约表上，填入行权价的下界 / 上界（可只填一端），表立刻收窄到该区间内的腿。用户改主意时一键清除回到全量。填反了（下界大于上界）时表不会变空，而是保持全量并提示填反了。

**Why this priority**: 这是本片唯一直接的用户价值。最大链的全腿视角有 639 行，用户真正会挂的行权价通常集中在 spot 附近的几档；没有筛选，定位靠横滑 + 纵滑硬找。它也是 `049` 移交过来、mockup 已定稿的那一块。

**Independent Test**: 可独立验：给定一条真实链，填入一个已知区间，断言呈现集合恰为该区间内的成员、且这些腿的排名相关标记与筛选前逐条相同。

**Acceptance Scenarios**:

1. **Given** 某视角已呈现其全量成员，**When** 用户填入下界与上界且下界 ≤ 上界，**Then** 表收窄到闭区间内的腿，顺序仍为服务端下发的顺序
2. **Given** 用户只填了下界，**When** 焦点离开，**Then** 上界视为不限，表收窄为「≥ 下界」
3. **Given** 用户填入的下界 > 上界，**When** 值生效，**Then** 表**保持全量**并给显式提示 —— MUST NOT 筛成空表（空表会被读成「这只票没有腿」）
4. **Given** 筛选生效且结果为 0 行，**When** 用户查看，**Then** 显示专用空态，其文案与「该视角零适格腿」明确不同，且就地给一次清除入口
5. **Given** 用户在输入框内，**When** 数字键盘弹起，**Then** 筛选行与其上方表头栈原位不动，输入框与至少三行结果同屏可见；右端槽位显「完成」
6. **Given** 筛选生效且用户失焦，**When** 用户查看筛选行右端，**Then** 该槽位显「清除」——「完成」与「清除」MUST NOT 同时占宽度
7. **Given** 用户连续快速输入多个字符，**When** 每个字符落下，**Then** MUST NOT 出现逐字符的可见加载抖动

### User Story 2 - 数据量大时，知道自己看到的不是全部 (Priority: P1)

某视角符合条件的腿超过该视角的截断阈值时，用户在列表末尾看到「已显示前 200 条 · 其余 24 条未显示」，明确知道列表被截了、还剩多少没看到、以及收窄的手段是什么。

**Why this priority**: 与 US1 同级，因为它是**截断这个动作的唯一补偿**。`050` 的权利金门槛已经部分推翻过 047 的「全量呈现原则」一次，代价靠计数补偿；本片是第二次推翻，不给计数就是第二次静默的数据消失。

**Independent Test**: 可独立验：构造一个成员数超阈值的视角，断言双计数出现、取值正确、且与 `051` 那对门槛计数在措辞与位置上可区分。

**Acceptance Scenarios**:

1. **Given** 某视角符合条件的腿超过截断阈值，**When** 用户查看列表末尾的计数区，**Then** 看到实际显示的条数与被截掉的条数，且 sticky 区块头同屏给出符合条件的总数（两处不重复同一个数）
2. **Given** 某视角符合条件的腿未超过阈值，**When** 用户查看，**Then** 截断计数不出现，MUST NOT 显示一个刺眼的空值或恒等的两个数
3. **Given** 同屏已有 `051` 的两道门槛计数，**When** 截断计数一并出现，**Then** 两对计数各自语义清晰、MUST NOT 用同一个词把「被门槛挡下」与「被截断」混成一件事
4. **Given** 用户填入筛选区间使结果降到阈值以下，**When** 结果更新，**Then** 截断计数消失
5. **Given** 列表被截断，**When** 用户滑到列表底部，**Then** MUST NOT 出现「加载更多」/ 分页控件 —— 收窄的唯一手段是筛选
6. **Given** 某意图视角有腿被流动性门槛排除，**When** 用户点该计数的入口切到全腿视角（`051` 已交付的路径），**Then** 那些被排除的腿**逐条可达** —— 全腿视角的截断阈值 MUST NOT 把它们吞掉

---

### User Story 3 - 切换视角不等待 (Priority: P2)

用户在三个视角之间来回切换时，不会每切一次就看一次加载态。

**Why this priority**: 纯体验。切换视角是这张表上最高频的动作（同一批腿换三种眼光看），而本片把「一次请求三份列表」拆成了三次独立请求 —— **不做预热，本片就是一次可感知的体验退化**。放 P2 是因为它不影响正确性。

**Independent Test**: 可独立验：进入详情页后不做任何操作，切到另一视角，测量到内容可见的等待时间。

**Acceptance Scenarios**:

1. **Given** 用户刚进入标的详情页，**When** 切换到另一个视角，**Then** 等待时间显著低于冷取（具体判据见 `SC-008`）
2. **Given** 用户在某视角内改了筛选区间，**When** 切换到另一视角，**Then** 该视角呈现的是它自己的筛选状态，MUST NOT 把上一个视角的区间带过去
3. **Given** 后台预取某视角时失败，**When** 用户停在当前视角，**Then** 当前视角零感知；切过去时才看到该视角自己的错误态与重试入口

---

### User Story 4 - 一个视角出问题，不牵连另外两个 (Priority: P2)

三次独立请求里某一次失败时，用户在其余视角看到的数据不被清空、不被降级。

**Why this priority**: 这是「拆成三次请求」这个动作**新引入**的失败面 —— 047 的单次请求要么全成要么全败，不存在部分失败。不处置就是把一个新的故障模式静默留给用户。

**Independent Test**: 可独立验：令某一个视角的请求失败，断言该视角显错误态而其余视角内容不变。

**Acceptance Scenarios**:

1. **Given** 三个视角中某一个的请求失败，**When** 用户停在另一个视角，**Then** 当前内容不受影响
2. **Given** 某视角处于错误态，**When** 用户切到它，**Then** 看到该视角自己的错误态与重试入口，MUST NOT 显示成空态（「读失败」与「确实没有腿」是两件事）

---

### Edge Cases

- **筛选区间完全落在链的行权价范围之外**（如上界低于最低行权价）→ 走「筛后 0 行」的专用空态，不走「该视角零适格腿」
- **筛选区间内只有死档腿** → 照常呈现（死档不因筛选而改变可见性判据，继承 047）
- **某视角成员数恰等于截断阈值** → 不算截断，截断计数不出现（边界取「严格大于才截」）
- **筛选把结果从超阈值降到阈值以下的那一刻** → 截断计数必须消失而不是停在旧值
- **用户在请求飞行途中切换视角** → 迟到的响应 MUST NOT 覆盖当前视角的内容
- **用户在跨交易日切换点前后各触发一次请求** → 见 `FR-003` / `FR-004`（唯一结构性、不靠概率的一致性缺口）
- **仓位水位在两次请求之间被改** → 三个视角全部失效重取（`FR-004a`）—— 它影响的是标的级的推荐标口径，不是只影响收租视角
- **链未就绪 / 跨 context 读故障** → 沿用既有的两个显式状态，本片不改其行为
- **输入非数字字符 / 三位小数 / 负数** → 拒绝该输入，MUST NOT 静默取整或截位后当作有效值

## Requirements _(mandatory)_

### 每视角独立请求与一致性（US4）

- **FR-001**: 每个视角 MUST 各自独立取数，且请求 MUST 携带该视角自己的筛选参数。
- **FR-002**: 每次取数 MUST 只返回该视角的腿，MUST NOT 把三个视角的腿合并下发。每个视角的呈现顺序 MUST 取自服务端下发的顺序，客户端 MUST NOT 重排（继承 `051`，本片不放松）。
- **FR-003**: 系统 MUST 检测「三个视角的业务日不一致」并自动重取全部（**最多一次**）；重取后仍不一致 MUST 显式提示，MUST NOT 静默呈现来自不同业务日的数据，也 MUST NOT 无限重取。<br>📌 检测 MUST 复用契约里**已有的** `asOf`，MUST NOT 为此新增版本戳字段。
- **FR-004**: 「两次请求落在不同业务日」这一情形 MUST 可被观测（不依赖读日志）。
- **FR-004a**: 仓位水位被改时，**三个视角 MUST 全部失效重取**，MUST NOT 只重取收租视角。<br>📌 存在理由：水位 → `intent` → **推荐标**，而推荐标是**标的级、不随 Tab 变**（跨片不变量 #3）⇒ 只重取收租视角会让另外两个视角继续用旧口径打标，**数字与标都在、只是口径不对，且不会红**。这条**修正了主 plan 未决 #1 里「改水位只影响 `rent` Tab」的描述**。
- **FR-005**: 单个视角的失败 MUST 被隔离：该视角显自己的错误态与重试入口，其余视角已取得的数据 MUST NOT 被清空或降级。**MUST NOT 把读失败呈现成空态。**
- **FR-006**: 迟到的响应 MUST NOT 覆盖用户已切走的视角或已变更的筛选条件所对应的内容。

### 行权价筛选（US1，自 `049` 移交）

- **FR-007**: 筛选行 MUST 落在 Tab 行与 12 列表头之间，含行权价下界 / 上界两个数值输入。
- **FR-008**: 筛选 MUST 与视角成员判据**复合**：先按视角取成员，再按区间收窄。两者 MUST NOT 互相覆盖。
- **FR-009**: 🚨 筛选 MUST NOT 进入排名基准（跨片不变量 #4）——「活跃度排名基准 = 该视角的全量成员」。⇒ 同一条腿在筛选前后，其排名相关标记恒不变。**实现者最自然的写法是「先筛再排名」（少算一些），那样写出来照样能跑、数字照样有，只是全错。**
- **FR-010**: 输入精度 MUST 为两位小数（`049` clarify 定案）。非数字 / 超精度 / 负数 MUST 被拒绝，MUST NOT 静默取整或截位后当作有效值。
- **FR-011**: 只填一端时，另一端 MUST 视为不限。
- **FR-012**: 下界 > 上界时筛选 MUST NOT 生效：表**保持全量**并给显式提示。MUST NOT 筛成空表。
- **FR-013**: 筛后 0 行 MUST 走专用空态，其文案 MUST 与「该视角零适格腿」明确不同，并 MUST 就地给一次清除入口。
- **FR-014**: 筛选行右端 MUST 为互斥槽位：输入获焦期间显「完成」（数字键盘没有系统级完成键，不给出口用户无从收起）；失焦且筛选生效时显「清除」。两者 MUST NOT 同时占宽度。
- **FR-015**: 软键盘 MUST NOT 触发整屏避让：筛选行与其上方表头栈原位不动，输入框与至少三行结果同屏可见。
- **FR-016**: 筛选条件 MUST NOT 持久化（不做「上次的筛选」「记住我的区间」）。
- **FR-016a**: 筛选 MUST **实时生效**（输入停顿后自动生效），MUST NOT 要求显式的应用 / 确认动作。用户连续输入时 MUST NOT 产生逐字符的可见加载抖动，且中间态的迟到结果 MUST NOT 覆盖最终值对应的结果。
- **FR-016b**: 🚫 MUST NOT 用「客户端对已在手的数据本地预筛」充当即时反馈 —— 客户端手上只有**截断后**的那一段，用户筛的区间可能大部分落在截断线之后，本地预筛会给出一个看起来完全正常的**错误子集**且不会红。筛选结果的唯一真相源是服务端。

### 截断与第二对计数（US2）

- **FR-017**: 服务端 MUST 在**排名与筛选之后**截断，顺序恒为 **排名 → 筛选 → 截断**。阈值**按视角分档**：两个意图视角 **200**，全腿视角 **800**。截断判据为「严格大于阈值才截」。
- **FR-017a**: 🚨 截断相关的呈现分支（双计数、截断提示、截断消失）**在真实数据上拿不到完整覆盖**（建仓视角零覆盖）。⇒ 本片 MUST 给出**不依赖真实链规模**的验证手段，且该手段 MUST 在 plan 阶段定死，MUST NOT 留到 impl 期临场发挥。
- **FR-017b**: 🚨 全腿视角的阈值 MUST 高于「`051` 那个入口所指向的腿仍可达」所需的规模 —— `051` ship 了「流动性门槛计数点击 → 切到全腿视角看被排除的腿」这个入口，全腿视角一旦截在那些腿之前，该入口就指向一张不含目标的表，**且不会红**。⇒ 本片 MUST 有断言覆盖「被意图视角排除的腿，在全腿视角内可达」。
- **FR-017c**: 全腿视角的 800 是**起手档**（按「覆盖当前最大真实链 639 + 约 25% 余量」取），MUST NOT 当作已标定值。链规模逼近任一阈值时 MUST 可被观测（不依赖读日志），使阈值失配是一个**可发现**的事件而非静默截断。
- **FR-018**: 截断生效时 MUST 在 `051` 已定的**非常驻区**槽位（MUST NOT 进 sticky 栈）显式呈现**实际显示的条数**与**被截掉的条数**，措辞形如「已显示前 200 条 · 其余 24 条未显示」。<br>🚫 MUST NOT 在此处复述「符合条件的条数」—— 该数已由 sticky 区块头承担（未筛选时「共 M 行」、筛选生效时「筛后 N · 全量 M」），同屏重复出现会被读成两个不同的量。<br>📌 **成立前提由结构保证**：区块头在 sticky 栈内，滚到列表底部时它仍在屏上 ⇒ 两处恒同屏可见。若将来把区块头移出 sticky 栈，本条 MUST 重审。
- **FR-018a**: 截断计数 MUST 附一句指向**筛选**的收窄指引 —— 因为分页与「加载更多」都不存在（`FR-021`），不给指引等于告诉用户「还有 24 条，但你够不到」。
- **FR-019**: 本片这对计数与 `051` 那对门槛计数 MUST 可区分：语义不同（被门槛挡下 vs 被截断）、措辞 MUST NOT 混用同一个词。
- **FR-020**: 未触发截断时，截断计数 MUST NOT 占据视觉重量（可隐藏或弱化），MUST NOT 显示一个刺眼的空值或恒等的两个数。
- **FR-021**: MUST NOT 提供分页 / 「划到底再加载」/ 「加载更多」以抵达被截断的腿 —— 收窄的唯一手段是筛选（继承 047 `FR-005` 对分页的禁令，本片不放松）。
- **FR-022**: 本片对 047 `FR-005`「全量呈现原则」构成**第二次部分 supersede**（第一次是 `050` 的权利金门槛）。该 supersede MUST 在本片 spec 与 PR body 显式登记，MUST NOT 当作无感知升级。

### 列改版（表达层）

- **FR-030**: 12 列的**列序**MUST 改为：`行权价/到期` → `bid` → `ask` → `折算费率` → `单笔权利金` → `OI` → `相对价差` → 其余列。<br>📌 存在理由：这四个量是「这单值不值得挂、挂不挂得出去」的完整判据集，散在表的两端时用户要横滑两次才能凑齐一次判断。<br>🚫 `bid` 与 `ask` MUST 拆成**两列**，不再共用一格。
- **FR-031**: **单笔权利金**（= `bid × 合约乘数`）MUST 由服务端计算并下发。<br>🚫 MUST NOT 由客户端乘一次 —— 合约乘数是市场规则不是合约属性，服务端已持有该常量（成交额在用它），客户端再乘就是同一判据两处各算一份（ADR-0064 不变量 ③）。
- **FR-032**: 列宽合计与首列冻结判据 MUST 不变 —— 横滑几何（`contentWidth` / 指示条长度比 / 位移语义）不被触碰（继承 `049`）。若新列集导致总宽变化，MUST 通过压缩后置列吸收，MUST NOT 改首列宽。

### 判据单点（费率下沉的连带约束）

- **FR-023**: 排序与截断 MUST 由与既有纯函数判据**等价**的实现产生。系统 MUST NOT 存在第二份会独立漂移的判据实现 —— 若判定被下沉到数据层，纯函数仍是判据的唯一真相源、下沉实现是它的镜像，且**等价性 MUST 可被自动化验证**（两者结果不一致时 MUST 变红）。<br>📌 存在理由：阈值 / 排序键在两处各写一份时，drift **不会红** —— 两边各自都算得出数，只是不是同一个数。

### 预热（US3）

- **FR-024**: 预热 MUST 为**错峰**形态：进入详情页时 MUST 只取当前视角；该视角落地后 MUST 在后台取其余两个。MUST NOT 在首屏并发取三份（三视角并发约 670 kB，弱网下拖慢首屏，且其中两份用户可能永远不看）。
- **FR-024a**: 每个视角 MUST 各自保留自己的筛选状态。切换视角 MUST NOT 把上一个视角的区间带过去；筛选变更 MUST 只重取当前视角，MUST NOT 连带重取其余两个。
- **FR-024b**: 后台预取 MUST NOT 干扰前台：其失败 MUST NOT 影响当前视角的呈现（切过去时再按 `FR-005` 显该视角自己的错误态），其完成 MUST NOT 引起当前视角的重渲染抖动。

### 跨片不变量遵从（继承，本片零改动）

- **FR-025**: 排名基准 = 该视角的全量成员（不变量 #4）。
- **FR-026**: `tier` 跟视角走，全腿视角恒用年化档界（不变量 #5）。
- **FR-027**: 排名特征集 MUST NOT 进入契约（不变量 #12）。可解释性由已在表上的费率列承担。
- **FR-028**: 045 的锚派生规则与意图矩阵 MUST 零改动（不变量 #13）。
- **FR-029**: 召回 / 打标 / 精排的判据本身 MUST 零改动 —— 本片只改它们被调用的位置与时机。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 在本机可达的**最大真实链**上（起草期实测全腿视角 639 行），三个视角均能取数并呈现，无白屏、无卡顿感知。📌 判据取「最大真实链」而非固定行数 —— `051` 已实证固定行数会随判据变化而不可达。
- **SC-002**: 用户填入筛选区间到结果更新可见，可感知延迟不劣于「本地即时收窄」的心理预期；连续输入期间零逐字符抖动。
- **SC-003**: 真机 sticky 栈（含加回的筛选行）占屏比 **≤ 35%**，且数据区可见行数 ≥ 3 行。📌 基线 = `051` 实测 138.5dp / 27.9%，加回 40dp 后推算约 32.7%；**MUST 用真机实测复核，MUST NOT 用 web 读数**。
- **SC-004**: 截断生效的每一种情形下，截断计数 100% 出现，且「已显示」与「未显示」两数之和恒等于符合条件的总数；未触发时 100% 不出现。
- **SC-004a**: 计数区与 sticky 区块头**不出现同一个数值**（`FR-018` 的可验证形态）—— 断言覆盖「未筛选 + 截断」与「筛选 + 截断」两种情形，因为两种情形下重复的是不同的那个数。
- **SC-005**: 同一条腿在筛选前后的排名相关标记逐条相同（`FR-009` 的可验证形态）。
- **SC-006**: 截断相关分支的自动化覆盖**不依赖真实链规模** —— 该覆盖手段在建仓视角（真实数据恒不触发截断）同样有效。
- **SC-007**: 排序 / 截断的判据等价性有自动化断言，且**已证明它会红**（人为让两份实现分歧一次，断言必须失败）。
- **SC-008**: 预取已完成的视角，切换过去 MUST NOT 出现可见的加载态；预取未完成时降级为正常加载态而非空态。首屏耗时 MUST NOT 因预热而劣于「只取一个视角」的基线。
- **SC-009**: 单视角失败时，其余视角内容零变化；错误态与空态在界面上可区分。
- **SC-010**: 跨交易日切换点上的一致性处置有可复现的验证（该场景 MUST 可被构造，MUST NOT 只靠等真实切换点）。
- **SC-011**: 本片对 047 `FR-005` 的 supersede 在 spec 与 PR body 均有显式登记。
- **SC-012**: 在**最大真实链**上，被意图视角的流动性门槛排除的腿，**100% 可在全腿视角内被找到**（`051` 那个入口的目标不被截断吞掉）。📌 这条是 `051` 已交付功能的回归防线，不是新功能验收。

## Assumptions

- **本片是跨端片** ⇒ 按 Constitution §V 走**单 PR**（server impl + 真后端 IT + `api-client` regen + mobile 消费同 PR），并落 `[Contract-Smoke]`。
- **截断的收益当前为零或负，仍照做** —— owner 2026-08-12 定案。起草期实测（见 § 背景）表明按最终分档阈值，12 条链里**只有收租视角的 2 条**会触发截断，建仓视角结构性永不触发；承载能力三个数（server p95 54.1ms、渲染 822 行 16 节点、payload 182 kB）均有余量。⇒ 本片做截断是**为未来的大链提前铺路**，不是解当前的瓶颈。这一取舍必须写进 PR body，否则半年后没人记得为什么付了这笔复杂度。
- **规模的驱动量是单只票的价位，不是标的池大小** —— 链大小 = 到期日数（16–17，几乎恒定）× 行权价档数（49→116）。标的池从 12 只扩到 500 只不会让单链变大。
- **筛选维度只有行权价一个** —— 不做权利金 / DTE / 费率 / 字段切换器（`049` NEGATIVE 约束原样继承）。
- **筛选行的形态已定稿** —— `049` mockup 5 帧中 4 帧（未筛选常态 / 筛选生效 + 双计数 + 清除 / 输入获焦 + 软键盘 + 「完成」/ 下界 > 上界 / 筛后 0 行）形态已锁，本片**不必重画**，但**那对双计数在 `049` 语境下是「筛后 N / 全量 M」，与本片截断那对不是同一件事**（主 plan §3 不变量 #12 的「命名撞车警告」）—— mockup 复用时 MUST 逐帧确认它表达的是哪一对。
- **「拆成三次请求」自己制造了一个新问题** —— 一致性（`FR-003`）在 047 的单次请求下不存在。它是本片的自带代价，不是外部约束。
- **常驻区余量归本片** —— `051` 不但没吃那 4.4%，还还回去 2.7%。本片是这笔余量的唯一消费者（筛选行 40dp）。
- **`049` 的横滑范式与位移语义本片不碰** —— 筛选行是 sticky 栈内新增的一条，不进横滑区，不改 `contentWidth`。
- **`050` 的三个 `*.rules.ts` 是判据 SoT** —— 本片若下沉判定到数据层，下沉实现是镜像而非新真相源（`FR-023`）。
