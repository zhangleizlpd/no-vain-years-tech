# Feature Specification: 选约表查询下沉 —— 每视角独立请求 + 响应收窄 + 表达层截断

**Feature Branch**: `053-optionsdesk-leg-query-pushdown`
**Created**: 2026-08-12（2026-08-13 依 `052` 交付重写）
**Status**: Tasks-ready（2026-08-14；clarify 两轮共 10 问 10 答, analyze 7 条发现已闭合）
**里程碑**: sell-put 可视化决策系统 —— optionsdesk 选约引擎重构的 **P4 片**（主 plan：`docs/private/plans/2026-08/08-11-optionsdesk-leg-engine-master.md` §2.5，本机私有）

## 背景：这一片在收尾什么

五片重构的前四片各解决了一层：`049` 修掉横滑自激环并重设计 Tab 壳；`050` 把判定层重做成召回 + 打标 + 精排；`051` 让 mobile 按新契约呈现；`052` 按 [ADR-0064](../../docs/adr/0064-optionsdesk-retrieval-layering.md) 落地五层分层、把召回搬进检索 port、并把成员判据参数化成**六个可覆盖的检索条件**（含抽屉 UI 与三态边际计数）。

到这里为止，**读取路径的形状仍是 047 的**：一次请求、三个视角共用同一份响应体、下发全量适格腿、零截断。`052` 虽已把 `perspective` 立在 port 与 query 参数上，但调用点一处没改（`get-legs.usecase.ts:430` 仍恒传 `LEG_TABS` 全集）。

本片做四件事：

1. **每个视角各自一次请求** —— 调用方与 controller 改按请求的 `perspective` 作答；port 签名不动（`052` 已为此留好参数）。
2. **响应按视角收窄** —— 七处 by-tab 结构收窄成单份，每腿删 `tabs`。见 `FR-005`。
3. **表达层截断 top-N + 截断计数** —— 截断作用在已排好序的尾巴上。
4. **列改版** —— 判据集聚拢到一次横滑内：新增 `单笔权利金` / `相对价差` 两列，删 `σ距` / `成交额` 两列，总宽恒 716。

三件连带项：**错峰预热**（`FR-025`）、**单视角失败隔离**（`FR-022`）、**三次请求的一致性处置**（主 plan 未决 #1，已定案 —— `FR-020` / `FR-021`）。

### 处理顺序

本片的服务端顺序是 [ADR-0064](../../docs/adr/0064-optionsdesk-retrieval-layering.md) 五层加一步截断：

```text
召回（含用户条件覆盖 + 候选上限 K） → 粗排(no-op) → 特征加工 → 精排 → 表达层截断 N
```

🚨 **不存在独立的「筛选」段** —— 六维条件已由 `052` 并入召回层（`recallTabs` / `intentTabsByTerm` / `intentTabsExcludedByLiquidity` 三个入口退役，判据全并进 `failedCriteria`），排名基准是**当前检索条件下的召回集**。

⚠️ **这订正主 plan §3 不变量 #4 的前半句**（「筛选不进入排名基准 ⇒ server 侧顺序恒为 排名 → 筛选 → 截断」）—— 该表述写于 `050` 期，`052` 已实际推翻它。不变量 #4 中**仍然成立**的是：**截断 MUST 发生在排序之后**。

### 🚨 「拆成每视角独立请求」的代价与正当性前提

这笔账是清醒付的，写在这里以免半年后没人记得为什么付：

| 项                           | 实测 / 推论                                                                                                                                     |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **DB 查询 3x**               | `retrieveCandidates` 全程只调 1 次（`get-legs.usecase.ts:427`）、排序与打标才是 per-tab（`:649`）⇒ 拆成三个请求让召回执行三遍，排序打标总量不变 |
| **首屏不变快**               | 两种做法首屏都是 1 次 DB，差的只是 2 个视角的内存排序                                                                                           |
| **切视角从零请求变一次往返** | 默认路径（无覆盖、同一 query key、`staleTime 30s`）下现在切视角是零请求。`FR-025` 的错峰预热正是这笔代价的对冲                                  |
| **截断不依赖拆请求**         | 三视角一份响应下每视角各截 `N` 同样做得到 ⇒ 拆请求**不是**截断的前提                                                                            |

⇒ **拆请求换来的唯一独有能力是「三套条件同时生效」**（三个视角各自持有并同时生效自己的检索条件，而非只有当前视角生效）。

**正当性前提（owner 2026-08-13 定案，MUST 在 PR body 复述）**：本片选择拆，理由是**为将来的多路召回 / 每视角不同数据源留接口**（ADR-0064 sunset #1 与 #3 的落地形态），而非解当前的性能瓶颈。🚫 MUST NOT 用「解耦」两个字概括本决策 —— 那会让上表四条代价在下一次评估时不可见。

### 截断的收益当前为零或负，仍照做

owner 定案：截断在当前规模下不构成需求，仍按计划做，为未来的大链提前铺路。承载能力三个数都还有余量：server `p50 45.5ms / p95 54.1ms` @730 行（`050` T017）；渲染 822 行虚拟化只挂 16 个节点、零白屏（`049` 真机）；payload 最大链约 640 腿 / 182 kB / 292 B 每腿。

🚨 **由此得到本片最重要的一条验证约束**：**截断相关的分支在真实数据上很可能拿不到覆盖**（意图视角的候选规模远小于全腿视角，很可能结构性永不触发）。这与 `051` 那条「`SC-010` 的 730 行量级已不可达」是同一类坑 —— 必须在 spec 阶段就定好用什么验，MUST NOT 留到 impl 期临场发挥（见 `FR-014` 与 `SC-006`）。

📌 **规模的驱动量是「单只票的价位」，不是「池子有多少只票」**：链大小 = 到期日数 × 行权价档数，其中到期日数几乎恒定（16–17），差异全在行权价档数（49 → 116）。⇒ 标的池从 12 只扩到 500 只**不会**让单链变大；进一只高价大票才会。

## Clarifications

### Session 2026-08-13

- Q: 「每视角独立请求」在 `052` 已经用 per-视角 override 满足了「不同视角不同过滤器」之后，还做不做？ → A: **仍做**。<br>代价与正当性前提已逐条写进 § 背景，MUST 在 PR body 复述。

- Q: 拆请求后七处 by-tab 响应结构怎么处置？ → A: **收窄成单视角**，按「链级 vs 视角级」切一刀（清单见 `FR-005`）。<br>定案依据：① mobile 侧七处消费**已经全是「取当前视角那一格」**（`leg-picker.rules.ts:103/131/146/291/379` + `leg-row.tsx:60,64` 的注释逐字写「由调用方取好那一格再传」）⇒ 收窄后客户端改动机械，且这些函数签名里的 `tab` 参数消失、调用点**编译期逐个点名** ② 顺手拆掉一个雷 —— `gateCounts` 现在是「全腿取标量 / 意图视角取分视角数」的分支取法，主 plan §2.3 那条「标量 ≠ build + rent，重叠区 `[30,49]` 双计，判据必须取不等式」的陷阱整条消失 ③ 保留 by-tab 是自相矛盾的：付了 DB 3x 却仍在每次响应里算并传另外两个视角。<br>🚨 **破坏性变更的爆炸半径已核实为零外部代价**：`FEATURE_MARKETS_ENABLED = process.env.EXPO_PUBLIC_FEATURE_MARKETS === 'true'`（`apps/mobile/src/core/feature-flags.ts`），EAS `production`（公开 / 商店）注入 `"false"` ⇒ optionsdesk 整栈被 `MarketsRouteGuard` 拦在门外；且它是 **build-time 内联**（Metro 打包时替换成字面常量）⇒ `eas update` 翻不动，公开构建**恒 off**。能打这些端点的客户端只有内测 / dev 构建，与 server 同 PR 更新。

- Q: 截断阈值 `N` 怎么定？ → A: **走实测标定**，沿 `050` T017 / `052` T016 的做法用 dev 全部链看「第 `N` 名之后还有没有值得看的腿」的分布。🚫 **若分布无断点则记为「不设 `N`」**，不许拍数（同 `052` T016 对单笔权利金下限的裁定）。<br>📌 标定判据 MUST 照着**认知负荷**设计而不是性能 —— `051` 真机实测 573 行虚拟化后只挂 16–17 个节点、零白屏、内存非单调有回收 ⇒ 「跑不动」不是本片的问题。

- Q: 预热怎么做（主 plan 只写了「预热」两字，无定义）？ → A: **错峰** —— 进详情页先只取当前视角，它落地后再后台并发取其余两个。<br>定案依据：首屏只付一份 payload（三视角并发约 670 kB，弱网下会明显拖慢首屏），切换仍零等待，且预取在秒级内完成 ⇒ 一致性窗口仍远小于「不预取」。

- Q: 三次请求跨交易日切换点落在不同业务日，怎么处置（主 plan 未决 #1）？ → A: **检测 + 重取** —— 复用契约里**已有的** `asOf`（区块级，每个响应都带），发现三个视角的业务日不一致即重取全部（最多一次），仍不一致则显式提示。<br>定案依据：① 跨交易日窗口里用户想看的是**最新**数据，钉住首个请求的业务日等于故意让后两个视角用旧数据，方向反了 ② **零新增契约字段** —— 主 plan 候选①「全量版本戳」想要的能力，`asOf` + `asOfFreshnessTier` 已经在了 ③ 「钉业务日」会引入新问题（客户端钉住旧业务日后看不到当天新数据，还得再配一套「服务端已有更新业务日 → 提示刷新」）。<br>📌 同场收窄：三个可变源里只有**时钟**是真开放的。**快照期**与业务日强相关（每天一次盘后采集窗），钉住业务日基本等于钉住它；**仓位水位**不是竞态而是用户自己的动作，有确定答案 —— 见下条。

- Q: 仓位水位在请求之间被改，只重取收租视角够不够？ → A: **不够，MUST 让三个视角全部失效重取**。<br>定案依据：主 plan 把这条写成「改水位 → 只影响 `rent` Tab」，**这个描述不成立**。水位 → `intent` → **推荐标**，而推荐标是**标的级、不随 Tab 变**（跨片不变量 #3，`051` `state_branches` 已钉死「标的级意图为收租、用户打开建仓 Tab → 推荐标按当前收租档带判」）⇒ 只重取收租视角会让另外两个视角继续用旧口径打标，**数字与标都在、只是口径不对，且不会红**。

- Q: 截断计数的措辞取哪个？ → A: **只带新信息** ——「已显示前 D 条 · 其余 N−D 条未显示」，**不复述「符合条件 N 条」**。<br>定案依据：「符合条件 N」与 sticky 区块头的那个数是**同一个数**，一屏内出现两次；两个数在一屏里长得不一样却相等，会被读成两个不同的量。<br>📌 代价与其消解：「符合条件的条数」改由区块头单独承担 ⇒ 两处必须同屏可见。**该前提由结构保证**（区块头在 sticky 栈内，滚到底部仍在屏上），并附「若区块头移出 sticky 栈则本条重审」的绊线。

- Q: `memberCount`（未覆盖条件下的候选数，供 sticky 区块头显「筛后 N · 全量 M」）下不下发？ → A: **下发**，服务端对**同一批已取回的链行**用「无覆盖」再跑一次召回判定得出。<br>定案依据：① **成本不是一次查库** —— `leg-retrieval.adapter.ts` 的 DB 层只下结构性谓词（`optionType: 'PUT'` + 快照日 + contract ids，`:51`/`:75`），六维判据是取回后跑纯函数 `recallCandidates(...)`（`:138`）⇒ 第二次判定是**纯 CPU**，同一批行、零额外往返 ② 没有它，用户在表上看不到「我筛掉了多少」的基准，而抽屉的「已改 N 项」徽标只答「改了几个维度」不答「少看到多少条腿」。<br>🚫 **MUST NOT 用 `052` 的六维边际计数加总充当它** —— 边际口径是「把这一维换回默认能多看几条」，被**两维同时挡下**的腿**两维都不计它**（`052` T010 有断言守）⇒ 加总**少报**，不是 `memberCount`。

- Q: `candidateCapDropped`（候选上限 `K` 的触及数）下不下发？ → A: **下发，且触及时按「异常」呈现**，与截断计数**不同款**。<br>定案依据：① **`K` 触及会让 `matchedCount` 静默失真** —— 它算在**已被 `K` 砍过**的集合上，于是「其余 N−D 条未显示」会少报，而条数与数值全都正常、**不会红** ② `K` 与 `N` 的语义与处置都不同：`K` 是给下游限流的保险丝（触及即系统异常，处置是调容量）、`N` 是用户可见条数（触及是正常呈现约定，处置是调展示）⇒ 呈现 MUST 可区分，MUST NOT 与截断计数混为一条。<br>🚫 **「下发但不呈现」被否** —— `050` 不变量 #12 明写「下发一批无人消费的字段会被『只加不删』永久锁死」。<br>📌 这与 `052` T005「`K` 的触及不进 `gateCounts`」不矛盾：那三个数是「判据挡下了什么」，这一个是「保险丝熔断了」，本条给它的正是**第三种**呈现，不是塞进那三个数里。

- Q: `052` 遗留的三项真机判据（抽屉是否真盖住底部 Tab 栏 / 输入法弹起后「搜」在不在屏内 / ⓘ 热区 44×44）在本片补验还是显式排除？ → A: **本片一并补验**，写进本片真机验收单。<br>定案依据：① 本片真机验收本就必跑（`SC-003` 列改版几何 + 切换手感）⇒ dev-client 装机 / 连 Metro / 打开屏的固定成本已经付了，加三项检查的**边际成本≈零** ② 它已经滑过一次 —— `052` tasks 的「故意零覆盖」登记写的是「mobile 增量零新视觉形态」，而 T012 的 mockup 绊线**实际触发了**并长出抽屉，该登记前提已失效 ③ 三项里「抽屉盖不盖得住底部 Tab 栏」若为否，是**功能缺陷**，越晚发现越贵，而本片动的正是同一屏。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 数据量大时，知道自己看到的不是全部 (Priority: P1)

某视角符合条件的腿超过该视角的截断阈值时，用户在列表末尾看到「已显示前 D 条 · 其余 N−D 条未显示」，明确知道列表被截了、还剩多少没看到、以及收窄的手段是什么。

**Why this priority**: 它是**截断这个动作的唯一补偿**。`050` 的权利金门槛已经部分推翻过 047 的「全量呈现原则」一次，代价靠计数补偿；本片是第二次推翻，不给计数就是第二次静默的数据消失。

**Independent Test**: 可独立验：构造一个成员数超阈值的视角，断言截断计数出现、取值正确、且与 `051` 那对门槛计数在措辞与位置上可区分。

**Acceptance Scenarios**:

1. **Given** 某视角符合条件的腿超过截断阈值，**When** 用户查看列表末尾的计数区，**Then** 看到实际显示的条数与被截掉的条数，且 sticky 区块头同屏给出符合条件的总数（两处不重复同一个数）
2. **Given** 某视角符合条件的腿未超过阈值，**When** 用户查看，**Then** 截断计数不出现，MUST NOT 显示一个刺眼的空值或恒等的两个数
3. **Given** 同屏已有 `051` 的两道门槛计数，**When** 截断计数一并出现，**Then** 两对计数各自语义清晰、MUST NOT 用同一个词把「被条件挡下」与「被截断」混成一件事
4. **Given** 用户在抽屉里收窄检索条件使结果降到阈值以下，**When** 结果更新，**Then** 截断计数消失
5. **Given** 列表被截断，**When** 用户滑到列表底部，**Then** MUST NOT 出现「加载更多」/ 分页控件 —— 收窄的唯一手段是抽屉里的检索条件
6. **Given** 某意图视角有腿被流动性条件排除，**When** 用户点该计数的入口切到全腿视角（`051` 已交付的路径），**Then** 那些被排除的腿**逐条可达** —— 全腿视角的截断阈值 MUST NOT 把它们吞掉

---

### User Story 2 - 一个视角出问题，不牵连另外两个 (Priority: P1)

三次独立请求里某一次失败、或三次响应落在不同业务日时，用户不会看到被清空的表，也不会静默看到混着两天的数据。

**Why this priority**: 这是「拆成三次请求」这个动作**新引入**的失败面 —— 047 的单次请求要么全成要么全败，不存在部分失败，也不存在跨业务日混用。不处置就是把两个新的故障模式静默留给用户。与 US1 同为 P1，因为它是本片自带代价的兜底，不是增强。

**Independent Test**: 可独立验：令某一个视角的请求失败，断言该视角显错误态而其余视角内容不变；另令三份响应带不同 `asOf`，断言触发一次重取且仍不一致时给提示。

**Acceptance Scenarios**:

1. **Given** 三个视角中某一个的请求失败，**When** 用户停在另一个视角，**Then** 当前内容不受影响
2. **Given** 某视角处于错误态，**When** 用户切到它，**Then** 看到该视角自己的错误态与重试入口，MUST NOT 显示成空态（「读失败」与「确实没有腿」是两件事）
3. **Given** 三个视角的响应落在不同业务日，**When** 客户端察觉，**Then** 自动重取全部一次；仍不一致时给显式提示，MUST NOT 静默混用两天的数据
4. **Given** 用户停在建仓视角，**When** 改仓位水位，**Then** 三个视角全部失效重取 —— MUST NOT 只重取收租视角

---

### User Story 3 - 切换视角不等待 (Priority: P2)

用户在三个视角之间来回切换时，不会每切一次就看一次加载态。

**Why this priority**: 纯体验。切换视角是这张表上最高频的动作（同一批腿换三种眼光看），而本片把「一次请求三份列表」拆成了三次独立请求 —— **不做预热，本片就是一次可感知的体验退化**。放 P2 是因为它不影响正确性。

**Independent Test**: 可独立验：进入详情页后不做任何操作，切到另一视角，测量到内容可见的等待时间。

**Acceptance Scenarios**:

1. **Given** 用户刚进入标的详情页，**When** 切换到另一个视角，**Then** 等待时间显著低于冷取（具体判据见 `SC-008`）
2. **Given** 用户在某视角内改了检索条件，**When** 切换到另一视角，**Then** 该视角呈现的是它自己的条件状态，MUST NOT 把上一个视角的条件带过去
3. **Given** 后台预取某视角时失败，**When** 用户停在当前视角，**Then** 当前视角零感知；切过去时才看到该视角自己的错误态与重试入口

---

### User Story 4 - 一次横滑就能凑齐一次判断 (Priority: P2)

用户判断「这单值不值得挂、挂不挂得出去」时，需要的几个量集中在一次横滑内，而不是散在表的两端要横滑两次。

**Why this priority**: 纯体验改善，与查询下沉正交（不依赖前三条，也不被它们依赖）。放 P2 是因为它不影响正确性，但它是这张表日常使用频次最高的痛点。

**Independent Test**: 可独立验：在最大真实链上横滑一次，断言判据集诸列同屏可见，且横滑几何（首列冻结宽度 / 内容总宽 / 指示条长度比）与 `049` 逐字相同。

**Acceptance Scenarios**:

1. **Given** 用户在选约表上，**When** 横滑一次，**Then** `bid` / `ask` / 折算费率 / 单笔权利金同屏可见
2. **Given** 用户要比对双边报价定挂单价，**When** 查看报价列，**Then** `bid` 与 `ask` 是**两列**、各自独立可读
3. **Given** 列集已改版，**When** 用户横滑到最右端，**Then** 末列完整露出，首列冻结宽度不变

---

### Edge Cases

- **某视角成员数恰等于截断阈值** → 不算截断，截断计数不出现（边界取「严格大于才截」）
- **收窄条件把结果从超阈值降到阈值以下的那一刻** → 截断计数必须消失而不是停在旧值
- **用户在请求飞行途中切换视角** → 迟到的响应 MUST NOT 覆盖当前视角的内容
- **用户在跨交易日切换点前后各触发一次请求** → 见 `FR-020`（唯一结构性、不靠概率的一致性缺口）
- **仓位水位在两次请求之间被改** → 三个视角全部失效重取（`FR-021`）
- **链未就绪 / 跨 context 读故障** → 沿用既有的两个显式状态，本片不改其行为
- **标定裁定「不设 `N`」** → 截断相关的呈现整体不落地，`FR-010`–`FR-019` 退化为「零截断」的显式登记，而非留一个恒不触发的空实现
- **列改版使内容总宽变化** → MUST 由后置列压缩吸收，MUST NOT 改首列宽（否则真机上表现为「右侧滑不到底」且不会红）

## Requirements _(mandatory)_

### 每视角独立请求与响应收窄（US2 · US3）

- **FR-001**: 每个视角 MUST 各自独立取数，请求 MUST 携带该视角标识与该视角自己的检索条件覆盖（复用 `052` 已 ship 的 `perspective` + 六维 query 参数，本片 MUST NOT 新增筛选维度）。
- **FR-002**: 每次取数 MUST 只返回该视角的腿，MUST NOT 把三个视角的腿合并下发。呈现顺序 MUST 取自服务端下发的顺序，客户端 MUST NOT 重排（继承 `051`，本片不放松）。
- **FR-003**: 检索 port 的签名 MUST 零改动 —— `052` 已把 `perspectives` 立在接口上。本片改的是调用方与 controller。
- **FR-004**: 服务端处理顺序 MUST 为 **召回（含用户覆盖 + 候选上限 `K`）→ 粗排 → 特征加工 → 精排 → 表达层截断 `N`**。截断 MUST 发生在精排之后。
- **FR-005**: 响应 MUST 按「链级 / 视角级」收窄。这是**破坏性变更**，与 `050`/`051` 的「只加不删」不同（可行性前提见 `FR-006`）：

  | 层                 | 字段                                                                                                                                                                                            | 处置                                                     |
  | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
  | 链级（不随视角变） | `symbol` · `state` · `asOf` · `asOfFreshnessTier` · `quoteAsOf` · `oiAsOf` · `source` · `spot` · `w` · `zone` · `lLevel` · `positionBucket*` · `intent` · `rentDepth` · 权利金移出数            | 每次请求照传（三次响应里恒等，正是 `FR-020` 的检测判据） |
  | 视角级             | `tabOrder` → **删**（数组顺序就是顺序）· `basisByTab` → 标量 `basis` · `criteriaByTab` → `criteria` · 分视角流动性排除数 → 标量 · 每腿 `tierByTab` → `tier` · 每腿 `activityByTab` → `activity` | 收窄成单份                                               |
  | 删除               | 每腿 `tabs`                                                                                                                                                                                     | 拆后恒等于当前视角，零信息量                             |
  | 新增               | `perspective`（回显）· `displayLimit`（该视角的截断阈值）· `matchedCount`（当前条件下符合条件的总数）· `memberCount`（**无覆盖**条件下的候选数）· 候选上限 `K` 的触及数                         | —                                                        |

  🚫 **`tabOrder` MUST 删而非收窄** —— 数组顺序**就是**顺序，再下发一份 code 列表是同一信息的第二份表达，必 drift。
  🚫 **实际显示条数 MUST NOT 下发** —— 它恒等于 `legs.length`；被截掉的条数同理由 `matchedCount − legs.length` 现算。下发第二份必 drift。

- **FR-006**: 本片的破坏性契约变更 MUST 在 spec 与 PR body 显式登记。📌 其可行性前提是**不存在旧客户端**：本片跨端走单 PR（Constitution §V），且 optionsdesk 整栈在公开构建里被编译期 flag 关闭、OTA 不可翻转（详见 § Clarifications 第二问）。
- **FR-007**: 每个视角 MUST 各自保留自己的检索条件状态；切换视角 MUST NOT 把上一个视角的条件带过去（`052` T012 已 ship，本片 MUST 保持不回退）。
- **FR-008**: 迟到的响应 MUST NOT 覆盖用户已切走的视角或已变更的条件所对应的内容。
- **FR-009**: `memberCount`（无覆盖条件下的候选数）MUST 由服务端对**同一批已取回的链行**用「无覆盖」再跑一次召回判定得出，MUST NOT 为它多查一次库。<br>🚫 MUST NOT 用 `052` 的六维边际计数加总充当它 —— 边际口径下被**两维同时挡下**的腿两维都不计它，加总**少报**。<br>📌 未覆盖任何条件时 `memberCount === matchedCount`，此时区块头 MUST NOT 并列显示两个相等的数。

### 截断与截断计数（US1）

- **FR-010**: 服务端 MUST 在精排之后按视角的阈值截断，判据为「**严格大于阈值才截**」。
- **FR-011**: 截断阈值 MUST **可注入**（默认取常量）。📌 这是 `FR-014` / `SC-006` 的落地手段。
- **FR-012**: 阈值 MUST **按视角分档** —— 全腿视角与两个意图视角的成员规模差一个量级，一律取同一个数会让其中一档要么形同虚设、要么砍掉不该砍的。
- **FR-013**: 各视角阈值 MUST 由**实测标定**产出，沿 `050` T017 / `052` T016 的分布分析做法。🚫 **若分布无断点，MUST 记为「不设该视角的阈值」而非拍一个数。**
- **FR-014**: 🚨 全腿视角的阈值 MUST 高于「`051` 那个入口所指向的腿仍可达」所需的规模 —— `051` ship 了「流动性排除数点击 → 切到全腿视角看被排除的腿」这个入口，全腿视角一旦截在那些腿之前，该入口就指向一张不含目标的表，**且不会红**。本片 MUST 有断言覆盖「被意图视角排除的腿，在全腿视角内可达」。
- **FR-015**: 链规模逼近任一阈值时 MUST 可被观测（不依赖读日志），使阈值失配是一个**可发现**的事件而非静默截断。<br>📌 **由 `FR-005` 结构性兑现，零新增字段** —— `matchedCount` 与 `displayLimit` **恒同时下发**（含未触发截断时），逼近度 `matchedCount / displayLimit` 因此随时可算。<br>⚠️ **前提是「未截断时也下发 `displayLimit`」** —— 若只在截断时下发，「逼近」恰恰观测不到，而那正是本条要防的静默。<br>🚫 MUST NOT 为此新增 `isNearLimit` 之类的派生布尔 —— 它可由两数算出，下发第二份必 drift（`050` 不变量 #12）。
- **FR-016**: 截断生效时 MUST 在 `051` 已定的**非常驻区**槽位（MUST NOT 进 sticky 栈）显式呈现**实际显示的条数**与**被截掉的条数**，措辞形如「已显示前 D 条 · 其余 N−D 条未显示」。<br>🚫 MUST NOT 在此处复述「符合条件的条数」—— 该数已由 sticky 区块头承担，同屏重复出现会被读成两个不同的量。<br>📌 **成立前提由结构保证**：区块头在 sticky 栈内，滚到列表底部时它仍在屏上 ⇒ 两处恒同屏可见。若将来把区块头移出 sticky 栈，本条 MUST 重审。
- **FR-017**: 截断计数 MUST 附一句指向**抽屉内检索条件**的收窄指引 —— 因为分页与「加载更多」都不存在（`FR-019`），不给指引等于告诉用户「还有 N 条，但你够不到」。
- **FR-018**: 本片这对计数与 `051` 那对门槛计数 MUST 可区分：语义不同（被条件挡下 vs 被截断）、措辞 MUST NOT 混用同一个词。未触发截断时 MUST NOT 占据视觉重量，MUST NOT 显示刺眼的空值或恒等的两个数。
- **FR-019**: MUST NOT 提供分页 / 「划到底再加载」/ 「加载更多」以抵达被截断的腿 —— 收窄的唯一手段是检索条件（继承 047 `FR-005` 对分页的禁令，本片不放松）。
- **FR-019a**: 本片对 047 `FR-005`「全量呈现原则」及其端点契约声明（`Leg picker table (ALL eligible legs, no pagination, no top-N)`）构成**第二次部分 supersede**（第一次是 `050` 的权利金门槛）。该 supersede MUST 在本片 spec 与 PR body 显式登记，MUST NOT 当作无感知升级。
- **FR-019b**: 本片同时使 047 的「**切 Tab 不重新请求**」承诺整条作废。该作废 MUST 在 spec 与 PR body 显式登记。
- **FR-019c**: 候选上限 `K` 的触及数 MUST 下发；触及时 MUST 按**异常**呈现，且 MUST 与截断计数**不同款**（截断是正常的呈现约定，`K` 熔断是系统异常，处置一个调展示、一个调容量）。<br>🚨 存在理由：`K` 触及会让 `matchedCount` **静默失真** —— 它算在已被 `K` 砍过的集合上，于是「其余 N−D 条未显示」少报，而条数与数值全都正常、**不会红**。⇒ 触及时的提示 MUST 说明该数可能不完整。<br>📌 与 `052` T005「`K` 的触及不进 `gateCounts`」不矛盾：那三个数是「判据挡下了什么」，本条给 `K` 的是**第三种**呈现，不是塞进那三个数里。

### 一致性与失败隔离（US2）

- **FR-020**: 系统 MUST 检测「三个视角的业务日不一致」并自动重取全部（**最多一次**）；重取后仍不一致 MUST 显式提示，MUST NOT 静默呈现来自不同业务日的数据，也 MUST NOT 无限重取。<br>📌 检测 MUST 复用契约里**已有的** `asOf`，MUST NOT 为此新增版本戳字段。
- **FR-021**: 仓位水位被改时，**三个视角 MUST 全部失效重取**，MUST NOT 只重取收租视角。<br>📌 存在理由：水位 → `intent` → **推荐标**，而推荐标是**标的级、不随 Tab 变**（跨片不变量 #3）⇒ 只重取收租视角会让另外两个视角继续用旧口径打标，**数字与标都在、只是口径不对，且不会红**。这条**修正了主 plan 未决 #1 里「改水位只影响 `rent` Tab」的描述**。
- **FR-022**: 单个视角的失败 MUST 被隔离：该视角显自己的错误态与重试入口，其余视角已取得的数据 MUST NOT 被清空或降级。**MUST NOT 把读失败呈现成空态。**
- **FR-023**: 「两次请求落在不同业务日」这一情形 MUST 可被观测（不依赖读日志）。

### 预热（US3）

- **FR-025**: 预热 MUST 为**错峰**形态：进入详情页时 MUST 只取当前视角；该视角落地后 MUST 在后台取其余两个。MUST NOT 在首屏并发取三份（三视角并发约 670 kB，弱网下拖慢首屏，且其中两份用户可能永远不看）。
- **FR-026**: 后台预取 MUST NOT 干扰前台：其失败 MUST NOT 影响当前视角的呈现（切过去时再按 `FR-022` 显该视角自己的错误态），其完成 MUST NOT 引起当前视角的重渲染抖动。
- **FR-027**: Tab 行 MUST NOT 出现错误 / 加载角标 —— 后台预取对前台零感知是 `FR-026` 的直接推论。

### 列改版（US4）

- **FR-030**: 12 列的**列序** MUST 改为（mockup 2026-08-13 定稿）：

  | #   | 列                        | 宽  | #   | 列        | 宽  |
  | --- | ------------------------- | --- | --- | --------- | --- |
  | 1   | `行权价/到期`（**冻结**） | 88  | 7   | `成本vsW` | 56  |
  | 2   | `bid/ask`（**保持合并**） | 88  | 8   | `Δ`       | 42  |
  | 3   | `折算费率`（列头即口径）  | 56  | 9   | `Vol`     | 46  |
  | 4   | **`单笔权利金`（新）**    | 50  | 10  | `活跃`    | 42  |
  | 5   | `OI`                      | 50  | 11  | `标注`    | 84  |
  | 6   | **`相对价差`（新）**      | 48  | 12  | `动作`    | 66  |

  📌 存在理由：`bid/ask` → `折算费率` → `单笔权利金` 是「这单值不值得挂、挂不挂得出去」的完整判据集，此前散在表的两端，用户要横滑两次才能凑齐一次判断。本序把它们聚成相邻三列，**一次横滑即可凑齐**。

- **FR-031**: `bid` 与 `ask` MUST **保持合并为一列**（单元格内 2 行 × 2 列：价格并排在上、挂牌量并排在下）。<br>🚫 **本条为 2026-08-13 订正** —— 起草时写的是「MUST 拆成两列」，理由是「共用一格时不便比对」。核过实装后该理由不成立：现状已是 2×2 网格并排，比对问题早已解决；而拆开后每列仍要各容一个价格 + 挂牌量，合计比现在的 88 更宽 ⇒ 为一个已被解决的问题多付 16px 预算。
- **FR-032**: **单笔权利金**（= `bid` × 合约乘数）MUST 由服务端计算并下发。<br>🚫 MUST NOT 由客户端乘一次 —— 合约乘数是市场规则不是合约属性，服务端已持有该常量（成交额在用它），客户端再乘就是同一判据两处各算一份（ADR-0064 不变量 ③）。
- **FR-033**: 列宽合计 MUST 恒为 **716**、首列冻结宽 MUST 恒为 **88** —— 横滑几何（内容总宽 / 指示条长度比 / 位移语义）不被触碰（继承 `049`）。🚨 改了在真机上表现为「右侧滑不到底」**且不会红**。
- **FR-034**: 新增两列的预算 MUST 由**删列**吸收，🚫 MUST NOT 靠缩小字号或减内边距硬塞（折行在 web 视口看不出来、真机才炸）。删的两列与其判据：

  | 删       | 省  | 判据                                                                                                                                                                                                               |
  | -------- | --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | `σ距`    | 46  | **零信息损失** —— `leg-row.rules.ts` 文件头逐字写明「Δ 与 σ距 是同一个 `absDelta` 的两种呈现（`\|Δ\| = Φ(−σ距)`），两列 MUST 同时有值或同时留占位」⇒ 由构造一一对应。留 Δ 是因为它带推荐标的判据（副标「带判据」） |
  | `成交额` | 52  | 可由 `Vol × 价格 × 合约乘数` 心算；且 `052` T007 实测流动性的有效信号是 **OI + 成交量**（按 OI 分组时相对价差几乎不动、反过来按价差分组时 OI 中位数非单调）⇒ 成交额是第三顺位衍生量                                |

  `46 + 52 = 98` 恰好填平 `单笔权利金 50 + 相对价差 48`。🚫 **MUST NOT 改砍 `活跃` 或 `标注`** —— 前者是 `052` T009 刚重做的活跃标、后者是 `051` 刚 ship 的「贴合」「月」标，砍掉等于废掉前两片的交付。

### 判据单点

- **FR-035**: 排序与截断 MUST 由与既有纯函数判据**等价**的实现产生。系统 MUST NOT 存在第二份会独立漂移的判据实现。<br>📌 存在理由：阈值 / 排序键在两处各写一份时，drift **不会红** —— 两边各自都算得出数，只是不是同一个数。<br>📌 `052` 立的检索 port 已把这条变成机器判据：port 接口内 `rg` 扫 `Prisma` / `sql` / `cursor` / `offset` / `limit` 必须零命中（守门脚本不变量 #5）⇒ 任何把 `ORDER BY … LIMIT` 下沉到数据层的做法都会当场撞守门。

### 真机验收（含 `052` 遗留补验）

- **FR-036**: 本片真机验收 MUST 覆盖 `052` 遗留的三项 Expo Web 验不到的判据：① 检索条件抽屉**是否真盖住底部 Tab 栏** ② 输入法弹起后「搜」按钮**是否仍在屏内** ③ ⓘ 提示的热区是否达 44×44。<br>📌 存在理由：本片真机验收本就必跑（`SC-003`），三项的**边际成本≈零**；而它们已因 `052` 那条「mobile 增量零新视觉形态」的登记前提失效而滑过一次（T012 的 mockup 绊线实际触发并长出了抽屉）。其中 ① 若为否是**功能缺陷**，而本片动的正是同一屏。

### 跨片不变量遵从（继承，本片零改动）

- **FR-040**: 截断 MUST 在排序之后（不变量 #4 后半句）。
- **FR-041**: `tier` 跟视角走，全腿视角恒用年化档界（不变量 #5）。
- **FR-042**: 排名特征集 MUST NOT 进入契约（不变量 #12）。可解释性由已在表上的费率列承担。
- **FR-043**: 045 的锚派生规则与意图矩阵 MUST 零改动（不变量 #13）。
- **FR-044**: 召回 / 打标 / 精排的判据本身 MUST 零改动 —— 本片只改它们被调用的位置与时机。
- **FR-045**: `052` 的六维检索条件、抽屉 UI、三态边际计数 MUST 零改动 —— 本片只消费。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 在本机可达的**最大真实链**上，三个视角均能各自取数并呈现，无白屏、无卡顿感知。📌 判据取「最大真实链」而非固定行数 —— `051` 已实证固定行数会随判据变化而不可达。
- **SC-002**: 收窄后的契约与客户端 by-tab 残留为零 —— 生成的 OpenAPI schema 与 `apps/mobile/src/optionsdesk/` 内 `rg` 扫 `tabOrder` / `basisByTab` / `criteriaByTab` / `tierByTab` / `activityByTab` 及 `xxxByTab[tab]` 索引形态**零命中**。
- **SC-003**: 列改版后真机 sticky 栈占屏比 **≤ 35%**，数据区可见行数 ≥ 3 行，且横滑到最右端末列完整露出。📌 基线 = `051` 实测 138.5dp / 27.9%；**MUST 用真机实测复核，MUST NOT 用 web 读数**。
- **SC-004**: 截断生效的每一种情形下，截断计数 100% 出现，且「已显示」与「未显示」两数之和恒等于符合条件的总数；未触发时 100% 不出现。
- **SC-005**: 计数区与 sticky 区块头**不出现同一个数值**（`FR-016` 的可验证形态）。
- **SC-006**: 截断相关分支的自动化覆盖**不依赖真实链规模** —— 该覆盖手段在真实数据恒不触发截断的视角上同样有效。
- **SC-007**: 排序 / 截断的判据只有一份实现，且「截断作用在已排序序列的尾部」有断言，并**已证明它会红**。
- **SC-008**: 预取已完成的视角，切换过去 MUST NOT 出现可见的加载态；预取未完成时降级为正常加载态而非空态。首屏耗时 MUST NOT 因预热而劣于「只取一个视角」的基线。
- **SC-009**: 单视角失败时，其余视角内容零变化；错误态与空态在界面上可区分。
- **SC-010**: 跨交易日切换点上的一致性处置有可复现的验证（该场景 MUST 可被构造，MUST NOT 只靠等真实切换点）。
- **SC-011**: 本片对 047 `FR-005` 的 supersede 与对「切 Tab 不重新请求」的作废，在 spec 与 PR body 均有显式登记。
- **SC-012**: 在**最大真实链**上，被意图视角的流动性条件排除的腿，**100% 可在全腿视角内被找到**（`051` 那个入口的回归防线，不是新功能验收）。
- **SC-013**: 仓位水位改动后，三个视角的推荐标口径**逐条一致**（`FR-021` 的可验证形态）—— 断言 MUST 覆盖「用户停在建仓视角时改水位」这条最容易漏的路径。
- **SC-014**: 各视角截断阈值的取值与**推导过程**写回本 spec，代码内零处未标定的占位常量；若某视角裁定「不设阈值」，该裁定与其判据同样写回。
- **SC-015**: `memberCount` 与 `matchedCount` 的关系有断言：未覆盖时两者相等且区块头不并列显示两个相等的数；收窄后 `memberCount > matchedCount`。且 `memberCount` 的计算**零额外 DB 往返**（同一批已取回行上的第二次纯函数判定）。
- **SC-016**: 候选上限 `K` 触及时其触及数下发且呈现可与截断计数区分；未触及时该呈现 100% 不出现。**已证明它会红**（人为把 `K` 注入成小值一次，触及呈现必须出现）。
- **SC-017**: `052` 遗留的三项真机判据在本片验收单上逐条有读数（抽屉盖住 Tab 栏 / 输入法弹起后「搜」在屏内 / ⓘ 热区 44×44），且结果写回本 spec。
- **SC-018**: 列宽合计恒 `716`、首列恒 `88` 有**机器断言**（对 `LEG_TABLE_COLUMNS` 求和），且改版前后该断言取值不变。📌 这条挡的是「顺手调一列宽度」——它在真机上表现为右侧滑不到底，而 typecheck 与 e2e 都不会红。
- **SC-019**: 表头在各自列宽内**零折行**，判据取真实最宽内容（`成本vsW` 在 56px 内、`bid/ask` 深实值腿两位数价格在 88px 内、单笔权利金四位数在 50px 内）。📌 mockup 期实测：表头字号 11px 时 `成本vsW` 折行，10px 才不折 ⇒ 实装若沿用别的字号，该列宽 MUST 重算。

## Assumptions

- **本片是跨端片** ⇒ 按 Constitution §V 走**单 PR**（server impl + 真后端 IT + `export-openapi` + `api-client` regen + mobile 消费同 PR），并落 `[Contract-Smoke]`。
- **拆成每视角独立请求是架构投资，不是性能优化** —— DB 查询 3x、首屏不变快、切视角多一次往返，三笔代价清醒付；换来的是「三套条件同时生效」与为多路召回 / 每视角不同数据源留的接口。这一取舍 MUST 写进 PR body。
- **截断的收益当前为零或负，仍照做** —— owner 定案，为未来的大链提前铺路。
- **规模的驱动量是单只票的价位，不是标的池大小** —— 链大小 = 到期日数（16–17，几乎恒定）× 行权价档数（49→116）。标的池从 12 只扩到 500 只不会让单链变大。
- **检索条件维度不新增** —— 六维已由 `052` ship，本片只消费（`FR-045`）。
- **`052` 的检索 port 是判据与存储的接缝** —— 本片 MUST NOT 改其签名，也 MUST NOT 让存储侧概念漏进它（`FR-035`）。
- **「拆成三次请求」自己制造了两个新问题** —— 一致性（`FR-020`）与部分失败（`FR-022`）在 047 的单次请求下都不存在。它们是本片的自带代价，不是外部约束。
