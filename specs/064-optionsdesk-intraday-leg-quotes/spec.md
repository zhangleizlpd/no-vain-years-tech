# Feature Specification: 美股期权腿盘中实时报价

**Feature Branch**: `064-optionsdesk-intraday-leg-quotes`
**Created**: 2026-08-19
**Status**: Planned
**Input**: 选约表与链分析报表读的是「最近一期交易日的全链快照」，而美股收盘采集跑在北京 06:30 —— 于是用户在美股盘中打开选约表，看到的是**上一交易日收盘的盘口**，却要据此决定卖哪一档。本 feature 让盘中的报价与候选集都走此刻的真实数据，且**零落库、零新表、零采集维度**：不留历史，只在被读的那一刻取一次。

## Clarifications

### Session 2026-08-19

- Q: 下拉刷新后候选集成员变了，怎么处理？ → A: 每次下拉刷新按此刻口径整体重新召回，并显式提示这一轮进出了哪些腿（成员**不**锁定 —— 锁定会让已不满足判据的腿留在表里，用户据此下单等于拿到一个判据没批准的腿）
- Q: 首屏与刷新时，实时那一批没到齐之前屏上显什么？ → A: 阻塞到齐再渲染 —— 首屏走 loading 态，下拉刷新时保留当前表直到新一批到齐再整体替换。**不**先渲染库内收盘档再覆盖（那会在首屏制造一次「按昨收召回 → 按此刻召回」的伪成员变化，正好撞上上一条）
- Q: 定窗的标的现价与召回 / 呈现用的现价，分别从哪来？ → A: 窗的边界用**实时底座已在维护的盘中价**算（它只是个包络，≤ 一个 tick 的陈旧可接受）；把标的自身放进同一批请求，取回的**同刻**现价用于召回判据与表头呈现。保住「一次页面加载 = 1 次外呼」，且判据吃到的现价与腿报价同刻
- Q: 降级发生时，运维侧怎么看得见？ → A: 通道级健康**复用实时行情底座已有的观测面**，本片不重复建心跳（底座 30 秒一拍，比按需触发的本片敏感得多）；本片只为**自己特有**的三类失败（部分合约未返回 / 窗超单批上限 / 定窗基准陈旧）留可聚合的痕迹 —— 那三类底座永远遇不到，它只取几十个正股码

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 盘中看到的是此刻的盘口，且看得出它是此刻的 (Priority: P1)

用户在美股常规交易时段打开某只锚的选约表。表里每条腿的买价 / 卖价 / 买卖挂单量 / Δ / 隐含波动率 / 成交量，以及表头的标的现价，都是**此刻**的，不是昨天收盘的。区块上方的时间显示为**时刻**（而非一个日期），下拉刷新后这个时刻向前推进。

当数据取不到此刻的值时（非交易时段、源故障、部分合约缺失），用户**一眼能看出这批数不是实时的**，而不是拿到一份看起来正常、实际上是昨收的表。

**Why this priority**: 这是本 feature 的全部理由 —— 用户拿盘口做卖出决策，昨收的买价卖价对这个决策没有意义。而「档位可辨」不是它的增强而是它的前提：只给实时值、不给档位标记，等于把「昨收」伪装成「此刻」，制造一个比现状更危险的静默失效面（现状至少口径是一致的昨收）。两者一起才是最小可用切片。

**Independent Test**: 美股盘中真机打开选约表，逐条与外部行情终端对拍买价 / 卖价 / 成交量；下拉刷新观察时刻推进。再分别构造非交易时段、源不可达、部分合约缺失三种情形，确认档位标记出现且数值未被清零。

**Acceptance Scenarios**:

1. **Given** 美股处于常规交易状态且当日为交易日，**When** 用户打开选约表，**Then** 每条腿的买价 / 卖价 / 买卖挂单量 / Δ / 隐含波动率 / 成交量与表头标的现价均为此刻的值，区块时间呈时刻
2. **Given** 用户已在选约表页面上，**When** 用户下拉刷新，**Then** 区块时间推进到新的时刻，且腿上的报价随之更新
3. **Given** 美股已收盘（或当日非交易日），**When** 用户打开选约表，**Then** 呈现收盘档数据，区块时间呈交易日，且界面明确标出这是收盘档而非实时档
4. **Given** 外部行情源不可达或超时，**When** 用户打开选约表，**Then** 整表回落收盘档、显式标出降级，且没有任何一项数值被显示为 0 或空白顶替
5. **Given** 外部行情源返回了大部分但非全部合约，**When** 用户打开选约表，**Then** 取到实时值的腿标实时档、未取到的腿保留收盘值并**逐行**标收盘档 —— 整页不因少数几行而统一降级
6. **Given** 任意档位，**When** 用户查看某条腿的持仓量，**Then** 该列的归属日恒为收盘档的归属日，且**不**随实时档变成当天

### User Story 2 - 候选集本身按此刻的口径召回 (Priority: P2)

三个视角（全部 / 建仓 / 收租）的候选集，其成员判据吃的是**此刻**的报价与标的现价，而不是昨收。于是：昨天权利金过低被门槛挡下、今天涨上来的腿，今天盘中就会出现在候选里；反之亦然。

**Why this priority**: US1 单独 ship 已经可用 —— 用户至少看到的每一行都是此刻的真数。但只要候选集还按昨收筛，用户就看不到「今天才变得值得卖」的那些腿，也会看到几条今天已经不合格的。它是 US1 的实质增强，不是它的前提。

**Independent Test**: 造一组腿，其收盘值落在召回门槛之外、而实时值能通过判据（以及反向的一组），断言候选集成员随口径切换而变化，且切换的**唯一**触发点是档位而非任何新增的筛选逻辑。

**Acceptance Scenarios**:

1. **Given** 某腿的收盘权利金低于门槛而此刻权利金高于门槛，**When** 在实时档下检索候选集，**Then** 该腿出现在候选集内
2. **Given** 某腿的收盘值可过判据而此刻值不能，**When** 在实时档下检索候选集，**Then** 该腿不在候选集内
3. **Given** 同一次请求，**When** 用户查看候选集与整条链，**Then** 两者读到的是同一批行、同一个报价时刻 —— 不存在「候选按此刻筛、链按昨收显示」的混合口径
4. **Given** 跳空开盘的一天，**When** 在实时档下检索候选集，**Then** 定义候选范围的价格区间以**此刻**的标的现价为基准，而非昨收
5. **Given** 某腿在上一次取数时满足判据、此刻不再满足，**When** 用户下拉刷新，**Then** 该腿从表中移除，且界面告知本轮「已不满足 1 条」—— 移除不是一次无声的重排

### User Story 3 - 单次取回装不下整个候选范围时不出现混合时刻 (Priority: P3)

当某只标的的候选范围超过一次可取回的合约数上限时，系统仍然不能让同一张表里的腿处在两个不同的报价时刻。

**Why this priority**: 今天用不上 —— 现有 13 只美股锚的候选范围最大 285 个合约，全部在单次上限之内。它是为将来接入周期权极密的标的（合约数量级更高的那类）留的正确性约束。晚做不影响 US1 / US2 的任何一条验收。

**Independent Test**: 把单次上限调到一个小值驱动超限路径，断言结果要么是同一时刻的一批、要么显式降级，且区块时间取的是最保守（最早）的那个。

**Acceptance Scenarios**:

1. **Given** 候选范围内的合约数超过单次可取回上限，**When** 用户打开选约表，**Then** 表内不存在两条来自不同报价时刻的腿被当作同一时刻呈现
2. **Given** 上述情形且系统选择分批取回，**When** 结果返回，**Then** 区块级时间取最早那批的时刻（偏保守），而非最晚那批

### Edge Cases

- **美股收盘后到当日收盘采集跑完之间的那段**（常规交易日约北京 04:00–06:30；⚠️ **半日市当天美股 13:00 ET 就收盘，该窗更长**）：实时档已关闭，而当日的收盘快照尚未落库 ⇒ 用户看到的是**再上一个交易日**的收盘档。这是现状既有行为，本 feature 不改变它，但实时档关闭后回落到的"收盘档"具体是哪一天，界面必须如实呈现该批数据自己的归属日，MUST NOT 显示成当天。
- **正在看的那一行消失**：实时召回意味着候选集在盘中会变。用户盯着某条腿准备下单时，它可能因价格移动而不再满足判据。这是**要的行为**（判据没变，是数变了）。由于取数只在进入页面与下拉刷新时发生，这件事**不会在用户眼皮底下自发出现**；它只会发生在刷新那一刻，且必须随刷新结果一并告知（FR-021）。
- **库内零快照行**（2026-08-19 订正）：新建的锚在首次收盘采集跑过之前，库内**有合约行、没有快照行** —— 原文写成「没有合约行也没有快照行」是**事实错误**：锚首建冷启动的第一相（链发现 + 日线）不受盘中判据约束，合约集当场就落库了；撞盘中闸的只有第二相的期权快照。⇒ 缺的只是「上一交易日的收盘快照」，而那份盘中根本取不到（vendor 的 snapshot 接口不吃时间参数）。实时源能给报价、也能给持仓量，于是本条的结局改为：开态且实时批取回成功 ⇒ 以那一批实时为基线成链；否则维持「未就绪」（见 `state_branches` 第 9 条与 FR-004a）。
- **实时源返回了库内没有的合约**：盘中新挂的合约。本 feature 不在盘中重跑链发现（见 Assumptions），这些合约当日不可见。
- **单条腿的部分字段为空**：外部源对某些合约只给部分字段。按「该行未取到实时」整行处理，MUST NOT 逐字段拼接出一行半实时半昨收的数据 —— 那种行没有任何一个时刻能解释它。
- **成交量与成交额的口径切换**：实时档下这两项是「截至此刻累计」，收盘档下是「当日最终」。同一个数字在两个档位下含义不同，用户若不知情会以为成交量缩水了。
- **跳空日**：定义候选范围的价格区间以标的现价为基准。用昨收算与用此刻算，在跳空日偏差最大 —— 这正是本 feature 最有价值也最容易出错的一天。
- **定窗基准本身不可用**：实时行情底座尚未写过盘中价（当日首拍之前），或它已陈旧到被底座自己判为不可用。此时窗无从定起 ⇒ 整体回落收盘档并标降级。MUST NOT 退而用收盘价定出一个窗来、却仍把结果标成实时档 —— 那是用一个昨天的边界去圈今天的合约，且外表看不出来。

## Requirements _(mandatory)_

### Functional Requirements

**取数与覆盖**

- **FR-001**: 系统 MUST 在美股常规交易状态且当日为交易日时，为候选范围内的全部合约取回此刻的报价，并以之覆盖库内收盘档的对应值。
- **FR-002**: 被覆盖的值 MUST 限于消费方实际使用的那些：买价、卖价、买挂单量、卖挂单量、Δ、隐含波动率、成交量，以及链级的标的现价与报价时刻。其余落库列（其它希腊值 / 最新价 / 昨收价 / 净持仓量）当前**无任何消费方**，MUST NOT 纳入覆盖 —— 覆盖没有读者的值只是无收益的成本。
- **FR-002a**（2026-08-19 补，原枚举遗漏）: **greeks 完整性标 MUST 随 Δ / 隐含波动率一起翻**。它不是第八个值，而是**描述那两格的标**：那两格已换成此刻的数、标却留着收盘档的结论时，两个方向都产出错误且都渲染得出来 —— 收盘档 greeks 缺失而此刻齐全 ⇒ 呈现侧按标把已在手的 Δ 掐成空、不判档不着色；收盘档齐全而此刻两格皆空 ⇒ 契约上声称「greeks 齐全」而两格是空。本条不是对 FR-002 的例外，而是它那句判据（「限于消费方实际使用的那些」）的应有之义 —— 该标**有**消费方，只是没被写进枚举。
- **FR-003**: 由上述值**派生**的量（成交额、单笔权利金、买卖价差及其相对值等）MUST 随之自动成为实时口径，MUST NOT 为它们另设一条覆盖路径 —— 派生量有第二个来源就等于同一个数在两处各算一份。
- **FR-004**: 持仓量、净持仓量及其归属日 MUST 恒取收盘档的值，MUST NOT 被实时值覆盖。理由是实测：美股期权持仓量在盘前更新、盘中冻结 ⇒ 盘中取回的与库内是同一个数，而把它的归属日标成当天是拿标签掩盖真实归属。
- **FR-004a**（2026-08-19 补，随 `state_branches` 第 9 条改写）: FR-004 的「恒取收盘档」以**存在收盘档基线**为前提。库内一期快照都没有时（新锚盘中首访），该前提不成立 —— 此时持仓量 MUST **整批**取自同一次实时返回，且链级归属日 MUST 取最近一个已收盘交易日（美股期权持仓量盘前更新、盘中冻结 ⇒ 此刻取回的那个数归属的正是上一场收盘）。🚫 MUST NOT 把它做成「这一格空了就用实时填」的单元格级规则：那会在**有**收盘档基线的链上，把一个归属 T−1 的数放进一张标着 T−2 的表里，而整页渲染正常、数字真实、只是差一天。⇒ 判据的颗粒度是「整条链的基线来自哪一批」，不是「单个格子空不空」。
- **FR-005**: 候选范围 MUST 由既有召回判据的常量**派生**，MUST NOT 手写第二份边界数。判据常量与范围边界必须只有一个落点。
- **FR-006**: 候选范围的价格区间 MUST 以**盘中**的标的现价为基准，MUST NOT 用收盘价。该基准取实时行情底座已在维护的盘中价 —— 范围是带余量的**包络**而非精确反解，容得下一个采集周期的滞后；越过包络的情形由 FR-007 的绊线守卫兜住。
- **FR-006a**: 召回判据与表头呈现所用的标的现价 MUST 与本批腿报价**同刻**取得 —— 标的自身随同一次请求一并取回，MUST NOT 为它单独多发一次请求，也 MUST NOT 用定窗那个略滞后的基准去喂判据。⇒ 系统内同时存在两个现价：**定窗的基准**（可滞后一个采集周期）与**判据与呈现的现价**（与报价同刻），两者职责不同，MUST NOT 合并成一个。
- **FR-007**: 系统 MUST 有一条守卫：若某条腿被候选范围排除、却能通过召回判据，则告警 —— 范围是判据定义域的**包络而非等价**，这条守卫是它漂移时的绊线。
- **FR-008**: 候选范围的计算 MUST 从一开始就按市场取参，即便当前只有美股一个取值 —— 这样将来判据按市场分表时只需加数据，不必重写范围的派生逻辑。

**档位与降级**

- **FR-009**: 每条腿 MUST 带一个可辨的报价档位（实时 / 收盘），且档位 MUST **逐行**成立，MUST NOT 页级一刀切。
- **FR-010**: 实时档的区块时间 MUST 是本次取数的**我方采集时刻**；收盘档的区块时间 MUST 是该批快照自身的归属交易日。MUST NOT 用外部源自报的时间戳判定新鲜度 —— 实测该时间戳是「最后成交时刻」而非报价时刻：低流动性标的在正常交易时段内它可以长时间不推进，而同一轮观测里也出现过它推进数百次、最新价一次没变。两个方向都说明它答的不是「这个数多新」。
- **FR-011**: 四类不可实时的情形 —— 非常规交易状态 / 源不可达或超时 / 部分合约未返回 / 单腿关键报价为空 —— MUST 各自显式回落收盘档并标出档位。MUST NOT 回落成 0、MUST NOT 清空既有值、MUST NOT 静默成功。
  - 📌 **上游实时行情底座的熔断不在这四类里** —— 它一旦打开就停止刷新盘中价，于是本系统经「定窗基准不可用」那条路径回落（见 Edge Cases）。两条路径的**用户可见结果相同、输入不同**，MUST NOT 合并成一条：合并会诱使实现方在本系统内再建一个断路器，而那会造出两个互不同步的阈值。
- **FR-012**: 标的现价缺失时 MUST 呈显式「未就绪」，MUST NOT 拿收盘价顶替 —— 顶替会让「链坏了」看起来像正常。
- **FR-013**: 界面 MUST 让用户能区分成交量 / 成交额在两个档位下的不同口径（实时档 = 截至此刻累计，收盘档 = 当日最终）。
- **FR-014**: 持仓量相关列的时间 MUST 取其自身的归属日呈现，MUST NOT 取区块级时间。

**开关与边界**

- **FR-015**: 是否走实时 MUST 由调用方传入的**显式开关**决定，且默认为**关**。MUST NOT 从鉴权状态、请求来源或任何其它上下文隐式推断 —— 隐式推断会让「将来加一种访问方式」静默改变外呼行为。
- **FR-016**: 开关为关时，系统 MUST 走纯库内收盘档，对外部行情源的请求次数 MUST = 0，且结果 MUST 与本 feature 上线前逐字节相同。
- **FR-017**: 候选集与整条链 MUST 读到同一批行、同一个报价时刻 —— 覆盖必须发生在两者的共同根上，MUST NOT 分别覆盖。
- **FR-018**: 候选范围内的合约数超过单次可取回上限时，系统 MUST NOT 让同一张表里的腿处在两个不同的报价时刻；若分批取回，区块级时间 MUST 取最早那批的时刻。
- **FR-019**: 本 feature MUST NOT 写入任何持久化存储 —— 零新表、零新列、零新采集维度。实时数据只在被读的那一刻存在。
- **FR-020**: 候选集 MUST 在每次取数（进入页面 / 下拉刷新）时按当次口径整体重新召回，MUST NOT 锁定成员集合 —— 锁定会让已不再满足判据的腿留在表里，而用户据此下单等于拿到一个判据没批准的腿。
- **FR-021**: 相邻两次取数之间的候选集成员变化 MUST 对用户显式可见（本轮新进 / 本轮已不满足各有多少）。MUST NOT 让成员静默增减 —— 用户可能正盯着某一行准备下单，那一行的消失必须是他看得见且解释得通的事件，而不是一次无声的重排。
- **FR-022**: 一次取数的结果 MUST 整体呈现 —— 屏上的成员集合与报价必须来自**同一次**召回。MUST NOT 先渲染库内收盘档、再用实时结果覆盖并重排：那会在首屏制造一次用户没有发起过的「成员变化」，且让他在头几百毫秒里读到一份按昨收筛出来的候选集。首屏走等待态；下拉刷新期间保留当前表，新一批到齐后整体替换。
  - 📌 这条约束的是**取数批次**，不是档位：同一次取数内部因部分合约未返回而出现的逐行档位差异（FR-011）是正常结果，不在此列。
- **FR-023**: 本片特有的三类失败 —— 部分合约未返回 / 候选范围超单批上限 / 定窗基准陈旧或缺失 —— MUST 各自留下可聚合的痕迹，MUST NOT 只落在用户屏上。**通道本身是否活着不由本片回答**：它复用实时行情底座的观测面（该底座按固定周期主动探测，而本片按需触发 ——「没人看就没数据」的指标会误导，不能当哨兵）。

### Key Entities

- **候选范围（窗）**：一次实时取数的合约集合。由召回判据常量派生的包络 —— 认沽、剩余期限区间、以现价为基准的行权价区间、标准合约。它**不是**第二个判据点，只是「哪些合约值得去问此刻的价」。
- **两个标的现价**：职责不同、不可合并。**定窗基准**用于圈出该问哪些合约，容得下一个采集周期的滞后；**同刻现价**随本批报价一并取回，是召回判据与表头呈现的唯一依据。把后者也用作前者会引入一次额外请求，把前者也用作后者会让判据与报价不同刻。
- **报价档位**：一条腿当前数值的时间口径，取值为实时或收盘。逐行成立，与区块级时间共同回答「我看到的这个数是什么时候的」。
- **链级上下文**：一次检索的时间三元组 —— 报价时刻（随档位变）、快照归属交易日、持仓量归属日。三者**不是同一天**，且这个事实必须在呈现层保持可见。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 美股常规交易时段内打开选约表，表内报价与同一时刻的外部行情终端逐条一致（抽样比对，允许差一次刷新间隔）；区块时间呈时刻，下拉刷新后推进。
- **SC-002**: 用户从打开选约表到看见实时报价的等待，在候选范围最大的标的（当前 285 个合约）上 P95 ≤ 1.5 秒。
- **SC-003**: 一次页面加载对外部行情源发起的请求次数 = 1（候选范围在单次上限内时）。
- **SC-004**: 四类降级情形下，用户均能从界面判断出这批数不是实时的；且四类情形中被显示为 0 或被清空的数值项 = 0 个。
- **SC-005**: 开关关闭时，选约表与链分析报表的输出与本 feature 上线前逐字节相同，且对外部行情源的请求次数 = 0。
- **SC-006**: 任意档位下，持仓量列呈现的归属日均为收盘档归属日，被标成当天的次数 = 0。
- **SC-007**: 候选集与整条链在同一次请求内的报价时刻不一致的情形 = 0 次。
- **SC-008**: 盘中价格移动导致的候选集成员变化，全部可由召回判据加实时值解释 —— 无法解释的进出 = 0 例。
- **SC-009**: 每一次导致成员变化的刷新，界面报出的进出条数与实际差集一致 —— 未被告知的静默增减 = 0 次。
- **SC-010**: 本片特有的三类失败在留痕面上可按类别分别聚合计数；发生了却无法归类的降级 = 0 例。

## Assumptions

- **盘中不重跑链发现，因此盘中新挂的合约当日不可见。** 链发现的外部接口限频远严于报价接口（一只标的的全链发现需要多次调用，而该接口的配额是报价接口的六分之一），盘中重跑不可行。次日收盘采集自然补上。合约集是否真会盘中新增未经实证，但无论结论如何，这个取舍相同。
- **实时取数只由「进入页面」与「下拉刷新」触发，无后台自动轮询。** 自动轮询会把外部源的配额消耗与用户停留时长绑定，且本 feature 的价值在「我现在看的这一眼是真的」，不在「它自己会动」。
- **不另设刷新节流。** FR-022 的「刷新期间保留当前表、到齐后整体替换」天然把刷新串行化 —— 一次未完成时不接受下一次 ⇒ 单用户的外呼频率上限就是单次往返的倒数，远在配额之内。真到了需要节流的那天，那说明触发方式已经变了（例如加了自动轮询），届时连同触发方式一起重新论证。
- **本 feature 只覆盖美股。** 港股期权链尚未接入（既无合约集也无快照），按市场取参的设计为它预留，但本片不实装。
- **合约乘数对美股恒为 100，本片不碰。** 按市场取值是另一片的事。
- **不落盘中历史。** 「开仓那天盘中的隐含波动率与价差是什么样」是一个独立诉求，已单独登记为 backlog，本片刻意不解决 —— 本片解决的是「我现在看到的数对不对」。
- **今天不存在游客可达的链读路径。** 访客经通道拿到的期权数据是外部行情源的原始快照，直连、不经过本系统的链检索；本系统对访客只开放三个写入口。因此 FR-015 的开关在今天没有第二个调用方 —— 它是为「将来真新增任何读路径时，默认就是不外呼」而预埋的，不是为一条已存在的路径而加。
- **外部行情源的既有配额压力不属本片。** 访客直连外部源已在消耗同一个配额桶，这是本 feature 之前就存在的状况，本片不改变也不缓解它。
- **实时源的可用性与熔断策略复用已上线的实时行情底座**（同一条外部通道、同一套熔断与限频桶），本片不新建第二套。
