# Feature Specification: 选约引擎 server 三层重构 —— 召回 / 打标 / 精排

**Feature Branch**: `050-optionsdesk-leg-recall-rank`
**Created**: 2026-08-11
**Status**: Draft
**里程碑**: sell-put 可视化决策系统 —— optionsdesk 选约引擎重构的 **P1 片**（主 plan：`docs/private/plans/2026-08/08-11-optionsdesk-leg-engine-master.md`，本机私有）

> 📌 **纯 server**。契约**只加不删**（不变量 #12）—— 这是 P1 / P2 能拆成两个 PR 的唯一前提。
> ⚠️ 但 **DTE 段变化会改变成员集合**，这是**行为变化**：本片 merge 当天用户看到的腿就变了，而 mobile 的显示口径还没跟上。可接受，但 MUST 在 PR body 显式 flag，不能当成「无感知升级」。

## 背景：为什么是判定层而不是零散 bug

047 ship 之后暴露的不是零散缺陷，而是**三个判据层面的问题**，它们互相咬合，逐个修会来回返工。

### 一、Δ 被误用成过滤器

现役把腿硬分成建仓 / 收租两族：建仓 = `|Δ| ∈ [0.40,0.55] ∧ DTE ≤ 14`，收租 = `DTE ∈ [150,365] ∧ Δ 带`。这让 **Δ 承担了「过滤器」的角色**，而 Δ 的真实用途是**偏好信号** —— 同一段 DTE 内该挑哪几张。

代价是可见的：greeks 缺失的腿（vendor 没给全）在现役实现里**两个意图 Tab 都进不去**，只能在全腿 Tab 里找。它并不是一条坏腿，只是少了一个用于打标的量。

### 二、建仓判据缺了最关键的一条

`|Δ|` 带只是「K 在 spot 附近」的**间接近似**，而真正的业务判据是**有效成本 `K − P` 必须低于当前 spot** —— 否则「用 put 代替直接买」这个前提就不成立。

两者不等价，边界会漏：`K = 115` / `spot = 110` / `P = 4` → 有效成本 111 > spot，而 Δ 带照收。这条腿被指派后的持仓成本比现在直接去市场买还贵，它不该出现在建仓视角里。

### 三、DTE 段是窄带精确匹配而非粗召回

`DTE ≤ 14` 与 `[150,365]` 之间有 **136 天的空档**。落在里面的腿哪个意图视角都进不去，只能在全腿 Tab 里看 —— 而 30–45 DTE 恰恰是业内公认的 sell-put 甜蜜点。

⇒ 一次把**判定层**（召回 / 打标 / 精排）重做，UI 层跟着契约走（P2）。

### 为什么门槛这一层要现在加

召回从窄带改粗召回会让候选集显著变大。没有硬门槛的话，进来的会有两类纯垃圾：

1. **一分钱腿** —— `weeklyRate = periodRate × 7/DTE`，DTE=1 时是 ×7 放大。一张只收 0.35 美元的 1 天期腿，折算费率会压过收 3.50 美元的 35 天期腿。
2. **挂不出去的腿** —— 相对价差宽到没有成交可能，进了候选集也只是噪音。

这两道门槛是**召回层的硬约束，不进精排**。它们的存在使得「不加额外的短腿分散手段」成为可接受的选择。

## Clarifications

### Session 2026-08-11

- Q: 精排发生在 server 还是 client？（现役 047 把「每个 Tab 自己的排序键」判给客户端） → A: **收回 server**。腿本体仍下发一份不重复，另加三个**有序的合约代码列表**（每 Tab 一份）。定案理由是从 P3 倒推的硬约束：P3 要做 server 侧 top-N 截断，而**截断必须发生在排序之后** —— 排序若留在 client，server 截断就会砍掉本该排前面的腿，且这种错**不会红**（返回条数对、数字都在，只是错的那批）。
- Q: 特征集归一化到 `0–1` 的基准取什么？ → A: **该 Tab 本次请求的候选集内 min-max**。与已有的活跃度排名同口径（不变量 #4 已是候选集内相对量），系统里不出现第二种「相对 / 绝对」语义，且零新参数要标定。⚠️ 已知代价：特征值**不可跨请求比较**，将来切加权评分时权重是在「相对位置」上调的。本轮字典序不受归一化影响 ⇒ 该选择对**本轮输出零影响**，代价全在将来。
- Q: 特征集放哪些字段？（FR-019 原写「字段齐全」，是未量化的形容词） → A: **连续量 8 项 + 布尔 / 序数量 5 项 = 13 项**，清单见 FR-019。收布尔量进来的理由：不变量 #8 的驱动力是「将来切加权时发现某个量拿不到」，而最可能被加权的恰是布尔量（月度链 = 流动性代理、Δ 贴合度 = 意图贴合），把它们排除等于留下同一个坑；布尔归一化是平凡的 0/1，增量成本极低。
- Q: FR-008「被门槛滤除的腿数」下发到什么粒度？ → A: **按门槛分两个数**（权利金滤除 N1 / 流动性滤除 N2）。单一总数无法区分两类，而两类的处置完全不同：一分钱腿是废腿（不用管），价差宽是该注意的流动性信号（该看看）——只报总数等于满足了 FR-008 的字面而非它的目的。P3 拆成每 Tab 独立请求后，每个响应各带自己的这对数即可，**形状不用改**。
- Q: 月度到期日（含假日提前）的判定数据源取哪个？ → A: **跨上下文只读直查交易日历**（`marketdata.trading_day`）。已实证可行：同一个端点的 `last-closed-session.ts:39` 已在这么读，跨 ctx 范式与机器强制注释都现成。判据 = 该月第三个周五；若该日非交易日则取其前一交易日。🚫 否决「从链自身到期日分布推断」—— 那是靠数据形状猜规则，链数据不全时会误判，而**误判时看起来完全正常**（标还在，只是标错了位置）。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 召回层换代：粗召回 + 有效成本硬判据（Priority: P1）

我在某只票上想接货（标的级意图 = 建仓）。我打开建仓视角，希望看到的每一条腿都满足「被指派后的持仓成本低于我现在直接去市场买」，并且不会因为期限窗口太窄而漏掉 15–49 天那一段 —— 那一段恰恰是权利金衰减最划算的区间。

**Why this priority**：这是本次重构的**business 正确性核心**。缺了有效成本判据，建仓视角会推荐比直接买还贵的腿；DTE 窄带则让最该看的一段完全不可见。两者都不是体验问题，是判据错。

**Independent Test**：用真实链数据跑同一只票，对比重构前后建仓候选集：① 重构后集合内**零条**腿的有效成本 ≥ spot；② 重构前进不了任何意图 Tab 的 15–49 天腿，重构后出现在建仓候选里。两条都不依赖打标层与精排层。

**Acceptance Scenarios**：

1. **Given** 某腿 `K = 115`、`bid = 4`、当前 `spot = 110`（有效成本 111 > spot），且其 `|Δ|` 与 DTE 均落在建仓的旧判据内，**When** 请求该票选约表，**Then** 该腿**不在**建仓候选集内（收租候选与全腿 Tab 不受此判据影响）。
2. **Given** 某腿 DTE = 35、有效成本低于 spot、两道门槛均通过，**When** 请求该票选约表，**Then** 该腿**同时**出现在建仓与收租候选集内（`[30,49]` 是两段刻意的重叠区）。
3. **Given** 某腿 greeks 缺失（`|Δ|` 无值）但 DTE、有效成本、两道门槛全部合格，**When** 请求该票选约表，**Then** 该腿**照常进入**对应意图候选集 —— 与 047 相反（Δ 已降级为标，不再参与召回）。
4. **Given** 某腿 DTE = 400，**When** 请求该票选约表，**Then** 它两个意图候选都不进，但**仍在全腿 Tab 可见**。

### User Story 2 - 两道硬门槛 + 被滤掉多少条必须看得见（Priority: P2）

我不想在候选集里翻到只收几分钱的腿，也不想翻到价差宽得根本挂不出去的腿。但我**必须知道**系统替我挡掉了多少条 —— 一次没有交代的数据消失，比多几行噪音危险得多。

**Why this priority**：门槛本身是召回层的配套（US1 放宽了召回，门槛负责收紧）。单独列出来是因为它带着一条**独立的、容易被省掉的**要求：可见的过滤计数。

**Independent Test**：构造含一分钱腿与宽价差腿的数据集，验证 ① 一分钱腿三个 Tab 全不见；② 宽价差腿不在建仓 / 收租但在全腿 Tab 可见；③ 响应里「被权利金门槛滤掉 N 条」的计数与实际滤除数一致。

**Acceptance Scenarios**：

1. **Given** 某腿 `bid` 低于权利金绝对门槛，**When** 请求该票选约表，**Then** 该腿**三个 Tab 一律不出现**，且响应携带的「被门槛滤掉」计数**包含它**。
2. **Given** 某腿相对价差高于流动性门槛，**When** 请求该票选约表，**Then** 该腿**不在**建仓 / 收租候选，但**仍在全腿 Tab 可见**（价差宽只说明难成交，作为参照仍有意义）。
3. **Given** 某腿完全无 `bid`（无报价），**When** 请求该票选约表，**Then** 按「不满足权利金门槛」处置（含计入计数），**MUST NOT** 当作 `bid = 0` 参与任何计算。
4. **Given** 某腿有 `bid` 但无 `ask`（无法计算相对价差），**When** 请求该票选约表，**Then** 流动性门槛判 fail-closed（不进建仓 / 收租），该腿仍在全腿 Tab 可见。
5. **Given** 某票所有腿都被门槛与 DTE 段挡下，**When** 请求该票选约表，**Then** 对应 Tab 显示空态且**仍可进入**，MUST NOT 隐藏或禁选该 Tab。

### User Story 3 - 打标层：Δ 从过滤器降级为偏好信号（Priority: P3）

Δ 不再决定哪条腿能进来，而是告诉我**在已经进来的这些里面，哪几条更贴合我当前的意图**。同时我希望一眼看出哪些到期日是月度链 —— 那是流动性最好的那批。

**Why this priority**：打标层不影响集合，只影响可读性。US1 / US2 落地后系统已经正确，US3 让它好用。

**Independent Test**：固定同一份召回集，切换标的级意图与水位档，验证推荐标的开关行为；对已知含月度到期日的链，验证月度链标的命中位置。集合本身不因打标发生任何变化。

**Acceptance Scenarios**：

1. **Given** 标的级意图 = 建仓，**When** 请求该票选约表，**Then** `|Δ|` 落在建仓 Δ 带内的腿被打**推荐标**，落带外的不打。
2. **Given** 标的级意图 = 收租且水位档已选，**When** 我打开**建仓** Tab，**Then** 该 Tab 内**一个推荐标都没有** —— 推荐标随标的级意图不随 Tab，这是正确信号，**MUST** 配就地说明让人知道为什么。
3. **Given** 标的级意图 = 收租但**水位未选**，**When** 请求该票选约表，**Then** 全表**零推荐标**，MUST NOT 取三档 Δ 并集替我做方向性假设。
4. **Given** 某到期日是当月第三个周五，**When** 请求该票选约表，**Then** 该到期日下的全部腿都带**月度链标**。
5. **Given** 当月第三个周五是市场假日、月度到期日因而提前，**When** 请求该票选约表，**Then** 提前后的那个到期日仍带月度链标（判据是「该月的月度到期日」，不是「是不是周五」）。
6. **Given** 任意一条腿被打了任意组合的标，**When** 请求该票选约表，**Then** 打标**不改变**它在任何候选集内的存在与否 —— 打标层零拦截。

---

### User Story 4 - 精排层：单主键 + 可替换排序器（Priority: P4）

我要能从屏幕上反推「为什么它排在前面」。所以本轮不要加权评分 —— 权重现在是拍脑袋的，也没有可校准的数据。但特征层要现在就备好，将来切加权时不用重做。

**Why this priority**：现役已有一套按档位的排序，不是坏的，只是不贴合新召回集。精排是三层里最不紧急的一层。

**Independent Test**：对同一召回集验证排序结果的确定性与主键正确性；对特征集验证字段齐全且取值落在归一化区间内。可脱离 US2 / US3 单独验。

**Acceptance Scenarios**：

1. **Given** 某 Tab 的召回集，**When** 请求该票选约表，**Then** 响应中该 Tab 的**有序合约代码列表**按**折算费率降序**排列 —— 顺序由 server 定，客户端不重排。
2. **Given** 两条腿折算费率完全相同，**When** 连续两次请求，**Then** 两次返回的顺序**逐行相同**（确定性次键：到期日升序 → 行权价降序 → 合约代码）。
3. **Given** 一条 DTE = 60、费率较高的腿与一条 DTE = 35、费率较低的腿，**When** 请求该票选约表，**Then** 前者排在前面 —— DTE **MUST NOT** 参与排序，也不做「离理想 DTE 越近越靠前」。
4. **Given** 同一条腿同时出现在建仓与收租 Tab，**When** 请求该票选约表，**Then** 它的档位判定在两个 Tab 里可以不同（建仓 Tab 用周化档界、收租 Tab 用年化档界），而**全腿 Tab 恒用年化档界**。
5. **Given** 排序器需要某个量，**When** 实现排序逻辑，**Then** 该量**只能**从特征集读取，MUST NOT 直接读原始腿数据。

### Edge Cases

- **月度到期日撞假日**：美股期权月度到期日在第三个周五为假日时提前至前一交易日。判据 MUST 是「该月的月度到期日」而非「是不是周五」，否则每年若干个月会静默漏标。
- **有效成本判据只在建仓语义下成立**：收租不接货，不受此限。把它误加到收租候选上会砍掉大量本来正确的深虚腿，而且**不会红**。
- **两段 DTE 的重叠区 `[30,49]`**：同一张合约在两个 Tab 里出现是**设计意图**，不是重复。它在两个 Tab 里的档位判定、活跃度排名、排序位次都可以不同。
- **活跃度排名基准**：恒为**该 Tab 的召回全量**，筛选**不**进入排名基准。⇒ 顺序恒为 **排名 → 筛选 → 截断**。最自然的写法是「先筛再排名」（少算一些），那样写出来照样能跑、数字照样有，**只是全错**。
- **收租意图下建仓 Tab 零推荐标**：正确信号。没有就地说明的话，它长得跟「打标坏了」一模一样。
- **门槛把某 Tab 清空**：Tab 仍可进入并显空态，MUST NOT 隐藏或禁选。
- **无 `bid` 与 `bid` 很低是两件事**：前者是「不知道」，后者是「知道且很低」。两者在**门槛处置上同归**（都挡下并计数），但 MUST NOT 通过「把无 `bid` 当 0」的方式实现 —— 那会污染费率与有效成本的所有下游计算。

## Requirements _(mandatory)_

### Functional Requirements

#### 召回层

- **FR-001**: 建仓候选的期限段 MUST 为 `DTE ∈ [1, 49]`（下界 1 因读端已滤「到期日 > 当日」）。
- **FR-002**: 收租候选的期限段 MUST 为 `DTE ∈ [30, 365]`。与建仓段在 `[30,49]` 的重叠是**刻意的**，MUST NOT 被「消歧」掉。
- **FR-003**: 全腿 Tab MUST NOT 设期限段。
- **FR-004**: 建仓候选 MUST 满足**有效成本 `K − bid` < 当前 spot**。此判据 MUST NOT 作用于收租候选与全腿 Tab。
- **FR-005**: System MUST 对**三个 Tab 一律**施加**权利金绝对门槛**（形如 `bid ≥ max(绝对下限, spot × 百分比)`）。
- **FR-006**: System MUST 对**建仓 / 收租候选**施加**流动性门槛**（相对价差上界）。全腿 Tab MUST NOT 受此门槛约束。
- **FR-007**: 两道门槛的阈值 MUST 落在**单一可配置点**，MUST NOT 散落在判定逻辑内（同 047 档位边界的纪律）。具体数值由实测标定，spec 不钉死。
- **FR-008**: System MUST 下发**被门槛滤除的腿数，按门槛分两个数**（权利金滤除 N1 / 流动性滤除 N2），使「有腿消失了」这件事可见且**可行动**。MUST NOT 合并成单一总数 —— 一分钱腿是废腿（不用管），价差宽是该注意的流动性信号（该看看），两类处置完全不同。
  🚨 本条**部分推翻 047 `FR-005`**「任何腿至少在一个 Tab 里可见，不存在落库了但哪儿都看不见的腿」——权利金门槛作用于全部三个 Tab，被它挡下的腿在 UI 上确实消失。这是有意识的取舍，计数是它的**唯一**补偿。
- **FR-009**: `|Δ|` MUST NOT 参与任何召回判定（降级为纯打标量）。greeks 缺失 MUST NOT 导致腿被排除出候选集。
- **FR-010**: 047 的三条读端过滤 MUST 原样保留：仅认沽、仅标准合约、到期日 **>** 当日。

#### 打标层

- **FR-011**: 推荐标 MUST 随**标的级意图**判定，MUST NOT 随当前 Tab 变化。建仓意图取建仓 Δ 带；收租意图取当前水位档对应的 Δ 带。
- **FR-012**: 标的级意图为「待定」（水位未选）或「不开新仓」时 MUST NOT 打推荐标，且 MUST NOT 取 Δ 三档并集替用户做方向性假设。
- **FR-013**: greeks 缺失的腿 MUST NOT 被打推荐标（缺 Δ 不能推定落在任何带内），但这 MUST NOT 影响它在召回集内的存在。
- **FR-014**: System MUST 对到期日为**该月月度到期日**的腿打**月度链标**。
- **FR-015**: 月度到期日 MUST 判为「该月第三个周五；若该日非交易日则取其前一交易日」，判据 MUST 取自**交易日历**（跨上下文只读直查），MUST NOT 简化为「是不是第三个周五」，也 MUST NOT 从链自身的到期日分布反推。
- **FR-016**: 活跃度排名的基准 MUST 为**该 Tab 的召回全量成员**；筛选 MUST NOT 进入排名基准。
- **FR-017**: 财报标的域划分（建仓域 / 收租长腿 / 收租短腿）沿用 047，本片 MUST NOT 改动其算法。
- **FR-018**: 打标层 MUST 零拦截 —— 任何标的有无 MUST NOT 改变腿在任何候选集内的存在与否。

#### 精排层

- **FR-019**: System MUST 产出**特征集**，含以下 **13 项**，取值**归一化到 `0–1`**（哪怕当前排序用不到）：
  - **连续量 8 项** —— 折算费率 · 有效成本相对 spot 的折价 · 相对价差 · 未平仓量 · 成交量 · 成交额 · `|Δ|` · DTE
  - **布尔 / 序数量 5 项** —— 是否月度链 · 是否整数行权价 · `|Δ|` 是否落在当前意图的 Δ 带内 · 该到期日是否跨越财报 · 活跃度排名
- **FR-019a**: 归一化基准 MUST 为**该 Tab 本次请求候选集内的 min-max**（与活跃度排名同口径）。三条边界处置 MUST 显式：
  - **该特征在候选集内全等**（含候选集只有 1 条腿）⇒ 恒取 `0.5`。取 `0` 会把全体误报成「都最差」，取 `1` 反之；常数取值不影响任何排序，故取中性值。
  - **原始量缺失**（如无 OI / 无成交量）⇒ 取 `0`，与 047 活跃度排名「缺失排末位」同口径，MUST NOT 与「真实值为 0」在下游被区别对待。
  - 布尔量 ⇒ `0` / `1`，不参与 min-max。
- **FR-019b**: 特征集 MUST NOT 下发 —— 它是 server 内部结构。排序已在 server 完成（FR-021a），下发一批无人消费的字段会被「只加不删」（FR-027）永久锁死。可解释性由**已在表上的费率列**承担（主键即费率降序）。
- **FR-020**: 排序器 MUST 只读特征集，MUST NOT 直接读原始腿数据。
- **FR-021**: 三个 Tab 的排序主键 MUST 为**折算费率降序**。
  📌 周化率与年化率差一个常数因子，是严格单调变换 ⇒ **两者降序结果逐行相同**。选 `basis` 是在选**显示口径与档界**，不是在选顺序。
- **FR-021a**: 精排 MUST 在 server 完成。响应 MUST 为**每个 Tab 各下发一份有序的合约代码列表**；腿本体仍下发一份，MUST NOT 按 Tab 重复。客户端 MUST 按该列表呈现，MUST NOT 自行重排。
  🚨 这条**推翻 047 D-API-1 / D-SOT-4**「每个 Tab 自己的排序键归客户端」。理由不是洁癖，是 P3 的硬约束：截断 MUST 发生在排序之后，排序留在客户端会让 server 截掉本该排前面的腿 —— 而返回条数与数值全都正常，**不会红**。
- **FR-022**: DTE MUST NOT 作排序主键，也 MUST NOT 实现「离理想 DTE 越近越靠前」。
- **FR-023**: 档位判定的 `basis` MUST 跟 Tab 走（建仓 Tab 周化档界 / 收租 Tab 年化档界），**全腿 Tab 例外恒用年化** —— 它混着 10 天与 200 天的腿，用周化档界判长腿会让整列全是死档。
- **FR-024**: 处理顺序 MUST 恒为 **排名 → 筛选 → 截断**。本片不实装筛选与截断（归 P3），但骨架顺序 MUST 已就位。
- **FR-025**: 排序 MUST 确定性 —— 同一输入的两次调用返回逐行相同的顺序。
- **FR-026**: 本轮 MUST NOT 引入加权评分。判定手段限定为「硬门槛 + 单主键 + 标签」。

#### 契约与交付

- **FR-027**: 契约 MUST 只加不删 —— 新增字段，旧字段一个不动，旧客户端不改一行仍可渲染。
- **FR-028**: 成员集合的行为变化 MUST 在 PR body 显式 flag，MUST NOT 当作「无感知升级」交付。
- **FR-029**: 045 的锚派生（W / 四区间 / L 层）与意图矩阵 MUST 零改动 —— 本片只**消费**它们。

### Key Entities

- **召回集（Recall Set）**：某个 Tab 在本次请求下的候选腿全集。由期限段 + 硬门槛 + 建仓语义的有效成本约束共同决定。它是活跃度排名与精排的作用域。
- **标（Mark）**：附着在腿上的非拦截性信号，四类 —— 推荐（随标的级意图）、活跃（候选集内相对排名）、财报（按到期日分组）、月度链（按月度到期日）。标的有无**不改变**集合。
- **特征集（Ranking Features）**：精排层的唯一输入面，**server 内部结构、不下发**。13 项，按该 Tab 候选集内 min-max 归一化到 `0–1`。字段现在就算全，为将来切加权评分留出零改动的切换点。⚠️ 归一化基准是候选集内相对量 ⇒ 特征值**不可跨请求比较**。
- **门槛（Threshold）**：召回层的硬约束，两条 —— 权利金绝对门槛（作用于三个 Tab）与流动性门槛（只作用于建仓 / 收租）。阈值单点可配。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 建仓候选集内**零条**腿的有效成本 ≥ 当前 spot（真实链数据全量核对，100%）。
- **SC-002**: 在真实链数据上，至少有 1 条 `DTE ∈ [15,49]` 的合格腿在重构前进不了任何意图 Tab、重构后出现在建仓候选内 —— 证明 136 天空档已被填上。
- **SC-003**: 两个滤除计数（权利金 / 流动性）**各自**与实际滤除条数**逐次相等**（零误差）。
- **SC-003a**: 归一化后的每一项特征取值**恒落在 `[0,1]` 闭区间内**（全量核对，含全等、缺失、单条候选集三种边界）。
- **SC-004**: 至少 1 条 greeks 缺失的腿在重构后进入意图候选集（047 下会被 Δ 带挡掉）—— 证明 Δ 已真正降级为标。
- **SC-005**: 标的级意图为收租时，建仓 Tab 内推荐标数**恒为 0**；意图为待定 / 不开新仓时，全表推荐标数**恒为 0**。
- **SC-006**: 同一输入连续两次请求，三个 Tab 的返回顺序**逐行相同**。
- **SC-007**: 该票选约表的端到端响应时间**不劣于** 047 基线（同一只票、同量级链数据，730 行量级）。
- **SC-008**: 未经改动的既有客户端针对新契约**零报错渲染**（契约向后兼容的机械判据）。
- **SC-009**: 门槛阈值、期限段边界、Δ 带边界各自**只有一处**定义（全仓扫描零重复定义）。

## Assumptions

- **相对价差的口径**取 `(ask − bid) / mid`，`mid = (bid + ask) / 2` —— 业内通行口径。阈值由实测标定（主 plan 未决 #2）。
- **权利金门槛的形态**取 `bid ≥ max(绝对下限, spot × 百分比)` 双参数 —— 绝对下限管掉一分钱腿，相对比例让门槛随标的价位缩放。两个参数的具体值由实测标定。
- **无 `ask` 时流动性门槛 fail-closed**（不进建仓 / 收租）—— 没有卖价就无法确认这条腿挂得出去，宁可少收不可错收；该腿在全腿 Tab 仍可见，信息不丢。
- **有效成本的 `P` 取 `bid`** —— 卖 put 收到的是买价，与 047 既有的有效成本口径一致。
- **spot 取链快照随附的标的价、未复权** —— 沿用 047 的既有纪律，本片不改。
- **月度到期日的判定走跨上下文只读直查交易日历**（`marketdata.trading_day`），无需引入新数据源 —— 同一端点的 `last-closed-session.ts` 已在这么读，范式现成。
- **本片不实装筛选与截断**（归 P3），但**排名 → 筛选 → 截断**的顺序骨架在本片就位，使 P3 只需填空而无需调整顺序。
- **显示口径的跟进归 P2** —— 年化 / 周化的主次字、推荐标的呈现、`tier` 跟 Tab 着色、Tab 语义从「族」改成「视角」，本片一律不碰。
