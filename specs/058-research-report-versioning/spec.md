# Feature Specification: 研报归档 —— 同标的多版本与元数据回声

**Feature Branch**: `058-research-report-versioning`
**Created**: 2026-08-16
**Status**: Draft
**Input**: 承接 057 已 ship 的投递通道。057 刻意把「同标的多版本」留作后续 feature（`version` 列已建但恒为初值、不实装规则）。2026-08-16 两次真实 agent 投递暴露出：投递方对自己声明的元数据零反馈、且声明错了在本通道内不可逆。本片实装版本规则 + 元数据回声。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 同一只票的研报形成可追溯的版本序列 (Priority: P1)

投递方为同一只标的先后投递多份研报（例如季度更新、事件驱动的补充分析）。他希望这些不是一堆彼此无关的记录，而是一条**有先后的版本线**：这是第几份、当前哪一份代表最新观点。

由于本通道对研报**只写不读**，投递方无从查询库中已有什么，所以「这是第几份 / 是不是最新」只能由归档方在投递应答里告诉他。

**Why this priority**: 这是本片的核心诉求，也是 057 明确记录为「后续 feature」的那一件。没有它，同标的的多份研报在库里是扁平并列的，「哪份代表当前观点」这个问题在归档侧无法回答。

**Independent Test**: 对同一标的连续投递三份不同的研报文件，仅凭三次应答即可判断出各自是第几版、以及最终哪一份是最新 —— 全程不需要任何读取接口。

**Acceptance Scenarios**:

1. **Given** 某投递方在某标的下尚无任何记录，**When** 他投递一份研报，**Then** 应答告知这是该标的下的第 1 版，且它就是当前最新。
2. **Given** 某投递方在某标的下已有第 1 版（研报日期 7 月），**When** 他投递另一份研报日期为 8 月的文件，**Then** 应答告知这是第 2 版且已成为当前最新。
3. **Given** 同上已有 8 月那版，**When** 他补投一份研报日期为 6 月的历史研报，**Then** 投递**被接受**、告知这是第 3 版、但**不是**最新，并同时告知现任最新那份的研报日期。
4. **Given** 某投递方在标的 A 下已有 2 版，**When** 他首次向标的 B 投递，**Then** 标的 B 的版本从 1 起算，与标的 A 的版本线互不影响。
5. **Given** 两个不同投递方都在同一标的下投递，**Then** 各自的版本线独立计数，任何一方的应答**不得**透露另一方投过几份。

---

### User Story 2 - 投递方能确认自己刚投进去的到底是什么 (Priority: P2)

投递方（实践中是一个 LLM agent）在请求里声明标题、研报日期、标的。这些声明**没有任何一层会校验**，而通道又没有读取面 —— 一旦声明错了，他既发现不了也改不掉。他需要归档方把**最终落库的值**回给他，作为自查的唯一手段。

**Why this priority**: 依赖 US1 的版本判定才能回显完整信息，故排在其后；但它是本片的直接触发原因 —— 2026-08-16 实测中，标题被编坏一个字节，而投递方向用户汇报的是他**意图**的标题，无人发现。

**Independent Test**: 故意用一个与意图不符的标题投递，仅凭应答即可当场发现落库值与意图不一致 —— 不需要查库、不需要问归档方。

**Acceptance Scenarios**:

1. **Given** 投递方提交了标题与研报日期，**When** 投递成功，**Then** 应答回显**最终落库**的标题与研报日期（不是把请求参数原样回吐）。
2. **Given** 投递方提交的标题在传输中被损坏，**When** 投递成功，**Then** 他能仅凭应答发现回显值与自己意图不符。
3. **Given** 某文件此前已投过、本次带着**不同**的标题 / 日期重投，**When** 命中幂等，**Then** 应答回显的是**库中那条**的标题 / 日期 / 版本号，而不是本次请求带来的值 —— 使「参数写错重投改不掉」这件事对投递方**显式可见**，而不是静默。

---

### User Story 3 - 标的投错了可以自助补救 (Priority: P3)

投递方把研报归到了错误的标的下（最常见形态：两地上市的公司选错市场）。他事后意识到错误，希望能自己纠正，而不是去麻烦归档方改库。

057 的现状是：同一投递方 + 同一文件字节被判为重复，**无论声明的标的是什么** —— 于是「用正确标的重投」这个最自然的补救动作，只会拿回那条错误记录。

**Why this priority**: 它降低的是**出错后果**而非出错概率，价值明确但不改变主流程；且独立于 US1 / US2 可单独交付。

**Independent Test**: 用错误标的投一份研报，再用正确标的投**同一个文件**，第二次应当产生一条正确的记录 —— 全程无人工介入。

**Acceptance Scenarios**:

1. **Given** 某投递方已用标的 A 归档了某文件，**When** 他用标的 B 投递**同一个文件**，**Then** 产生一条归属标的 B 的独立记录（而非返回标的 A 那条）。
2. **Given** 上述两条记录并存，**Then** 归档侧**只存一份文件对象**（同样的字节不因归到两个标的下而多占存储）。
3. **Given** 某投递方用**同一标的 + 同一文件**重投，**Then** 幂等行为与 057 完全一致（返回首次那条，不新增），**上传超时后原样重投仍然安全**。

---

### Edge Cases

- 同一条版本线上两份研报**日期相同**时，谁算最新？（须有确定性规则，不能出现两份同时最新或两份都不最新）
- 两个投递并发落在同一条版本线上时，版本号会不会重复或跳号？
- 本片上线前已存在的记录，其版本号如何与新规则衔接？（不得重排既有号，也不得让新投递从 1 重新开始）
- 投递方在同一标的下投递了很多版之后，配额如何计算？（每一版各自计入，不因同属一条版本线而合并）
- 幂等命中的那条记录**本身**不是当前最新时，应答里的「最新」信息该以谁为准？（应以库中该线的真实状态为准，而非本次请求）

## Requirements _(mandatory)_

### Functional Requirements

**版本序列**

- **FR-001**: 系统 MUST 以「投递方 + 标的」为身份，为其下的每一次成功投递分配一个版本号。
- **FR-002**: 版本号 MUST 在该身份内单调递增、从 1 起、无空洞；它表达的是**第几次投递**，MUST NOT 依据研报日期排序。
- **FR-003**: 不同投递方、或同一投递方的不同标的，MUST 各自拥有独立的版本线，互不影响、互不可见。
- **FR-004**: 系统 MUST 能判定某条版本线上「当前最新的那一份」，判据 MUST 是**研报日期最大者**，而非版本号最大者。
- **FR-005**: 研报日期相同时，最新判定 MUST 确定且唯一 —— MUST NOT 出现两份同时最新或全线无最新。
- **FR-006**: 系统 MUST 接受研报日期早于或等于该线现有最新的投递，MUST NOT 以「日期不够新」为由拒绝。
- **FR-007**: 当本次投递未成为最新时，应答 MUST 告知现任最新那份的研报日期。

**元数据回声**

- **FR-008**: 投递成功的应答 MUST 回显本次记录**最终落库**的标题与研报日期，而非把请求参数原样回吐。
- **FR-009**: 应答 MUST 包含本次记录的版本号，以及它是否为该线当前最新。
- **FR-010**: 幂等命中时，应答回显的标题 / 研报日期 / 版本号 / 最新状态 MUST 取自**库中那条已有记录**，MUST NOT 取自本次请求参数。
- **FR-011**: 应答 MUST NOT 泄露其他投递方在同一标的下的任何信息（含版本数量、日期、是否存在）。

**幂等与归属**

- **FR-012**: 幂等的判定身份 MUST 是「投递方 + 标的 + 文件内容」三者；同一投递方以**不同标的**投递同一文件 MUST 各自成为独立记录。
- **FR-013**: 同一投递方以**相同标的**重投同一文件 MUST 保持 057 的幂等语义（返回首次那条、不新增记录与对象、未完成态就地续做），版本号 MUST NOT 因重投而变化。
- **FR-014**: 同一份文件字节无论被归到几个标的、几个投递方名下，归档侧 MUST 只保存一份文件对象。
- **FR-015**: 每一条记录的字节数 MUST 各自计入其投递方的配额（057「口径蓄意高估、方向保守」不变），MUST NOT 因同属一条版本线或共享同一对象而免计。

**并发与迁移**

- **FR-016**: 同一条版本线上的并发投递 MUST NOT 产生重复版本号，MUST NOT 产生空洞。
- **FR-017**: 本片上线前已存在的记录 MUST 保持可用，其版本号 MUST NOT 被重排或改写。
- **FR-018**: 在已有记录的版本线上新投一份，新版本号 MUST 建立在既有记录之上，MUST NOT 从 1 重新开始。

**边界（本片明确不做）**

- **FR-019**: 系统 MUST NOT 对投递方声明的标的做存在性校验，MUST NOT 建立到行情标的目录的引用约束 —— 标的仍是投递方单方声明的值（理由见 Assumptions）。
- **FR-020**: 本通道 MUST 保持只写不读（057 FR-012 / FR-013 不变）—— 本片新增的回显仅限**投递方自己这一次及自己这条版本线**的信息，MUST NOT 演变成任何形式的查询 / 列举面。

### Key Entities

- **归档记录**：一次成功投递的元数据。归属一个投递方与一个标的，携带研报日期、标题、来源、版本号、内容指纹、归档对象位置、完成状态。
- **版本线**：由「投递方 + 标的」确定的一组归档记录，内部按版本号有序；其「当前最新」由研报日期决定。
- **归档对象**：研报文件本体。位置由内容指纹单独导出，与投递方、标的均无关 ⇒ 同一字节全局只存一份。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 投递方对同一标的连续投递 3 份不同研报后，仅凭这 3 次应答就能说出各自是第几版、以及哪一份是当前最新 —— 无需任何读取接口、无需询问归档方。
- **SC-002**: 补投研报日期早于库中现有记录的历史研报，接受率 100%（拒绝次数 0）。
- **SC-003**: 投递方把标的投错后，用正确标的重投同一文件即可得到一条正确记录，全程人工介入次数为 0。
- **SC-004**: 每一项由投递方声明的必填元数据（标的 / 研报日期 / 标题）在应答中均有对应回显，覆盖率 100% —— 使「声明值被损坏」这类错误可在投递当场被发现。
- **SC-005**: 同一条版本线上并发投递时，版本号重复数为 0、空洞数为 0。
- **SC-006**: 同一份文件字节被归到 N 个标的或 N 个投递方名下时，归档侧占用的对象份数恒为 1。
- **SC-007**: 上线前已存在的记录，版本号被改写的条数为 0。

## Assumptions

- **「最新」不落存储、按需判定**：把「谁是最新」写成一个持久状态需要在每次投递时维护，并发下会出现两条同时为最新或全线无最新。本片假定它按研报日期即时判定即可，不作为独立状态维护。
- **日期相同时以投递顺序决胜**：研报日期相同的两份，取**后投递的那一份**（版本号更大者）为最新。理由：这是投递方唯一能主动控制的维度，语义上也符合「后交的那份是修订稿」的直觉。
- **不校验标的**：057 已记录的理由（会拒绝合法的新标的、引入刻意避免的跨上下文依赖）之外，本片补充一条决定性的：2026-08-16 实际发生的错是**两地上市选错市场**（同一家公司的 A 股与港股代码**都存在于行情标的目录中、且名称相同**），存在性校验与名称比对都拦不住它 —— 付出跨上下文依赖的代价却挡不住主要失败模式，交易不划算。
- **能挡住上述错误的手段（服务端从研报内容中取证，只提示不拒绝）不在本片范围**：它需要引入研报正文文本抽取能力，属独立一轮选型评估。
- **回显标的名称（instrumentName）不在本片范围**：它需要跨上下文读取行情标的目录，触发独立的架构取舍（共享只读服务 / 物化视图 / 临时直读三选一）。本片刻意收敛在单一上下文内，使版本与回声这两件事不被架构讨论阻塞。若要纳入，应作为独立增量。
- **投递方数量与投递频率维持在人工产出物的量级**（057 的每分钟 2 次限额不变），版本线长度不会达到需要分页或归档的规模。
- **既有记录的版本号一律视为 1**，本片上线时无需数据回填计算 —— 现有记录在各自版本线内均为唯一一条。

## Out of Scope

- 任何形式的研报读取 / 列举 / 下载 / 预览接口（057 FR-012 / FR-013 保持）。
- 标的存在性校验、跨 schema 引用约束、标的名称回显。
- 服务端研报内容取证（从正文中抽取证券代码与声明值比对）。
- 作废 / 撤回某一版的能力 —— 投错标的的旧记录在本片后仍会留在库中，清理属归档方本人的运维动作。
- 研报在 App 端的呈现（仍属 PRD §3.8 后续 feature）。
