# 注释出处探针：三版判据的实测与两条根因追查

> 2026-09-01。起因：本人（Claude）在一次实现中把未核实的交易所规格当事实写进 PR 正文与 ADR，
> 维护者据此提出「我无法再用你的语气判断哪些是你核实过的、哪些是猜的」。本文记录为回答这个
> 问题所做的全部测量与追查，供 [`comment-provenance.md`](../../conventions/comment-provenance.md) 引用。

## 1. 三版探针与它们的失败方式

判据本身是**语义的**（「这句断言有没有出处」），三次尝试把它做成文本模式，两次失败：

| 版本 | 判据                                                          | 命中「无出处」  | 失败方式                                                                                                                                                  |
| ---- | ------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| v1   | 含证据宣称词（实测/实证/已确认…）且同行无 `日期 / URL / 路径` | 428 / 720 行    | **假阳 ~99%**：本仓真正在用的出处形式是**观测值本身**（`inactive 仅 cn 22 / hk 8 / us 0`）与**具名实验**（`p3b E13` / `T015` / `probe`），v1 一个都没枚举 |
| v2   | 同上 + 把观测值 / 具名实验也算出处                            | 191 / 720 行    | 仍高估：逐条读完 191 条后，真·裸宣称目测个位数；其余是「不是事实断言、而是在谈证据本身」（`无实测证据前不动`）或出处在**相邻行**                          |
| v3   | vendor 作**主语** + 行为动词，出处在**上下 3 行**内即算       | **62 / 169 行** | 可用。与 v1 相比总体缩了 4.3×、命中缩了 9.2×                                                                                                              |

**教训**：`claude-md-audit` skill 维度 5 早写过同款结论（2026-08-03 实证：按文本模式扫语义属性，
两轮 precision 探针几乎全假阳，此维**只能语义判定，禁做成正则硬拦**）。本次三版复现了它。

## 3. 两条独立的根因追查，形状完全一致

### 3.1 `alert/realtime-quote.rules.ts` 的三句腾讯断言

三句（`腾讯直给四舍五入` / `按 v_ 变量对齐而非请求顺序` / `对无效码返回空 payload`）在本仓 `git blame`
全部落到根 commit（`chore(repo): initial public snapshot`），本仓查不到写作时刻。但证据链完整：

```text
docs/private/plans/2026-06/06-07-…md   ← 原始 PoC（2026-06-08 真实请求），三句全在同一行内，带测量值
  → specs/024-alert-realtime/plan.md   ← 「PoC 已复验」
  → specs/024-alert-realtime/tasks.md  ← 「T006 vitest 锚 PoC §5.1 真实响应样本」
  → alert/realtime-quote.rules.spec.ts ← 文件头写明锚点 + 真实报文
  → alert/realtime-quote.rules.ts      ← ❌ 只剩结论，无指针
```

### 3.2 「vendor 不提供历史期权快照」

出处在 `specs/047-…/spec.md`（引 p3b §6.5，带链接）。该断言在代码 / ops / shim 中被复述
**10 次以上**，每一次复述都丢了指针。

⇒ **两条独立链条同形：证据在 spec 层完整，在代码注释层被丢弃。不是编造，是链路断在最后一跳。**

## 4. 一处反例：同一事实两处待遇不同

`vendor 财报视野约半年` 这一个事实：`marketdata/sync-earnings-event.usecase.ts` 处带着 `p3b E8`，
`optionsdesk/earnings-mark.rules.ts` 处裸着。⇒ **掉指针是随机疏漏，不是系统性不写。**

## 5. 本仓已有的标准答案

`marketdata/futu-option-snapshot.adapter.ts` 的 `inconsistent` 累加器注释同时做了三件事：给结论、
给核查动作与日期、**并显式声明该结论是反推的且会过期**（「反推出来的东西会过期, 且过期时不报错」）。
规约第 3 条直接照抄它，不另发明。

## 6. 外部证据（决定规约第 1 条的那条）

- **错注释实质降低模型表现，缺失 / 不完整注释影响相对轻微**（Macke & Doyle，单测生成任务；经
  [arXiv 2601.23059](https://arxiv.org/pdf/2601.23059) 综述引用）⇒ 拿不出出处时「不写」优于「写一句听起来对的」。
- **即便明确指示模型忽略注释，准确率基本不变；CoT 也无法脱离误导性文本**
  （[CodeCrash, arXiv 2504.14119](https://arxiv.org/pdf/2504.14119)）⇒ 「让下游 agent 自己判断别信」这条路堵死。
- 代码注释领域**没有**任何标准管「这句断言凭什么」：TSDoc 标准标签集无出处类标签；
  codetag（TODO/FIXME/…）字段全是追踪元数据；唯一一次标准化尝试
  [PEP 350](https://peps.python.org/pep-0350/) **Status: Rejected**（2005）。⇒ 规约无现成规范可抄。
