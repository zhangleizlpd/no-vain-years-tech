# 注释出处探针：三版判据的实测与两条根因追查

> 2026-09-01。起因：本人（Claude）在一次实现中把未核实的交易所规格当事实写进 PR 正文与 ADR，
> 维护者据此提出「我无法再用你的语气判断哪些是你核实过的、哪些是猜的」。本文记录为回答这个
> 问题所做的全部测量与追查，供 [`comment-provenance.md`](../../conventions/comment-provenance.md) 引用。

## 1. 三版探针与它们的失败方式

判据本身是**语义的**（「这句断言有没有出处」），三次尝试把它做成文本模式，两次失败：

| 版本 | 判据                                                          | 命中「无出处」  | 失败方式                                                                                                                                                  |
| ---- | ------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| v1   | 含证据宣称词（实测/实证/已确认…）且同行无 `日期 / URL / 路径` | 428 / 720 行    | **假阳 ~99%**：本仓真正在用的出处形式是**观测值本身**（`inactive 仅 cn 22 / hk 8 / us 0`）与**具名实验**（`p3b E13` / `T015` / `probe`），v1 一个都没枚举 |
| v2   | 同上 + 把观测值 / 具名实验也算出处                            | 191 / 720 行    | 仍高估：逐条读完 191 条后，真·裸宣称目测个位数；其余是「不是事实断言、而是在谈证据本身」（`无实测证据前不动`）或出处在**相邻行**                          |
| v3   | vendor 作**主语** + 行为动词，出处在**上下 3 行**内即算       | **62 / 169 行** | 可用。与 v1 相比总体缩了 4.3×、命中缩了 9.2×                                                                                                              |

**教训**：`claude-md-audit` skill 维度 5 早写过同款结论（2026-08-03 实证：按文本模式扫语义属性，
两轮 precision 探针几乎全假阳，此维**只能语义判定，禁做成正则硬拦**）。本次三版复现了它。

## 3. 两条独立的根因追查，形状完全一致

### 3.1 `alert/realtime-quote.rules.ts` 的三句腾讯断言

三句（`腾讯直给四舍五入` / `按 v_ 变量对齐而非请求顺序` / `对无效码返回空 payload`）在本仓 `git blame`
全部落到根 commit（`chore(repo): initial public snapshot`），本仓查不到写作时刻。但证据链完整：

```text
docs/private/plans/2026-06/06-07-…md   ← 原始 PoC（2026-06-08 真实请求），三句全在同一行内，带测量值
  → specs/024-alert-realtime/plan.md   ← 「PoC 已复验」
  → specs/024-alert-realtime/tasks.md  ← 「T006 vitest 锚 PoC §5.1 真实响应样本」
  → alert/realtime-quote.rules.spec.ts ← 文件头写明锚点 + 真实报文
  → alert/realtime-quote.rules.ts      ← ❌ 只剩结论，无指针
```

### 3.2 「vendor 不提供历史期权快照」

出处在 `specs/047-…/spec.md`（引 p3b §6.5，带链接）。该断言在代码 / ops / shim 中被复述
**10 次以上**，每一次复述都丢了指针。

⇒ **两条独立链条同形：证据在 spec 层完整，在代码注释层被丢弃。不是编造，是链路断在最后一跳。**

## 4. 一处反例：同一事实两处待遇不同

`vendor 财报视野约半年` 这一个事实：`marketdata/sync-earnings-event.usecase.ts` 处带着 `p3b E8`，
`optionsdesk/earnings-mark.rules.ts` 处裸着。⇒ **掉指针是随机疏漏，不是系统性不写。**

## 5. 本仓已有的标准答案

`marketdata/futu-option-snapshot.adapter.ts` 的 `inconsistent` 累加器注释同时做了三件事：给结论、
给核查动作与日期、**并显式声明该结论是反推的且会过期**（「反推出来的东西会过期, 且过期时不报错」）。
规约第 3 条直接照抄它，不另发明。

## 6. 外部证据（决定规约第 1 条的那条）

- **错注释实质降低模型表现，缺失 / 不完整注释影响相对轻微**（Macke & Doyle，单测生成任务；经
  [arXiv 2601.23059](https://arxiv.org/pdf/2601.23059) 综述引用）⇒ 拿不出出处时「不写」优于「写一句听起来对的」。
- **即便明确指示模型忽略注释，准确率基本不变；CoT 也无法脱离误导性文本**
  （[CodeCrash, arXiv 2504.14119](https://arxiv.org/pdf/2504.14119)）⇒ 「让下游 agent 自己判断别信」这条路堵死。
- 代码注释领域**没有**任何标准管「这句断言凭什么」：TSDoc 标准标签集无出处类标签；
  codetag（TODO/FIXME/…）字段全是追踪元数据；唯一一次标准化尝试
  [PEP 350](https://peps.python.org/pep-0350/) **Status: Rejected**（2005）。⇒ 规约无现成规范可抄。

**第二轮：三层机制本身的实测（2026-09-01 当日追加）**

前六节回答的是「这条规约该不该有、内容写什么」。本轮回答**机制到底触没触发、触发了有没有用** ——

## 7. 布线与触发面：8 个预登记探针

结论先行：**三层全部按设计工作，但发现两个覆盖缺口，其中一个当日修掉。**

| #   | 操作                                     | 预期        | 实际                            |
| --- | ---------------------------------------- | ----------- | ------------------------------- |
| B1  | Bash `cat` 覆盖面文件                    | 不注入      | ✅ 不注入 —— **缺口**           |
| B2  | Read 覆盖面文件                          | rule 注入   | ✅ 注入（连带时间语义共 2 条）  |
| B3  | Read 未覆盖文件（`main.ts`）             | 不注入      | ✅ 不注入                       |
| B4a | Write 新建 `marketdata/*.adapter.ts`     | hook 注入   | ✅ 注入，non-blocking，文件照落 |
| B4b | 同文件再 Write                           | 去重沉默    | ✅ 沉默                         |
| B4c | Write 新建 `marketdata/*.service.ts`     | hook 沉默   | ⚠️ **两层全沉默**（已知接受）   |
| B6a | Bash heredoc 写 `optionsdesk/*.rules.ts` | hook 不触发 | ⚠️ 不触发 —— **缺口**           |
| B6b | Edit 同文件                              | hook 注入   | ✅ 注入                         |

顺带钉死的机制事实（此前只是推测）：

1. **rule 注入按 session 去重** —— 第二次 Read 同一个覆盖面文件不再注入。
2. **Write / Edit 不触发 rule** —— path rule 只挂在 **Read 工具**上。
3. **hook 的 `additionalContext` 落在触发它的那次写入之后** —— 它管不了当次内容（已构思完），
   只能影响后续修订。「构思之前靠 rule、落盘之后靠 hook」这个分工由时序实证，不是设计意图的自述。

🚨 **B1 + B6a 合起来是一个真缺口**：`.claude/rules/*.md` 的 path 触发只认 Read 工具，
而仓里存在明确引导「能用 Bash 就用 Bash 读写文件」的会话形态 —— 那种会话里**主力层根本不点火**，
`sed` 类编辑也绕过 hook。⇒ 当日修复见 §10。

## 8. 子 agent 维度，以及取证管道翻车三次

| 问题                             | 结论           | 证据                                                                  |
| -------------------------------- | -------------- | --------------------------------------------------------------------- |
| rule 在子 agent 的 Read 上注入吗 | **注入**       | 校准 agent 逐字复述出两条 rule 全文，含只在 rule 里存在的 `2555 秒`   |
| hook 对子 agent 的 Write 触发吗  | **触发**       | 校准 agent 逐字复述完整 rubric，含 `p3b E8·T015`                      |
| worktree 隔离里触发吗            | **触发**       | 该文件路径的 hash marker，mtime 落在该 agent 运行窗口内               |
| hook 记帐记在谁名下              | **父 session** | 4 个 marker 全在父 sid 目录下                                         |
| sidechain transcript 记录注入吗  | **不记录**     | 确凿收到 rubric 的 agent，其 transcript `hook_additional_context` = 0 |

最后一行是**平台事实**，且是本轮最贵的一条：子 agent 的 transcript 对两类注入都失明，
**「transcript 里没有」不能当「没发生」的证据**。取证只能靠文件系统级真相（marker）或让 agent 逐字复述。

### 三次翻车，都是「反例存在但管道看不见」

1. **marker 检查只 `ls` 顶层找新 sid** —— 子 agent 的 marker 记在**父 sid** 目录里。
   后果：一度断言某个 agent 的 hook 自述是编造的，**冤枉了它**。翻案靠补算路径 hash 去全目录 `find`。
2. **拿 transcript `grep` 当否定证据** —— 而 sidechain 根本不记录注入。
   后果：一度得出「两层在子 agent 里全不生效」，把整个行为实验的解读推翻错了方向。
   翻案靠：先拿**已知阳性**（主 session 自己的 transcript）校准 grep 管道，再放逐字复述型校准 agent。
3. **`grep` 整个 transcript 数关键词** —— 命中的 `15:30` 全部来自 agent **读进去的文件自身**
   （仓内既有注释「`{cn,hk}` 在北京 15:30 就会分岔」，与东证无关），assistant 输出块里 0 次。
   后果：差点得出「rule 注入臂也断言了东证收盘时刻」这个反向结论。翻案靠把统计口径限定到
   `.type=="assistant"` 的 text 块。

⇒ 固化三句：**否定性结论的仪器必须先过已知阳性**；**记录器之外要有文件系统级真相或第一人称复述做交叉**；
**统计 agent 行为时，grep 口径必须限定到它自己的输出块**，否则会把「它读到的」算成「它写的」。

⚠️ 第三条在**写下这句之后又立刻犯了第四次** —— 起草 §9 时把「B 臂断言东证收盘 15:30」记成 5/5，
按同一口径复核才发现是 4/5（有一例只写了「早于 16:00，具体以时段表为准」，没给具体时刻）。
⇒ 这类纪律**写下来不等于会照做**，与 §9 测的是同一件事：起作用的是「落笔前那一刻手边有没有这条」，
不是「仓里有没有这条」。

## 9. A/B 行为实验（n=20）

**设计**：两臂读**同一份文件内容**，唯一差别是路径是否命中 rule 的 glob
（真仓路径 vs scratchpad 拷贝）。全部禁网、禁读其他文件 ⇒ 答案不在手边，
每个样本只能在「标 `ASSUMED:` / 不写 / 写裸断言」三者中选。两种任务形态各 10 例：

- **显式**：给 `isWithinPostCloseWindow` 补一段「美股收盘定稿机制」说明（注释是**主任务**）
- **隐性**：草拟「接入 jp 市场」的 diff（注释是**副产品**，更接近真实开发）

### 结果

| 任务形态 | 臂                | codetag 命中 | 未验证声明 | 自评置信度代替出处 | 判定                      |
| -------- | ----------------- | ------------ | ---------- | ------------------ | ------------------------- |
| 显式     | A（rule 注入）    | **5/5**      | 4/5        | 0/5                | 5 合规                    |
| 显式     | B（无注入，对照） | **0/5**      | 1/5        | 0/5                | 1 部分 + 4 不合规         |
| 隐性     | A（rule 注入）    | **3/5**      | 2/5        | 0/5                | 3 合规 + 2 走「不写」默认 |
| 隐性     | B（无注入，对照） | **0/5**      | 0/5        | 0/5                | 5 不合规                  |

（隐性 A 臂那 2 例 codetag 为 0，是因为它们**回避了**高风险断言、把事实推给 `market-session.rules.ts`
的时段表 —— 那正是规约①的默认②「不写」。它们仍留了一条裸的时区断言，故记「部分」。）

### 🚨 最硬的一条：裸断言不是「省事但大概率对」，它们**互相矛盾**

隐性任务里，两臂都会碰到同一个外部事实：**东证大納会 / 大発会何时由半日改全日**。

| 臂             | 5 个样本各自写下的年份                               |
| -------------- | ---------------------------------------------------- |
| B（无注入）    | **2009 / 2011 / 2009 / 2010 / 2022** —— 四个互斥值   |
| A（rule 注入） | **0/5 给年份**（标 `ASSUMED:` 说未查证，或直接不写） |

五个样本给出四个互斥年份 ⇒ 其中**至少 3 个是错的**，而每一条读起来都同样自信、
都会原样进代码注释。这条比「有没有 codetag」更值钱：它证明无出处断言的问题不是风格，是**准确率**。

同一组里 B 臂 4/5 断言「东证收盘 15:30」（A 臂 0/5 断言）—— 而 15:30 很可能是**对的**。
⇒ 论点不是「裸断言都错」，是**读者无法从注释本身分辨哪条对**。这正是规约第 1 条引的那两篇外部实证
（§6）所说的失败形态：下游摆脱不掉误导注释，而它长得和正确注释一模一样。

### 落盘后那层也有实效（非零，但性质不同）

有一例走 hook 通道（新建覆盖面文件，无 rule 注入）：初版半合规 → **rubric 注入后自发 6 次 Edit 修订**，
补齐 `ASSUMED:` 的「错了会怎样」，并按「拿不出出处默认不写」**删掉了一条无出处的 vendor 猜测**。
⇒ 兜底层不是装饰，但它买到的是「回去对一遍」，不是「一开始就写对」。

### 边界（照实说）

- n=20 仍是 pilot；两臂各 10 例，不做显著性声称。
- 显式任务把「补注释」当主任务，比真实开发更容易合规 —— 测到的是**命中率上界**；
  隐性任务才是接近真实的那一档，而两臂差距在隐性任务里**更大**不是更小。
- A 臂的 treatment 实际含两条 rule（还有时间语义那条），但时间语义 rule 不含 codetag 词汇，
  codetag 效应可归因给出处 rule。
- 两臂的「基础质量」没有差异：B 臂的技术分析同样深、同样命中真实风险形态，
  **差的只是出处纪律**。这排除了「A 臂只是碰巧分到了更强的 agent」。

## 10. 由本轮产出的改动

1. **`pretooluse-comment-provenance.sh` 增开 `PreToolUse(Bash)` 通道**（补 §7 的 B1 + B6a 缺口）。
   刻意**扩展既有脚本而不是新写一个** —— 同一份 rubric 文本、同一套 marker，
   否则就是在第二处写一份判据（那正是被测文件自己反复强调的反模式）。
   - Bash 侧**读写一视同仁**：读命令的注入落在**构思之前**（价值最高，等同 rule 层时刻），
     写命令的注入落在构思之后（等同 Write/Edit 档，作事后修订触发器）。
   - 路径**归一到仓相对形式**再做 `(session, 文件)` 去重 —— 不归一则绝对路径（Write/Edit）
     与相对路径（Bash）互不认识，同一个文件注入两次。
   - 用 `tr -c` 白名单法从命令串里捞路径，而不是逐个列 shell 元字符（黑名单必漏）。
   - 对照表测试 `pretooluse-comment-provenance.test.sh`：26 例，含 3 组定向变异验证
     （砍 Bash 分支 → 11 红；砍去重 → 恰好 3 条去重臂红；砍路径归一 → 恰好跨通道那条红）。
2. **`comment-provenance.md` §5 的三层表改写** —— 「构思之前」现在有两个入口（Read 工具 / Bash 读命令），
   并写明**判断覆盖时先问走的是哪个工具，别按「读还是写」分**。

### 仍未覆盖（明确留白）

- `marketdata/*.service.ts` 这类**在 rule glob 内、但不在 hook 面内**的后缀，新建文件时两层全空
  （§7 探针 B4c）。hook 面收窄是按 PoC 数据蓄意的，此条属已知接受的残余，现已有实测坐标。
- **聊天正文 / PR 描述里的断言仍然没有任何机制看得见。** 本轮 B 臂的产出就是这个失败形态在
  受控环境下的样子 —— 同一个模型，同一份上下文，少一层注入就 10/10 写裸断言。
