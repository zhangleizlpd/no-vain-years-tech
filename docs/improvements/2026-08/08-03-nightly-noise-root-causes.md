两个认知都错：按 run 史锚定「最后一次绿」，**perf = 06-08、real-backend = 06-22**——不是间歇 flake，是各有一个测试**从出生那晚起一次没绿过**，恒红被「软信号 + 每晚自动开 issue」掩护了近两个月（清理时 open issue 已堆 **48 张**，含 sweep 的历史堆积）。

## 取证链（可复用的方法）

1. **按 run 史找绿转红日**：`gh run list --workflow=X --limit 100` 取最后 success 的日期与 headSha —— 别只看最近几次。
2. **对齐嫌疑测试的出生时间**：`git log --diff-filter=A -- <spec>` —— SC-005 于 06-09 01:53 合入 vs 最后绿 06-08 21:48；034 契约 06-23 05:21 合入 vs 当晚 22:19 即首红。**出生即红 = 排除回归类假设**。
3. **本地双臂复现**：
   - SC-005 本地 `RUN_PERF_IT=1 PERF_IT_REPS=1` → **125ms 全绿** ⇒ 测试自身健康；
   - post-T-1 干净 main dispatch（run `30760401856`，轻量化 suite）**照红** ⇒ 排除「suite 并发争抢」主因；
   - ⇒ 剩下唯一差异 = `PERF_IT_REPS=300`。
4. **读代码闭合机制**（见下）。中途一个假设被证伪：曾疑 CI 失败源于 CalendarSourceFallbackChain WARN 风暴，本地复现零 WARN ⇒ 那是超时后其他并行文件的日志串流。

## 根因

|        | 机制                                                                                                                                                                                                       | 一句话                                             |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| SC-005 | rep 数继承 `PERF_IT_REPS`（auth P95 的**单端点采样数**，nightly=300），而 SC-005 一个 rep = 完整 tick（200 标的求值 + 触发派发 + DB 收尾），300 个必超 120s timeout                                        | **knob 语义错配**：采样数 ≠ 全量重放数，贵三个量级 |
| 034    | `FakeIdeationLlmProvider` 单例、剧本游标全生命周期单调；contract-smoke 一次 boot 顺序跑全部套件 ⇒ 032 耗尽三轮剧本后，034 澄清轮拿到越界空轮 → 0 token 帧。module 注释「调用序固定一一对位」只对单套件成立 | **共享单例 + 按调用次数对位** 在多套件下必坏       |

## 修复（#830）

1. provider 加 `loopByToolMenu`（真 boot bake 专用）：按当轮工具菜单环扫选轮，与套件数量/次序解耦；IT 游标语义不变。
2. SC-005 独立 knob `PERF_TICK_REPS` 默认 1（预算断言一个 rep 即成立），登记 `check-env-sync` `ALLOWLIST`。
3. 连带（本地复现时实证的 harness 泄漏）：contract-smoke harness 钉 `CODE_INDEX_PROVIDER=fake`（本地 `.env` 的 http 隧道端点漏进来 → repos 503）+ `OSS_PUBLIC_BASE_URL=''`（备案域真值漏进来 → 037 断言红）。
4. 三条 nightly 的 issue 创建加同名去重（同一断裂一张票）。

## 验证与结果

- fake provider 单测 18/18（新增 5 条，含复刻 034 越界空轮现场的回归反例）
- SC-005 双臂：`RUN_PERF_IT=1 PERF_IT_REPS=300` 下 128ms 过（不再继承）
- 本地 contract-smoke **18/20 → 20/20**
- 修复后 main dispatch **双绿**：perf run `30761363333`（06-08 后首绿）/ real-backend run `30761367819`（06-22 后首绿）
- 48 张堆积 issue 全关，open issues 归零

## 耐久教训（已进矩阵 T-3）

1. **软信号连红第一晚就该当事故治** —— 恒红信号 = 零信息，且掩护一切真回归（19/20 绿的套件里任何新破坏都被同一张红脸盖住）。
2. **「连红 N 次」要用 run 史 + 出生时间对齐取证**，别拿最近几次的印象当病程 —— 两条的真实病程都比 plan 记的长 3-7 倍。
3. **共享单例的 fake + 按调用次数对位剧本**是多套件冒烟的结构性反模式；对位应锚定**语义**（工具菜单/相位），不锚定次数。
