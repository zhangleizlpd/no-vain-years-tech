# prod 优雅关停：补上 `enableShutdownHooks()` 并让关停预算自洽

> **调优 / 改造记录**（per [docs-organization](../../conventions/docs-organization.md) 三类记录）。
> 修的是 issue #824，来源是 [BullMQ 关停顺序](08-02-bullmq-shutdown-order.md) §7 顺带发现的独立问题。

## 1. 问题

`apps/server/src/main.ts` **没有调用 `app.enableShutdownHooks()`**。

NestJS 官方明确：`onModuleDestroy` / `beforeApplicationShutdown` / `onApplicationShutdown` **只在**显式 `app.close()` 或（收到 SIGTERM/SIGINT **且**调过 `enableShutdownHooks()`）时触发（[Lifecycle events](https://docs.nestjs.com/fundamentals/lifecycle-events)）。

⇒ prod 容器收到 SIGTERM 时，本仓所有关停钩子**一个都不跑**：

- BullMQ Worker 不会 `close()` ⇒ **in-flight job 不等跑完就随进程消失**，变成 stalled job。BullMQ 的兜底是「stalled 由其他 worker 接管」，但本仓是**单实例部署**，没有其他 worker。
- Redis / Prisma 连接不走各自的收尾路径。

**缺失是 100% 静默的** —— 服务照常起、健康检查照常绿，只在部署/重启那一刻悄悄丢 job。事实上这一行缺了几个月，直到排查另一个问题时才顺带撞见。

## 2. 改了什么

| 改动                                                           | 为什么                                       |
| -------------------------------------------------------------- | -------------------------------------------- |
| `main.ts` 在 `listen()` **之前**加 `app.enableShutdownHooks()` | 之后加会留下「已开始收流量但钩子未挂」的窗口 |
| `docker-compose.tight.yml` app 服务加 `stop_grace_period: 40s` | **不加等于白等**（见 §3）                    |
| 新增 `scripts/checks/check-shutdown-hooks.ts`，接进 PR 门      | 那一行是整个接线，删掉是静默的               |
| `test/integration/queue-shutdown-order.it.spec.ts` 追加一条    | 证明 `close()` 真的会等 in-flight job        |

## 3. 关停预算必须自洽（否则「等」是假的）

docker 默认 `stop_grace_period` 是 **10s**，到点 SIGKILL。而本应用的关停要等：

| 层                 | 值                                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 单个关停点超时     | 10s（`security/close-with-timeout.ts`）                                                              |
| 单 provider 内最坏 | 20s（内部串行两次 `close()`）                                                                        |
| 整体最坏           | ≈20–25s（Nest 对同模块 providers 的钩子**并行**，[上一轮实测](08-02-bullmq-shutdown-order.md) 确认） |

⇒ 用默认 10s 会得到「看起来在优雅关停、实际到点被砍」的最坏结果 —— 比不启用还糟，因为它制造了一种已经处理好的错觉。

设 **40s**，留约 15s 余量。🚨 **关键认识：`stop_grace_period` 是上限不是固定等待** —— 容器提前退出 docker 立刻继续，所以给足**不产生日常部署代价**。

> 改任一侧（超时值 / 宽限期）都要回来核这笔账。`main.ts` 与 compose 两处注释互相指认。

## 4. 怎么验的（两臂对照）

**判别量的选择走了两次弯路，记下来**：

| 尝试                                 | 结果           | 为什么不成立                                    |
| ------------------------------------ | -------------- | ----------------------------------------------- |
| 比较 SIGTERM 后的**退出码**          | 两臂都是 143   | Nest 走完钩子后会**重新抛该信号**，所以两边一样 |
| 比较**退出耗时**（无 in-flight job） | 两臂都是 0.02s | 没有 job 在飞，本来就无事可等                   |
| **临时在关停钩子里加 2s 延迟**       | ✅ 判别成立    | 直接测「钩子到底跑没跑」                        |

最终实验：给 `RedisLifecycle.onApplicationShutdown` **临时**塞一个 2s 延迟，两臂同样的探针、同样的 boot：

| 臂  | `enableShutdownHooks()` | SIGTERM → 退出耗时           |
| --- | ----------------------- | ---------------------------- |
| A   | 有                      | **2.03s** ← 钩子执行了       |
| B   | 无                      | **0.03s** ← 钩子**根本没跑** |

两臂 boot 日志同为 29110 字节（同一条 boot 路径），排除「其中一臂没起来」。

### 🚨 前三轮测量全部无效（同一个坑踩第二次）

前三轮两臂都得到 0.02s，我一度以为「没有差异」。真因是**上一轮遗留的 node 进程还占着 3199 端口**：

- 健康检查打的是**那个旧进程**，所以「服务起来了」判定为真
- 每个新 arm 因端口被占**秒退**
- 铁证：arm 日志**是空的**（0 字节），而有效轮次是 29110 字节

这与上一轮那个 41 分钟的自旋孤儿是**同一类错误**，而我刚把那条教训写进 [上一份记录](08-02-bullmq-shutdown-order.md) §8.3 就又犯了。

**修法（已固化进实验脚本）**：每轮开跑前断言**端口空闲**，起来后再断言**监听该端口的 PID 就是本轮起的那个**。这两条前置断言能一次性堵掉整类「打到了别人身上」的假测量。

## 5. 遗留：没做健康检查摘流

issue #824 里列的第 2 个前置问题（「要不要同时上健康检查摘流」）**本轮没做**。

现状是「收到 SIGTERM → 立刻开始关停」，而不是「先从负载均衡摘掉 → 排空在途请求 → 再关停」。单实例部署下这条链本来就不完整（摘掉了也没有第二个实例接），所以优先级不高，但**不要因为本记录存在就以为它已经解决**。

## 6. 方法论留痕

1. **「判别量」本身要先验证。** 退出码和耗时都是看起来合理的判别量，实测都不成立。找不到自然判别量时，**临时注入一个人为可观测的差异**（这里是 2s 延迟）比硬凑要可靠得多。
2. **测量前置断言 > 事后解释。** 「端口空闲」+「端口主人是本轮进程」两条断言，成本各一行，能堵掉整类残留污染。我是在浪费了三轮之后才加上的。
3. **同一个坑会隔一轮再踩。** 残留进程污染测量这条，我上一轮刚写进文档。写下来不等于用得上 —— **它得变成脚本里的一行断言，而不是文档里的一句话**。
