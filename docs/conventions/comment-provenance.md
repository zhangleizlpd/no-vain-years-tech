# 注释出处约定

> 管一件事：**注释里出现「外部世界会怎样」的断言时，写不写、怎么写。**
> 实测与根因追查见 [`docs/improvements/2026-09/09-01-comment-provenance-probe.md`](../improvements/2026-09/09-01-comment-provenance-probe.md)。

## 适用面

**只管「外部世界断言」** —— 关于 vendor / 交易所 / 第三方平台 / 外部库**运行时行为**的陈述。

不管（本约定零适用）：本仓自己的代码在做什么、我们的设计取舍、我们自己写的 shim 与端点行为
——那些从相邻代码即可证否，读者不需要第二个来源。

## 一、要不要写

```text
这条断言是关于外部系统行为的吗？
├─ 否 → 本约定不管，照常写
└─ 是 → 我此刻能指出出处吗？
        ├─ 能  → 写，带 EVIDENCE: 指针
        └─ 不能 → 三选一，按优先级：
                  ① 去验证（联网查一手文档 / 实取一次 / 翻 fixture），然后按「能」走
                  ② 不写                                    ← 默认
                  ③ 代码行为确实依赖它、非写不可 → 标 ASSUMED:
```

🚨 **② 是默认而不是保底**，判据是外部实证：**错注释会实质降低模型表现，而缺失注释影响相对轻微**
（见实测记录 §6）。⇒ 拿不出出处时，**「不写」的代价小于「写一句听起来对的」**。

🚨 **MUST NOT 指望下游读者自己打折** —— 实测：即便明确指示模型忽略注释，其准确率基本不变；
CoT 也无法脱离误导性文本。一条无出处的断言会**主动**把下一个读者（人或 agent）带偏。

## 二、怎么写

两个 codetag。取 codetag 形态是为了白嫖现成工具面（IDE 高亮 / `rg` 可枚举），不是为了好看。

```ts
// EVIDENCE: <断言> —— <出处>
// ASSUMED:  <断言> —— 未验证；<失效时会怎样>
```

**`EVIDENCE:` 的出处**取以下任一（按可核对性排序）：

| 形式                      | 例                                                     |
| ------------------------- | ------------------------------------------------------ |
| 一手文档 URL              | 交易所 / vendor 官方页                                 |
| 仓内 fixture 或 spec 路径 | `__fixtures__/…json` · `*.adapter.spec.ts` 的真实响应  |
| SDD / ADR 锚              | `specs/NNN/spec.md` · `ADR-00NN` · `FR-0NN`            |
| 具名实验                  | `p3b E8` · `T015` · `066 U2` —— 本仓既有词汇，别造新的 |
| 实测日期 + **观测值**     | `2026-08-25 实测：30 只 12 拍 360 行里 OI 只变动一次`  |

🚨 **观测值本身就是合法出处** —— 给出可复算的数（`72/100` / `→ 403` / `2555 秒`）比给一个日期更强。
这是本仓既有的主流写法，不是新增要求。

## 三、复述别人的实测，要点名是谁测的

同一事实在仓内被复述时，**指针必须跟着走**。做不到就点名来源方（「维护者 2026-09-01 直查 prod」），
**MUST NOT 写成无主语的「实测」** —— 读者会以为本文作者复算过。

判据来自实测记录 §3：本仓两条独立证据链都在「spec → 代码注释」这一跳掉了指针，
而 §4 那个反例证明它是**随机疏漏**而非系统性不写 —— 所以它值得一道守卫，而不是一次清理。

## 四、`ASSUMED:` 必须写明失效后果

反推出来的结论**会过期，且过期时不报错**。故 `ASSUMED:` 至少答两问：**凭什么这么推**、
**它错了会怎样**。范本见 `marketdata/futu-option-snapshot.adapter.ts` 的 `inconsistent` 累加器注释
（结论 + 核查动作与日期 + 显式声明是反推且会过期，三件齐全）。

🚫 **MUST NOT 用自评置信度代替出处**（「大概」「应该是」「我比较确定」）—— 自评在没见过的情形下
不可靠，而指针任何时候都可核对。二元表达：**要么给得出出处，要么直说未验证**。

## 五、为什么这条约定必须靠工具而不是自觉

「有没有出处」是**语义判定**：本仓三版文本探针的假阳率见实测记录 §1，与 `claude-md-audit`
skill 维度 5 的既有结论一致 —— **禁做成正则硬拦**。

⇒ 守卫形态是**注入自检**，不是 blocking check。**三层，覆盖的是三个不同时刻**：

| 时刻               | 机制                                                                                                   | 覆盖                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| **构思注释之前**   | `.claude/rules/comment-provenance-sync.md`（path-scoped，Read 命中即注入）                             | 改既有文件的主流路径（Read → Edit）                     |
| 已构思完、落盘之前 | `scripts/hooks/pretooluse-comment-provenance.sh`（`PreToolUse(Write\|Edit)`，按 (session, 文件) 去重） | **新建文件**（path rule 此时不触发）+ 未先 Read 就 Edit |
| 事后               | 无                                                                                                     | 语义属性，禁做成正则（见 §5 开头）                      |

🚨 **第一层才是根上那道** —— hook 注入时注释文本已经写好了，它问的是「回去对一遍」；
path rule 在 Read 命中时注入，那时还没动笔。hook 是**兜底**不是主力。
