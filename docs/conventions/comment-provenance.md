# 注释出处约定

> 管一件事：**「外部世界会怎样」的断言出现在会留存的文字里时，写不写、怎么写。**
> 载体有三种：**代码注释**（主场）、**PR 正文**、**commit message**（release-please 会把
> subject 抄进 CHANGELOG）。判据同一套，差别只在措辞与守卫时刻（见 §5）。
> 实测与根因追查见 [`docs/improvements/2026-09/09-01-comment-provenance-probe.md`](../improvements/2026-09/09-01-comment-provenance-probe.md)。

## 适用面

**只管「外部世界断言」** —— 关于 vendor / 交易所 / 第三方平台 / 外部库**运行时行为**的陈述。

不管（本约定零适用）：本仓自己的代码在做什么、我们的设计取舍、我们自己写的 shim 与端点行为
——那些从相邻代码即可证否，读者不需要第二个来源。

⚠️ **载体维度与内容维度是两件事，别混**：换了载体（注释 / PR 正文 / commit message）判据不变；
换了内容（外部世界 → 我们自己的代码）才出适用面。PR 正文里讲「这个 PR 改了什么」不归本约定管，
讲「交易所会怎样」才归。

## 一、要不要写

```text
这条断言是关于外部系统行为的吗？
├─ 否 → 本约定不管，照常写
└─ 是 → 我此刻能指出出处吗？
        ├─ 能  → 写，带 EVIDENCE: 指针
        └─ 不能 → 三选一，按优先级：
                  ① 去验证（联网查一手文档 / 实取一次 / 翻 fixture），然后按「能」走
                  ② 不写                                    ← 默认
                  ③ 代码行为确实依赖它、非写不可 → 标 ASSUMED:
```

🚨 **② 是默认而不是保底**，判据是外部实证：**错注释会实质降低模型表现，而缺失注释影响相对轻微**
（见实测记录 §6）。⇒ 拿不出出处时，**「不写」的代价小于「写一句听起来对的」**。

🚨 **MUST NOT 指望下游读者自己打折** —— 实测：即便明确指示模型忽略注释，其准确率基本不变；
CoT 也无法脱离误导性文本。一条无出处的断言会**主动**把下一个读者（人或 agent）带偏。

## 二、怎么写

两个 codetag。取 codetag 形态是为了白嫖现成工具面（IDE 高亮 / `rg` 可枚举），不是为了好看。

```ts
// EVIDENCE: <断言> —— <出处>
// ASSUMED:  <断言> —— 未验证；<失效时会怎样>
```

**`EVIDENCE:` 的出处**取以下任一（按可核对性排序）：

| 形式                      | 例                                                     |
| ------------------------- | ------------------------------------------------------ |
| 一手文档 URL              | 交易所 / vendor 官方页                                 |
| 仓内 fixture 或 spec 路径 | `__fixtures__/…json` · `*.adapter.spec.ts` 的真实响应  |
| SDD / ADR 锚              | `specs/NNN/spec.md` · `ADR-00NN` · `FR-0NN`            |
| 具名实验                  | `p3b E8` · `T015` · `066 U2` —— 本仓既有词汇，别造新的 |
| 实测日期 + **观测值**     | `2026-08-25 实测：30 只 12 拍 360 行里 OI 只变动一次`  |

🚨 **观测值本身就是合法出处** —— 给出可复算的数（`72/100` / `→ 403` / `2555 秒`）比给一个日期更强。
这是本仓既有的主流写法，不是新增要求。

## 三、复述别人的实测，要点名是谁测的

同一事实在仓内被复述时，**指针必须跟着走**。做不到就点名来源方（「维护者 2026-09-01 直查 prod」），
**MUST NOT 写成无主语的「实测」** —— 读者会以为本文作者复算过。

判据来自实测记录 §3：本仓两条独立证据链都在「spec → 代码注释」这一跳掉了指针，
而 §4 那个反例证明它是**随机疏漏**而非系统性不写 —— 所以它值得一道守卫，而不是一次清理。

## 四、`ASSUMED:` 必须写明失效后果

反推出来的结论**会过期，且过期时不报错**。故 `ASSUMED:` 至少答两问：**凭什么这么推**、
**它错了会怎样**。范本见 `marketdata/futu-option-snapshot.adapter.ts` 的 `inconsistent` 累加器注释
（结论 + 核查动作与日期 + 显式声明是反推且会过期，三件齐全）。

🚫 **MUST NOT 用自评置信度代替出处**（「大概」「应该是」「我比较确定」）—— 自评在没见过的情形下
不可靠，而指针任何时候都可核对。二元表达：**要么给得出出处，要么直说未验证**。

## 五、为什么这条约定必须靠工具而不是自觉

「有没有出处」是**语义判定**：本仓三版文本探针的假阳率见实测记录 §1，与 `claude-md-audit`
skill 维度 5 的既有结论一致 —— **禁做成正则硬拦**。

⇒ 守卫形态是**注入自检**，不是 blocking check。**按时刻分四档**（同一个 hook 脚本承担其中三档，
刻意不拆成多个脚本 —— 判据与 rubric 在一处，拆开必漂移）：

| 时刻               | 机制                                                                                  | 覆盖                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **构思注释之前**   | `.claude/rules/comment-provenance-sync.md`（path-scoped）                             | **Read 工具**命中覆盖面文件 —— 改既有文件的主流路径（Read → Edit）                       |
| **构思注释之前**   | `scripts/hooks/pretooluse-comment-provenance.sh` 的 `PreToolUse(Bash)` 分支           | Bash **读**命令（`cat` / `sed -n` / `grep`）—— path rule 只认 Read 工具，不认 Bash       |
| 已构思完、落盘之前 | 同一脚本的 `PreToolUse(Write\|Edit)` 分支，以及 Bash **写**命令（heredoc / `sed -i`） | **新建文件**（path rule 此时不触发）+ 未先 Read 就 Edit + 一切绕过 Write/Edit 的 Bash 写 |
| **发布之前**       | 同一脚本的 `PreToolUse(Bash)` 分支，识别 `gh pr create/edit`、`git commit`            | **PR 正文 / commit message** —— 不按路径判，按「对外发布动作」判                         |
| 事后               | 无                                                                                    | 语义属性，禁做成正则（见 §5 开头）                                                       |

🚨 **「构思之前」那两行才是根上那道** —— 落盘前注入时注释文本已经写好了，它问的是「回去对一遍」；
构思前注入时还没动笔。落盘前那层是**兜底**不是主力（兜底仍有实效：注入后自发回改是实测到的，见实测记录 §9）。

🚨 **path rule 不认 Bash** —— 它挂在 Read 工具上。仓里存在明确引导「能用 Bash 就用 Bash 读写文件」
的会话形态，那种会话里主力层根本不点火；这正是 hook 要接 `Bash` matcher 的唯一理由（实测记录 §7）。
⇒ 判断某条通道有没有覆盖时，**先问它走的是哪个工具**，别按「读还是写」分。

🚨 **发布通道的 rubric 与注释那份刻意不同文** —— 注释的读者是下一个改这个文件的人，PR 正文的
读者是 review 的人、翻归档的人、读 CHANGELOG 的人。合成一份两头都不贴切。发布那份多两条：
**复述仓内结论时指针要跟着走**、**别把「单日探针观测到 X」升格成「X 是交易所规格」**（两条都是
本仓实撞过的形态，见 §3 与实测记录）。

⚠️ **聊天正文拦不到，且这是结构性的** —— 没有工具调用就没有 `PreToolUse`。文件写入与命令执行
都经工具（可拦），说话不经工具（不可拦）。⇒ 别指望再加一层能覆盖它。

路径类通道**共用一套 `(session, 仓相对路径)` marker**：同一个文件一个 session 只注入一次，
且路径先归一到仓相对形式才比对 —— 不归一则绝对路径（Write/Edit）与相对路径（Bash）互不认识，
同一个文件会注入两次。刷屏会把规约训练成墙纸。
