# ADR-0065: 研报库第 11 Bounded Context — 私有桶 + server 代理上传（amend ADR-0045 两条被否决项）

- Status: Accepted (2026-08-15)
- Deciders: @zhangleizlpd
- Tags: server / bounded-context / research / object-storage / guest-channel
- Relates: [ADR-0045](0045-object-storage-image-upload.md)（对象存储选型 + 图片直传架构；**本 ADR amend 其两条被否决项**）/ [ADR-0032](0032-backend-bounded-context.md)（bounded context 拆分框架）/ [ADR-0043](0043-server-flat-module-paradigm.md)（扁平贫血范式 + port 三分法）/ [ADR-0052](0052-alert-bounded-context.md)（第 6 ctx，PRD 同级板块独立成 ctx 的先例）/ [ADR-0041](0041-server-common-directory-policy.md)（通道层 guard 落 `security/` 的先例）/ [ADR-0058](0058-server-integrations-layer.md)（平台层 vendor I/O 适配器）；实施载体 = [057-research-report-guest-ingest](../../specs/057-research-report-guest-ingest/spec.md)

## Context

[PRD §3.8 研报库](../prd/portfolio/portfolio-master-prd.md) 的第一个 use case 落地：隧道内的外部投递方经 openclaw skill 投递个股 PDF 研报，server 中转落私有对象存储，元数据落 PG。

两个决策需要抽出 feature plan 之外：

1. **研报是不是一个独立的 bounded context**，还是塞进 `marketdata`。
2. **本片的上传架构与 ADR-0045 的两条被否决项直接冲突** —— 那份 ADR 明确否决过「后端代理上传」与「private bucket + 签名 GET」，而本片正是两者。这不是"忘了看 ADR"，是同一个问题在**不同驱动用例**下换了答案，必须留痕。

### ADR-0045 的 sunset_trigger 命中情况（逐条核过）

| trigger 原文                                                                                                               | 命中                        | 说明                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| blob 需求从「小图片」扩张到视频 / 大文件 / 分片续传 / PKM 大附件 → 上传架构（§2）重审                                      | ✅ **字面命中**             | 本片 blob 是 16MB 上限的 PDF                                                                                                                                                                               |
| 出现需私密化的**图片**资产（付费内容 / 私密相册 / 非公开 profile）→ 访问模型（§3）从 public-read 重审为 private + 签名 GET | ⚠️ **类比命中，非字面命中** | 🚨 trigger 原文限定「**图片**资产」，而本片是 **PDF**。精神完全适用（都是「需要私密化的用户资产」），但**字面上对不上** —— 写在这里是为了不让后人以为字面命中过；将来若要收紧该 trigger 的措辞，本行是理由 |

其余 trigger（换云 / 盗链 / 海外延迟 / 成本）本片均未命中。

## Decision

### §1 立第 11 个 bounded context `research`，跨 ctx 面为 0

依据是**仓内既成先例**，不是 DDD 论证：研报库在 PRD 里与 §3.5 预警管理、§3.6 笔记管理**同级**，而 §3.5 已落成独立 ctx `alert`（[ADR-0052](0052-alert-bounded-context.md)，6 model）。塞进 `marketdata` 会造成同级板块两套落法。

另两条硬理由：

1. `marketdata.Announcement` 的 `instrumentId` 是**必填 FK 且在唯一键内**，行业 / 宏观研报没有它 ⇒ 那张表结构上不可复用。
2. marketdata 30 张表的共同不变量是「vendor 采集、可 truncate 后重新 backfill」。研报**不可重采**（它是用户资产），放进去会把「该 schema 能否整体重建」的答案从「能」变成「不能」。

**跨 ctx 面 = 0**：`symbol` 存归一后的 `market:code` **裸字符串**，不建到 `marketdata.instrument` 的外键、不做存在性校验 —— 校验会拒绝合法的新标的（研报常常先于标的入库），且引入本可避免的 Q7-B 依赖。对齐 [014](../../specs/014-stock-detail/spec.md) 已确立的「与 015 运行时零跨 ctx，仅共享 `market:code` 逻辑键」。

> ⚠️ **「跨 ctx 面 = 0」已被 2026-08-16 复审改为 1**（一条 Q7-B 只读，见 § 复审记录）。上段正文冻结为 2026-08-15 原决策留痕，不回改 —— 其中「不建外键、不做存在性校验」的部分**至今仍然成立**，被放宽的只有「不引入 Q7-B 依赖」那半句。

ESLint boundaries 里 `research` 的 disallow **含 `account`**：guest 面走通道层常量 token、零用户 principal，不碰 `JwtAuthGuard`。这是一条**刻意的绊线** —— PRD §3.8 已规划 app 侧投递入口，那个 feature 接入时需要 `JwtAuthGuard`，lint 会红；那次改 allowlist 的动作就是「鉴权入口从一条分叉成两条」的显式时刻，不该悄悄发生。

### §2 上传架构：private bucket + **server 代理上传**（amend ADR-0045）

**ADR-0045 §2 的「client 直传、后端绝不代理字节」在本片不成立**，因为驱动用例变了：

|                         | ADR-0045（头像 / 背景图）         | 本片（研报）                                                                                                                    |
| ----------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 谁上传                  | app 用户，持系统账号              | 隧道内的**外部投递方**，无系统账号                                                                                              |
| 客户端能否拿到 OSS 凭证 | 能（凭证 scope 锁到他自己的前缀） | **不能** —— 给投递方 OSS 凭证等于把桶的写入面交给隧道外的第三方；且 FR-015 明确要求投递方**不得获知**系统访问归档存储所用的凭证 |
| 字节量级                | 数 MB 图片，量大                  | 约 2MB/份，一天几份                                                                                                             |

⇒ 代理上传在本片不是"扩展性差"，而是**唯一符合信任边界的形态**：投递方的凭证只能证明"请求经由那条隧道代理而来"，OSS 凭证始终留在 server 侧。字节量级也让"代理字节"这条代价在本片近乎为零。

**平台层零新签名代码**：复用 `integrations/oss/oss-policy.ts` 的 V4 PostObject 表单签名（server 拿到签名后自己组 `FormData` POST）。刻意**不引 `ali-oss`** —— 仓内 OSS 能力是手写 V4 签名、零 SDK；引入它只用得上 1% 能力，却要付 Trivy HIGH+ 阻塞面与 `pnpm --prod --legacy deploy` 的 prune-后-才-fatal 风险面。

**有网络 I/O ⇒ 留 port**（[ADR-0043](0043-server-flat-module-paradigm.md) port 三分法第三类）：`ObjectStoragePort` 的 `putObject` 有**三态**结局 —— 确认成功 / 确认被拒 / **无法确定**（超时、连接中断、5xx）。后两者绝不可合并：把"无法确定"当"被拒"，一个其实传成功的投递方会被告知失败并去重传，而我们**没有读权限去回查**（见 §3）。

### §3 访问模型：private bucket + 只写凭证（amend ADR-0045）

**ADR-0045 §3 的 public-read 在本片直接不适用**：研报含用户的持仓与主观判断。

RAM 策略只给 `research/` 前缀的 `oss:PutObject`，**无读 / 列举 / 删除**（FR-018）。这条约束有两个非显然的下游后果，都已写进实现：

1. **孤儿对象清不掉** ⇒ 写序必须是「DB 写 PENDING → OSS put → DB 翻 COMMITTED」，「查得到」（扫 `status='PENDING'`）是唯一的补救前提。反过来先传对象的话，落库失败会留下一个不可见、不可清、持续吃配额的孤儿。
2. **不能靠事后 HEAD 回查判定写入结果** ⇒ 三态判定只能基于写入动作**自身**的响应（这正是 §2 那个 port 不提供 `head` / `exists` 的原因：那类方法在这套策略下根本调不通，留着只会引诱人去用）。

**FR-018 在代码侧没有任何可断言的载体** —— 服务端怎么写都改变不了凭证的权限。它唯一的回归防线是 `research-oss.vendor.spec.ts` 里那条**反例**断言（写 `research/` 之外必须 403 AccessDenied），Phase 0 已用真凭证实证。⇒ **每次轮换 AK 之后必须手工重跑该文件**。

### §4 单向收集箱：通道与服务两层各自独立拒绝读取

服务端**不实装任何 GET / PATCH / DELETE**（FR-012）；通道层（guest-proxy nginx 的 `limit_except POST`）**独立地**再拒一次（FR-013）。

不依赖对方的理由：「服务端恰好没实现」是会被未来某个 PR 悄悄打破的状态 —— 某天有人加了内部 list 端点、路径前缀一样，就直接对隧道内的投递方开放了。

## Alternatives Considered

| 方案                                                    | 否决理由                                                                                                                                                                              |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **塞进 `marketdata` ctx**                               | `Announcement` 的必填 FK `instrumentId` 使那张表不可复用；且会给「vendor 采集、可 truncate 重建」的底座装上不可重采的用户资产                                                         |
| **给投递方发系统账号 token 走标准口子**                 | `JwtAuthGuard` 是**全站鉴权面**，全部 authed controller 共用 ⇒ 给投递方一个能过它的 token = 把持仓 / 交易记录 / 自选 / 期权锚 / chat 会话全部给他。与「面越小越好」的通道设计直接冲突 |
| **给投递方直接下发 OSS 上传凭证（沿用 ADR-0045 直传）** | 违反 FR-015（投递方不得获知系统访问归档存储的凭证）；且凭证一旦泄漏，桶的写入面暴露给隧道外                                                                                           |
| **复用账号 B 的图片桶（同一组 `OSS_*` 凭证）**          | 两个阿里云账号、两种 ACL、两种用途；那把 AK 的 RAM 作用域是 `avatar/` + `background/`，与研报桶权限交集为空。并进同一个 config union 会让「哪把 AK 写哪个桶」变成运行时才发现的错     |
| **引入 `ali-oss` SDK**                                  | 只用得上 1% 能力，却引入完整依赖树的 Trivy 阻塞面与部署 prune 风险；仓内已有经真桶验证的手写 V4 签名                                                                                  |
| **先传对象再落库（单段写）**                            | OSS 成功 + DB 失败会留下不可见、不可清、持续吃配额的孤儿 —— 而我们没有删除权限                                                                                                        |
| **事后 HEAD 回查确认写入结果**                          | 需要读权限，与 §3 的只写凭证直接冲突                                                                                                                                                  |

## Consequences

**正向**：研报库有了独立的演进空间（PRD §3.8 自评含导入 / 存储 / 阅读器 / 版本化四块）；平台层零新签名代码；投递方凭证泄漏的最坏后果被限定为「向归档区写入垃圾」。

**代价**：

- server 代理字节 ⇒ 一份 16MB 研报会在进程内驻留一份完整 Buffer。已由四层体积天花板兜住（nginx 20MB > OSS `content-length-range` 17MB > multipart 16MB，让中间那层先跳闸，因为它是唯一能给干净 ProblemDetail 的一层）。
- 无删除权限 ⇒ 孤儿对象只能积累不能清理。已由 PENDING 行的可扫性 + 每投递方 8GB 配额兜住。
- 与 ADR-0045 并存两套 OSS 配置（两个账号、两组 env、两个 config namespace）。这是有意的：合并会让权限错配从"编译期不同的 config"退化成"运行期的 403"。

## 对 ADR-0045 的 amend（Superseded-in-part）

ADR-0045 的 **Alternatives Considered** 表里两行在本 ADR 的驱动用例下**不再成立**，但**对该 ADR 自身的驱动用例（profile 图片）仍然成立**：

| ADR-0045 原否决项                   | 原否决理由                                                            | 本 ADR 的修正                                                                                                                                                                           |
| ----------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **后端代理上传（client→后端→OSS）** | 「代理图片字节、扩展性差、与现代最佳实践背道」                        | 当上传方是**隧道内的第三方**而非系统账号用户时，代理是唯一符合信任边界的形态（见 §2 对照表）。**profile 图片仍走直传，ADR-0045 §2 不变**                                                |
| **private bucket + 签名 GET**       | 「profile 图本就公开 → 语义不符；每次显示要签、CDN 缓存复杂，无收益」 | 研报含持仓与主观判断，语义恰好相反。本片更进一步：**连签名 GET 都不做**（凭证只具写入能力），读取路径是本人走对象存储管理面 + DB 直连。**profile 图片仍 public-read，ADR-0045 §3 不变** |

⇒ ADR-0045 的状态**不变**（仍 Accepted）：它对自己的驱动用例依然正确。本 ADR 只是记录「同一问题在不同信任边界下的另一个答案」。

> 🚫 **本 ADR 刻意不写反向 sunset_trigger**（如「12 个月内无第二个 use case 就折叠本 ctx」）。该提议建立在「研报只是一张表」的前提上，而 PRD §3.8 自评「体量足够独立成篇」，含导入 / 存储 / 阅读器 / 版本化四块 —— 前提已被证伪，不该把一条基于错误前提的复审挂在这里。

## 复审记录 — 2026-08-16（058 同标的多版本与元数据回声）

> **触发源不是 frontmatter 的任何 `sunset_trigger`** —— 5 条逐条核过均未命中（最接近的第 5 条限定「跨账号共享 / 多租户」，本片是单投递方回显）。触发源是 [058](../../specs/058-research-report-versioning/spec.md) 的新需求：投递方对自己声明的 `symbol` **零反馈**，是 2026-08-16 实测两类投递错误的共同根因，而这条通道**只写不读**（§4）⇒ 应答体是投递方唯一可能的自查面。前置事实：057 已 ship，`research` 至今零跨 ctx。
>
> ⚠️ 留给下次的判据：**「跨 ctx 面 = 0」这类断言天然不会自带 sunset_trigger** —— 写它的时候还不知道哪个未来需求会来碰它。⇒ 这类断言的复审只能由 feature 侧的 `Gate 0.4` 扫描抓（058 plan 即由此扫出本条），不能指望 ADR 自己预告。

**复审结论：跨 ctx 面 0 → 1。** 形态 = 对 `marketdata.instrument.name` 的**一条 Q7-B 只读直查**（catalog Q7-B：`PrismaService` 直查 callee 表 + `// CROSS-CONTEXT-READ:` 注释，仅限只读）。落点 `research/ingest-research-report.usecase.ts`，走 `market_code` 复合唯一键单行查找，只 `select` `name` 一列。

### ① 原 §1 的两条理由，只有第二条被放宽

原文给「不碰 `marketdata.instrument`」列了两条理由，本次复审**逐条判**，结论不对称：

| 原理由                                             | 判定                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「校验会拒绝合法的新标的（研报常常先于标的入库）」 | **不适用，且继续有效。** 该后果的前提是「把查询结果当**准入条件**」。058 的读是**只读回显**：查得到就回名字，查不到回 `null`，投递照常 201 成功（fail-open，058 `FR-013` / `FR-015`）⇒「拒绝合法新标的」在结构上不可能发生。这条理由对**外键 / 存在性校验**依然成立 —— 那两样本次**没有**被放宽，仍然禁（058 `FR-028` 把这条明写成了否定式不变量）。 |
| 「引入本可避免的 Q7-B 依赖」                       | **被放宽。** 「本可避免」在 057 成立（当时无人需要标的名称）；058 起它不再可避免 —— 替代品只有「放弃 `FR-012`~`FR-018` 这一整块用户价值」。⇒ 依赖从「白付的成本」变成「有对价的成本」，对价 = 只写通道里唯一的自查手段。                                                                                                                             |

⇒ **这条区分不是措辞讲究**：把两条理由一起判作「已过时」，下一个人就会顺手给 `symbol` 加存在性校验或外键，而那正是 057 明确不要的东西（研报先于标的入库是常态）。

### ② 为什么是 Q7-B 而不是 Q7-A（防回潮留痕）

1. **同表同字段先例**：`alert` 已有一条对 `marketdata.instrument.name` 的 Q7-B 只读（[ADR-0052](0052-alert-bounded-context.md) §3 第 2 条，落地在 `alert/evaluate-alerts.usecase.ts:168`）。本片是**同一张表、同一个字段、同一种形态**的第二例 —— 若判它该走 A，等价于宣告已 ship 的那条也错了，但没有任何新证据支持这个反转。
2. **摊销判据**（判据同 [ADR-0048](0048-marketdata-portfolio-cross-layer-dependency.md) § 复审记录）：投影机器（Q7-A 的事件流 + 消费者 + 投影表）的本质是把**读时计算摊销到写时**。本场景读频率 = **每次投递一次**，且该端点被**每分钟 2 次**限频卡死；读时计算 = **一次索引单行查找**（`uk_instrument_market_code`）⇒ **无摊销对象**，事件机器在为不存在的读压力做优化。Outbox 消费侧基建至今仍为空（同 ADR-0048 复审第 2 条），走 A 还要连带建平台级消费基建。
3. **A 在本片有一条额外的反向代价**：物化视图会把「找不到名称」从「目录里确实没有」变成「投影还没追上」，而本片的 fail-open 让**查不到与查失败对外完全不可区分**（`FR-014`）⇒ 副本陈旧只会表现为回显覆盖率**静默下降**，没有任何一层会红。实时直查没有这个失效模式。
4. **Q7-C 仍禁**：不 `@Inject()` marketdata 的任何 use case / service（catalog 禁列，`check-server-moat` Check 2 拦）。也**不**为一条查询包一层 `SecurityModule` 共享读服务 —— 仓内两处真实先例（上述 alert 那条 + `marketdata/sync-option-contract.usecase.ts:232`）都是 usecase 内直查 + 注释。

### ③ 升 A 的 trigger（写明什么**不**构成）

**不构成**升级压力的三类（先写死，防止误报）：

- 回显字段变多（多 `select` 一列不是新的读压力）；
- `research` 再多一个投递入口（PRD §3.8 规划的 app 侧投递）—— 仍是「每次投递读一次」，只是投递方多了一个；
- `instrument` 行数增长 —— 单行索引查找与表大小无关。

**真 trigger 三条**：

1. **读频率量级跳变** —— 投递面从「单个 CLI agent + 2 次/分限频」变成批量导入 / 多用户并发投递，使名称查询成为投递路径上**可测量**的成本（摊销对象出现）；
2. **读形态从单行变聚合** —— research 需要的不再是「一次 `market_code` 单行 `name`」，而是跨行 / 跨表（按行业列举、批量回显、join 报价）⇒ ADR-0048 判据里「读时计算」那一半变了，直查不再是一句话；
3. **`instrument` 的 schema 语义变更实际咬过一次** research 的查询（如加软删列未同步过滤、`name` 拆多语言列）—— 耦合债从账面变现实。

> ⚠️ **一个易混的第四类，它不是升 A**：若出现「回显的名称必须与**投递时点**一致」的快照需求（改名后旧记录仍显示旧名），正确动作是**落列**（`ResearchReport.instrumentName`）+ 重审 058 `FR-017` 的「刻意不落列」取舍，**不是**建物化视图 —— 快照需求要的是时点冻结，物化视图给的是最终一致的活数据，方向相反。
