> 顺序约定：holdings（09:00）须先于 marketdata（09:05）——**非 FK 硬依赖**（`portfolio.holding` 对 `marketdata.instrument` 无外键，market+code 字符串引用；holdings 走 prod API 服务端算好再写），对调安全，rationale 详见下节 [故障排查](#故障排查本地每日同步)。两个 `run-scheduled.sh` 由仓库 `scripts/*/setup.*` 生成（脚本头注明「请勿手改，重跑 setup 覆盖」），改调度/目标改生成器后重跑 setup。
>
> **自包含副本（两者皆是）**：两个任务都跑 `~/.nvy` 下的**冻结副本**、**不依赖任何 git worktree**——marketdata 由 setup `cp sync.sh`；holdings 由 `setup.ts:materializeRuntime` 把运行时源码拷入 + 在 `~/.nvy/holdings-sync` 装独立 `node_modules`（`playwright-core` + `tsx`，约 23M，`pnpm install --ignore-workspace`）。**根治** worktree 被删/切分支即停摆（见 06-22 holdings 因 worktree 删停摆教训）。代价：改 sync 代码须重跑对应 setup 覆盖副本。
>
> **跑完上报（每跑必报）**：两个本地每日同步都**套通用 wrapper** `ops/lib/nvy-run-reported.sh`（setup 拷一份到 `~/.nvy/lib`），跑完**成功 / 失败都推**一条飞书 report（机器 + 任务 + 耗时 + stdout 末尾数字：holdings 持仓 / 已清仓 / 交易数，marketdata 逐表计数）+ 写心跳 `~/.nvy/heartbeats/<task>.beat`。飞书传输集中在 `ops/lib/feishu-send.sh`（openssl 签名免 python3），全机复用，sync 脚本**零飞书代码**（只管干活 + 打 stdout + exit 0/非0）。配置走共享文件 `~/.nvy/feishu-alert.env`（`NVY_ALERT_WEBHOOK_URL` + `NVY_ALERT_FEISHU_SECRET`；签名校验启用后 secret 必填；仓库外、含 secret 不入库），launchd wrapper `set -a` source 它；**webhook 缺失 → 静默跳过**（优雅降级）。
>
> **no-show 看门狗**：wrapper 在任务进程内推，看不见任务**根本没跑**（Mac 睡死 / plist 丢 / launchd 没醒）→ 既无成功 report 也无失败告警 = 静默。看门狗 `com.nvy.watchdog`（每日 10:00，`ops/lib/nvy-watchdog.sh`）查上述心跳过去 ~25h 有没有写过，没写就推飞书。**局限**：本机看门狗逃不出「整机宕 / 全程睡死」——那种唯有**外部**监控能兜（healthchecks 之类；单人 3 机暂不上，见 [子plan 调研结论](../../docs/private/plans/2026-06/06-26-scheduled-tasks-report-wrapper-watchdog.md)）。
>
> **心跳目录解析**：wrapper（成功 / 失败都）写 `<dir>/<task>.beat`，看门狗读同一 `<dir>`，故二者必须落同处。`<dir>` = `NVY_HEARTBEAT_DIR`（若设）否则 `${HOME:-/var/lib/nvy}/.nvy/heartbeats`。本地 launchd 有 `$HOME` → `~/.nvy/heartbeats`；**prod systemd 不注入 `$HOME`**（裸 `$HOME` 在 `set -u` 下会 unbound 崩溃，故 wrapper 用 `${HOME:-/var/lib/nvy}` 兜底），套 wrapper 的 systemd 任务（如 77 cert）在 `/etc/nvy-alert.env` 显式设 `NVY_HEARTBEAT_DIR=/var/lib/nvy/heartbeats`（干净路径；同文件被 cert + 看门狗两个 unit 共享 source，自然一致）。

> **交易日历健康探针（044）—— 三条反直觉设计，改之前先读**：
>
> 1. **判据不在 bash 里，全在 `ops/jobs/marketdata-calendar-health.sql`**（单一共享产物）。`ops/jobs/marketdata-calendar-health.sh` 只做「跑谓词 → 打摘要 → `exit` 谓词给的码」，**无 if / 无阈值**。原因：仓内无 bash 测试框架 → bash 里的判断必然无测试覆盖（撞宪法 §II NON-NEGOTIABLE）；把判断下沉到 SQL 后，它被 `marketdata.calendar-044.health.it.spec.ts` 用 Testcontainers **真测**（埋 25h/27h 心跳 + 主源/降级 `served_by`）。⇒ **改判据改 SQL，别改 bash；也别在 bash / 别处内联复制那段 SQL**（两份必漂移，一漂移「判断已被真测」就成了假话）。同一条谓词被 `marketdata-calendar-health.sh` 与 `marketdata-sync-report.sh` **共用**。
> 2. **`--on-success silent`（健康不推）—— 偏离「每日批任务成功也推」的默认，故意为之**：每 4h × 成功也推 = 6 条/日刷屏 → 训练出「反正都 ✅，不看了」，真告警来时被淹没。代价 = 没有正向 liveness → **由看门狗兜**（`marketdata-calendar-health:43200`，≈12h/3 次 no-show 才报）。这两个决定是一对，**只删其一 = 探针停摆后彻底静默**。
> 3. **探针不经 app 进程**（FR-010 的结构性要求）：直读 PG（`docker exec psql` 只读，同 sync-report 通路）。app 整个挂掉 → 心跳自然陈旧 → 照样告警。走 app 的健康端点做不到这点（app 死了谁都不响）。
>
> **表级数据健康探针（2026-08-02 新增）—— 与上者同范式，但判的是另一回事**：
>
> 1. **它补的洞**：2026-08-01 四个维度在 prod 静默丢数、`sync_run` 连续十几天全绿无人发现（`announcement` 停 12 个交易日 / `buyback` 同期零增量 / `shareholder_change` 一周只采 1/7 / `fund_holding` 上线 18 天 0 行）。既有三道防线全部漏判：`alertIfDegraded` 只看 `failed`、`FreshnessSlaCheck` 量的是 **run 年龄**而非**数据年龄**（跑了但没产出 → run 永远新鲜）、`rowsFetched` 全仓只有一处埋点。⇒ 判据必须挂在**数据**上、跑在**采集进程之外**。日历探针探的是「日历填充心跳」，覆盖不到这一类。
> 2. **判据是「逐票哨兵 EXISTS」而不是「全表 `max(date)` + 行数下界」——性能是硬约束不是偏好**：被监控表的索引一律 `(instrument_id, date)` 前导，**没有任何 date 前导索引** ⇒ `max(date)` 是全表扫（`volatility_daily` 1590 万行 / 1.9 GB），而 77 可用内存仅 ~580 MB 且无 swap，每 4h 冲一次 page cache = 探针自己变成事故源。逐票走 uk 索引，实测全谓词 **74 ms**。**想改回聚合判据 → 先加 date 前导索引**。
> 3. **AND / OR 语义是分开定的，别统一**：cn/hk 侧每个 (维度, 市场) 配 **2 只哨兵、全陈旧才判红**（个股停牌不误报，代价是单票掉队看不见）；us 侧因白名单只有个位数且每只都是 045 雷达锚定标的，取 **任一掉队即红**。⚠️ 聚合键必须是 **(维度, 市场)** 不能只按维度 —— `eod_bar`/`fundamental` 的 marketScope 是 {cn,hk}，只按维度聚合时 cn 侧整个停摆会被 hk 侧健康值**平均掉**判绿（首版就是这么写的，被 IT 变异用例当场抓出）。这条与 044「不被健康市场平均掉」是同一教训。
> 4. **覆盖边界（说清楚没覆盖什么）**：只抓「维度级停摆」，**不抓单票掉队**（严格版属期权链完整性核对，随 p4 落）。报告期语义（`fund_holding` / `revenue_segment` 等）、覆盖式 upsert（`index_membership` 等）、稀疏事件流（`buyback` / `allotment` 等）三类**不适用数据年龄判据**，硬塞进来只会制造长期噪音，故不在本批监控面内。
>
> **收到 🔴 怎么办**：摘要行直接给出每个市场的心跳龄 + `served_by`（如 `cn=27h前⚠陈旧/tencent | hk=1h前/static⚠降级 | us=1h前/futu`）。① **⚠陈旧** → 日历填充在失败，查 server 日志 `trading-calendar-sync` 的 `lastError`（`select * from marketdata.calendar_sync_health;`）；② **⚠降级** → 该市场主源失效、下一层在兜底，属需人工介入态（查主源是否改了接口/被封）。**降级 ≠ 健康**。分市场看：

> | ------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
> | cn / hk | `[腾讯 L1, 静态年历 L2]` | 腾讯挂了、静态层在兜 —— **L2 仅覆盖当年**，不修则跨年时静态表耗尽全盘爆炸                                                                                                                                                |

## 故障排查（本地每日同步）

> holdings / marketdata 两个每日同步的失败模式 + 修复。每次失败 wrapper 都推飞书失败 report（成功也推），看门狗只兜「根本没跑」的 no-show，**不覆盖「跑了但失败」**——失败靠飞书 report 感知。

### holdings 同步

先分清失败在哪一步：run 流程 = 启 CDP Chrome（固定 profile）→ 同花顺导出 xlsx 下载 → 上传 `api.shintongtech.com`。看 stdout / `~/.nvy/holdings-sync/sync.log` 尾行定位。

1. **`refresh token 已失效（401）`—— 上传步鉴权失效（最常见）**
   - **根因**：holdings 用 003 refresh token（存 `~/.nvy/holdings-sync.json` 的 prod 槽，`upload-holdings.ts` **只在轮转成功时才回写存储**），DB 里是 `device_type=UNKNOWN` 的家族。任何在 App/网页做的**「全端登出 / 退出所有设备」** = server `revokeAllForAccount`（`updateMany where {accountId, revokedAt:null}`）会**连带撤掉 holdings 这条 token 家族**。此后每天 09:00 headless：读死 token → rotate → 401 → **headless 无 TTY 不能短信重登（设计如此）** → 存储不更新 → 次日继续拿同一死 token。
   - **症状识别**：每天同一个 401、`holdings-sync.json` mtime 冻结在最后成功日；**同花顺抓取照常成功（xlsx 正常下载），失败纯在「上传前换 token」这步——别去查抓取 / 62→77 迁移**。refresh TTL = 30d 滑动窗口、轮转重签（`security/refresh-token.rules.ts` `REFRESH_TTL_DAYS`），**不会一天内自然过期** → 401 必是「被撤销」或「账号非 ACTIVE」，不是到期。
   - **修复（只能手动交互重登，短信 2FA 只本人手机能收，无法自动化）**：仓库根 `pnpm holdings:upload --base-url https://api.shintongtech.com`（默认 base-url 是 dev，**必须显式 prod**）→ 输手机号 + 验证码 → 重新种 token 家族写回同一存储 → 定时任务自愈。重登后可 `pnpm holdings:upload --headless --base-url https://api.shintongtech.com` 复现 09:00 上传路径验证（绿 = 好）。
   - **取证（prod DB 只读，走 marketdata 同款只读通路）**：`ssh mbw-staging` → `docker exec -i nvy-tight-postgres-1 psql -U mbw -d mbw`。`refresh_token` / `account` 表在 **`account` schema**（非 security）；token 存纯 **SHA-256 hex** hash（无 salt），拿存储里的 raw token 算 `sha256` 反查行看 `revoked_at`。**「全端登出」的 DB 签名 = 多条 token 精确到毫秒同一 `revoked_at`**（一把 `updateMany` 撤）；账号状态查 `account.account.status`（非 ACTIVE 也折 401）。

2. **`Browser context management is not supported`（connectOverCDP）—— 调试 Chrome 脏状态**：固定 profile 的调试 Chrome（端口 18800，独立 profile）实例脏 → `kill` 18800 监听 PID，下次 sync 自启干净实例修复。

3. **`net::ERR_INTERNET_DISCONNECTED`**：抓取时断网，瞬态，次日自动重试。

   - webhook/secret 一律复用本机共享文件（本地 `~/.nvy/feishu-alert.env`、62/77 `/etc/nvy-alert.env`，`NVY_ALERT_*`）；systemd 单元加 `EnvironmentFile=-/etc/nvy-alert.env`。**不新建** webhook/token。
3. **本表登记**：归到对应 host section，补一行（任务 / 调度 / 触发器 / 执行 / 仓库锚点 / 用途）。
4. 退役任务：删行 + 在相关 runbook 注明退役（别留 stale 行）。
5. path rule `.claude/rules/scheduled-tasks-registry.md` 会在触及 `.timer` / `scripts/**/setup.*` 时自动加载提醒——但本地 launchd `.plist`（装在 `~/Library/LaunchAgents/`）/ crontab 在仓库外，rule 触发不到，需**手动**记得登记。
